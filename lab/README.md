# Laboratório

Experimentos **fora do produto**: páginas à parte, publicadas ao lado da app (`dist/lab/…`) para validar uma possibilidade antes de ela virar etapa do [`PLAN.md`](../PLAN.md). Nada daqui entra no `index.html` da app, nem nas regras do núcleo (i18n, store, tokens de design obrigatórios). As regras que continuam valendo: TypeScript strict, sem `any`, sem dependências novas, sem requisição de rede (a página leva a mesma CSP da app) e testes no Vitest.

O laboratório é o épico `epic/lab` (PR [#160](https://github.com/fabianofranca/mapping/pull/160)): toda mudança entra por um PR com base nesse branch, nunca na `main`, conforme o [`CLAUDE.md`](../CLAUDE.md) ("Fluxo de trabalho").

> O experimento "Figma somente leitura" (colar "Copy as SVG" ou o JSON da API e desenhar com Konva) foi encerrado e removido; o laboratório segue só com os componentes. O que ele mostrou: "Copy as SVG" e o JSON da API dão para desenhar, a cópia nativa do Figma (fig-kiwi) não. O código fica no histórico do git.

## `components/` — Componentes por template

**Pergunta:** dá para montar telas **sem importar imagens**, só com componentes genéricos de uma especialização, e ter o desenho refletindo as propriedades da anotação?

**Onde:** `https://fabianofranca.github.io/mapping/preview/lab/components/` (ou `npm run dev:lab`; build em `dist/lab/components/index.html`).

**Decisões (do dono):** instâncias posicionadas por **retângulo**, como as marcações de hoje (uma tela sem imagem é um canvas em branco; cada instância ocupa o próprio retângulo; o template se adapta ao tamanho, nada é esticado). **Um arquivo por componente**; a especialização só referencia (`"component": "components/button.json"`, caminho relativo ao arquivo da especialização; chave nova, `formatVersion` 4 experimental).

**Formato do componente (`mapping-component`, `lab/components/componentFormat.ts`):** `id`, `name`, `size` (inicial), `minSize`, `preview` (valores de exemplo dos campos) e `template`, uma árvore de primitivas genéricas: `frame` (com `layout` `none`/`row`/`column`, `gap`, `padding`, `align`, `justify`, `clip`), `rect`, `ellipse`, `text`, `path` (com `viewBox`, escalado para a caixa) e `slot` (espaço para outro componente). Tamanhos: px, `"fill"`, `"hug"` ou `"50%"`; em `layout: none`, âncoras (`left`/`right`/`top`/`bottom`/`centerX`/`centerY`). Qualquer atributo pode ser uma **expressão sobre os campos**: `{"$field": "label", "default": "Botão"}`, `{"$if": {"$eq": ["variant", "ghost"]}, "then": …, "else": …}`, `{"$switch": "variant", "cases": {…}, "default": …}`, `{"$concat": […]}`; `visible` aceita condições (`$has`, `$not`, `$and`, `$or`). Campos booleanos são `enum` `sim`/`não`, lidos por veracidade. Validação com caminho e mensagem (`parseComponent.ts`); layout e instanciação em `instantiate.ts` (puro, sem DOM; o texto é medido por uma função injetada, o Konva na página).

**Design system de verdade:** o botão **Material 3** carrega o Material Design 3 (baseline, tema claro) escrito nesse formato, em `lab/components/samplesMaterial3.ts`: doze componentes (top app bar, button com as cinco variantes, FAB, text field outlined, switch, checkbox, chip, card, list item, navigation bar, modal bottom sheet e scrim), com os tokens de cor, tipografia (Roboto) e forma da especificação pública e ícones dos Material Icons, mais uma tela de configurações num Pixel (412 × 917) só com instâncias. É o teste de que o formato genérico representa um design system existente sem nada específico dele no código.

**Como usar:** **Exemplos** carrega a especialização de exemplo (seis componentes: barra do app, avatar, botão, cartão, interruptor, campo de texto) e uma tela de login montada só com instâncias. Clique numa instância: o painel da direita mostra os campos do tipo (do `mapping-spec`) e editar redesenha na hora; arraste para mover; as alças redimensionam com o template se re-adaptando ao vivo; `Delete` exclui; `Ctrl+Z` desfaz. **Adicionar** na biblioteca cria uma instância com os valores de `preview`. **Baixar exemplos (zip)** entrega a pasta (especialização + `components/*.json` + a tela) para editar num editor de texto e reabrir com **Abrir pasta…** (Chrome/Edge) ou **Abrir arquivos…**; os problemas de carga aparecem em Avisos (arquivo ausente, componente inválido com o caminho do erro, tipo sem componente). **Exportar tela** grava a tela (`*.screen.json`, instâncias com retângulo e valores); **PNG** rasteriza o desenho.

**Posições fixas:** o toggle da barra é um modo do editor: os componentes não se arrastam nem se redimensionam (a seleção continua, sem alças), mas a **tela** continua sendo movida como sempre (pan arrastando o fundo ou sobre uma instância, zoom, Ajustar): o que fica fixo é cada componente dentro dela. A caixa (x, y, L, A), o Pai, a Ordem e **Trazer para frente** ficam desabilitados. Os campos do tipo continuam editáveis e redesenham na hora; **Adicionar** e **Excluir** seguem valendo. É um modo da visualização, não um dado da tela: não vai para o `*.screen.json`, não é por instância nem fica guardado entre sessões. Não é a trava `locked` das marcações da app, que é por item e gravada no projeto (bloqueia mover, redimensionar e excluir o item e deixa anotar livre). **Decisão do dono:** é o ensaio da visualização por componentes na app, em que as propriedades mudam mas os componentes não são arrastados.

**Containers (Box, Row, Column):** um componente cujo template tem um `slot` é um container; as instâncias filhas têm `parentId` e a ordem entre irmãos é a ordem na lista da tela. O slot pode declarar `layout` (`row`/`column`, com `gap` e `padding` ligados a campos): o editor então **recalcula e grava os retângulos dos filhos** a cada mudança (`arrange.ts`), em vez de criar uma segunda fonte de verdade; `none` (Box) deixa cada filho no próprio retângulo. Mover um container leva os filhos; arrastar uma instância para dentro de um container a adota (o alvo fica realçado) e, num Row/Column, a posição do centro define a ordem; o painel tem **Pai** e **Ordem** para fazer o mesmo sem arrastar. Na biblioteca Material 3, `Box`, `Row` e `Column` são os primitivos do Compose (spacing, padding, background, shape); na tela de exemplo os chips e os botões de ação estão dentro de Rows. Decisão registrada: entre instâncias o layout é opcional e escreve retângulos; dentro de um template continua sendo o do próprio componente.

**Fontes do design system:** a especialização declara `fonts` (`[{ "family": "Roboto", "file": "fonts/Roboto-Regular.ttf", "weight": 400 }]`; `weight` aceita faixa de fonte variável, `"100 900"`; `style: "italic"`). Os arquivos (`.ttf`, `.otf`, `.woff`, `.woff2`) são lidos como bytes da pasta ou dos arquivos escolhidos e registrados com `FontFace` (`fonts.ts`): a CSP bloqueia fonte por URL, não uma face construída de bytes em memória. Depois da carga os textos são remedidos e a tela redesenhada. O painel **Fontes** mostra carregada, ausente ou falhou; ausente cai na fonte do sistema. O zip traz `material3/fonts/LEIA-ME.txt` com os arquivos da Roboto a baixar (as fontes não ficam no repositório nem no build: licença e tamanho).

**O que observar no teste:** se escrever um componente à mão é razoável (o formato é a parte que iria para o produto); se o layout `row`/`column` + âncoras cobre os componentes reais de um design system ou falta algo (empilhamento automático entre instâncias ficou de fora de propósito); a fidelidade do texto (fonte do sistema).

**Caminho para o produto, se der certo:** `component` no tipo da especialização (formatVersion 4), o renderizador `instantiate` + `renderScene` dentro de `src/canvas/` desenhando as marcações que têm anotação tipada com componente, e uma "imagem sem arquivo" (tela em branco com tamanho) no `mapping.json`.
