# Safe files — 2026-11-09 (épico `epic/arquivos-seguros`, PR #1141, MCP 0.28.7, schema v18)

## Corrigido

- Importing or replacing an image in the app now really picks a free name in `images/`: the name no longer lands on top of a file that is in the folder but the project does not cite, an image that the trash still keeps for undo, or another import in progress (pasting two images in a row). Before, deleting an image, importing another with the same name and undoing the removal lost the original bytes.
- Image and specialization names no longer distinguish uppercase from lowercase, or the composed from the decomposed form of accents: importing `foto.jpg` with `Foto.jpg` in the project becomes `foto-2.jpg`, and `add_container`/`replaceContainer` refuse a file that differs only in case (`duplicate-file`); the specializations `Material` and `material` no longer write `specs/Material.json` over `specs/material.json`. Projects that already had two such names keep opening.
- Accepting a proposal whose image has an occupied destination (a loose file in `images/`, an image in the undo trash, or a name that differs only in case) is refused as "the image already exists", without writing anything, instead of overwriting.
- In the MCP, the image name chosen in the batch (`add_container`, `replace_container`) also ignores case: `Tela.png` does not pick the name of a `tela.webp` that is already in `images/`, and two images of the same batch that differ only in case end up with different files.
- `revise_proposal` no longer follows a symbolic link in `proposals/<id>/images` or `specs` out of the roots: the folder is refused (`outside-roots`) and nothing is listed, deleted or written at the link's target.
- `list_proposals`, `propose_changes` and `list_threads` no longer fail because of a `proposal.json` or `comments/*.json` that is too large or unreadable due to permissions: the item goes to `broken`, with the error code, and the others are listed.
- A stray number after the `Z` of a component's SVG path (`M0 0 L10 0 L10 10 Z 5`) no longer hangs the MCP server in `render_*` and `get_marking_image`: the path ends there.
- `list_markings` accepts in `container` the full reference that `get_project` returns in `containers[].ref` (`mapping://projeto/i/código`); the reference of another project still gives `not-found`.
- `get_code_hints` no longer fails with `RangeError` when a whole-annotation `ref` closes a cycle through the hierarchy (a child that points to its owner) or through the owner/child link: the cycle is cut and the target comes as `repeated`.
- Creating a project in a folder never again writes over a `mapping.json` that appeared after the folder was chosen (for example, an MCP `create_project`, git or an editor with the "Create a project in this folder?" dialog open): the app rechecks before importing the images and before saving and, if the file appeared, creates nothing, leaves the loose images alone and opens the project that was already there, with the notice "This folder already has a project; it was opened instead of a new one."
- The notice "This folder already has a project; it was opened instead of a new one." now appears at the top, after the project opens (before, it vanished along with the home screen and the person never saw it); the banner can be dismissed.
