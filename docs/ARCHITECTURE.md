# Architecture

Serverless Preact/TypeScript application. The project state is an immutable JSON object; everything that changes that object goes through a store _action_.

## Layers

```
model  →  store  →  storage / canvas / ui (app)
```

Each layer only knows the ones to its left.

| Layer      | Folder                                  | Responsibility                                                                                                            |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `model`    | `src/model/`                            | `mapping.json` types, schema (zod), invariants, migrations and **all business rules**, as pure, immutable functions.      |
| `store`    | `src/store/`                            | Project state with undo (`history.ts`), actions (`project.ts`), persistence session (`session.ts`), UI and derived state. |
| `storage`  | `src/storage/`                          | Folder (File System Access), local project (IndexedDB), zip, image/EXIF reading, autosave.                                |
| `canvas`   | `src/canvas/`                           | Isolated Konva: imperative `CanvasController`, renderers, component layer, input (pointer/keyboard) and viewport.         |
| `ui`/`app` | `src/ui/`, `src/app/`                   | Preact components: home screen, editor, panels and dialogs; `controller.ts` orchestrates opening/creating projects.       |
| support    | `src/i18n/`, `src/theme/`, `src/utils/` | Texts (pt-BR/en-US), theme tokens and CSS, errors (`report.ts`), main/preview channel, safe `localStorage`.               |

## Data flow

```
user action
  → action (store/project.ts)
  → pure operation (model/…): (Project) => Project
  → snapshot in the history (store/history.ts) + project signal (and committed)
  → shown project (shownProject: committed or the review's "how it would look", clipped by the open perspective)
  → derived (store/derived.ts): visible layers, indicators, pending items, list, incomplete list…
  → canvas (one draw per frame; geometry from `project` with the gesture preview, clipped by the perspective) and UI (the shown project and the computeds)
  → autosave (storage/autosave.ts) → mapping.json (folder or IndexedDB), without the "Only me" perspectives; those go to IndexedDB, in a database of their own
```

- **Store** (`createProjectStore`): holds the current project and the `past`/`future` stacks of snapshots (limit of 100). An operation that throws a rule error comes back as an `ActionResult` with `ok: false`, without changing the state. A gesture (drag/resize) is grouped and becomes **one** undo entry.
- **Committed project × gesture preview**: during a gesture, `updateGesture` replaces `store.project` on every `pointermove` (the preview). The store also exposes **`store.committed`**: the project without the previews. Outside a gesture it is the same object as `project`; during the gesture it stays at the project from the start and only changes in `commitGesture`/`cancelGesture` (in a batch, with no intermediate value). The **canvas** reads `project` (the geometry follows the finger), clipped by the open perspective (`drawnProject`); the **interface** (`Editor*`, panels, list, dialogs, notices) and `derived.ts` read `committed` (or the shown project, which starts from it), and components that only need a slice (is there a project? is there a selection? project name?) use `useComputed`. Result: dragging does not re-render the Preact tree nor recompute pending items, indicators, visibility and the list. Visible consequence: the panel's x/y/width/height fields update when the gesture is **released**. `tests/components/editorRenders.test.tsx` guards the limit (30 moves, at most 2 renders of `EditorScreen`, `EditorPanel` and `EditorTopBar`).
- **Project state × UI state**: the JSON and undo live in the store; selection, visible layers, mode (navigate/draw), view mode (`viewMode` and the `viewShow` choice, `Alt+H`: the mode starts off with each project's editor and is never saved; turning it on goes back to Navigate. `viewShow` (`store/viewMode.ts`: Containers, Images, Outline, Names, Arrows and the layers with drawings left unchecked) starts with everything checked except Outline and is kept **per project copy**, in this browser, in a versioned `localStorage` blob (`mapping.viewShow`, zod, try/catch, the 20 most recent copies; without a `copyId` it only lasts for the session; a layer that does not exist is ignored and a new layer starts checked). In the mode, `markingVisibility` returns every marking as `'hidden'` (nothing is selected on touch), `canvasVisibility` returns it whole (the "Markings without annotations" filter does not apply, and hiding the outline does not hide the marking for the arrow), `drawnMarkings` loses the drawings of the unchecked layers (the `ComponentDrawing` carries the `layerId`; the drawing cache is not rebuilt), `drawingLayers` lists the layers that draw, the `CanvasController` clears selection, hover, draft and review marks in the frame and hands the `view` (the five items) to the renderers, and the pointer treats the mode as Navigate, without arrows on touch. **Only the screens** (Containers and Images checked, the rest unchecked) gives the canvas of the former clean view. The interface is `ui/ViewModePanel.tsx`: the **Show on canvas** `IconButton` (only enabled in the mode) and the popover, opened by `ui.viewPanel` (`setViewMode` opens it when turning on and closes it when turning off); Esc closes the panel (the `Popover` consumes the key) and, without a panel, exits the mode), open panel, collapsed sections of Details (`collapsed`), collapsed tree nodes (`collapsedTree`) and viewport live in `EditorUi` (`store/ui.ts`) and never go to the file or the history. The open tool windows, the sizes of each side and the height of the Layers window live in `store/toolWindows.ts` (module signals, per device, kept in `localStorage` with try/catch); zoom, cursor and image area live in `canvas/viewState.ts`, written by the canvas and only read by the interface.
- **Derived state** (`createEditorDerived`): one `computed` per editor, calculated once and read by canvas, panel and list, over the shown project. They depend only on the project, the open perspective and the UI, **not on the viewport**: pan and zoom do not recompute them. The visible layers (`visibleLayers`) hide the `hiddenLayers` of the open perspective (`derived.perspective`) or, in Main, those of `ui.hiddenLayers`.
- **Lock**: `locked` on images and markings blocks moving, resizing and deleting; selection, name and annotations stay free. The rules live only in `model/locks.ts`: the interface queries them (`can…`) so as not to offer what would be refused, and the model operations apply them again and throw `locked`, so no path (gesture, panel, shortcut, store action) bypasses the lock. The lock protects the **locked item**, not its parent: locking a parent locks the geometry of the descendants without touching their `locked`, but a locked descendant never blocks the parent (moving the parent carries it along, keeping the relative position; deleting the parent deletes it, and `markingDeletionImpact`/`imageDeletionImpact` report `lockedDescendants`/`lockedMarkings` so the confirmation can warn how many). The derived state `derived.markingLocks` (and `hasLocks`) feeds the Tree and the canvas. On the canvas, `intentAt` returns the `locked` intent over the locked item (no handles, `not-allowed` cursor, a mouse drag becomes the `blocked` gesture; on a touch screen the drag remains a pan). The padlock badge (`renderers/lockBadge.ts`, tokens `cv-lock`, `cv-lock-glyph` and `size-lock-badge`) appears on the selection and on the locked item under the mouse (`state.hoverLock`, computed once per frame and only in projects with locks). Locking, unlocking and "lock all" are actions (`setMarkingLocked`, `setImageLocked`, `setImageMarkingsLocked`), each with one undo entry.
- **Index** (`projectIndex(p)`): maps by id and groupings (child markings, annotations by marking and by owner, backlinks), memoized in a `WeakMap<Project, …>`: a new project (new version) rebuilds the index once; later reads are O(1).
- **Session and saving** (`openSession`): the only writer of `mapping.json`, with a single queue for saving, checking for external changes, reloading and deciding the conflict. State machine, queue jobs and contracts are in the ["Session and saving"](#session-and-saving) section below.
- **Change proposals** (format in [`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md)): three pieces, all outside the project JSON.
  - **Storage** (`ProjectStorage.listProposals/readProposal/writeProposal/removeProposal/statProposal`, plus `stampProposals(skip?)`): `proposals/<id>/proposal.json` in the folder (`statProposal` and `stampProposals` only in the folder, like `statMapping`; `stampProposals` walks `proposals/` **once** and stamps each proposal (`size:lastModified`) through the handle of the entry itself, instead of `listProposals` + `statProposal` per item; final proposals, `applied` and `withdrawn`, already read with a known stamp go into `skip` and **are only rechecked in the full check** (focus, return to the page, **Check the folder now**), not on every cycle; a new folder in `proposals/` is still seen on every cycle, and so are `open` and `superseded`), in IndexedDB (same file store, with the key `proposals/<id>/proposal.json`; writing a proposal marks the project as "not exported") and in the zip (`ProjectFiles.proposals` and `proposalImages`, read and written as they are: the text of each `proposal.json` comes back identical, and so does that of an invalid file, so the export loses nothing). The images waiting for acceptance use `readImage`/`writeImage`/`removeImage` with the full path `proposals/<id>/images/…`. `storage/loadProposals.ts` reads and validates (zod, `parseProposalText`; the file's `id` must be the folder's): an invalid file becomes a separately listed problem and does not bring down the rest. **`removeProposal(id)`** deletes the whole proposal: in the folder, `proposals/<id>/` recursively (the `proposal.json` and the images waiting for acceptance; it does not fail if it no longer exists); in the local project, the `proposals/<id>/…` keys in one transaction, marking "not exported" like `writeProposal`. Both refuse an `id` outside `PROPOSAL_ID_RE` (an empty id or one with `..` would point to the whole `proposals/`).
  - **Session** (`store/proposals.ts`, `session.proposals`): the in-memory list (`list`, newest first; each proposal keeps its object while it does not change), `problems`, `notices` (new, changed or deleted from outside) and the writing, which only this module does. The proposal's **`revision`** gets the same check as `mapping.json`: every write rereads the file and, if the text differs from what the session last read or wrote (MCP replaced or withdrew the proposal, an editor touched it), **adopts the disk version and redoes the change on top of it** instead of overwriting it (each change is a pure function of the proposal: decide, annotate, apply), writes `revision + 1` and updates the known stamp. Decisions and notes are written immediately, without delay, in a single queue (`mutate`). A file that changed and became unreadable is not overwritten. **`remove(id, onRemoved?)`** is the queue's other operation: it rereads the file, adopts the disk version if it changed from outside and **refuses** if the proposal is (or became again) open (`not-removable`; the rule is the model's `canRemoveProposal`: only withdrawn, superseded and applied) or became unreadable (`unreadable`); otherwise it deletes through the storage (`remove-failed` if it fails, with the proposal still in the list), takes the proposal out of the list **without** the `removed` notice (the person deleted it: the next `scan` does not find the proposal even in `known`) and clears its notices. `onRemoved` runs synchronously right after, with no window for an undo in between. A new proposal with `supersedes` pointing to the deleted one stays listed: `supersededBy`, `leftBehind` and `compareProposals` only consult the proposals present. **Guard on deciding over revised content** (stage #644, decision 8): `Mutation` also receives `seen`, the version the session had before rereading the file. When the agent revised the proposal from outside, `revisions` grew relative to `seen`; `unseenRevisedIds(seen, p)` (model) lists the changes replaced or added by those revisions. `decide`/`decideMany` refuse with `revised`, without writing, if any change that would change state (requested or cascaded) is in that set; the session has already adopted the disk version, so the review now shows it (with the mark) and the next decision works. Notes and Apply accepted are redone as before; a note on a withdrawn change moves up to the proposal level and its id goes into `revisions[].dropped[].notes` (`droppedEntryOf`/`withDroppedNote`). When the reread brings a new revision, the notice is `revised` (with the counts of the newest revision; `noticeKindFor`) in place of `changed`. `session.sync()` checks the folder together with `mapping.json` (`proposals.scan()` every ~3 s and on focus return): a proposal that is new, changed or deleted from outside goes into `notices`; a known file that becomes unreadable for a moment (an editor writing) is ignored until it is valid again.
  - **Actions** (`store/proposalActions.ts`, `session.proposalActions`): `decide`/`decideMany` (the rule is the model's `decide`; one write per call, with the previous decision map for the batch "Undo"), `restoreDecisions` (rewrites the previous map in a single write, only if the decisions are still those from afterwards), `addNote`/`editNote`/`removeNote` and `applyAccepted`. **Apply accepted** is a project undo entry: it computes with the model's `applyAccepted`, copies the images from `proposals/<id>/images/…` to `images/` (refuses if the file or the source is missing, or if the destination belongs to another image), applies to the project, writes `mapping.json`, writes the proposal (`applied`, `status`) and only then deletes the sources. The entry carries a `HistoryLink` (`store/history.ts`): undoing removes the `applied` from those changes and returns the images to `proposals/<id>/`; redoing puts them back. Deciding after an undo discards the "redo" (`discardRedoOf`), which would leave project and proposal out of agreement. **Undo and redo wait for the write**: `HistoryLink.undo`/`redo` return a promise with the result of `proposals.mutate`; while it is pending, `canUndo`/`canRedo` are false and `undo`/`redo` refuse (two consecutive `Ctrl+Z` do not cross). If the write fails, the step is reverted (project and stacks go back to what they were, if nothing else changed them), the proposal stays as it was on disk and `ProjectStore.linkFailure` carries the error, which the undo buttons show as a toast (`proposal.error.writeFailed`); `reportError` still runs. **Failures midway**: if `mapping.json` does not save (`save-failed`), the entry is undone without a "redo" (`abandoned`), the copies leave `images/` and the proposal is not written; if `mapping.json` was written and `proposal.json` failed (`write-failed`), `MutationPlan.compensate` undoes the entry the same way, confirms with `flush` the rewrite of the previous project (the session schedules it on its own, because the committed state is no longer the written one) and only then removes the copies (the file on disk cites them until the rewrite; if it fails, the copies are left for the session's cleanup once the write passes, and `pendingFiles` still lists them, which makes a later `adopt` try to remove them again to no effect). In both cases the accepted changes remain "awaiting application" and applying again completes it. **Deleting a proposal** (`removeProposal`, which the review calls through `review.removeProposal`): refuses with `read-only` (read-only project) and `reviewing` (review open; the list does not even appear in it), deletes through the queue and then `ProjectStore.detachLinks(id)` removes the proposal's `HistoryLink` from all undo and redo entries. The **entries stay**: undoing and redoing the application now only touch the project, without touching the proposal (which no longer exists) or returning images to `proposals/<id>/`. The images the application copied to `images/` belong to the project and follow the session's normal cleanup (`cleanUp`: undo removes them from disk keeping the content in the trash, redo restores them), so `mapping.json` never cites a missing file. The review (`review.removeProposal`) also removes from the `mapping.reviewResume` blob the resume entry and the "seen" entry of that proposal in this copy (always through `safeStorage`; a proposal with the same id that arrives later is truly New). In the interface, the ⋯ menu "Delete proposal…" of `ProposalRow` only exists on closed rows and is disabled with `store.locked`; `ProposalList` opens the confirmation (`Dialog` `alert`, with the proposal's title and the warning that it cannot be undone), keeps the dialog open until the action finishes and passes the `returnFocus` that takes focus to the action of the row that took the deleted one's place (or the previous one; with no rows, to the first button of the empty state): one owner per closing.
  - **Review = read-only project** (decision 1): `store.reviewing` (derived from `setReviewing(id)`, which `review.open` calls, and `setReviewing(null)` in `close`) makes `apply` and gestures refuse with `reviewing`; `canUndo`/`canRedo` and `undo`/`redo` only apply to entries with a `HistoryLink` of the open proposal (`link.tag`; the application of its accepted changes, and never that of another proposal nor an entry without a link, with silent refusal), and the session's `addImages`/`replaceImage` also refuse. **The review shows only Main** (stage #659, decision 12): `review.open` calls `session.perspective.setLocked(true)`, which opens Main (with the `review` notice if another one was open; only the in-memory choice changes, the one saved in the browser stays) and locks the selector (`open` returns `false`); `close` unlocks, and the previous perspective does not reopen on its own. The rest of the blocking belongs to the interface (4.4), which disables what would be refused.
  - **Review state** (`store/review.ts`, `createReviewState(session)`, in the editor context as `review`): open proposal, selected target (`ReviewTarget`), Current/Proposed view, filters, `undoable` (the last decision, with the previous map, for the batch "Undo"), `seen` (the proposals already opened in this copy) and `newConflicts`.
    - **Resume and "seen", per project copy.** A single blob in `localStorage` (`mapping.reviewResume`, validated with zod, always in try/catch via `safeStorage`), versioned: `{ v: 2, seen: string[], resume: Record<"copyId|proposalId", { selected, view, filters, knownConflicts } (`filters.onlyRevised` missing in an old blob counts as off, without changing the blob version)> }`. The copy is `ProjectStorage.copyId` (see "Project copy", below): the same proposal in the imported zip, in its unzipped folder or in two folders with the same name are different reviews, with different conflicts and position. **`seen`** keeps the proposals already opened (ids only, no limit); **`resume`** keeps the point where the person stopped, the 12 most recent **per copy** (those of other copies are not touched). Separate on purpose: evicting a resume entry never returns the proposal to "New". An unknown version, corrupted text or the old format (a flat `Record`) are discarded, not migrated. Without a `copyId` (only read-only storages, which never reach the session), the scope is empty and Diagnostics logs it.
    - **Writing and reading.** On open, on each selection, filter, view or navigation and on close, `remember()` rereads the blob and replaces only this proposal's entry in this copy (another tab does not lose its own), and merges into the in-memory `seen` what the blob has (reassigning the signal only if a new id came in: `derived.rows` depends on it). What another tab marked as seen enters this tab on the next write or open, not before (accepted limit: there is no observer of the `storage` event). With `localStorage` blocked, the write is swallowed and the in-memory `seen` holds within the session. On reopening, `resumed: 'full'` goes back to the last item, with the same filters and the same view; without an entry (`'none'`), it falls to the first pending change and the Proposed view. An image or layer filter that no longer exists is dropped (the layer counts if it exists in the current project **or** in the preview, because it may have been created by the proposal).
    - **New conflicts.** Conflicts are never stored as such: they are recomputed against the current project (the model's `changeStatus`). `newConflicts` is computed live: the current conflicts that were not in `knownConflicts` at open, so a conflict that appears during the review (project reloaded from outside) shows up as "New conflict" at once. On close, the ones the person knew or saw announced on open ("N new conflict(s)") and the ones they decided become known; a conflict that appeared during the review and was left undecided comes back as new on the next open. On the first open in a copy nothing is new (there is nothing to compare with) and reopening without changes never marks a new conflict (finding 11 of the first test round). **Apply in progress** (return of gate 8.2): between `store.apply` and the publication of `proposal.json` with `applied`, the project already has the accepted changes and the proposal does not yet; `review.apply()` (the only caller of `applyAccepted`, ratchet in `tests/tooling/applyAcceptedCallers.test.ts`) holds the review with `derived.hold()` on click and releases it when done, whatever the result. In the meantime `validation`, `conflictIds` and `situation` (and what derives from them: `invalid`, `canApply`, `newConflicts`, the canvas badges) keep the snapshot from before, pinned to the open proposal (another proposal opened in the meantime sees the live values), and `canApply` is false ("Applying the accepted changes…"). Limit: the redo of an application (Ctrl+Z and Ctrl+Shift+Z) still reevaluates in the `link.redo` window.
    - **"New", a single contract.** `rows[].fresh` (open, with no decision or note, not opened in this copy) is the truth: the status bar counts the `fresh` ones, the Proposals window puts the **New** badge and the primary action on **every** `fresh` row, and `review.open` removes that proposal's `added` notice from the queue (`proposals.dismissNotice`), so the "New proposal · Review" at the corner of the canvas does not come back after it was reviewed. The notice's X still clears the whole queue.
  - **Derived state** (`createReviewDerived` in `store/derived.ts`, `review.derived`): `rows` (the Proposals window: progress, conflicts, "new", what was left behind and who superseded), `tree`, `levels` (three-state decision with "partial" and counts per level, `reviewKey`), `levelTypes` and `changeTypes` (badges; the level rule is the model's `levelType`), `situation`/`conflictIds` (conflict, current value and locked item), `counts` (includes "accepted awaiting application"), `revisedIds`/`revisionSummary`/`counts.revised` (the "Revised" mark: changes with a mark and no decision, `visibleRevisedChanges`; the `onlyRevised` filter and the "Revised · N to check" line of `rows[].revised` read from there), `validation`/`invalid`/`canApply` (the accepted set, `validateAccepted`), `preview` ("how it would look", `previewProject`), `shownProject` (below), `visibleIds` (filters), `pendingIds`, `notes`, `supersession` (`leftBehind` and `compareProposals`), `fieldIndex` (the changes by entity and field, `fieldChangeIndex`: the whole creation or removal and the per-field changes of each marking, image, annotation and layer, the annotation changes per marking and the annotations that leave each marking; memoized by the changes, so deciding does not rebuild it) and `fullPreview` (the "how it would look" without the decisions, to show a rejected creation; memoized by the changes, by the applied ones and by the project, and read only when the interface asks). In `rows`, `supersededBy` is the proposal whose `supersedes` points to the row, whatever its status: an **applied** proposal is history and does not change status when superseded; the row shows "Applied · superseded by <title>" and **Open the new one** derived from the new one, writing nothing (only an open proposal becomes `superseded`). Memoized by the project (`store.committed`) and by the proposal: the tree, the conflicts and the types depend only on the changes and the project, so deciding does not recompute them; validation only runs with pending accepted changes. Supporting pure functions (change and level type, filters, pending items, navigation, status of the Proposals window row, reminder on leaving) in `src/model/proposalView.ts`.
  - **The shown project (`review.derived.shownProject`)**: the project the screen describes. It is the base (outside the review and in the **Current** view, the committed one, `store.committed`; in the **Proposed** view, the "how it would look", the preview) passed through `perspectiveView` of the open perspective (`projectInPerspective`, `store/perspectiveShown.ts`; `perspectiveView` is memoized by project and by perspective object, so pan and zoom do not recompute it; in Main or in a perspective the project does not have, it is the base itself). The review locks Main, so with an open proposal the clipping is the identity. It is the **only** source for everything that says what is on screen: the Tree and the List, the empty state and the canvas notices, the breadcrumb, the status bar (selection), the minimap, the selection shortcuts (Alt+↑/↓, Delete, Alt+L, Alt+N), the validation of the selection after a reload, "Compare" and the editor's derived state (`createEditorDerived(store, ui, shown, …, perspective)`: visible layers, indicators, visibility, incomplete, List and Incomplete), created after the review in `EditorContext`. The canvas derives `drawnProject` from it: outside the review, it draws `store.project` (with the gesture preview) clipped by the open perspective (the preview of dragging a root changes `perspectives[].items`, which is why the clipping comes from `store.project` and not the committed one); when it is the proposal's preview, `proposedDisplay(shownProject, proposal)` only translates the file of the new or replaced images to `proposals/<id>/images/…`; the cursor and the image area follow the same project. In a new import, image, marking and layer only exist in the preview, and all of this shows them in the Proposed view. Whoever still reads `store.committed`/`store.project` directly in `src/ui/**` and `src/app/**` is in the allowlist of `tests/tooling/shownProjectReaders.test.ts`, each with the reason (the project name in the bar, the edit dialogs, the other side and the ghosts of Details in the review, the "before" image of Compare, the diagnostics; Details, inside and outside the review, read the shown project); a new reader breaks the test.
- **Anchored conversations** (format in [`COMMENT-FORMAT.md`](COMMENT-FORMAT.md), Comments stage): four pieces, all outside `mapping.json` (they do not enter undo, they do not bump the schema).
  - **Storage** (`ProjectStorage.listThreads/readThread/writeThread/removeThread/statThread`, plus `stampThreads(resolved)`): `comments/<id>.json` and `comments/resolved/<id>.json` in the folder (`statThread` and `stampThreads` only in the folder, like `statProposal`: the local project is not observed; `stampThreads` walks `comments/` or `comments/resolved/` once and stamps through the entry's handle, instead of `listThreads` + `statThread` per item), in IndexedDB (same keys in the file store; writing or deleting marks the project as "not exported") and in the zip (`ProjectFiles.threads`, optional; only those two paths enter, with a valid id, and the text of each file comes back identical, and so does that of an invalid one). All refuse an id outside `THREAD_ID_RE`. `listThreads(resolved)` lists only the names in a folder, which is what the check needs (the scan itself uses `stampThreads`). `storage/loadThreads.ts` reads and validates (`parseThreadText`; the file's `id` must be the name's): an invalid file becomes a separately listed problem and goes to Diagnostics (`threads.invalid`), without bringing down the others.
  - **Session** (`store/threads.ts`, `session.threads`): the in-memory list (`list`, newest first; it joins the two copies of the same conversation with `mergeThreadCopies`), `problems` and `resolvedLoaded`. The **`revision`** gets the same check as `mapping.json` and the proposal: every write rereads both folders and, if the text differs from what the session last read or wrote (the MCP server appended a message, an editor touched it), adopts the disk version, **redoes the operation** (a pure function of `model/threadOps.ts`) and writes with `revision + 1`; a file that became unreadable is never overwritten. Resolving and reopening **move** the file: it writes to the destination and only then deletes the source, so a successful write never leaves two copies (if deleting the source fails, the next read joins them). Everything runs in a **single queue**. The check (`session.sync`, together with the proposals') scans **only `comments/`**, by stamp, and reads only the file that changed; resolved ones are read on open (`loadThreads`) and on request (`threads.loadResolved()`), and `collect()` reads them before exporting.
  - **Actions** (`store/threadActions.ts`, `session.threadActions`): `open`, `post`, `resolve`, `reopen`, `remove` and `removeMany`. All refuse without writing when the project is read-only (`read-only`), when a proposal review is open (`reviewing`) and without an identity (`no-identity`). `kind` never comes from the caller: the app only builds a `human` author, with the identity's name and email (ratchet in `tests/tooling/threadAuthors.test.ts`).
  - **Per device** (never in the project): the **identity** (`store/identity.ts`, key `mapping.identity`, edited in the **Identity** section of Settings, `ui/IdentitySettings.tsx`; the email goes through a `something@something` check) and the **"read"** state (`store/threadReads.ts`, `mapping.threadReads`: a versioned and validated blob with the `lastReadAt` of each conversation per project copy, `ProjectStorage.copyId`; corrupted text or an unknown version are discarded). Both go through `safeStorage`: blocked `localStorage` breaks nothing.
- **Copy reference and crop** (stage 3a.2, only in folder projects: `storage.folderName` is the reference's `<project>`): `app/itemClipboard.ts` builds the reference (`formatRef` + `shortCode` from the model; the reference is just the URL, with no readable path, with the project encoded) and the item data (`model/clipboard.ts`: the item, the descendant markings and the annotations) and writes them with `utils/clipboard.ts` (`text/plain` and, where the browser supports it, the web format `web application/x-mapping-item+json`, ignored by other programs; without support, text only). The crop (`storage/imageCrop.ts`) decodes the project's original file (not the display bitmap), draws the marking's `rect` and reduces the longer side to 2048 px; the blob's promise goes straight to the `ClipboardItem` so the write starts inside the gesture. **Ctrl/Cmd+C** (`copy-reference`) and **Ctrl+Alt+C** (`copy-crop`) only take the key when there is something to copy: outside a text field, with no text selected on the page and with a marking/image selected (or focus on an annotation card, `[data-annotation]`, or on the focused property (field, pair or row)); otherwise the native copy continues. Menus: buttons next to the ID in Details and on the annotation card (`ui/CopyActions.tsx`), the ⋯ menu of the Tree row (`ItemMenu`, fixed `Popover`) and the canvas context menu (`ui/CanvasContextMenu.tsx`, opened by `ui.canvasMenu`; `PointerInput` opens it only with the right mouse button; the `contextmenu` of a long press on a touch screen does not open it). The short notice ("Reference copied") is `ui.toast` (`showToast`).
- **Bitmaps** (`displayImages.ts`): the displayed images are loaded on demand; `retain(paths)` releases the bitmaps the project no longer uses. A file that comes back through undo is reloaded. **The map never contains a closed bitmap**: `retain`, `invalidate` and `dispose` remove the path from the map immediately and only call `close()` on the next frame (`requestAnimationFrame`), because the canvas may have a pending draw from the frame in which the bitmap was still on the Konva node, and drawing a closed `ImageBitmap` throws `InvalidStateError: drawImage … detached` (finding 10 of the first round). The image renderer (`canvas/renderers/images.ts`) also never puts a closed bitmap (zero width and height) on a node: the reserved space stays.
- **Errors**: `reportError(context, error)` logs to the console and keeps the last 20; the "Diagnostics" window (bottom) lists them in a table, with "Copy" and "Clear"; the strip's alert dot uses the "seen up to" of `store/diagnostics.ts`.

## Session and saving

The session (`src/store/session.ts`) is the **only** code that reads and writes the `mapping.json` of an open project (ESLint rule `sessionStorageSyntaxRules` in `eslint.config.js`; the exceptions are `storage/loadProject.ts`, which opens and reloads, and, in the controller, the creation of the folder project; existence checks use `hasMappingFile` from `storage/folder.ts`, without `loadMapping`). What is **not** part of `mapping.json` also goes through it: the "Only me" perspectives go to IndexedDB through `localSync` (below).

### `AutoSaver` (`src/storage/autosave.ts`)

| State          | Meaning                                                                                                                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`       | `saved`, `saving` or `error`: what the status bar shows. `saving` covers the debounce (250 ms), the wait in the queue and the write in progress.                                         |
| `dirty`        | There was a change since the last successful write.                                                                                                                                      |
| queue (`tail`) | **A single queue**: the write (`flush`) and the jobs of `enqueue(job)` (check, reload, conflict decision) run one at a time, in order; none of them calls `flush`/`enqueue` from inside. |
| `generation`   | Goes up on `reset()`: the write in progress at that moment ends without touching the state (the pending change was discarded by the reload).                                             |

Transitions: `schedule()` → `dirty`, `saving`, restarts the timer → `flush()`; `flush()` → enqueues the write; the write starts by marking **`saving`** (also when the previous one failed), clears `dirty`, calls `save()`; success → `saved` if nothing new came in; failure → `dirty`, `error`, `reportError('save')`; `reset()` → cancels the timer and the enqueued write that has not started yet, `saved` (or as soon as the one in progress finishes). **Invariants**, with a random-walk test in `tests/storage/autosave.test.ts`: `saved` ⇒ nothing in progress, nothing pending, no timer; write in progress ⇒ `saving`; `error` ⇒ nothing in progress.

### The session

| State          | Meaning                                                                                                                                                                                                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `saveStatus`   | The saver's `status`.                                                                                                                                                                                                                                                                                                                      |
| `conflict`     | `null`, `{ reloadFailed: false }` (decision pending: "Project changed outside the app" dialog) or `{ reloadFailed: true }` (Reload failed: file gone or unreadable; the decision remains).                                                                                                                                                 |
| `disk`         | The `mapping.json` as the session last read or wrote it: `revision` (lives here, not in the store: writing creates no undo and does not render), `text` and `lastModified`. The date comes from a `stat` on open, which only counts if the file is still the known one.                                                                    |
| `written`      | The committed snapshot that the disk has. Starts equal to the opened project only when the file is exactly its serialization (a project migrated, repaired on open or written in a non-canonical format starts as `null`, and the first edit writes); becomes `p` on every write and the adopted project on reload; `null` in "Keep mine". |
| `exported`     | The snapshot of the last zip that went out (`noteExported`, called by the controller's `markExported` on download or share): writing it afterwards is not a new change for the "unexported" indicator. Generating the zip (`collectFiles`) without downloading registers nothing (8.7).                                                    |
| `pendingFiles` | Images that the session wrote and no written `mapping.json` cites yet; the write removes only the ones it cites; on reload, those not cited by the adopted project are deleted (orphans).                                                                                                                                                  |
| `pendingSync`  | The check that is enqueued and not yet started: concurrent `sync` calls accumulate `images` in it and receive the same promise (one in progress and at most one waiting).                                                                                                                                                                  |

**The four queue jobs:**

- **Write** (`persist`): nothing to do if the disk already has the committed state (`onDisk`: identity with `written`, or the same content, without the "Only me" ones, except for the `updatedAt` that undo renews). Otherwise it reads the file (`readMapping`, the only read point): no file (deleted from outside) or equal to the known one → writes; **empty and different** → someone is writing: waits `EMPTY_RETRY_DELAY_MS` and rereads, up to `EMPTY_RETRY_ATTEMPTS` times, and then gives up with `EmptyMappingError` (`session.emptyMapping` in Diagnostics, `status = 'error'`); **different** → `conflict`, `ExternalChangeError`. Then it writes the pre-migration backup, the images that came back through undo, the package folders `specs/<id>/` (the content stays in an in-memory session cache, by `id@version`, so undo can rewrite what `cleanUp` deleted; when the version changes, the folder is rewritten **on top**, without deleting anything first: the old version stays only in memory) and the copies of `specs/`, rereads with the same rule if it wrote something, writes `revision + 1` (the text is `serialize(fileProject(p, localIds))`: it never carries the "Only me" perspectives), updates `disk` and `written`, calls `onChanged` (if what was written is not the exported one) and only then deletes what is no longer used (`cleanUp`, which also removes from the rewritten package folders the files that only the old version had, `removeSpecFile`, recomputed from the folder listing and repeated on the next write if they fail; a failure goes to Diagnostics). The `mapping.json` on disk never points to a file that was already deleted (during the rewrite of a package the folder may have files of the new version while `mapping.json` still cites the old one, but nothing disappears); removed files go to an in-memory `trash` (in a folder, the `File` that was read stops being readable when the file is deleted) until no history snapshot references them.
- **Check** (`syncProject`, via `sync`): open conflict → `unchanged`; gesture → `busy`; `saving` (a write scheduled or enqueued and not yet started: it checks by itself before writing) → `busy`. A `sync()` requested during a write in progress is a job behind it: it runs afterwards and answers with what it finds (usually `unchanged`, the file is what the session just wrote). If the date changed, it reads: equal → only updates the date; empty with nothing pending → `unchanged` (an editor writing); different with the **write in error** (the pending change does not reach the disk on its own; a file that is empty for good also falls here) → opens the `conflict` and returns `conflict`; different with nothing pending → `loadProject` and, if still `idle()` (edits are synchronous and can come in between the `await`s; the guard is reread before swapping the project), `adopt` → `reloaded`. After the job, outside the queue, `proposals.scan()` (the proposals' queue may wait for the session's, in the `flush` of apply accepted; never the other way around).
- **Reload** (`resolveConflict('reload')`): `loadProject` in `try/catch`; failure → `reloadFailed`; otherwise `adopt` (swaps the store's project, clears the history, `saver.reset()`, deletes the orphans of `pendingFiles`) and checks the images. It never rejects. The external reload (the Check also calls `adopt`) carries the in-memory "Only me" perspectives over to the disk's project (`carryLocalPerspectives`), reconciled by `reconcilePerspective` from the previous project to the new one; a file with another `project.id` carries none, and the UI state's arrivals (`arrivals`) are cleared.
- **Keep mine** (`resolveConflict('keep')`): adopts the disk's revision (a read that throws counts as a missing file), `written = null`, closes the conflict and writes over it; if the disk is locked, the result is `status = 'error'`, not a rejection.

**An empty file forever** (an editor that died after truncating): "Save failed"; "Retry" repeats the attempts and fails again; three ways out: Export (carries the committed state), deleting the file from outside (the next attempt writes) and the conflict dialog, which the check opens with the write in error ("Keep mine" writes over it; Reload gives `reloadFailed`).

**Contracts.** `flush(): Promise<FlushResult>` never rejects and joins the queue; `ok: true` ⇔ the committed project as of the moment of the call is on disk; `ok: false` ⇔ the pending change remains (`saveStatus === 'error'`), with the cause in `error` (`ExternalChangeError` ⇔ open conflict). An edit during the check (`store.apply`) schedules the write synchronously (`saving`), so the check in progress returns `busy` and never adopts the outside file between the edit and the `flush`. `onChanged` (`SessionOptions`) is called by the write of `mapping.json` with content not yet exported and by each write of `proposal.json` (`createProposalStore({ onChanged })`); the controller uses it for the "Unexported changes" indicator (IndexedDB keeps the same flag in `saveMapping`/`writeProposal`). `collectFiles()` returns `saved: false` when the zip carries a committed state that the disk does not have yet. `close()` waits for the queue (a check or reload in progress) before writing the pending change and closing.

**Perspectives in the session** (stage #659; model in `src/model/perspective*.ts`, format in [`FORMAT.md`](FORMAT.md), "v16 fields"). Each perspective is "For everyone" or "Only me", and **Who sees it** only decides where it lives:

- **For everyone** goes in `mapping.json` (`perspectives[]`, plus `arrivals[]` and `project.id`, v16). **Only me** stays in this browser's IndexedDB, in a database of its own (`mapping-perspectivas`, `storage/localPerspectives.ts`: one `perspectives` store, `project.id` → list, in the same format as an item of `perspectives`, validated with zod per entry), so as not to require a new version of the local projects' database (the reason for the folder recents). Without IndexedDB (`openLocalPerspectives` returns `null`) the option is unavailable: `createPerspective` with `local` and `setPerspectiveLocal(id, true)` fail with `local-unavailable`.
- **In memory both live together** in `project.perspectives`, so undo, gestures and reconciliation apply to both; what tells them apart is `session.perspective.localIds`. The session opens by merging the "Only me" ones that the controller read from IndexedDB (`mergeLocalPerspectives`, `store/localPerspectiveSync.ts`: each one goes through `reconcilePerspective` from the project to itself, just to clean up; an id that the file already has takes the file's value). Everything that writes or exports uses `fileProject(p, localIds)` (`store/perspectives.ts`): `persist`, `onDisk` and `collectFiles` (the zip) never carry an "Only me", and the session, as always, is the only one that writes `mapping.json` (`revision + 1`). `attachLocalSync` observes the committed project and, when the list of "Only me" ones changes (by object identity), enqueues `save(project.id, list)` into IndexedDB, without blocking; a failure goes to Diagnostics and the next change tries again.
- **Switching Who sees it** (`perspectiveActions.setPerspectiveLocal`, outside undo; refuses with `read-only`, `reviewing` and `gesture-active`) follows an order that never loses data. _For everyone → Only me_ (`makeLocal`): writes to IndexedDB first (`persistIncluding`; if it fails, `local-unavailable` and nothing changes), only then enters `localIds` and the file is rewritten without it. _Only me → For everyone_ (`makeShared`): `hold` keeps the id in IndexedDB, it leaves `localIds`, the file is rewritten **with** it and the `flush` waits for `mapping.json`; if it fails, it goes back to "Only me" (`save-failed`), and only with the file written does `release` let IndexedDB forget it. Since the project does not change, `rewriteFile` clears `written` and schedules the write. Creating with `local` puts the id in `localIds` in the same batch as the `apply`, so `mapping.json` never ends up citing an "Only me"; duplicating inherits the original's Who sees it.
- **The open perspective** is UI state (`session.perspective.id`; `null` is Main), outside undo, kept in `localStorage` by `project.id` (`mapping.openPerspective`, versioned blob validated with zod, the 20 most recent, through `safeStorage`). Opening a project resumes the saved one. If the open perspective ceases to exist in the committed state (deleted here, undone, deleted in another browser or by an external reload), an `effect` goes back to Main and shows the `removed` notice with the name; the same notice goes out on open if the saved one no longer exists. Switching perspective does not enter undo and writes nothing.

**Interface.** `useExternalChanges` (mounted in `Editor.tsx`) calls `session.sync()` with the window visible in an **adaptive check**: a chained `setTimeout` (not a `setInterval`), in which the next cycle starts `clamp(4 × duration of the last cycle, 3 s, 30 s)` after the last one **finished** (`EXTERNAL_POLL_MS` = 3 s, `EXTERNAL_POLL_MAX_MS` = 30 s, `EXTERNAL_POLL_FACTOR` = 4), so on a fast folder (desktop) it stays at ~3 s and on a slow one (Android, cloud) the interval grows up to 30 s. The cycle is **postponed** to the next 3 s interval when there is work in progress (`session.busy()`: a write scheduled or in progress, a gesture under way, a decision, note or proposal application being written). When focus or the page returns, it checks **immediately**, with `sync({ images: true })` and the final proposals; `reloaded` shows "Project updated from outside". The conflict dialog (`EditorDialogs`) uses `Dialog` with `closable={false}`: no X, and Esc and clicking the backdrop do nothing. Selection, visible layers and viewport are UI state and stay as they are (the selection is only cleared if the item disappeared: `session.reloads`). Only the **folder** implements `statMapping`/`statImage` (`session.watchable`); the local project is not observed. Images replaced from outside are found by the stamp (`size:lastModified`) of each file, checked when focus returns and after reloading, and `onImagesChanged` makes the controller call `display.invalidate(path)`.

**Old internal names.** The product is called "Mapping", but two names invisible to the user keep the old `mapeador`, to avoid requiring a migration of the data already stored in browsers: the IndexedDB database of the local projects (`mapeador-imagens`, in `storage/local.ts`; the folder recents one, created later, is already `mapping-folders`) and the service worker caches (`mapeador-…`, in `pwa/sw.js`). The `localStorage` keys already use the `mapping.` prefix. In the files, `app: "mapeador-imagens"` and `format: "mapeador-spec"` are still read; the `app` is normalized to `"mapping"` on read, so the next write already uses the new value.

## Spaces, containment and gestures

**Two coordinate spaces.** A marking lives in the **container**'s space (`containerId` filled in; `rect` in pixels
of the original image, inside it) or in the **canvas**'s (`containerId: null`, the canvas marking; `rect` in canvas
units, integers, even negative). `spaceOf(p, marking)` (`src/model/hierarchySettle.ts`) returns the space (`placement` and
bounds); `toCanvasRect`/`fromCanvasRect` (`geometry.ts`) convert from one to the other. Screen conversions stay in
`src/canvas/`, as always; space conversions, which change the stored data, stay in the model.

**Containment is derived and stored.** The `parentId` of a marking and of a container is never chosen: `settleHierarchy(p)` (pure,
idempotent, returns the same object if nothing changes) recomputes it from the geometry and, before that, decides the space of each
non-floating marking (the container that fully contains it, otherwise the canvas; if it changed, it converts the `rect` and the descendants go along).
The rules are in [`FORMAT.md`](FORMAT.md), "v13 fields (containment)": inside means fully contained, the parent is the smallest one in the
same space, the container's parent is the smallest canvas marking that contains it, and floating ones stay outside the tree. In ties
(equal rectangles; candidates of equal area for parent, also for the container) **the current relation holds** and the array order only
decides the new tie: within a group of equal rectangles the outside-in order is the topological sort of the current
`parentId`s (the parent before the child; among the free ones, the one that comes first in the array; whoever has no parent in the group enters by the array;
a cycle is broken by the one that comes first), and among candidates of equal area the current `parentId` stays if it is one of them (of each group
only the innermost counts), otherwise the one that comes last wins. Reordering siblings never changes parents, not even in the next settle; the settle
remains deterministic, idempotent and does not change the order of the arrays, but the result depends on the current `parentId` in ties. Members (`membersOf`, `projectIndex.members`/`canvasRoots`) come from `parentId` and are never stored. **Containment belongs to Main only**: a perspective (v16) does not decide who contains whom, only which roots appear and where (see "Perspectives", below).

**When it settles.** At the end of **every** model operation that touches geometry (draw, move, resize marking,
move/resize/replace/delete container, apply proposal: `applyAccepted` settles after the patch). It does **not** settle on
read, on migration or on open (reading never writes and never changes data), and the operation accepts `settle: false`, used **only**
in gesture previews. No tolerance: the model only knows "fully contained"; the tool (the interaction) is what helps the person
get there.

**Drawing during the gesture.** The preview (`settle: false`) only decides where things appear: containment does not change until
release, and the canvas does not decide who contains whom. So that the frame cost depends on what is dragged, and not on the project, the canvas
moves the nodes of what is moving into a group at the bottom of the overlay layer (see "Performance", "Drag group") and
returns them to the layers they came from when the gesture ends or is canceled; the usual drawing order (floating ones above the
others, components below the borders) only applies again on release.

**The clipped settle (`settleFrom`, #882).** The settle at the end of an operation does not look at the whole project: `settleFrom(before,
next)` compares the two by object (`src/model/settleDelta.ts`) and settles only what the operation touched, with the **same result** as the full
settle (`settleHierarchy(next)`, which without `before` still settles everything: repair, tests, outside callers). Affected
space: the before and the after of every new, deleted or replaced marking; of every new, deleted or replaced container, its own and the
canvas; the space whose relative order of markings changed (reordering siblings changes the rank in ties); and, when in doubt (more than half
of the markings changed, repeated id), the whole project. The canvas spaces and those affected by a container, reordering or giving up
are settled whole (spatial index of `spaceIndex.ts`); in the others, only those that fit (including equal) in a rectangle that
changed, before or after, are reviewed (`settleLocal.ts`): a marking's parent depends only on who contains it, on the ranks of equal
rectangles and on the current parent. The sweep uses the positions and boxes of the markings of each space, kept per markings array
(`settlePositions.ts`, filled on demand and passed from one operation to the next without sweeping the project). The perspectives and the
"Came from…" marks are reconciled by `reconcilePerspectivesFrom`, the same algorithm over a lean view of the two projects (containers,
canvas markings and replaced markings), instead of building the index of the whole project. The proof of equivalence is a randomized test of
sequences of public operations (`tests/model/settleSequences.test.ts`, seed printed on failure), besides the randomized test of projects
against the frozen reference (`tests/model/settleEquivalence.test.ts`). The clipping assumes what every model operation receives: a
project from before that is already settled.

**Reconciliation of the perspectives.** At the end of the settle (`settleHierarchy`, unless `settle: false`), `reconcilePerspectives(before, after)`
(`src/model/perspectiveReconcile.ts`) keeps `perspectives[].items` and `arrivals[]` consistent with the new geometry, without moving anything on
screen: a deleted root goes away; one that stopped being a root (entered another marking) gives way to the new root, placed so that the item stays
where it was; an item that became a root enters where it was, by the position in `before`; no repeated root (the first holds); `hiddenLayers` only
with layers that exist; whole-marking position. The "Came from…" mark goes away when the root disappears, stops being a root or changes place in
Main. With nothing to change it returns the same object. The `before` comes from `SettleOptions.before` (`src/model/hierarchySettle.ts`): the
actions fill it with `settleOptions(base)` (`src/store/project.ts`), the project from the **start of the operation**; at the end of a gesture, the
project from the **start of the gesture** (the preview already touched `items`, and comparing with it would lose the root change). An explicit `before` takes
precedence over the settle's own, which without it uses the incoming project (a model operation called by another, or the "Only me" reconciled on
open, where before and after are the same and it only cleans up). `pruneHiddenLayers` removes from the perspectives the layers the project lost.

**The gesture.** When dragging or resizing, the canvas calls `beginGesture`, and each pointer move becomes a preview with
`settle: false`: containment stays **frozen** while the pointer moves and the canvas draws the result without recomputing the
tree. On release, the canvas computes the **snap** and the **absorption** and calls the `finish…` action of the same operation (`finishMarkingMove`,
`finishMarkingRect`, `finishImagePlacement`), which repeats the operation with the final values and `settle: true` (and `before` = the project from the start of the gesture, to reconcile the perspectives) over the project from the start
of the gesture; only then `commitGesture`: **one** undo entry with geometry, space and containment together. The final operation
never fails (if it fails, it settles the last valid preview).

- **Snap:** when moving, the target container lights up and a marking dropped almost entirely inside it is pulled in, so that the
  person does not have to hit the exact pixel.
- **Absorption:** when resizing a marking, whatever ended up **almost** entirely inside it lights up and, on release, the
  marking grows until it covers it; the item becomes a member. The tolerance is `ABSORB_TOLERANCE` (in screen pixels, in `src/canvas/`):
  it is an **interaction** rule, never the model's, and so it is never stored nor applied by a proposal or by MCP.
- Moving a marking **inside a container** carries the descendants; on the **canvas** it moves only it (the members stay where they are and
  containment is redone). Nothing ties the marking to the container: it can leave it and become a canvas marking, or enter
  another container with the `rect` converted.

**Multiple selection and joint drag.** `ui.selection` remains the **primary** item (handles, Details); `ui.selectionGroup`
holds the **other** items attached to the primary's object, so any direct write to `ui.selection` undoes the group
with no extra code; `selectedItems(ui)` joins the two. Shift+click (and Ctrl+click or Cmd+click, which count the same on the canvas, including
over a handle, and in the Tree; on macOS Ctrl+click is the right click and does not join; in proposal review none of the three counts), the double
click and "Select with contents" (`selectionWithContents`, `src/model/multiSelection.ts`) build the group. The joint drag is the pure operation `moveItems`: all or
nothing (a lock or an overlap with a container that does not move fail), with the displacement in canvas units; the container's
marking receives it divided by the scale and clamped to the container, and an item carried by another (a marking inside a moved container,
a descendant) does not receive a separate displacement. The previews use `settle: false`; on release, the final action repeats the operation with the
settle and there is **one** undo entry. Dragging from the Palette uses `componentDropTarget` (`src/ui/componentTarget.ts`, pure: slot,
container or canvas, and what to light up) and the `useComponentDrop` hook, with the MIME `application/x-mapping-component`; the **Add**
button uses the same target from the selection.

The keyboard arrows move the selection through the pure operation `nudgeItems` (`src/model/multiSelection.ts`): 1 px, or 10 px with Shift, in the
own space of each item (container marking in image pixels, at any scale; canvas marking, floating and container
in canvas units). A container carries its markings, a container marking carries its descendants and the arrow (stroke) does not move. It is all or
nothing, as in `moveItems` (locked, leaving the container or a container overlapping another: nothing moves, with no notice). The movement is a
store gesture: the first arrow calls `beginGesture`, each repetition `updateGesture` (preview with `settle: false`) and `commitGesture`
closes with the settle in a single undo entry. Press and release is a one-step gesture; holding the key (repeat) is a single
gesture, closed on keyup, on window focus loss or when another key is pressed. The key only applies with focus on the canvas or on no control
(`body`); it does not apply in a text field, Tree, menu, tabs etc., with `defaultPrevented`, in read-only, in proposal review nor
with a pointer gesture in progress, and it applies in Navigate and Draw. Alt+↑/↓, Alt+Shift+↑/↓ and Ctrl+Shift+arrows keep the uses
they already had.

The **selection rectangle** (SM2) is Shift+drag in any mode (Navigate and Draw): the gesture in `src/canvas/input/pointer.ts`
becomes the `select-rect` intent and draws the rectangle (dashed border `cv-select`, fill `cv-select-fill`) in `state.marquee`,
through the overlay layer, with no live preview or automatic scrolling. Over a selected item or handle in Navigate, Shift+drag
still moves or resizes, and what does not pass the drag threshold remains Shift+click. On release, the pure function
`marqueeItems` (`src/canvas/input/marquee.ts`) picks the items **entirely** inside the rectangle and they are **added** to the
selection (it never removes an item; it keeps the primary, or, with no prior selection, the first of the new ones in Tree order). The "only the outer ones"
rule applies: it reuses `movingItems`, so a marking of a container that was included, or a descendant of it, does not enter (it already goes with the container),
and a container inside a canvas marking that was included does enter. Invisible items (hidden layer, visibility, view mode) do not
enter, arrows only with "Show arrows" on, and locked ones do enter. Esc or a canceled pointer erases the rectangle without changing the selection.
The gesture does not change the project and does not generate an undo entry.

**Parent marking (Wrap).** `wrapItems` (`src/model/multiSelection.ts`) creates a marking that wraps the selection, with one or more
items (a single non-floating marking or container too: the new one goes around it with an 8 px margin, clamped to the
container and the current parent). Non-floating markings and containers enter (arrows and notes stay outside containment). The model does not
choose a parent: it creates the new one with the set's **current parent** in `parentId` (the relation that the stable tie-break keeps) and settles, and the
settle checks the rest. Where it appears: the **Wrap** button of the multiple-selection summary, the **Ctrl/Cmd+G** shortcut
(`useEditorShortcuts`) and the **Wrap** entry of the canvas context menu and of the ⋯ of the Tree row (`WrapMenuItem` in
`src/ui/CopyActions.tsx`). All four go through `src/app/wrapSelection.ts`: `currentWrapItems` says what to wrap now (the current
selection; or, in a menu, only the row's item when it is outside the selection), `canWrapNow` checks (outside read-only
and review, and whether any item enters) and `wrapItemsNow` calls the `wrapItems` action, selects the new marking and warns
`multi.wrapFailed` if the model refuses. The shortcut only takes the key when `canWrapNow` holds and never with focus on a text
field; otherwise the event goes on to the browser.

- **Space:** if everything that enters is markings of the same container, the new one belongs to that container; otherwise it is the canvas's, with the
  rectangle in canvas units rounded outward, and a container's marking counts as the **whole container** (only the
  container can be a child of a canvas marking).
- **Current parent:** among the markings of the same space that contain the set (outside the selection and its descendants), the one the
  settle would choose (`enclosingAmong` in `src/model/hierarchySettle.ts`): the common parent of the top-level selected ones, if it is one of the
  smallest area; otherwise, the innermost in the chain of equal rectangles. Never the last in the array, which after reordering markings with the
  same rectangle can be the outer one (#549).
- **Rectangle:** the one that wraps everything, with a margin of `MIN_MARKING_SIZE` (8 px) on each side, clamped to the container and to the set's **current parent**,
  so that the new one never takes the set out of the parent it already had.
- **Position in the array:** before the first selected marking. The new one has no relation to the selected ones, so the tie of
  equal rectangle with them is new and the array decides: the earlier one is the outer one. The new one is born with the **current parent** in `parentId`: it
  fits in it and no smaller one contains it, and even with a rectangle equal to the parent's the current relation keeps it outside, whether it comes before or
  after in the array. This way the new one becomes a child of the parent the selected ones had and the direct parent of them. Unselected markings
  that fall inside the rectangle also become children: that is the geometry.
- **After:** one undo entry; the new one is selected alone, with no name and no annotations. The lock does not prevent it, because
  no existing geometry changes, only `parentId`.

**Perspectives: gestures and restrictions** (stage #659, decisions 5 and 8; `src/store/perspectiveGestures.ts`). With a perspective open the
canvas draws `perspectiveView(project, perspective)` and calls the **same** actions of `project.ts` with **view** coordinates; it is the
action that translates them, and the canvas knows nothing about perspectives beyond not starting what belongs to Main only (`IntentContext.perspectiveOpen`).
The `…InView` functions return `null` in Main or when the usual rule applies, and the action falls back to the model operation.

- **Dragging changes the position, not the data.** Moving a root (container or canvas marking, floating included) changes only its item in
  `perspectives[].items` (`moveRootsInPerspective`): the project's `placement`/`rect` stays, and the gesture is **one** undo entry as
  always. A canvas marking that is a child of another, or a container inside a canvas marking, drags the **whole root**. Inside a
  container (container marking, drag, resize) the Main rule applies. Changing the scale of a root container writes only the
  scale to the project; the resized floating marking writes the size to the project and the position to the item. The lock and the overlap in the view
  (`image-overlap`) apply as in Main, and snapping into a container on release belongs to Main. The joint drag and the keyboard arrows
  (`itemsMoveInView`) move the roots in the perspective and, in the same operation, the rest as usual.
- **"Main only"** (`principal-only`, a `StoreErrorCode` code; `principalOnly` tells the interface when to disable the command with the hint):
  drawing a canvas marking that is not floating (the whole creating operation is refused), the arrow route (`setArrowRoute`,
  `previewArrowRoute`: the arrow's ends remain), **Arrange**, **Delete** of a root and resizing a canvas marking that is not
  floating (moving remains). The pointer no longer starts the gesture: with no container under the point the Draw mode becomes pan, and only the arrow's
  ends have a handle. Drawing inside a container works.
- **Creating a root outside Main.** The new root (container or floating) enters the perspective where it was created, at the position it has in the
  project, and **arrives in Main** (`creationInPerspective` → `arriveInPrincipal`, `src/model/perspectivePlace.ts`): the place in Main is
  computed in the perspective's view (near the reference root, the other end of an arrow that links it; the nearest free one if
  occupied; otherwise the arrival area), the root is moved, the project settles, and only then does the `Came from…` mark enter `arrivals` (the settle
  would remove the mark of whatever changed place). `kind` and `referenceId` are not stored: they go in `session.perspective.arrivals` (`onArrival`),
  for the Details notice, and `dismissArrival` removes the mark.
- **Arrows between different roots** do not carry the waypoints to the view (the view uses the automatic route, `points: []`); between
  those of the same root the points move with it.
- **Conversations:** the canvas point (outside a container) only has a pin in Main (`pinPlaces(…, principal)`); the container point follows the
  container, which the view brings or not.

**Lock.** Locking a canvas marking locks the `placement` of the containers inside it (`canEditImagePlacement`); the
inheritance remains in `markingLockStates`, which the padlock of the Tree and of the canvas read.

## Specializations in the project and typed annotations

The file format is in [`SPEC-FORMAT.md`](SPEC-FORMAT.md) and the project's (stable ids, `ref` references, pending items) in
[`FORMAT.md`](FORMAT.md). Here are the behavior rules that the code applies.

**Lifecycle** (`model/specializations.ts`; each operation is one undo entry):

- **Apply:** validates the file, copies it to `specs/` and creates the specialization's layers at the end of the list. With the same `id` already in the
  project: a greater `version` offers **Update**; equal or lower warns and does nothing.
- **Update version:** replaces the copy in `specs/`; new layers are created, the existing ones keep color and annotations and the name
  follows the new version's; the ones that disappeared become **free layers**. An annotation that became invalid (new required field, removed option or
  type, disallowed relation, label removed from a target) **is not changed**: it appears as incomplete, with the reason.
  A removed type leaves the annotation read-only, with the action "Convert to free annotation".
- **Remove:** either **deletes the data** (the layers, their annotations **and the ones linked to them in other layers**, with a
  count confirmation), or **converts to free layers**: the typed annotations become free (`type` and `values` null) with the
  values as text in `entries` (in field order, empty fields omitted, `table` flattened as `parameters[1].name: source`,
  `ref` as the target's label), the type's name becomes the `name` when it is empty, and links and `inherit` are kept. In both
  cases the copy in `specs/` goes away. References from other specializations that pointed to removed or
  converted data become broken (pending items), and the confirmation says how many.
- **The specialization's layers** cannot be deleted or renamed (only by removing the specialization); the color can be changed;
  they show the specialization badge and can be reordered and hidden (any layer can be hidden, even all of them; there is no active layer).

**Typed annotations in the interface:**

- **Create:** in a specialization layer, "+ Annotation" lists that layer's types. A type with `requiresOwner` asks for the **owner**
  first (an annotation of the same marking whose type accepts this child); with no possible owner, the message says what to create first. From
  the owner, the editor offers one button per `allowedChildren` type, which creates the child already linked in the child type's layer (if the
  layer is hidden, it creates and offers to make it visible). Fields with `default` come filled in.
- **Editors by field type:** `string` and `number` in a text field, `date` in the native picker, `enum` in segmented buttons
  (up to 3 options) or a list, `table` in rows that can be added, removed and reordered, `ref` with the current target and the actions Choose,
  Clear and Go to target (the picker lists **only the accepted targets**, grouped by annotation, with search; with no target, the message
  explains what is missing). There is no field for extra keys.
- **Incoming references:** an annotation that is a target shows who points to each tuple or row (`name ← Input input_name (Name)`),
  and deleting a target warns how many references will break.
- **Pending items** (`model/issues.ts`, computed, never stored; saving incomplete is always allowed): empty required field
  (including a table column), incompatible value, nonexistent option or type, missing owner or owner of a disallowed type, broken reference
  and unaccepted target (lost the label or stopped being free). They appear as an alert on the annotation, along with the marking's indicators
  on the canvas and in the **Incomplete** filter of the List.
- **Display** (`model/typedDisplay.ts`, pure functions; the interface passes the translated texts): title "type name · instance
  label" (label: `name`, otherwise the `labelField`; with no label, just the type); values in field order with the `label`, empty optional ones
  omitted and empty required ones as `id: —` in the alert color; `table` as a summary in semantic zoom (`attributes: 3 rows`)
  and in full in the panel and the list; `ref` as `data: → User.name`, or `data: → (broken reference)` in an alert.

## Image intake and optimization

Applies to every image that enters through the app (file, camera, paste, drag and replace). The decision is a pure function in
`model/imageOptimization.ts`; the re-encoding (canvas, `toBlob`) lives in `storage/imageImport.ts`.

- **Optimization on import, before any marking exists:** the optimized image becomes the "original", and the coordinates are born
  on it. The longer side is capped at `MAX_IMAGE_SIDE` (2560 px, no option in the interface; a smaller image is not enlarged). The format is
  WebP: lossy (quality `LOSSY_QUALITY`, 0.85) for photos and **lossless** for PNG sources; if the browser does not produce WebP,
  JPEG for photos and PNG for PNG sources. If the image did not need to be reduced, the re-encoded one only replaces the file if it is smaller;
  if it was reduced, the reduced version always holds. Re-encoding removes the metadata (GPS included); EXIF normalization comes
  first. In the zip, images go in uncompressed (`STORE`). Images from earlier projects and files already existing in a folder
  used to create the project are left untouched.
- **Paste** (Ctrl/Cmd+V with focus outside a text field; in a text field, paste remains text paste) adds the image at the
  center of the visible area or, if it overlaps another, in the nearest free space. The generated name is `img-YYYYMMDD-HHMMSS.<ext>`, with a
  suffix `-2`, `-3`… on collision.
- **Drag and drop** (`app/imageIntake.ts`): file(s) onto an empty area enter at the drop point (or in the nearest free
  space); **a single** file onto an existing image **replaces** it (same aspect ratio: directly; different aspect ratio: warning and
  `needsReview`); several files always enter as new ones; whatever is not an image is ignored with a warning. The target lights up during the
  drag.

## Performance

- **Index and derived state** (`model/projectIndex.ts`, `store/derived.ts`): `projectIndex(p)` is memoized in a
  `WeakMap<Project, ProjectIndex>` (it works in Node), so `issues`, `refs`, `hierarchy` and the listing use maps by id instead of
  `find`/`filter` in loops. `derived.ts` separates what depends on the **project and the UI** from what depends on the **viewport**: pan and zoom only
  update the stage transform and whatever depends on scale (semantic-zoom text, line widths).
  The stage receives position and scale in a single call (`stage.setAttrs({ x, y, scaleX, scaleY })` in `CanvasController.render`): Konva
  batches the attributes into a single cascade, and each transform attribute applied separately would clear the transform cache of all
  nodes (thousands, in a large project) and fire `absoluteTransformChange` on them; zoom went from 3 cascades per frame to 1
  (`tests/canvas/CanvasController.test.ts` counts: zoom 1, pan 1, edit 0).
- **Dirty layers** (`CanvasController.render`): the stage has 5 layers (`images`, `components`, `markings`, `floating`,
  `overlay`) and the frame redraws only the ones that changed, with `layer.batchDraw()` on each, instead of `stage.batchDraw()`. Each
  renderer says whether it touched any node: `ImageRenderer.changed` and `MarkingRenderer.render` (returns `main` and `floating`, the stack of the
  markings layer and that of the floating one) reuse `sameInputs` and do not rebuild a node whose inputs did not change (nor the name
  text); `ComponentLayerRenderer.render`, `setZoom` and `refreshImages` already returned the boolean; arrows (the stroke comes from data, not
  from Konva attributes), review marks, pins, arrival marks and overlays only run, and only dirty their own layer,
  when what they read changed (`REVIEW_KEYS`, `PIN_KEYS`, `ARRIVAL_KEYS`, `OVERLAY_KEYS`). Pan, zoom and resize
  change the stage transform and dirty all of them (`stage.batchDraw()`). Konva also schedules the drawing of the layer of a node whose
  attribute changed; the explicit marking covers what it does not see. Effect: editing the name of a marking redraws `markings` and
  `overlay` (not `images` or `components`), changing the selection redraws only those two, and a frame with no change redraws
  none (`tests/canvas/dirtyLayers.test.ts`).
- **Level of detail by zoom** (`canvas/renderers/levelOfDetail.ts`, used by `MarkingRenderer.render`): by the on-screen size of the
  marking, `full`, `border` or `hidden`. Below 24 px in width **or** height (token `size-lod-min-marking`)
  it draws only the border (no halo, double line, "needs review" badge or ⚠); below 2 px in **both** dimensions
  (`size-lod-hide-marking`) the group is invisible, like one outside the screen. The selected one (including in multi-selection,
  `frame.items`), the one under the mouse and the one with a review mark stay complete at any size; the level is part of the node's inputs
  (`inputs`), so crossing a threshold rebuilds the node. Konva walks every child of a group, visible or not, so the node only attaches
  the visible parts to the group (`syncParts`): from far away a group has only the border, and the `drawScene` of the markings layer in the
  2,000 scenario dropped from ~21 to ~9 ms (18 thousand to 4 thousand nodes). Zoomed in (≥ 24 px) nothing changes. The token `size-indicator-min-marking`
  was removed (unused in drawing).
- **On-demand nodes** (`MarkingRenderer.render`, decision 8 of the canvas-scale stage): the Konva node of a marking is only created
  in the first frame in which it is drawn (visible, level of detail ≠ `hidden`, inside the screen area); otherwise there is no
  node, and `node(id)` and `headers.get(id)` return `undefined` (the overlay and anything else that reads them handle `undefined`). The created node
  stays until the marking leaves the project (it is not destroyed when it leaves the screen), is created already under the right parent (`parentFor`, the
  drag group if it is moving) and only existing nodes count in the stack order. Selecting a marking with no node (Tree, List) takes
  the canvas to it (`centerSelection`), and the next frame creates it. `MarkingRenderer.shown` counts the drawn ones and
  `CanvasController` publishes it in `data-drawn-markings` on the `.canvas-host`. Effect: opening already zoomed in creates only the nodes in view
  (65 of 2,000 in the test scenario, ~50 ms against ~175 to 285 ms per frame); with **Fit all** every marking is above 2 px and
  every one gets a node, so opening fully in view is not shorter (`tests/canvas/lazyNodes.test.ts`).
- **On-demand node parts** (`markings.ts`, `semanticCard.ts`; CD2 of the canvas-performance stage, decision 5): `createNode` creates only
  the group and the border (2 nodes per marking in Fit all). The halo, the double line (`inner`), the badge, the alert (`alertClip` and
  `alert`) and the name (`createSemanticNode`, only with a name and a mode other than `none`) are created in the first frame in which they are visible;
  the fields of `MarkingNode` are optional and whoever reads them handles their absence. Once created, the parts stay (hidden and outside the attachment of
  `syncParts` when they do not show). The marking that is selected, under the mouse or with a review mark is complete by exception and creates
  its own. `MarkingRenderer.destroy` (called by `CanvasController.destroy`) and the removal of a marking also destroy the
  detached parts: they are not children of the group, and without this the shapes stayed in Konva's hit color registry.
- **On-demand component drawings** (`componentLayer.ts`; decision 3, gate opened in CD1: opening 2,000 markings went from
  206.6 to 406.7 ms with components, +96.9%): the drawing is only assembled (`renderScene`) in the first frame in which its box
  (scene matrix, or the anchor in the rectangle, for the screen-pixel ones, plus a 64 px margin) crosses the visible area, and it stays until the
  marking leaves the project or the drawing object changes. Once assembled and off screen, the node is only hidden. Pan and zoom go through
  `ComponentLayerRenderer.reveal` (assembles what came in, hides what left, without re-instantiating or redoing the whole order), and the usual
  `render` only runs when the drawings, the visible set, the positions or the theme change. `data-components` still
  counts every drawing that appears (`size`), wherever the view is; `mountedCount` counts the assembled ones.
- **Level of detail of arrows** (`renderers/arrowDetail.ts`, `renderers/arrows.ts`; CD3 of the canvas-performance stage, decision 7; gate
  opened in CD1: with 1,000 arrows, pan and zoom of 2,000 markings in Fit all were 47.5% and 28.5% above `--sem-setas`
  in Chromium): `arrowDetail` is a pure function, like `levelOfDetail`, that gives `full`, `thin` or `hidden` by the on-screen length of the stroke
  (sum of the segments of the `path` × zoom, `arrowPathLength`, kept by `ArrowShape`) and by the size of the two ends, reading the
  tokens `size-lod-min-marking` (24 px) and `size-lod-hide-marking` (2 px); no new token. **`hidden`** (not painted and has no
  label): both ends are markings that are invisible by the marking rule. **`thin`** (length < 24 px): only the stroke, no halo,
  head or label; the body goes into the same pass as the stroke of the full ones (`BodiesMerge`), so there is no new pass.
  **`full`**: the selected arrow (including in multi-selection), the one that links a selected marking or one under the mouse (or with a review
  mark) and the rest. Besides the level, an arrow whose box (`bounds`, with the label margin) does not cross the visible area is not painted and has
  no label. The `DetailPlan` of `ArrowRenderer` keeps the measurement of each arrow (length and size of the ends, with zoom at 1) until the
  project, the positions or the theme change; each frame only applies the zoom, the visible area and the exceptions. Pan and new positions go
  through `ArrowRenderer.reveal` (only the visible area and the level, nothing else), and `render` runs with the selection, the mouse, the theme, the zoom and the
  project. `data-arrows` counts the painted arrows (`full` + `thin`, drag group included). Dragging a marking still
  takes its arrows to the drag group, each at its own level.
- **Budgets and targets (final check, CD5 of the canvas-performance stage; baseline in #888 and #1219):** CD4 (ready image
  per container) was closed `not_planned`: the gate (decision 8) did not open, because with 2,000 markings pan (19.5 ms) and zoom
  (26.5 ms) were already below 33 ms in Chromium (CD3 measurement). Final measurement, Chromium 153, 1280×860, median of 3 runs
  (`npm run perf:canvas -- 2000 5000 --vezes 3`), in ms, with 2,000 markings and 1,000 arrows: open in Fit all 128.5, pan 20.6,
  zoom 31.1, edit 9.8, drag 23.2 (10 moves); with 5,000: 210.9, 55.0, 54.4, 11.3 and 30.8. Targets of decision 10 with 2,000:
  edit ≤ 16 ms **met**; pan and zoom ≤ 33 ms **met**; open ≤ 128 ms **not met by 0.5 ms** (128.5; the three runs
  gave 125.7, 128.5 and 196.2, the cloud machine fluctuates). Without arrows: open 101.1, pan 21.7, zoom 26.8, edit 2.9; with components
  (21 screens per container): open 293.8, pan 65.7, zoom 58.8, edit 14.0. With 5,000 markings pan and zoom stay at ~55 ms and have no
  target. jsdom budgets (`renderPerformance.test.ts`): drag ≤ 16 ms (met), pan and zoom ≤ 33 ms (met), edit
  ≤ 16 ms as a target with a 35 ms ceiling (with 16 ms the test passed 6 out of 10 times, so the ceiling stays), first frame in Fit all
  < 111.5 ms. `npm run test:scale` (`GROWTH_RETRY=0`): canvas pan 3.34×, zoom 4.01× and first frame 2.22×, all < 6×.
- **Drag group** (`CanvasController.syncDrag`/`applyDrag`, `canvas/dragSet.ts`; decisions 5 to 7 of the canvas-scale stage):
  during a store gesture (`store.gestureActive`: moving or resizing a marking, moving items or a container, route and end of an
  arrow), whatever moves goes into a **group at the bottom of the overlay layer** (below the arrival strip, the review
  marks, the pins and the handles); the stage keeps 5 layers (#476, #517) and, on each `pointermove`, only `overlay` is
  redrawn. The set that moves is the **difference between the project drawn from before the gesture and the preview's**
  (`dragSetOf`, a pure function): the marking, container and arrow whose object changed, plus the markings of a container that moves
  (they move with the image without changing object) and the arrows that touch any marking that moves. The set only grows until
  release. The canvas chooses nothing from the model: containment and final position remain up to `finish…` and the settle. Each
  renderer receives the set (`setDragged`) and, in the usual `render`, **moves the same node** with `moveTo` (never clones) to the
  subgroup of its stack, in the usual drawing order (images, component drawings, arrows, markings, floating
  drawings and markings); the node that moves does not count in the stack position it left and is updated wherever it is. On release or cancel the
  set empties, the frame goes through every renderer (even with no project change) and the nodes go back to their previous parent and index,
  redrawing the layers involved. Details: the component drawing that moves stays in a group per container with
  the position and scale of the image group (`ComponentLayerRenderer.mirrors`); the arrows that move have their own body and label

### `mcp/` (MCP server)

A Node server (stdio) outside `src/`, with its own `tsconfig.json` (no DOM). It may only import `src/model/`: ESLint rejects `src/ui`, `src/canvas`, `src/app`, `src/storage`, `src/store`, `src/i18n`, `src/theme`, `src/utils`, browser libraries and any network module (`node:http`, `fetch`…). `npm run build:mcp` (`mcp/build.mjs`, esbuild) generates `dist-mcp/mapping-mcp.js`: a single CommonJS file, with the dependencies and the documentation (`?raw`) embedded, plus a `dist-mcp/package.json` `{"type":"commonjs"}` (this repository is `"type": "module"`).

- `main.ts` reads the arguments (`args.ts`, repeatable `--root`) and connects the stdio transport; `server.ts` creates the `McpServer`, registers the tools (`tools.ts`) and the documentation resources (`docs.ts`: `mapping-docs://AGENT-GUIDE.md`, `FORMAT.md` and `SPEC-FORMAT.md`).
- **Paths** (`paths.ts`): `Roots` is the only point that turns what the agent typed into a disk path. It rejects `..`, an absolute path outside the roots and a symbolic link that leaves them (compares the `realpath`); `resolveProjectFile` applies the same to files cited inside a `mapping.json` (`images/…`, `specs/…`), which is untrusted input. The `root` of `create_project` is resolved the way `main.ts` resolves `--root` (from the working directory), by the real path or by the folder name, if unique; with an absolute `path`, it must contain the path (`invalid-arguments`). `isWithin` receives the path API (the test uses `path.win32`). Writing is atomic (`writeFileAtomic`: temporary file in the same folder + rename).
- **Projects** (`projects.ts`): `discoverProjects` finds folders with `mapping.json` at any depth (does not follow symbolic links, ignores hidden folders and `node_modules`, does not enter a project it found); `findProject` accepts a folder name, a path relative to a root or an absolute one and returns the candidates if the name repeats; `loadProject` reads `mapping.json` and `specs/` and validates everything by `deserialize` of `src/model/` (in-memory migrations; **reading never writes**). `createProject.ts` creates the folder (`mapping.json` and `.gitignore`; `images/` is born in the app, with the first image).
- **References** (`items.ts`): `Refs` builds the `mapping://` references (only the URL; `ref` and `bare` give the same text) with `shortCode`/`formatRef`; the readable names and paths (`Image › Parent › Marking`, via `markingPath`/`label`) go only in the answers' own fields, never in the reference text; `resolveItem` interprets with `parseRef` what the agent pasted (complete reference, `m/code` + `project`, id) and looks in one project or in all. Ambiguity becomes an error with the candidates.
- **Views** (`views.ts`, `markingList.ts`): build the compact JSON answers only with model functions (`projectIndex`, `projectIssues`, `getBacklinks`, `refsOf`, `markingLockStates`…), with no business rule of their own.
- **Batch writing**: `operations.ts` is the (zod) schema of the `plan_changes` operations; `batch.ts` applies them in order over a copy of the project, **only with the pure operations of `src/model/`** (invariants, locks, specializations, links and references belong to the model; the batch only translates what the agent reported: references, `$name` aliases, layers and types by name, `ref` values and tables in the agent's format), keeps the error of each operation without stopping (one that depends on an alias from an operation that failed gets `alias-unavailable`) and builds the readable summary; `modelErrors.ts` explains each `ModelErrorCode` (an exhaustive `Record`). `changes.ts` runs the batch over the project read from the folder (`prepareBatch`) and builds the common answer of `plan_changes` (preview, **writes nothing**) and of `propose_changes`. **No server path writes `mapping.json`** (`apply_changes` no longer exists): the server only writes the empty project of `create_project` and `proposals/`.
- **Proposals**: `proposals.ts` (`Proposals`) implements `propose_changes`, `list_proposals`, `get_proposal`, `get_proposal_review` and `withdraw_proposal` over the pure functions of `src/model/` (`buildProposal`, `reviewTree`, `changeStatuses`, `reviewProgress`, `compareProposals`, `supersedeProposal`, `withdrawProposal`); there is no business rule of its own. `proposalStore.ts` is the only module that writes to disk: it creates `proposals/<id>/` (new images first, `proposal.json` last, without overwriting; the created folder is removed if something fails) and updates an existing proposal by re-reading the file immediately before writing and writing `revision + 1` (the app may be deciding at the same time; after 3 attempts, `revision-conflict`). `proposalRefs.ts` resolves `mapping://<project>/p/<code>` (the short code comes from `shortCodesFor`, the same rule as for items); `proposalViews.ts` builds the compact views (state of each change, levels, progress, notes). `sourceTools.ts` (`find_by_source`, `find_types_by_source`) and `specValidation.ts` (`validate_specialization`: the errors come from `parseSpecText`, the same function as the app's import; the warnings, from `specWarnings` in `src/model/specWarnings.ts`).
- **Images** (`mcp/image/` and `imageTools.ts`, phase 3a.4): `get_marking_image` and `get_container_file` read the original file of the project (through `resolveProjectFile`, so only inside the roots), decode, crop, downscale, draw the outlines and encode, and return an `image` content (base64) preceded by the JSON text that describes it (`respondWithImage` in `tools.ts`). The **codecs** (`codecs.ts`) are those of `@jsquash` (libpng, mozjpeg and libwebp compiled to WebAssembly), whose `.wasm` files go into the single file as bytes through the `wasm:` plugin of `mcp/build.mjs` (virtual name because of the `.d.ts` next to each `.wasm`; the list lives in `mcp/wasmFiles.mjs`, which `vite.config.ts` also reads for the tests). They are instantiated on demand from the bytes (`new WebAssembly.Module`), without reading files or using the network; WebP is encoded without SIMD, straight from the codec factory, because the package's `init` chooses the variant with a dynamic `import()` that the single file does not load. **Crop, downscale and outline** (`raster.ts`) are pure TypeScript over RGBA: the downscale is the average of the area covered per pixel (weighted by opacity) and the outline is drawn **after** the downscale, inside the rectangle and with a dark halo, to have the same thickness at any scale; `compose.ts` joins the stages and `formats.ts` detects the format and reads the dimensions **from the header** (PNG, JPEG and WebP) before decoding, refusing files over 64 MB or 100 megapixels (a "decompression bomb" on disk does not exhaust memory). The JPEG is decoded with the EXIF orientation applied, as the browser does in the app. A file with dimensions different from those in `mapping.json` does not bring the tool down: the coordinates are adjusted proportionally and the answer carries a `warning`. `orientation.ts` rotates the pixels by the EXIF orientation (all 8), applied by `decodeImage` on the JPEG. For clients that do not show `image` in the chat, `mcp/imageServer.ts` delivers each generated image also by local URL: an HTTP server on loopback (`127.0.0.1`, random port, random per-process token in the path) that keeps the images only in memory (LRU of 64 images and 64 MB), starts on the first requested image, does not hold the process (`unref`) and shuts down with `--no-http`; the tools add `url` and `markdown` to the answer. It is the only exception to ESLint's "no network" rule, and only for listening: the server makes no outgoing request and nothing goes to disk.
- **Adding images**: `imagePrepare.ts` repeats the app's import (`storage/imageImport.ts`) over the same codecs, with the model's decisions (`planOutputSize`, `chooseOutputFormat`, `shouldUseEncoded`, `withExtension`): image already rotated by EXIF, longest side up to 2560 px (`resize`) and WebP (lossless if the source is PNG).
- **Specialization code**: `codeViews.ts` builds the views (`code` per platform in a single shape, `{ symbol, definition, params?, values?, notes? }`, with the `definition` of the `path` resolved — `url` and `ref` of the specialization's `repo`, `localFile` and `exists` by the project's local clone —, by `typeCodeView` and `packageCodeView` (`get_component`), and the calls of `get_code_hints`: `types` by `specId/typeId`, `repos` and, in the tree, only `args`, `values` and `linked` per annotation) and `findByCode.ts` the search of `find_by_code` (the types and their annotations); both use the pure functions of `src/model/` (`codeLink`/`repoLink`, `codeLocalPath`, `codeBlueprint`, `findByCode`). `codeFiles.ts` is the only module that touches the disk by code path, and only with `stat`/`realpath` (the server **never reads or writes code**, guaranteed by `tests/mcp/noCodeRead.test.ts`); the check is confined to the client's working directory (`Roots.workDir`), because the `localPath` may climb above the roots and the `path` comes from a file editable by third parties.
- **Import by signature** (stage #1079): the import has **three parts**, and the rule "the server never reads code" stays whole. (a) The **extractor** `mapping-signature.mjs` (`signature/`, delivered in the Release next to `mapping-mcp.js`) runs **outside the server**, by the agent, in the library's clone: it reads the code (or the Figma JSON) and writes the sheet; it does not speak MCP, does not open a project and writes nothing besides its output. It lives in `signature/`, is generated by `npm run build:signature` (called by `build:mcp`) into `dist-mcp/mapping-signature.js` (CJS) and `dist-mcp/mapping-signature.mjs` (ESM, the Release one) and only writes to `--out`. (b) The pure **importer** `planSignatureImport` (`src/model/signatures/`) receives the sheet and the specialization and returns fields, `code` or `sources` and warnings, always the same for the same input. (c) The `plan_signature_import` tool (`signatureImport.ts`) is the shell of (b): it reads the sheet (inline or a `.json` inside the roots: `readJsonFile` in `library.ts` rejects any other extension **before** any call to the disk), finds the package and the previous sheet (the one that the `code` or the `source` cites in `signature`, read from the package), translates the importer's errors into the server's codes and merges the imported type into the **raw JSON** of the specialization file (`mergeOrdered.ts`: zod reorders the root keys, and the preview must keep the file's order). It is read-only: the agent writes the specialization and the sheet and validates with `validate_library`. **Why:** the sheet is derived JSON data, not code, so the server still does not read code (`tests/mcp/noCodeRead.test.ts` has the case of the `signatureFile` that is not `.json`); leaving everything to the skill would make the same signature give different fields on each run and whatever is left out would vanish without a trace; and the mapping rule lives in one place, the model, which another surface can reuse.
- **Distribution**: the push to `main` (the epic merge) triggers `.github/workflows/mcp-release.yml`: the `decide` job publishes only if the `mcp-v<version>` tag of `SERVER_VERSION` (`mcp/version.ts`) does not exist yet (logic in `scripts/release/stableRelease.mjs`; the `epic` job of `ci.yml` fails the PR of an epic that changes the release inputs, `scripts/release/releaseInputs.mjs`, without bumping the version), and the `release` job creates the tag and the Release together, after running lint, typecheck and tests, generates `dist-mcp/mapping-mcp.js`, runs it copied outside the repository (`--version`) and attaches it to the Release with the `.sha256`. A hand-created `mcp-v<version>` tag triggers the same workflow (plan B). Installation and use for those who consume the server: `docs/MCP.md`.
- **Answers**: compact JSON in the text only (no `structuredContent`, which would double the context spent); an expected failure is a `ToolError` and becomes `isError` with `{"error": {"code", "message", …}}`. The code is `ToolErrorCode` (`errors.ts`): the literal union of the `MCP_ERROR_CODES` registry with the `ModelErrorCode`s; every code in the registry is in the "Errors" section of `docs/AGENT-GUIDE.md` (`tests/mcp/errorCodes.test.ts`).
- **Who writes**: only `paths.ts` (`writeFileAtomic`), `createProject.ts` (the folder, the `.gitignore` and the new `mapping.json`; `images/` is born in the app, with the first image) and `proposalStore.ts` (`proposals/`). The rule is twofold: ESLint rejects importing the write functions of `node:fs` in the other modules of `mcp/**`, and `tests/mcp/staticGuards.test.ts` sweeps `mcp/**/*.ts` recursively checking who calls which write function and who cites `mapping.json`. The folder constants (`MAPPING_FILE`, `IMAGES_DIR`) and the `.gitignore` text (`gitignoreWithBackups`) come from the model, the same as the app's. The new files of a proposal use temporary + `link` (never overwrites); without hard links (`EPERM`, `ENOTSUP`, `ENOSYS`, `EXDEV`: exFAT, network shares), `writeFile` with `wx`; on both paths, deleting the temporary file is best effort (`removeTemp`: refused by antivirus or a mounted folder, it becomes a warning on stderr and the `.tmp` stays, ignored by the app and the server), so that it never errors with the file already written. The `images/` names reserved by other proposals follow what can still be applied (`reservedImages`): in an open one, the pending and accepted ones; in a superseded one (and in the previous one of a `supersedes`), only the accepted ones.
- **Known limits** (accepted and documented):
  - **Window in `proposal.json`**: the server (when superseding or withdrawing) and the app (when deciding) re-read the file and compare the text immediately before renaming over it, but neither locks the file. A decision written by the app in the microsecond interval between the re-read and the server's `rename` is silently lost (the app later adopts the disk version). It only happens on a `status` change with the app writing at the same instant; if it ever hurts, the `status` can move to a marker file instead of rewriting the JSON.
  - **Writing the new one before marking the previous one**: `propose_changes` with `supersedes` writes the new proposal and only then marks the previous one as `superseded`. If the process dies between the two, two `open` proposals remain, with the new one's `supersedes` pointing to the previous one (`list_proposals` already shows `supersededBy`). If marking fails without a crash, whatever the error, the answer carries the `supersede-failed` warning and the new one stays written. Deriving "superseded" from the new one's `supersedes` for `open` as well (as the app already does for `applied`) remains as a future evolution.
- Tests in `tests/mcp/` (Vitest `mcp` project, `node` environment). `specValidation.test.ts` checks that `validate_specialization` returns the same errors as `parseSpecText`; `proposalStore.test.ts` tests the proposal's `revision` check; `imagePrepare.test.ts` tests EXIF orientation and optimization (images from `images.ts`); `staticGuards.test.ts`, `errorCodes.test.ts` and `version.test.ts` are the ratchets for writing, error codes and version × docs; `read.test.ts` brings up `dist-mcp/mapping-mcp.js` over stdio with the SDK client, over a temporary folder (`workspace.ts`) with the project of script 13.9 and variations (without `specs/` copies, schema v5, hostile `mapping.json`, symbolic link outside, colliding ids).

### `src/storage/`

- `folder.ts` (folder, and `ensureGitignore`, which writes `backups/` into the `.gitignore` when creating a project in a folder), `local.ts` (IndexedDB), `zip.ts` (export/import, with `proposals/` and `comments/`), `autosave.ts`, `imageImport.ts` and `exif.ts` (reading and optimizing images), `existingImages.ts`, `share.ts`.
- `localPerspectives.ts` (the "Only me" perspectives in IndexedDB, `mapping-perspectivas` database per channel, one list per `project.id`; outside `ProjectStorage`, opened once per app by the controller), `loadProject.ts` (read and validate `mapping.json` + `specs/`, on open and on reload; also returns `libraryIssues`, levels 1 and 2 of the validator over each `specs/<id>/` package, via `specPackage.ts`), `loadProposals.ts` (read and validate `proposals/`), `loadThreads.ts` (read and validate `comments/`), `imageCrop.ts` (PNG crop for copying).
- All of them implement the `ProjectStorage` interface (`types.ts`); the session does not know whether it is a folder or local. Only the folder has `folderName`, `statMapping` and `statImage` (what the app checks from outside).
- **Folder access** (`folder.ts`, `folderCalls.ts`): each folder is resolved once and reused (**stored handles**: a path → promise map, with a single retry from the root on `NotFoundError`); independent files are read and written in parallel with a limit (`mapLimit`, `FOLDER_CONCURRENCY` = 4); proposals and conversations are swept in a single pass (`stampProposals`, `stampThreads`); `loadMappingStamped` reads `mapping.json` and the stamp at once; the call counter (`folderCalls.ts`, `session.folderCalls`) counts the calls and the time of the last operation of each kind, and the copied Diagnostics carries the `folder:` line (only with a project in a folder); the check for external changes is adaptive (from 3 s to 30 s, see "Interface" in "The session").
- **Folder recents**: the browser does not let you store the path of a folder, but it lets you store the **handle** (`FileSystemDirectoryHandle`, serializable in IndexedDB) and ask for permission again. `local.ts` (`openFolderLibrary`) stores each opened folder in a separate database, `mapping-folders`, and not in the local projects database: a new store there would require a new database version, and an old open tab would block the upgrade. There are two stores: `folders` (the list row: id, project name, folder name and last use) and `handles` (id → handle). There is never a path. The list (`list`) **reads no handle**: the home screen never depends on the browser being able to rebuild one; the handle is only read on clicking **Open** in a new visit (`handle(id)`; `app/recents.ts` keeps this visit's handles in memory) and, when storing, only those of the entries with the same folder name, for `isSameEntry`. `remember` compares with `isSameEntry` (the same folder updates the entry instead of duplicating; with `replaceId`, "Locate folder…", the entry starts pointing to the chosen folder and, if it was already in the list, the two become one). `folder.ts` provides `isReopenable` (the handle has `queryPermission`, `requestPermission` and `isSameEntry`), `ensurePermission` (queries `readwrite` and, if not `granted`, asks) and `isOriginPrivate`. **An OPFS folder** (`navigator.storage.getDirectory()`, recognized by `isSameEntry`/`resolve` of the root) **is never stored**: the folder picker does not return it (only the e2e tests use it in its place), and Chromium 1243 (full `chrome` and the headless shell) crashes the page when reading an OPFS handle back from IndexedDB (`get` or `getAll`; writing, `structuredClone` and `postMessage` pass). This was measured in CI; with handles from the real picker it cannot be measured in CI, so the manual script checks reopening in real Chrome. Without these features, without IndexedDB or without folder mode (`showDirectoryPicker`), nothing is stored and the list shows only the projects on this device. All access in `try/catch`: a failure when storing goes to the Diagnostics and does not prevent the project from opening. None of this touches `mapping.json`. `LocalLibrary.list()` does not sort: the order of the home screen is that of `recentProjects`.
- **Clone folder of external documents** (`docRepoFolders.ts`): the `doc` of a type may be `{ repo, path }`, a `.md` from a repository declared in `docRepos` of the specialization (formatVersion 11). The app reads the file from the clone folder that the person connects **once per machine** (`showDirectoryPicker`, on a click). The handle stays in IndexedDB, in a database of its own, `mapping-doc-folders` (name per channel: the preview appends `-preview`, like the others), in the `folders` store, with the repository `url` normalized as the key (no trailing `/` or `.git`: `normalizeRepoUrl`). The read queries `queryPermission` in **read** mode and returns `permission` if it is not `granted`; the one who renews it is the "Allow access to <repo>" button, because `requestPermission` only works on a click. An in-memory `Map` keeps the same handle: without IndexedDB (or if it does not open within 3 s), the folder lasts until the tab is closed. All access in `try/catch`, with the failure in the Diagnostics. It **stays out of `mapping.json`** because the folder belongs to this machine and this browser: the handle does not serialize to JSON and should not go in the zip, the commit or through the MCP. What the project keeps is `docRepos[<id>].localPath`, a relative path that the MCP uses to read the document on disk (Settings › Repositories › Documents). The "Open in repository" link on the component page is navigation only (`<a>` to the `urlTemplate`): the CSP and `connect-src 'none'` do not change, and the app still makes no network request. Without a folder picker or without `urlTemplate`, the section shows only the link or `<repo>: <path>`.
- **Project copy (`ProjectStorage.copyId`)**: the key of the per-device state that belongs to a copy (the review resume, `store/review.ts`). Local: the project id (`LocalLibrary.open(id)`). Folder: the id of the recents entry, which is per physical folder (`isSameEntry`) and survives **Locate folder…** (the entry merged with another of the same folder takes that one's id). A folder outside the recents (without IndexedDB, a handle without `isSameEntry`, OPFS, a failure when storing): one id per folder name **per tab** (`sessionCopyId` in `app/recents.ts`, in `sessionStorage` through `safeStorage`, with a fallback `Map`). It is defined when the storage is created, **before** the session opens, and never changes; only the read storages (opening, checking the chosen folder) lack it. The schema has no project id, and one would not resolve the same proposal in two copies (the imported zip and its unzipped folder).

### Focus and keyboard

The focus model lives in `ui/focus.ts`. Three ideas underpin the rules below: opening a modal is synchronous with the render that puts it in the DOM (there is no frame with the `<dialog>` closed and no focus return); the focus origin is stored **once per slot**; and each way of closing has **one** owner that decides where the focus goes (the modal's return only acts when focus is lost, after any explicit owner).

- **Modal** (`Dialog`, `RefPicker`, via `useModal`): `showModal`, initial focus, the count in `modalOpen` and the registration of the return all happen in a `useLayoutEffect`, in the same commit that puts the `<dialog>` in the DOM. A `<dialog>` in the DOM is always open, with focus inside and the return registered, even if it leaves before the next frame. `modalOpen` (a signal) says whether a modal is open; the editor shortcuts and image pasting read it, instead of looking for `dialog[open]` in the document.
- **Return on close** (`restoreFocus`, called in a microtask after the render that closes, because Preact unmounts the dialog before applying the rest of the same render): it only acts when focus is lost (on the `body` or inside the modal that left); then it goes to whoever opened it; if the opener left the DOM, to the explicit target (`returnFocus`, an element or a function read on close); **without** an explicit target, to the nearest focusable container of the opener; lastly, to the first control of `data-focus-root` (`App.tsx`). With an explicit target the model does not guess a container, but, if the target also left the DOM, it goes to the tool window (`[data-window]`, the `section` with `tabindex=-1`) that contained the opener, before the last resort (stage #1273: after **Link to…** + Enter the Details swap the `MarkingPanel` for the `ArrowPanel` and focus stays on the window, already with the arrow). The container fallback may focus a tool window (`section.tool-window[tabindex=-1]`) instead of a control: this is acceptable and stays this way.
- **Origin in the host's slot** (`useDialogSlot`): the editor (`useEditorDialogs`), the home screen and the creation steps of `AnnotationsPanel` have a dialog slot (one at a time). The focus origin is stored in the gesture that opens the first dialog, and a swap in the same slot inherits it (Settings › View keyboard shortcuts, type › owner); the host wraps the slot with `DialogSlotContext` and the first `Dialog` mounted under it claims the origin (`useFocusOrigin`). Dialogs opened on top (the steps of `SpecsDialog`) and standalone ones store theirs at render time.
- **One owner per close**: for each way of closing, a single piece of code decides the focus. Whoever closes and takes focus elsewhere does so by the commit (synchronously or in `useLayoutEffect`), before the modal's return, which then does nothing. Examples: the home screen closes Delete and Remove from list **after** the action and passes `returnFocus` to the row that remains; without a dialog (Remove from list on the row), Home itself takes focus to the row in the commit of the new list. "Go to the annotation" (backlinks, pending items, creation, Ctrl+Enter in the picker) belongs to the panel (`AnnotationsPanel`, in the commit that draws the card). The export dialog returns focus to the **Export** button in the bar (`buttonRef`, exposed by `dialogs.exportButton`), because the zip is generated with it disabled.
- **Specialization notices** (stage #486, `formatVersion` 10): the notice (`notices` on the type, on the field and on the `table` column) only informs; it is not a pending item (`AnnotationIssueCode` and Incomplete do not change) and nothing is blocked because of it. The data comes from two pure functions in `src/model/`, with no DOM and memoized by the project version like `projectIndex`: `noticeUsage(p)` (`notices.ts`: each notice of the loaded specializations with the annotations it affects: the type's, the one with a non-empty value in the field, the one with a non-empty value in the column in some row) and, on top of it, `src/model/noticeList.ts` (`buildNoticeList` and `noticeCounts` for the window, `noticedCount` and `noticesByAnnotation` for the tab and the bar, `changeNotices` for the review). `store/derived.ts` only applies the UI filters (`noticeKind`, `noticesInUseOnly`, `noticesVisibleOnly`, in `store/ui.ts`) and the visible layers over the memoized list (`noticeList`, `noticeCounts`, `noticedCount`), with no `find`/`filter` in loops and no recomputation on pan or zoom. The **Notices** window (`src/ui/NoticesView.tsx`, bottom, `Ctrl+Shift+8`, a tab between Incomplete and Diagnostics; the order of the tabs is that of `TOOL_WINDOWS`, not the number's) groups by notice (`removed`, `deprecated`, `diverges`, `pending`; then the order of the specializations, layers and types), with the badge, the place, the message, the `since` and the count in the group header and one row per annotation (marking, layer, annotation, value); choosing the row takes you to the annotation by the same path as Incomplete. The tab shows how many annotations have some notice and the status bar shows "Notices: N" (hidden when N = 0; clicking opens the window). In the review, the `ChangePopover` shows, below the values of the change, the notices the change brings (`ui/review/ChangeNotices.tsx`, read from the preview with all the changes, `fullPreview`); Accept and Apply do not depend on them.
- **Tool windows** (`ui/toolWindowLayout.ts`): whoever opens (`openToolWindow`: strip, tab, shortcut, `Ctrl+L` and the programmatic paths: `openReview` and `useShowProblem` of the review, `updateFeedback` of `SpecsDialog` and the "go to the annotation" of Incomplete in `EditorWindows`) stores the `document.activeElement` per window, in a UI `Map` (never in the store, not persisted); a window open since load has no origin. Whoever closes is `closeToolWindow` (the X, `hide-window`, `toggle-window` and the click on the strip go through it): it only acts with focus inside the window and, still with the window in the DOM (no frame with focus on the `body`, no microtask), it focuses the first that exists and is outside it: the opener → the window's button in the strip (`data-strip-window`) → canvas (`data-canvas-area`). Opening a window that hides another on the same side applies the same order to the one that left. In the bottom window, switching tabs remounts the section (keyed by id) and would lose the tab's focus: `openToolWindow` takes focus to the active tab of the new window, in a microtask that adds to that of `showAndFocusToolWindow` in the list of exceptions to `useFocusRequest`. **Esc in the Details and Comments windows:** the `onKeyDown` of `ToolWindow` (only for those two ids) calls `closeToolWindow` (the same path as the X) with a plain `Escape`, when the Esc was not consumed (`defaultPrevented`: menu, popover, `HelpTip`), there is no open modal (`modalOpen`) and the target is not a typing field (`isTypingField`); `preventDefault` and `stopPropagation` keep the Esc from reaching the editor shortcuts (the selection stays). Opening by code still does not move focus. In `SpecsDialog` the stored origin is inside the dialog and leaves the DOM when it closes, so when closing Incomplete the strip button applies (accepted). Opening the review from the List (bottom window) swaps the List for Proposals and focus goes to the active tab, not to the `body`. When the opener disappears from the DOM (the **Review** button leaves when the Proposals list becomes the review tree), the strip button (`data-strip-window`) applies, never the `body`; and the opener is only the origin if it actually opened the window (Incomplete does not open Details that were already open). **Lint lock:** `no-restricted-imports` (with `importNames`) forbids importing `showToolWindow`, `hideToolWindow` and `toggleToolWindow` from `store/toolWindows` in `src/ui/**` and `src/app/**`, except in `ui/toolWindowLayout.ts` (`tests/tooling/` proves that the rule refuses). **Intentional** (owner's decision, 2026-11-02): the two-press `Ctrl+Shift+N` (with the window open and focus outside it, the first press only focuses it and the second closes it, as in an IDE) and the Catalog, which on closing restores neither the Tree nor the Layers.
- **Menus and popovers** (`ActionMenu`, `MenuPopover`, `Popover`): on every close (Esc, choice, outside click, scroll), `returnFocusToTrigger` takes the focus that was in the menu to the trigger, before it leaves the DOM; on a choice, before the item's action, so that a dialog opened by it stores the trigger as its opener. If the outside click put focus elsewhere, it stays there. The canvas context menu, with no trigger, returns focus to whoever had it when it opened. The `Popover` can be controlled (`open`/`onOpenChange`): the review marker opens on hover and on focus, and a panel stores which marker is open; with `scroll="follow"` it repositions instead of closing when the page scrolls (the scroll that brings the focused marker into view does not close it). **Limit:** the `Popover` finds the trigger as the first focusable control of the host outside the panel (a heuristic that serves today's uses: the color palette, the layer rows menu and the copy reference and crop menu); a host with another control before the trigger would need a `ref`.
- **Action that takes the control out of place** (`keepFocusAfterAction`, stage #1425): the ⋯ of a Tree row (`ItemMenu`: Wrap changes the row's parent) and the order buttons of the Details (the one that reaches the end becomes disabled) store the focus before the action and, two microtasks later (the action's render comes in between), use `restoreFocus`: the origin control, the tool window that contained it (Tree ⋯, `returnFocus` null) or the neighboring button (order), never the `body`. `restoreFocus` also treats focus on a disabled control as lost, and `tryFocus` refuses a disabled control.
- **Focus after render: a single idiom.** `useFocusRequest()` stores the request and fulfills it in the `useLayoutEffect` of the owner's next render (the grip of the moved row, the new table row, the "+ Pair" after discarding a pair). No `requestAnimationFrame`, `useEffect` or microtask for focus, with these exceptions: the modal's return (above), which the canvas context menu also uses (`restoreFocusAfterRender`, a microtask); **Alt+N** (`useEditorShortcuts.ts`), which opens Details and clicks "+ Annotation" in a `requestAnimationFrame`, after the window draws; `showAndFocusToolWindow` (a module function; the render scheduled by the signal runs in an earlier microtask) and the Tree's **Locate** (`TreeWindow`): `revealInTree` opens the selection's ancestors by signal, the Tree only draws the new rows in the render that this signal schedules, and the `afterPaint` (`MarkingTree.tsx`, a `requestAnimationFrame`) waits for that drawing to find the `aria-current` row inside its own `ref` and focus it. The same `afterPaint`, without focus, scrolls the Tree to a selection that changes from outside.
- **No selectors between components**: a component does not find another through the global DOM or through its class. Use a `ref` (`buttonRef` in `Button`/`IconButton`, `inputRef` in `TextField`, `triggerRef` in `ActionMenu`), `returnFocus`, a signal, or `[data-…]`/`[role=…]` inside its own `ref` (`data-dialog-body`, `data-grip`, `data-cell-value`, `data-recent-open`, `data-tooltip`). ESLint rule (`no-restricted-syntax` in `src/ui/**` and `src/app/**`, `eslint.config.js`): `document.querySelector*`/`getElementById`/`getElementsBy*` and a selector with `.` in `querySelector(All)` and in `closest` are errors (the window and the left column are found by `[data-window]`, `[data-tool-column]` and `[data-panes]`); named exceptions `ui/focus.ts` (`data-focus-root`) and `ui/toolWindowLayout.ts` (`data-window`), and the Alt+N of `useEditorShortcuts.ts` with a justified `eslint-disable`. `tests/tooling/focusRules.test.ts` proves that the rule refuses the old pattern.

**Keyboard policy:**

- **Enter in a text field commits and focus stays in the field** (`CommitInput`, the Value of the pairs); a guard keeps the `change` that the browser fires next from saving again (an undo entry). The guard only holds while the external value (in the pair, the saved pair) is still the base of that save and is reset when it changes: after undoing, the same text saves again; after the render, the field shows the external value and the duplicate `change` has nothing to save, even with an `onCommit` that normalizes the text. Once saved, the draft becomes the saved text, so undoing shows the earlier value, not the draft. Exception: **Enter in the Key** of a pair goes to the Value. Enter in a dialog `<form>` submits; Enter and ↑↓ in the reference picker and in the review levels follow what each one does.
- **Alt+Enter**: new row / new pair.
- **Esc in a field**: with something to revert, it goes back to the saved value and **stops there** (`preventDefault` + `stopPropagation`: it does not close the surrounding dialog or menu); with nothing to revert, it **bubbles up** (closes the menu or dialog; in the editor, the shortcuts ignore text fields). Esc in a new pair discards it and focus goes to the "+ Pair".
- **Esc outside a field, with focus inside Details or Comments**, closes the window (see "Tool windows"); in a field, it belongs to the field (rule above).
- **Menus and popovers** return focus to the trigger on every close (above).
- **`aria-keyshortcuts` always in ARIA syntax** (`Control+E`, `Control+Shift+Z`, `Alt+Enter`, `F1`), generated by `ariaKeys(label)` (`app/shortcuts.ts`) from the human label (`Ctrl+E`), which stays only in the hint; a label that is not a key ("Ctrl+click") does not become an attribute. `IconButton`, `Segmented` and `DecisionControl` apply `ariaKeys`; `tests/tooling/focusRules.test.ts` requires an ARIA literal or `ariaKeys(…)` in every `aria-keyshortcuts=`.

### Styles (`src/theme/`)

`tokens.ts` is the single source of the design tokens (colors in the light and dark themes, spacing, radius, typography, sizes, opacities, durations, z-index, shadows, breakpoints and the layer palette). The `tokensCss` plugin (`vite.config.ts`) delivers it as `virtual:tokens.css`, imported first by `main.tsx`, and there is no `tokens.css` file to edit. For a new value, add it to `tokens.ts` and use `var(--name)` in the CSS: the design system's `space-0.5` becomes `--space-0-5`; for text, use the `--t-text*` roles. `breakpoints.ts` holds the breakpoints (the app's minimum width, the compact desktop and the mockups' reference; media queries do not accept `var()`; a test checks that the CSS uses the same numbers); `src/model/layers.ts` mirrors `layer-01`…`layer-10`. Density is also a token: the roles `--control-height` (28px), `--control-height-sm`, `--control-radius`, `--control-icon` (16px) and `--control-check`, with a single value (no change by width). The CSS files are imported by `main.tsx` in this order: `base.css` (reset, notices, global focus), `controls.css` (Button, IconButton, TextField, Select, Choice, Segmented, Tabs, Tooltip), `layout.css` (screens, banners and the narrow-window notice), `editor.css` (desktop structure: main bar, strips, windows, breadcrumbs, status bar, minimap), `panels.css` (panels, tree, layers, annotations, list), `details.css` (Details: identity, PropertyGrid, LayerGroup, grids, reference and picker), `canvas.css` (canvas area), `forms.css` (common fields and details) and `dialogs.css` (dialogs, help, diagnostics). The order matters: later files win ties in specificity.

### Components

A library (`formatVersion` 4) brings, per annotation type, a component file ([`COMPONENT-FORMAT.md`](COMPONENT-FORMAT.md)). The app draws these components on the canvas, over containers without a file or, if the person wants, over photos.

**Rule: drawing is derived, never saved.** The `mapping.json` stores nothing about the drawing: no scene, box, resolved color or font. It stores only what it always stored (images, markings and annotations with the field values) and, in containers without a file, `file: null` and `background` (schema v10). The drawing comes from the marking, the applied package and the values, every time; exporting, zipping and reopening give the same drawing because the data is the same. The marking draws the **first typed annotation of its own** (in the order of the `annotations` array) whose type has a component in the applied version (`markingComponent`, `src/model/componentCatalog.ts`); only the marking's own annotations draw. Without a catalog or without a component, the marking is plain and nothing changes.

- **Catalog and fonts in memory** (`src/store/componentLibrary.ts`, created by the session). For each applied specialization with a package in `specs/<id>/`, the library reads the components and fonts once per `id@version` (applying, updating, undoing and external reload invalidate). The catalog (`ComponentCatalog`) lives in a signal; components that fail to load become `problems` and do not bring down the rest. Fonts become a `FontFace` from the file's **bytes** (`src/storage/fonts.ts`; the CSP blocks fonts by URL, but accepts an in-memory `ArrayBuffer`). Each finished registration bumps `fontsEpoch`, and the drawings are remeasured. A missing font falls back to the system font, with a notice in Diagnostics.

In the browser the measurement is real; in Node and in the MCP server it is always the approximate one (which is why the MCP never arranges, see below).

Changing the rectangle, a value, the catalog, the measurer or `fontsEpoch` redraws; pan and zoom do not. In the Proposed view, the catalog that the derived state reads (`review.components`, `src/store/proposedCatalog.ts`) is that of the applied library plus the specialization packages that the open proposal creates or updates, read from `proposals/<id>/<folder>/` when the proposal opens (not when the view changes nor when one decides) and without saving anything in `specs/`; in the Current view, the catalog is the library's (`session.components`), the very same object. The `component-overflow` pending item ("The component does not fit") is produced here, joined with the model's, and therefore enters Incomplete and the count.
- **Konva layer** (`src/canvas/components/componentLayer.ts`, `renderScene.ts`, `screenRenderer.ts`). It sits between the images and the markings, with one node per marking that draws (the component's `slot` does not draw an outline in the product, `showSlots: false`; only tests and the viewer show the reserved area) and **diff by identity** of the `ComponentDrawing` (same object, node untouched). The drawing cache instantiates the component in the box in units (`rect` ÷ density) and puts `translate(rect.x, rect.y) · scale(density)` in the scene root's matrix, so Konva (which reads the scale from the matrix), the MCP raster and the viewer do not change contract; `screen` and `stroke.scale: false` ignore the density. The cache comparison gains `density` per entry (changing the density re-instantiates only the container's markings; pan and zoom do not instantiate). `slotExcess`, `shortfalls` and the slot clip come out in image pixels. Sizes: `componentMinSize` returns the `minSize` × density (rounded up), the initial `size` is `size` × density and Arrange (`arrangeMarking`, `fitMarking`) measures in units and saves in pixels. The drawing proof (`component-overflow`) inherits from the cache and remains in image pixels.
- **Reading direction** (schema v20, `src/model/direction.ts`). `direction` (`ltr` or `rtl`; absent means `ltr`) on the project and on the container; `effectiveDirection(p, containerId)` is the container's, if it sets one, otherwise the project's (the canvas and the floating markings, `containerId` null, follow the project). The direction does not change any marking pixel.

Pure function: for each ready size (`containers[]`, `formatVersion` 6) of the applied specializations, if `container width ÷ ready size width` is 1.5, 2, 3 or 4 (tolerance of 2 px), it returns the factor and the ready size; the height only breaks ties (the one whose `factor × height` is closest wins; then the first in the order of the specializations), because capture usually crops bars. ### Content Security Policy

`dist/index.html` carries this policy in a `<meta http-equiv="Content-Security-Policy">`, right after the `charset` (it only applies to what comes after it):

```
default-src 'none';
script-src 'sha256-…';   style-src 'sha256-…';
img-src 'self' data: blob: https: http:;   connect-src 'none';
worker-src 'self';   manifest-src 'self';
object-src 'none';   frame-src 'none';   form-action 'none';   base-uri 'none';
require-trusted-types-for 'script';   trusted-types default
```

This is the policy of the `app` profile (the `index.html`). `pwa/csp.ts` has two profiles, `CspProfile = 'app' | 'static'`, a required parameter of `buildCsp`, `injectCsp`, `verifyCsp` and `applyCsp`. The `static` profile (the guide `public/guia/`, generated by `scripts/guia.ts`, and the viewer demo, `viewer/demo/`) has `img-src 'self' data: blob:` and does not require Trusted Types. The guide builds the panel with a non-empty `innerHTML` (example data, escaped) and the demo does not load the `default` policy; neither shows a remote image, so in them an outbound image remains blocked by the browser. The rest of this section describes the `app` profile.

**Why it exists.** The app already makes no network request with user data, but that was only a promise in the code. With `connect-src 'none'` (and `default-src 'none'`) the browser starts refusing `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, fonts and frames from any origin, including our own: a bug, a compromised dependency or a malicious JSON opened in the app cannot take the project off the device through those paths. **Images are the exception:** `img-src` allows `https:` and `http:` (a component can display an image by URL, from any origin; see "Threat model (remote images)" below), and what keeps the image from becoming an outbound channel is no longer the CSP alone. `form-action 'none'` and `frame-src 'none'` close the paths through forms and `iframe`; `base-uri 'none'` prevents rewriting relative URLs; `object-src 'none'` turns off plugins.

**How it is generated.** `pwa/csp.ts` (pure functions) and the `contentSecurityPolicy` plugin of `pwa/buildPlugins.ts`. The plugin runs **after** vite-plugin-singlefile (which inlines the JS and CSS in `generateBundle`, in the normal phase in 2.3.3 and in `order: 'post'` in 2.3.4) and **before** `serviceWorker()`: both of our plugins have `enforce: 'post'` and come after `viteSingleFile()` in the list in `vite.config.ts`, which holds with any version of singlefile (locked by `tests/build/pluginOrder.test.ts`). This order exists because the build hash that `sw.js` carries must see the HTML already with the policy. For each `<script>` and `<style>` block of the final HTML it computes the SHA-256 of the exact content (with CRLF normalized, as the browser does) and puts it in `script-src`/`style-src`. That is why the policy **cannot be written by hand in the source `index.html`**: any change in the bundle changes the hash. In `npm run dev` there is no CSP (Vite injects inline scripts for HMR); it only exists in the build, which is what is published and what the E2E tests open.

**The build fails** (`verifyCsp`, called by `applyCsp`) if: the CSP is missing; a fixed directive is altered; there is any `'unsafe-*'`; some embedded block has no matching hash (or a hash is left over without a block); there is a `<script src>`, `<link rel="stylesheet">`, `style=""` or inline handler in the HTML. In the `app` profile it also flags: an `img-src` different from `'self' data: blob: https: http:`, a missing `require-trusted-types-for 'script'` or `trusted-types default`, and the absence of `<meta name="referrer" content="no-referrer">` in the `index.html`. In the `static` profile the check is the earlier one (`img-src 'self' data: blob:` exactly) and the Trusted Types directives are flagged, because they must not be there. `tests/app/cspBuild.test.ts` covers each case.

**What the CSP allows and why.**

| Directive                                            | Value                     | Reason                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `script-src`, `style-src`                            | only the block hashes     | The app is a single file: one embedded JS and one CSS. Styles applied by JS (CSSOM: `el.style.x = …`, `style.setProperty`, Preact's `style` object and Konva) are **not** blocked; the `style=""` attribute and `setAttribute('style', …)` are.                             |
| `img-src 'self' data: blob: https: http:`            | own, data, blob, web      | Icons (`./icons/…`), project images (`blob:` URLs), embedded images and images by URL from any origin. Fixed: the `http:` switch belongs to the app (URL policy), not to the CSP; there is no build variable. `createImageBitmap` and the canvas do not go through the CSP. |
| `require-trusted-types-for 'script'`                 | —                         | The HTML and script sinks (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `script.src`, `navigator.serviceWorker.register`…) only accept values from a Trusted Types policy. See "Trusted Types" below.                                                  |
| `trusted-types default`                              | only the `default` policy | Creating any other policy (`trustedTypes.createPolicy('x', …)`) is refused by the browser.                                                                                                                                                                                  |
| `connect-src 'none'`                                 | nothing                   | The central rule. The service worker is not affected: it runs in another context and the page's policy does not apply to it.                                                                                                                                                |
| `worker-src 'self'`                                  | `./sw.js`                 | Registration of the service worker (only on `https:`; on `file://` there is no service worker and the directive goes unused).                                                                                                                                               |
| `manifest-src 'self'`                                | `./manifest.webmanifest`  | The `<link rel="manifest">` is inserted by `attachManifest()` only on `https:`.                                                                                                                                                                                             |
| `object-src`, `frame-src`, `form-action`, `base-uri` | `'none'`                  | No plugins, no frames, no form submission (the app's forms use `onSubmit` with `preventDefault`) and no `<base>`.                                                                                                                                                           |

#### Trusted Types

The `default` policy lives in `src/app/trustedTypes.ts`, imported **before any other code** in `src/main.tsx`. It accepts only what the app actually uses:

- `createHTML`: only the empty string (Konva does `container.innerHTML = ''`; Preact only uses `innerHTML` with `dangerouslySetInnerHTML`, which the code does not use);
- `createScriptURL`: only exactly `'./sw.js'` (constant `SERVICE_WORKER_URL`). Chromium treats `navigator.serviceWorker.register` as a `TrustedScriptURL` sink; without this the service worker would not register. It is the only exception to the "only the empty string" rule, decided by the owner on 2026-10-31;
- no `createScript`.

Any other HTML, script or script URL is refused by the browser (`TypeError` and a `require-trusted-types-for` violation), and another policy (`createPolicy` with another name) is too (`trusted-types default`). A browser without Trusted Types: the policy is not installed and the rest of the CSP still holds. **Practical rule:** no `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `dangerouslySetInnerHTML` with content, nor `script.src`; build the DOM through JSX or `textContent`. If a new legitimate use appears, stop and record it in the PR instead of loosening the policy.

#### Referrer

The `index.html` carries `<meta name="referrer" content="no-referrer">`: no request the page makes (remote image included) reports which address it came from. `verifyCsp` requires the meta in the `app` profile.

#### Remote images: policy, consent and loader

A component's `image` node (a literal `src` or exactly `{ "$field": "<field>" }`, a `string` field or a `string` column of the `table`
in a `repeat`; `$concat`, `$switch` and other expressions in `src` are a parser error, so the component does not assemble a URL with values
from other fields and send project data to whoever wrote the specialization) requests an image by URL. `width`/`height` `hug` is an error: the
arrangement never depends on the downloaded image. The specialization does not declare origins.

- **First gate, the policy** (`model/remoteImages.ts`, pure, only `URL`): `checkRemoteImageUrl(value, { allowHttp,
allowLocalNetwork })` returns `{ ok: true, url, origin, local }` or `{ ok: false, reason }` (`empty`, `invalid`, `insecure`,
  `credentials`, `too-long`, `private-host`). Only `https:` (and `http:` with the switch on), no username and password, up to 2048
  characters; a literal IP, `localhost`, a name without a dot and the suffixes `.local`, `.localhost`, `.internal`, `.home.arpa`, `.lan` and `.intranet` are refused while the
  local network switch is off.
- **Second gate, consent** (`storage/imagePermissions.ts`): per **origin** (scheme included, so `http://a.com` and
  `https://a.com` are different origins), per browser, only in `localStorage` with try/catch. It **never** goes into the project, the
  specialization, the zip or the proposal (a third party's project cannot authorize itself, and a reused specialization `id` does not
  inherit permission) and is never automatic. The strip above the canvas (derived state in `store/derived.ts`) lists the new origins of the
  open project, with **Allow these** and **Not now** (the default, valid for the session); a new origin that appears later
  (edit, MCP, proposal) brings it back with only that one. Settings › Privacy lists the allowed origins with **Revoke** and has
  three switches, all off by default and with a warning: **any origin** (no strip; the local network still asks for its own
  consent), **unencrypted images (`http:`)** (separate from the previous one) and **local network**. A fourth, **servers
  without CORS**, allows the attempt described below. It applies equally in read-only mode and in both views of the review.
- **Loader** (`canvas/components/imageLoader.ts`, the only place that creates an `Image` for a remote URL): `crossOrigin = 'anonymous'`
  and `referrerPolicy = 'no-referrer'`; up to 6 in parallel, 20 s timeout, refuses above 8192 px on a side or 40 MP, displays a
  bitmap reduced to 2048 px on the longer side, in-memory cache per URL (64 entries, `close()` deferred to the next frame) and a failure
  not retried in the session. States per image: `loading`, `loaded`, `opaque`, `blocked-consent`, `invalid`, `failed`, `too-large`;
  all except `loaded` and `opaque` draw the reserved area. `canvas/components/remoteImages.ts` is the bridge (policy, consent,
  loader) for the main canvas and for the Catalog gallery; failures go to Diagnostics, once per URL.
- **Without CORS:** with the switch on, the loader first tries with `crossOrigin` and, if that fails, **once** without it; the image
  becomes `opaque`. An `opaque` image is only drawn on the main canvas. **Every pixel read** (`toDataURL`, `toBlob`,
  `getImageData`, `toCanvas`) uses the reserved area in its place: the only read over a layer with an image is the Catalog gallery's
  (`canvas/components/exampleImages.ts`, always `pixelSafe: true`); the minimap does not read pixels and the crops only read
  project images (`blob:`). `tests/canvas/pixelReads.test.ts` fails if a new read appears outside that list.
- **Known limits:** in the app published on `https:`, Chrome and Edge treat `http:` as mixed content (they try `https:` and,
  without it, the image becomes `failed`) and may block a public site's access to the local network or ask for their own permission; both
  actually work through `file://`. The app does not work around this.
- **MCP and viewer:** the server **never downloads** an image: it draws the reserved area in `get_marking_image` and returns the URL as text
  in the values (the agent only saves a URL that came from the work's source or the owner, never an invented one). The embeddable viewer has the
  `remoteImages` option, off by default; when on, it follows the URL policy and receives from the host a function
  `allowOrigin(origin)` (default refuse everything), with no consent of its own; the CSP belongs to the host site.

#### Threat model (remote images)

An image is only requested from the network when **both gates in the app** agree: the URL passes the policy (`src/model/remoteImages.ts`; `http:` only with the switch on) **and** the origin has consent in this browser (or the "Allow images from any origin" switch is on). The CSP sits on top, allowing `https:`/`http:`. Who covers each threat:

| Threat                                                                                                                    | Who covers it                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1. Project data leak through injected code or a bug (`new Image().src = 'https://x/?d=…'`)                               | The browser no longer blocks the outbound image. Covered by: `script-src` with hashes only (no injected script runs) and Trusted Types (no injected HTML), a single image creator (lint rule); `src` restricted to a literal or `{ "$field" }`. `connect-src 'none'` remains.                                  |
| T2. Tracking of whoever opens the project (IP, time) by whoever wrote the specialization, the proposal or the annotation  | Consent per origin, per browser; `no-referrer`; no credentials.                                                                                                                                                                                                                                                |
| T3. Malicious URL in a field value (agent through the MCP, proposal, edit)                                                | Pure policy in the model: only `https:`, no username and password, up to 2048 characters, no private host.                                                                                                                                                                                                     |
| T4. Memory exhaustion (huge image) and excess requests                                                                    | Loader with a concurrency limit, timeout, maximum decoded size and a reduced display bitmap; in-memory cache only, with eviction.                                                                                                                                                                              |
| T5. Tainted canvas breaking the Catalog gallery                                                                           | `crossOrigin = 'anonymous'` by default; server without CORS: the image does not load and the reserved area remains. With the CORS switch on, the `opaque` image is only drawn on the main canvas and never read back.                                                                                          |
| T6. Private network (router, `localhost`, internal services)                                                              | Local network switch off by default: a literal IP, `localhost`, a name without a dot and the suffixes `.local`, `.localhost`, `.internal`, `.home.arpa`, `.lan`, `.intranet` are refused by the policy (`private-host`); when on, each local origin asks for its own consent, not even "any origin" covers it. |
| T7. Persistence and resending of third-party content                                                                      | The image is never saved: not in the project, not in the zip, not in IndexedDB, not in the service worker cache (`pwa/sw.js` already ignores requests to another origin). Only the URL (text) stays in the `mapping.json`.                                                                                     |
| T8. MCP server making requests on the agent's behalf                                                                      | The MCP **never** downloads images: it draws the reserved area and returns the URL as text.                                                                                                                                                                                                                    |
| T9. Image over `http:` (the URL, with tokens, and the image travel unencrypted and can be read or swapped on the network) | Switch off by default, consent separate from the `http` origin, notice in the strip and in Privacy; the swapped image does not run code (it is decoded as an image, with no script).                                                                                                                           |
| T10. Site cookies on an image without CORS                                                                                | Switch off by default, warning, `no-referrer` and a single retry.                                                                                                                                                                                                                                              |

**A single image creator.** The `imageCreationSyntaxRules` rule of `eslint.config.js` forbids `new Image`, `createElement('img')`, assignment to `.src`/`.srcset`, `setAttribute('src'|'srcset')` and `fromURL` in `src/**` and `viewer/**`, except in `src/canvas/components/imageLoader.ts` (the loader) and in `src/storage/**` (the project images, through `blob:`). Test in `tests/tooling/imageCreationLint.test.ts`. This way no new code assembles an image URL outside the policy.

**Residual threat.** A bug in our code that puts data in an image URL is no longer blocked by the browser (it used to be). Whoever controls a consented origin learns when and from which IP the project is opened and which markings appear on screen. And an agent or a proposal can put in a URL from a new origin: it is only requested after that origin's consent, or immediately if the "any origin" switch is on.

**Download, sharing, clipboard and drag and drop** do not depend on the CSP: downloading the zip uses the system's "Save as" (`showSaveFilePicker`, written by the handle's `createWritable`) where it exists (Chrome and Edge, including on `file://`) and, without it, a click on `<a download href="blob:…">` (navigation/download is not governed by `default-src`); `navigator.share` and `navigator.clipboard` are browser APIs (copying the reference writes the text first, with `writeText`, always allowed, and only adds the custom format when `clipboard-read` is already granted, because writing a `web …` format requires that permission and the app does not ask for permission when copying); dragging, dropping and pasting arrive as `File`/`DataTransfer` inside the page. The "Unexported changes" notice of a project on this device (`markExported` in `app/controller.ts`) only goes away when the file has left: through the picker, after the write's `close()`; through sharing, when the `navigator.share` promise resolves. Canceling the picker or the sharing (`AbortError`) changes nothing, and a write failure shows the error in the dialog. With `<a download>` the app does not know whether the person saved: the notice goes away on the click and the dialog warns that, if they cancel the save, they need to export again (`app/ExportDialog.tsx`, `storage/share.ts`).

**Dependencies.** zod 4 tests `Function('')` to generate compiled validators; under the CSP this becomes a violation (caught, but logged in the console and emitted as `securitypolicyviolation`). `src/utils/zodConfig.ts` (imported first by `main.tsx`) turns on `jitless`, and zod uses the interpreted path, without `eval`. JSZip only uses `new Function` in a `setImmediate` _fallback_ that is not reached in the supported browsers.

**For whoever changes the app.** Dynamic style: use CSS properties (`--var`) through Preact's `style` object; do not use `dangerouslySetInnerHTML` with `style=""`, a `<style>` injected at runtime, `eval`, `new Function`, `import()` of an external URL or `fetch`. Also do not use `innerHTML` with content or `script.src` (Trusted Types), and do not create an image by URL outside the loader. If a new feature needs the network, it requires deciding the policy again (and what is promised to the user in the README), not loosening the directive.

**Tests.** `tests/e2e/csp.spec.ts` (Playwright): the `<meta>` comes before any resource; `fetch`, XHR, WebSocket, EventSource, external image, `eval`, inline `<script>` and `setAttribute('style')` are blocked and no request leaves the page; the main flow (create a project, add an image, mark, annotate, copy ID, drag and paste images, export the zip) ends with **zero** `securitypolicyviolation` events; so do the zip sharing (simulated Web Share) and opening through `file://`. `tests/e2e/cspServiceWorker.spec.ts`: a local `https` server (like GitHub Pages) with the main version at `/` and a preview build (`VITE_CHANNEL=preview`) at `/preview/`: service worker installation, precache, offline use, the "New version available" notice when `sw.js` changes, and the two service workers coexisting, with no violations. This test uses `openssl` and `--ignore-certificate-errors` (the service worker does not register with a self-signed certificate without it).

### Build and PWA

`vite.config.ts` uses `vite-plugin-singlefile` (a single `index.html`) and stamps `pwa/sw.js` with a build hash, which is what makes the browser detect a "new version". `VITE_CHANNEL=preview` (see `src/utils/channel.ts`) separates the preview's storage, manifest and service worker.

**Isolated preview.** The deploy publishes `main` at `/` and the branch at `/preview/` in the same Pages artifact; production is never replaced (a push to `main` publishes only `main`). The preview build, with `VITE_CHANNEL=preview`, appends the suffix `-preview` to the IndexedDB database name and the prefix `preview:` to the `localStorage` keys (so it never migrates or deletes the main version's projects), shows a fixed strip warning that the data is separate, uses the name "Mapping (preview)" in the manifest (`PREVIEW_APP_NAME`, `pwa/build.ts`) and registers the service worker in the `/preview/` scope.
