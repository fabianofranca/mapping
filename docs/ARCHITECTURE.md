# Arquitetura

Aplicação Preact/TypeScript sem servidor. O estado do projeto é um objeto JSON imutável; tudo o que muda esse objeto passa por uma _action_ do store.

## Camadas

```
model  →  store  →  storage / canvas / ui (app)
```

Cada camada só conhece as da esquerda.

| Camada     | Pasta                                   | Responsabilidade                                                                                                                    |
| ---------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `model`    | `src/model/`                            | Tipos do `mapping.json`, schema (zod), invariantes, migrações e **todas as regras de negócio**, como funções puras e imutáveis.     |
| `store`    | `src/store/`                            | Estado do projeto com desfazer (`history.ts`), actions (`project.ts`), sessão de persistência (`session.ts`), UI e estado derivado. |
| `storage`  | `src/storage/`                          | Pasta (File System Access), projeto local (IndexedDB), zip, leitura de imagens/EXIF, autosave.                                      |
| `canvas`   | `src/canvas/`                           | Konva isolado: `CanvasController` imperativo, renderers, camada de componentes, entrada (ponteiro/teclado) e viewport.              |
| `ui`/`app` | `src/ui/`, `src/app/`                   | Componentes Preact: tela inicial, editor, painéis e diálogos; `controller.ts` orquestra a abertura/criação de projetos.             |
| apoio      | `src/i18n/`, `src/theme/`, `src/utils/` | Textos (pt-BR/en-US), tokens e CSS do tema, erros (`report.ts`), canal main/preview, `localStorage` seguro.                         |

## Fluxo de dados

```
ação do usuário
  → action (store/project.ts)
  → operação pura (model/…): (Project) => Project
  → snapshot no histórico (store/history.ts) + project signal (e committed)
  → projeto à vista (shownProject: confirmado ou "como ficaria" da revisão, recortado pela perspectiva aberta)
  → derived (store/derived.ts): camadas visíveis, indicadores, pendências, lista, lista de incompletas…
  → canvas (um desenho por quadro; geometria de `project` com a prévia do gesto, recortada pela perspectiva) e UI (o projeto à vista e os computed)
  → autosave (storage/autosave.ts) → mapping.json (pasta ou IndexedDB), sem as perspectivas "Só eu"; estas vão ao IndexedDB, num banco só delas
```

- **Store** (`createProjectStore`): guarda o projeto atual e as pilhas `past`/`future` de snapshots (limite de 100). Uma operação que lança erro de regra volta como `ActionResult` com `ok: false`, sem alterar o estado. Um gesto (arrastar/redimensionar) é agrupado e vira **uma** entrada de desfazer.
- **Projeto confirmado × prévia de gesto**: durante um gesto, `updateGesture` troca `store.project` a cada `pointermove` (a prévia). O store expõe também **`store.committed`**: o projeto sem as prévias. Fora de um gesto é o mesmo objeto de `project`; durante o gesto fica no projeto do início e só muda no `commitGesture`/`cancelGesture` (em lote, sem valor intermediário). O **canvas** lê `project` (a geometria acompanha o dedo), recortado pela perspectiva aberta (`drawnProject`); a **interface** (`Editor*`, painéis, lista, diálogos, avisos) e o `derived.ts` leem `committed` (ou o projeto à vista, que parte dele), e componentes que só precisam de uma fatia (há projeto? há seleção? nome do projeto?) usam `useComputed`. Resultado: o arrasto não re-renderiza a árvore Preact nem recalcula pendências, indicadores, visibilidade e lista. Consequência visível: os campos x/y/largura/altura do painel atualizam ao **soltar** o gesto. `tests/components/editorRenders.test.tsx` guarda o limite (30 movimentos, no máximo 2 renderizações de `EditorScreen`, `EditorPanel` e `EditorTopBar`).
- **Estado do projeto × estado da UI**: o JSON e o desfazer ficam no store; seleção, camadas visíveis, modo (navegar/desenhar), modo visualização (`viewMode` e a escolha `viewShow`, `Alt+H`: o modo nasce desligado com o editor de cada projeto e nunca é gravado; ligar volta ao Navegar. `viewShow` (`store/viewMode.ts`: Containers, Imagens, Contorno, Nome, Setas e as camadas com desenho desmarcadas) começa com tudo marcado menos o Contorno e é guardada **por cópia do projeto**, neste navegador, num blob versionado do `localStorage` (`mapping.viewShow`, zod, try/catch, as 20 cópias mais recentes; sem `copyId` vale só para a sessão; camada que não existe é ignorada e camada nova nasce marcada). No modo, `markingVisibility` devolve toda marcação como `'hidden'` (nada se seleciona ao toque), `canvasVisibility` a devolve inteira (o filtro "Marcações sem anotação" não vale, e esconder o contorno não esconde a marcação para a seta), `drawnMarkings` perde os desenhos das camadas desmarcadas (o `ComponentDrawing` traz o `layerId`; o cache de desenhos não é refeito), `drawingLayers` lista as camadas que desenham, o `CanvasController` zera seleção, hover, rascunho e marcas da revisão no quadro e entrega o `view` (os cinco itens) aos renderers, e o ponteiro trata o modo como Navegar, sem setas ao toque. **Só as telas** (Containers e Imagens marcados, o resto desmarcado) dá o canvas do antigo Ver limpo. A interface é `ui/ViewModePanel.tsx`: o `IconButton` **Mostrar no canvas** (só habilitado no modo) e o popover, aberto por `ui.viewPanel` (`setViewMode` o abre ao ligar e o fecha ao desligar); o Esc fecha o painel (o `Popover` consome a tecla) e, sem painel, sai do modo), painel aberto, seções recolhidas de Detalhes (`collapsed`), nós recolhidos da árvore (`collapsedTree`) e viewport ficam em `EditorUi` (`store/ui.ts`) e nunca vão para o arquivo nem para o histórico. As janelas de ferramenta abertas, os tamanhos de cada lado e a altura da janela Camadas ficam em `store/toolWindows.ts` (signals de módulo, por dispositivo, guardados no `localStorage` com try/catch); zoom, cursor e área das imagens ficam em `canvas/viewState.ts`, escritos pelo canvas e só lidos pela interface.
- **Estado derivado** (`createEditorDerived`): `computed` por editor, calculados uma vez e lidos por canvas, painel e lista, sobre o projeto à vista. Dependem só do projeto, da perspectiva aberta e da UI, **não do viewport**: pan e zoom não os recalculam. As camadas visíveis (`visibleLayers`) escondem as `hiddenLayers` da perspectiva aberta (`derived.perspective`) ou, na Principal, as de `ui.hiddenLayers`.
- **Trava**: `locked` em imagens e marcações bloqueia mover, redimensionar e excluir; a seleção, o nome e as anotações seguem livres. As regras vivem só em `model/locks.ts`: a interface as consulta (`can…`) para não oferecer o que seria recusado, e as operações do modelo as aplicam de novo e lançam `locked`, então nenhum caminho (gesto, painel, atalho, ação do store) contorna a trava. A trava protege o **item trancado**, não o pai dele: trancar um pai trava a geometria dos descendentes sem mexer no `locked` deles, mas um descendente trancado nunca impede o pai (mover o pai o leva junto, mantendo a posição relativa; excluir o pai o exclui, e `markingDeletionImpact`/`imageDeletionImpact` informam `lockedDescendants`/`lockedMarkings` para a confirmação avisar quantos). O estado derivado `derived.markingLocks` (e `hasLocks`) alimenta a Árvore e o canvas. No canvas, `intentAt` devolve a intenção `locked` sobre o item trancado (sem alças, cursor `not-allowed`, o arrasto do mouse vira o gesto `blocked`; numa tela de toque o arrasto continua sendo pan). O emblema do cadeado (`renderers/lockBadge.ts`, tokens `cv-lock`, `cv-lock-glyph` e `size-lock-badge`) aparece na seleção e no item trancado sob o mouse (`state.hoverLock`, calculado uma vez por quadro e só em projetos com trava). Trancar, destrancar e "trancar todas" são actions (`setMarkingLocked`, `setImageLocked`, `setImageMarkingsLocked`), cada uma com uma entrada de desfazer.
- **Índice** (`projectIndex(p)`): mapas por id e agrupamentos (marcações filhas, anotações por marcação e por dono, backlinks), memoizados em `WeakMap<Project, …>`: um projeto novo (nova versão) reconstrói o índice uma vez; leituras seguintes são O(1).
- **Sessão e gravação** (`openSession`): o único escritor do `mapping.json`, com uma fila só para gravar, conferir alterações externas, recarregar e decidir o conflito. Máquina de estados, trabalhos da fila e contratos na seção ["Sessão e gravação"](#sessão-e-gravação) abaixo.
- **Propostas de alteração** (formato em [`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md)): três peças, todas fora do JSON do projeto.
  - **Armazenamento** (`ProjectStorage.listProposals/readProposal/writeProposal/removeProposal/statProposal`): `proposals/<id>/proposal.json` na pasta (`statProposal` só na pasta, como `statMapping`), no IndexedDB (mesmo store de arquivos, com a chave `proposals/<id>/proposal.json`; gravar uma proposta marca o projeto como "não exportado") e no zip (`ProjectFiles.proposals` e `proposalImages`, lidos e gravados como estão: o texto de cada `proposal.json` volta idêntico, e o de um arquivo inválido também, para a exportação não perder nada). As imagens que esperam a aceitação usam `readImage`/`writeImage`/`removeImage` com o caminho completo `proposals/<id>/images/…`. `storage/loadProposals.ts` lê e valida (zod, `parseProposalText`; o `id` do arquivo precisa ser o da pasta): um arquivo inválido vira um problema listado à parte e não derruba o resto. **`removeProposal(id)`** apaga a proposta inteira: na pasta, `proposals/<id>/` recursivo (o `proposal.json` e as imagens que esperam a aceitação; não falha se já não existe); no projeto local, as chaves `proposals/<id>/…` numa transação, marcando "não exportado" como `writeProposal`. Os dois recusam um `id` fora de `PROPOSAL_ID_RE` (um id vazio ou com `..` apontaria para `proposals/` inteira).
  - **Sessão** (`store/proposals.ts`, `session.proposals`): a lista em memória (`list`, a mais nova primeiro; cada proposta mantém o objeto enquanto não muda), `problems`, `notices` (nova, alterada ou apagada por fora) e a gravação, que só este módulo faz. A **`revision`** da proposta tem a mesma conferência do `mapping.json`: toda gravação relê o arquivo e, se o texto difere do que a sessão leu ou gravou por último (o MCP substituiu ou retirou a proposta, um editor mexeu nela), **adota a versão do disco e refaz a mudança sobre ela** em vez de sobrescrevê-la (cada mudança é uma função pura da proposta: decidir, anotar, aplicar), grava `revision + 1` e atualiza o carimbo conhecido. Decisões e notas gravam na hora, sem atraso, numa fila única (`mutate`). Um arquivo que mudou e ficou ilegível não é sobrescrito. **`remove(id, onRemoved?)`** é a outra operação da fila: relê o arquivo, adota a versão do disco se mudou por fora e **recusa** se a proposta está (ou voltou a estar) aberta (`not-removable`; a regra é `canRemoveProposal` do modelo: só retirada, substituída e aplicada) ou ficou ilegível (`unreadable`); senão apaga pelo armazenamento (`remove-failed` se falha, com a proposta ainda na lista), tira a proposta da lista **sem** o aviso `removed` (a pessoa apagou: o `scan` seguinte não encontra a proposta nem em `known`) e limpa os avisos dela. `onRemoved` roda de forma síncrona logo depois, sem janela para um desfazer no meio. Uma proposta nova com `supersedes` apontando para a apagada continua listada: `supersededBy`, `leftBehind` e `compareProposals` só consultam as propostas presentes. **Guarda da decisão sobre conteúdo revisado** (etapa #644, decisão 8): `Mutation` recebe também `seen`, a versão que a sessão tinha antes de reler o arquivo. Quando o agente revisou a proposta por fora, `revisions` cresceu em relação a `seen`; `unseenRevisedIds(seen, p)` (modelo) lista as mudanças trocadas ou acrescentadas por essas revisões. `decide`/`decideMany` recusam com `revised`, sem gravar, se alguma mudança que mudaria de estado (pedida ou em cascata) está nesse conjunto; a sessão já adotou a versão do disco, então a revisão passa a mostrá-la (com a marca) e a decisão seguinte vale. Notas e Aplicar aceitas são refeitas como antes; a nota numa mudança retirada sobe ao nível da proposta e o id dela entra em `revisions[].dropped[].notes` (`droppedEntryOf`/`withDroppedNote`). Quando a releitura traz uma revisão nova, o aviso é `revised` (com as contagens da revisão mais nova; `noticeKindFor`) no lugar de `changed`. `session.sync()` confere a pasta junto com o `mapping.json` (`proposals.scan()` a cada ~3 s e ao voltar o foco): proposta nova, alterada ou apagada por fora entra em `notices`; um arquivo conhecido que fica ilegível por um instante (editor escrevendo) é ignorado até ficar válido.
  - **Ações** (`store/proposalActions.ts`, `session.proposalActions`): `decide`/`decideMany` (a regra é `decide` do modelo; uma gravação por chamada, com o mapa de decisões anterior para o "Desfazer" do lote), `restoreDecisions` (regrava o mapa anterior numa única escrita, só se as decisões ainda são as de depois), `addNote`/`editNote`/`removeNote` e `applyAccepted`. **Aplicar aceitas** é uma entrada de desfazer do projeto: calcula com `applyAccepted` do modelo, copia as imagens de `proposals/<id>/images/…` para `images/` (recusa se o arquivo ou a origem faltam, ou se o destino é de outra imagem), aplica ao projeto, grava o `mapping.json`, grava a proposta (`applied`, `status`) e só então apaga as origens. A entrada leva um `HistoryLink` (`store/history.ts`): desfazer tira o `applied` daquelas mudanças e devolve as imagens a `proposals/<id>/`; refazer põe de novo. Decidir depois de desfazer descarta o "refazer" (`discardRedoOf`), que deixaria projeto e proposta em desacordo. **Desfazer e refazer esperam a gravação**: `HistoryLink.undo`/`redo` devolvem uma promessa com o resultado do `proposals.mutate`; enquanto ela está pendente, `canUndo`/`canRedo` ficam falsos e `undo`/`redo` recusam (dois `Ctrl+Z` seguidos não se cruzam). Se a gravação falha, o passo é revertido (projeto e pilhas voltam ao de antes, se nada mais os mudou), a proposta fica como estava em disco e `ProjectStore.linkFailure` leva o erro, que os botões de desfazer mostram por toast (`proposal.error.writeFailed`); o `reportError` continua. **Falhas no meio**: se o `mapping.json` não grava (`save-failed`), a entrada é desfeita sem "refazer" (`abandoned`), as cópias saem de `images/` e a proposta não é gravada; se o `mapping.json` gravou e o `proposal.json` falhou (`write-failed`), `MutationPlan.compensate` desfaz a entrada do mesmo jeito, confirma com `flush` a regravação do projeto de antes (a sessão a agenda sozinha, porque o confirmado deixou de ser o gravado) e só então tira as cópias (o arquivo em disco as cita até a regravação; se ela falha, as cópias ficam para a limpeza da sessão quando a gravação passar, e `pendingFiles` ainda as lista, o que faz um `adopt` posterior tentar removê-las de novo sem efeito). Nos dois casos as aceitas continuam "aguardando aplicação" e aplicar de novo conclui. **Apagar uma proposta** (`removeProposal`, que a revisão chama por `review.removeProposal`): recusa com `read-only` (projeto somente leitura) e `reviewing` (revisão aberta; a lista nem aparece nela), apaga pela fila e então `ProjectStore.detachLinks(id)` tira o `HistoryLink` da proposta de todas as entradas do desfazer e do refazer. As **entradas ficam**: desfazer e refazer a aplicação passam a mexer só no projeto, sem tocar na proposta (que já não existe) nem devolver imagens a `proposals/<id>/`. As imagens que a aplicação copiou para `images/` são do projeto e seguem a limpeza normal da sessão (`cleanUp`: o desfazer as tira do disco guardando o conteúdo na lixeira, o refazer as restaura), então o `mapping.json` nunca cita um arquivo que falta. A revisão (`review.removeProposal`) também tira do blob `mapping.reviewResume` a entrada do retomar e a da "vista" daquela proposta nesta cópia (sempre por `safeStorage`; uma proposta de mesmo id que chegue depois é Nova de verdade). Na interface, o menu ⋯ "Apagar proposta…" de `ProposalRow` só existe nas linhas fechadas e fica desabilitado com `store.locked`; `ProposalList` abre a confirmação (`Dialog` `alert`, com o título da proposta e o aviso de que não dá para desfazer), mantém o diálogo aberto até a ação terminar e passa o `returnFocus` que leva o foco à ação da linha que ocupou o lugar da apagada (ou da anterior; sem linhas, ao primeiro botão do estado vazio): um dono por fechamento.
  - **Revisão = projeto somente leitura** (decisão 1): `store.reviewing` (derivado de `setReviewing(id)`, que `review.open` chama, e `setReviewing(null)` em `close`) faz `apply` e gestos recusarem com `reviewing`; `canUndo`/`canRedo` e `undo`/`redo` só valem para entradas com `HistoryLink` da proposta aberta (`link.tag`; a aplicação das aceitas dela, e nunca a de outra proposta nem uma entrada sem vínculo, com recusa silenciosa), e `addImages`/`replaceImage` da sessão também recusam. **A revisão mostra só a Principal** (etapa #659, decisão 12): `review.open` chama `session.perspective.setLocked(true)`, que abre a Principal (com o aviso `review` se havia outra aberta; só a escolha em memória muda, a guardada no navegador fica) e trava o seletor (`open` devolve `false`); `close` destrava, e a perspectiva de antes não reabre sozinha. O resto do bloqueio é da interface (4.4), que desabilita o que seria recusado.
  - **Estado da revisão** (`store/review.ts`, `createReviewState(session)`, no contexto do editor como `review`): proposta aberta, alvo selecionado (`ReviewTarget`), visão Atual/Proposto, filtros, `undoable` (a última decisão, com o mapa anterior, para o "Desfazer" do lote), `seen` (as propostas já abertas nesta cópia) e `newConflicts`.
    - **Retomar e "vista", por cópia do projeto.** Um blob só no `localStorage` (`mapping.reviewResume`, validado com zod, sempre em try/catch via `safeStorage`), versionado: `{ v: 2, seen: string[], resume: Record<"copyId|proposalId", { selected, view, filters, knownConflicts } (`filters.onlyRevised` ausente num blob antigo vale desligado, sem mudar a versão do blob)> }`. A cópia é `ProjectStorage.copyId` (ver "Cópia do projeto", abaixo): a mesma proposta no zip importado, na pasta descompactada dele ou em duas pastas com o mesmo nome são revisões diferentes, com conflitos e posição diferentes. **`seen`** guarda as propostas já abertas (só ids, sem limite); **`resume`** guarda o ponto onde parou, as 12 mais recentes **por cópia** (as de outras cópias não são tocadas). Separados de propósito: evictar uma entrada do resume nunca devolve a proposta a "Nova". Versão desconhecida, texto corrompido ou o formato antigo (um `Record` plano) são descartados, não migrados. Sem `copyId` (só storages de leitura, que nunca chegam à sessão), o escopo é vazio e o Diagnóstico registra.
    - **Gravação e leitura.** Ao abrir, a cada seleção, filtro, visão ou navegação e ao fechar, `remember()` relê o blob e troca só a entrada desta proposta nesta cópia (outra aba não perde a dela), e junta ao `seen` em memória o que o blob tem (reatribuindo o signal só se entrou um id novo: `derived.rows` depende dele). O que outra aba marcou como vista entra nesta aba na próxima gravação ou abertura, não antes (limite aceito: não há observador do evento `storage`). Com o `localStorage` bloqueado, a gravação é engolida e o `seen` em memória vale dentro da sessão. Ao reabrir, `resumed: 'full'` volta ao último item, com os mesmos filtros e a mesma visão; sem entrada (`'none'`), cai na primeira mudança pendente e na visão Proposto. Um filtro de imagem ou camada que deixou de existir sai (a camada vale se existe no projeto atual **ou** na prévia, porque pode ter sido criada pela proposta).
    - **Conflitos novos.** Os conflitos nunca são guardados como tais: são recalculados contra o projeto atual (`changeStatus` do modelo). `newConflicts` é computado ao vivo: os conflitos atuais que não estavam em `knownConflicts` na abertura, então um conflito que surge durante a revisão (projeto recarregado por fora) aparece como "Conflito novo" na hora. Ao fechar passam a conhecidos os que a pessoa conhecia ou viu anunciados ao abrir ("N conflito(s) novo(s)") e os que ela decidiu; um conflito surgido durante a revisão e deixado sem decisão volta como novo na próxima abertura. Na primeira abertura numa cópia nada é novo (não há com o que comparar) e reabrir sem mudança nunca marca conflito novo (achado 11 da primeira rodada de testes). **Aplicar em curso** (devolução do portão da 8.2): entre o `store.apply` e a publicação do `proposal.json` com `applied`, o projeto já tem as aceitas e a proposta ainda não; `review.apply()` (o único chamador de `applyAccepted`, catraca em `tests/tooling/applyAcceptedCallers.test.ts`) segura a revisão com `derived.hold()` no clique e solta ao terminar, qualquer que seja o resultado. Nesse meio tempo `validation`, `conflictIds` e `situation` (e o que deriva deles: `invalid`, `canApply`, `newConflicts`, os selos do canvas) ficam com o retrato de antes, preso à proposta aberta (outra proposta aberta no meio tempo vê os valores ao vivo), e `canApply` é falso ("Aplicando as aceitas…"). Limite: o refazer de uma aplicação (Ctrl+Z e Ctrl+Shift+Z) ainda reavalia na janela do `link.redo`.
    - **"Nova", um contrato só.** `rows[].fresh` (aberta, sem decisão nem nota, não aberta nesta cópia) é a verdade: a barra de status conta as `fresh`, a janela Propostas põe o selo **Nova** e a ação principal em **toda** linha `fresh`, e `review.open` tira da fila o aviso `added` daquela proposta (`proposals.dismissNotice`), então o "Nova proposta · Revisar" do canto do canvas não volta depois de revisada. O X do aviso continua limpando a fila toda.
  - **Estado derivado** (`createReviewDerived` em `store/derived.ts`, `review.derived`): `rows` (a janela Propostas: andamento, conflitos, "nova", o que ficou para trás e quem substituiu), `tree`, `levels` (decisão de três estados com "parcial" e contagens por nível, `reviewKey`), `levelTypes` e `changeTypes` (selos; a regra do nível é `levelType`, do modelo), `situation`/`conflictIds` (conflito, valor atual e item trancado), `counts` (inclui "aceitas aguardando aplicação"), `revisedIds`/`revisionSummary`/`counts.revised` (a marca "Revisada": mudanças com marca e sem decisão, `visibleRevisedChanges`; o filtro `onlyRevised` e a linha "Revisada · N para conferir" de `rows[].revised` leem daí), `validation`/`invalid`/`canApply` (o conjunto aceito, `validateAccepted`), `preview` ("como ficaria", `previewProject`), `shownProject` (abaixo), `visibleIds` (filtros), `pendingIds`, `notes`, `supersession` (`leftBehind` e `compareProposals`), `fieldIndex` (as mudanças por entidade e campo, `fieldChangeIndex`: a criação ou remoção inteira e as alterações por campo de cada marcação, imagem, anotação e camada, as mudanças de anotação por marcação e as anotações que saem de cada marcação; memoizado pelas mudanças, então decidir não o refaz) e `fullPreview` (o "como ficaria" sem as decisões, para mostrar uma criação rejeitada; memoizado pelas mudanças, pelas aplicadas e pelo projeto, e lido só quando a interface pede). Em `rows`, `supersededBy` é a proposta que aponta `supersedes` para a linha, qualquer que seja o status dela: uma proposta **aplicada** é histórico e não muda de status ao ser substituída; a linha mostra "Aplicada · substituída por <título>" e **Abrir a nova** derivados da nova, sem gravar nada (só uma proposta aberta vira `superseded`). Memoizado pelo projeto (`store.committed`) e pela proposta: a árvore, os conflitos e os tipos dependem só das mudanças e do projeto, então decidir não os recalcula; a validação só roda com aceitas pendentes. Funções puras de apoio (tipo da mudança e do nível, filtros, pendências, navegação, status da linha da janela Propostas, lembrete ao sair) em `src/model/proposalView.ts`.
  - **O projeto à vista (`review.derived.shownProject`)**: o projeto que a tela descreve. É a base (fora da revisão e na visão **Atual**, o confirmado, `store.committed`; na visão **Proposto**, o "como ficaria", a prévia) passada por `perspectiveView` da perspectiva aberta (`projectInPerspective`, `store/perspectiveShown.ts`; `perspectiveView` é memoizado por projeto e por objeto de perspectiva, então pan e zoom não o recalculam; na Principal ou numa perspectiva que o projeto não tem é a própria base). A revisão trava a Principal, então com proposta aberta o recorte é a identidade. É a **única** fonte para tudo o que diz o que está na tela: a Árvore e a Lista, o estado vazio e os avisos do canvas, a trilha, a barra de status (seleção), o minimapa, os atalhos de seleção (Alt+↑/↓, Delete, Alt+L, Alt+N), a validação da seleção depois de uma recarga, "Comparar" e o estado derivado do editor (`createEditorDerived(store, ui, shown, …, perspective)`: camadas visíveis, indicadores, visibilidade, incompletas, Lista e Incompletas), criado depois da revisão em `EditorContext`. O canvas deriva `drawnProject` dele: fora da revisão, desenha `store.project` (com a prévia do gesto) recortado pela perspectiva aberta (a prévia de arrastar uma raiz muda `perspectives[].items`, por isso o recorte sai de `store.project` e não do confirmado); quando é a prévia da proposta, `proposedDisplay(shownProject, proposal)` só traduz o arquivo das imagens novas ou trocadas para `proposals/<id>/images/…`; o cursor e a área das imagens seguem o mesmo projeto. Numa importação nova, imagem, marcação e camada só existem na prévia, e tudo isso as mostra na visão Proposto. Quem ainda lê `store.committed`/`store.project` direto em `src/ui/**` e `src/app/**` está na allowlist de `tests/tooling/shownProjectReaders.test.ts`, cada um com o porquê (o nome do projeto na barra, os diálogos de edição, o outro lado e os fantasmas dos Detalhes na revisão, a imagem "antes" do Comparar, o diagnóstico; os Detalhes, dentro e fora da revisão, leem o projeto à vista); um leitor novo quebra o teste.
- **Conversas ancoradas** (formato em [`COMMENT-FORMAT.md`](COMMENT-FORMAT.md), etapa Comentários): quatro peças, todas fora do `mapping.json` (não entram no desfazer, não sobem o schema).
  - **Armazenamento** (`ProjectStorage.listThreads/readThread/writeThread/removeThread/statThread`): `comments/<id>.json` e `comments/resolved/<id>.json` na pasta (`statThread` só na pasta, como `statProposal`: o projeto local não é observado), no IndexedDB (mesmas chaves no store de arquivos; gravar ou apagar marca o projeto como "não exportado") e no zip (`ProjectFiles.threads`, opcional; entram só esses dois caminhos, com id válido, e o texto de cada arquivo volta idêntico, o de um inválido também). Todos recusam um id fora de `THREAD_ID_RE`. `listThreads(resolved)` lista só os nomes de uma pasta, que é o que a conferência de ~3 s precisa. `storage/loadThreads.ts` lê e valida (`parseThreadText`; o `id` do arquivo precisa ser o do nome): um arquivo inválido vira um problema listado à parte e vai ao Diagnóstico (`threads.invalid`), sem derrubar as outras.
  - **Sessão** (`store/threads.ts`, `session.threads`): a lista em memória (`list`, a mais nova primeiro; junta as duas cópias da mesma conversa com `mergeThreadCopies`), `problems` e `resolvedLoaded`. A **`revision`** tem a mesma conferência do `mapping.json` e da proposta: toda gravação relê as duas pastas e, se o texto difere do que a sessão leu ou gravou por último (o servidor MCP acrescentou uma mensagem, um editor mexeu), adota a versão do disco, **refaz a operação** (função pura de `model/threadOps.ts`) e grava com `revision + 1`; um arquivo que ficou ilegível nunca é sobrescrito. Resolver e reabrir **movem** o arquivo: grava no destino e só então apaga a origem, então uma gravação bem-sucedida não deixa duas cópias (se apagar a origem falhar, a leitura seguinte as junta). Tudo roda numa **fila única**. A conferência (`session.sync`, junto com a das propostas) varre **só `comments/`**, pelo carimbo, e lê apenas o arquivo que mudou; as resolvidas são lidas na abertura (`loadThreads`) e sob pedido (`threads.loadResolved()`), e `collect()` as lê antes de exportar.
  - **Ações** (`store/threadActions.ts`, `session.threadActions`): `open`, `post`, `resolve`, `reopen`, `remove` e `removeMany`. Todas recusam sem escrever com o projeto somente leitura (`read-only`), com a revisão de proposta aberta (`reviewing`) e sem identidade (`no-identity`). `kind` nunca vem do chamador: a app só monta autor `human`, com o nome e o e-mail da identidade (catraca em `tests/tooling/threadAuthors.test.ts`).
  - **Por dispositivo** (nunca no projeto): a **identidade** (`store/identity.ts`, chave `mapping.identity`, editada na seção **Identidade** das Configurações, `ui/IdentitySettings.tsx`; o e-mail passa por uma conferência `algo@algo`) e o **"lida"** (`store/threadReads.ts`, `mapping.threadReads`: um blob versionado e validado com o `lastReadAt` de cada conversa por cópia do projeto, `ProjectStorage.copyId`; texto corrompido ou versão desconhecida são descartados). Ambos passam por `safeStorage`: o `localStorage` bloqueado não quebra nada.
- **Copiar referência e recorte** (etapa 3a.2, só em projetos de pasta: `storage.folderName` é o `<projeto>` da referência): `app/itemClipboard.ts` monta a referência (`formatRef` + `shortCode` do modelo; a referência é só a URL, sem caminho legível, com o projeto codificado) e os dados do item (`model/clipboard.ts`: o item, as marcações descendentes e as anotações) e os grava com `utils/clipboard.ts` (`text/plain` e, onde o navegador suporta, o formato web `web application/x-mapping-item+json`, ignorado por outros programas; sem suporte, só o texto). O recorte (`storage/imageCrop.ts`) decodifica o arquivo original do projeto (não o bitmap de exibição), desenha o `rect` da marcação e reduz o lado maior a 2048 px; a promessa do blob vai direto ao `ClipboardItem` para a gravação começar dentro do gesto. **Ctrl/Cmd+C** (`copy-reference`) e **Ctrl+Alt+C** (`copy-crop`) só assumem a tecla quando há o que copiar: fora de campo de texto, sem texto selecionado na página e com uma marcação/imagem selecionada (ou o foco num cartão de anotação, `[data-annotation]`, ou da propriedade em foco (campo, par ou linha)); senão o copiar nativo continua. Menus: botões ao lado do ID em Detalhes e no cartão da anotação (`ui/CopyActions.tsx`), menu ⋯ da linha da Árvore (`ItemMenu`, `Popover` fixo) e menu de contexto do canvas (`ui/CanvasContextMenu.tsx`, aberto por `ui.canvasMenu`; o `PointerInput` o abre só com o botão direito do mouse; o `contextmenu` de um toque demorado numa tela de toque não o abre). O aviso curto ("Referência copiada") é `ui.toast` (`showToast`).
- **Bitmaps** (`displayImages.ts`): as imagens exibidas são carregadas sob demanda; `retain(paths)` solta os bitmaps que o projeto não usa mais. Um arquivo que volta pelo desfazer é recarregado. **O mapa nunca contém um bitmap fechado**: `retain`, `invalidate` e `dispose` tiram o caminho do mapa na hora e só chamam `close()` no quadro seguinte (`requestAnimationFrame`), porque o canvas pode ter um desenho pendente do quadro em que o bitmap ainda estava no nó do Konva, e desenhar um `ImageBitmap` fechado lança `InvalidStateError: drawImage … detached` (achado 10 da primeira rodada). O renderizador das imagens (`canvas/renderers/images.ts`) também nunca põe num nó um bitmap fechado (largura e altura zero): fica o espaço reservado.
- **Erros**: `reportError(contexto, erro)` registra no console e guarda os últimos 20; a janela "Diagnóstico" (inferior) os lista em tabela, com "Copiar" e "Limpar"; o ponto de alerta da faixa usa o "visto até" de `store/diagnostics.ts`.

## Sessão e gravação

A sessão (`src/store/session.ts`) é o **único** código que lê e grava o `mapping.json` de um projeto aberto (regra ESLint `sessionStorageSyntaxRules` em `eslint.config.js`; as exceções são `storage/loadProject.ts`, que abre e recarrega, e, no controller, a criação do projeto em pasta; as conferências de existência usam `hasMappingFile` de `storage/folder.ts`, sem `loadMapping`). O que **não** é do `mapping.json` também passa por ela: as perspectivas "Só eu" vão ao IndexedDB por `localSync` (abaixo).

### `AutoSaver` (`src/storage/autosave.ts`)

| Estado        | Significado                                                                                                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`      | `saved`, `saving` ou `error`: o que a barra de status mostra. `saving` cobre o debounce (250 ms), a espera na fila e a gravação em andamento.                                                       |
| `dirty`       | Houve alteração desde a última gravação bem-sucedida.                                                                                                                                               |
| fila (`tail`) | **Uma fila só**: a gravação (`flush`) e os trabalhos de `enqueue(job)` (conferência, recarga, decisão do conflito) rodam um de cada vez, na ordem; nenhum deles chama `flush`/`enqueue` por dentro. |
| `generation`  | Sobe em `reset()`: a gravação em curso naquele momento termina sem mexer no estado (o pendente foi descartado pela recarga).                                                                        |

Transições: `schedule()` → `dirty`, `saving`, reinicia o timer → `flush()`; `flush()` → enfileira a gravação; a gravação começa marcando **`saving`** (também quando a anterior falhou), zera `dirty`, chama `save()`; sucesso → `saved` se nada novo entrou; falha → `dirty`, `error`, `reportError('save')`; `reset()` → cancela o timer e a gravação enfileirada ainda não iniciada, `saved` (ou assim que a em curso terminar). **Invariantes**, com teste de passeio aleatório em `tests/storage/autosave.test.ts`: `saved` ⇒ nada em curso, nada pendente, nenhum timer; gravação em curso ⇒ `saving`; `error` ⇒ nada em curso.

### A sessão

| Estado         | Significado                                                                                                                                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `saveStatus`   | O `status` do saver.                                                                                                                                                                                                                                                                                                                 |
| `conflict`     | `null`, `{ reloadFailed: false }` (decisão pendente: diálogo "Projeto alterado fora da app") ou `{ reloadFailed: true }` (Recarregar falhou: arquivo sumiu ou ilegível; a decisão continua).                                                                                                                                         |
| `disk`         | O `mapping.json` como a sessão o leu ou gravou por último: `revision` (mora aqui, não no store: gravar não cria desfazer nem renderiza), `text` e `lastModified`. A data nasce de um `stat` na abertura, que só vale se o arquivo ainda é o conhecido.                                                                               |
| `written`      | O snapshot confirmado que o disco tem. Nasce igual ao projeto aberto só quando o arquivo é exatamente a serialização dele (projeto migrado, reparado ao abrir ou gravado em formato não canônico nasce `null`, e a primeira edição grava); vira `p` a cada gravação e o projeto adotado ao recarregar; `null` em "Manter as minhas". |
| `exported`     | O snapshot do último zip que saiu (`noteExported`, chamado pelo `markExported` do controller no download ou compartilhamento): gravá-lo depois não é mudança nova para o indicador "não exportadas". Gerar o zip (`collectFiles`) sem baixar não registra nada (8.7).                                                                |
| `pendingFiles` | Imagens que a sessão gravou e nenhum `mapping.json` gravado cita ainda; a gravação tira só as que ela cita; ao recarregar, as não citadas pelo projeto adotado são apagadas (órfãs).                                                                                                                                                 |
| `pendingSync`  | A conferência enfileirada e ainda não iniciada: chamadas concorrentes de `sync` acumulam `images` nela e recebem a mesma promessa (uma em curso e no máximo uma esperando).                                                                                                                                                          |

**Os quatro trabalhos da fila:**

- **Gravação** (`persist`): nada a fazer se o disco já tem o confirmado (`onDisk`: a identidade com `written`, ou o mesmo conteúdo, sem as "Só eu", a menos do `updatedAt` que o desfazer renova). Senão lê o arquivo (`readMapping`, o único ponto de leitura): sem arquivo (apagado por fora) ou igual ao conhecido → grava; **vazio e diferente** → alguém está escrevendo: espera `EMPTY_RETRY_DELAY_MS` e relê, até `EMPTY_RETRY_ATTEMPTS` vezes, e então desiste com `EmptyMappingError` (`session.emptyMapping` no Diagnóstico, `status = 'error'`); **diferente** → `conflict`, `ExternalChangeError`. Depois grava o backup pré-migração, as imagens que voltaram pelo desfazer, as pastas de pacote `specs/<id>/` (o conteúdo fica num cache em memória da sessão, por `id@versão`, para o desfazer regravar o que o `cleanUp` apagou; quando a versão muda, a pasta é regravada **por cima**, sem apagar nada antes: a versão antiga fica só em memória) e as cópias de `specs/`, relê com a mesma regra se gravou algo, grava `revision + 1` (o texto é `serialize(fileProject(p, localIds))`: nunca leva as perspectivas "Só eu"), atualiza `disk` e `written`, chama `onChanged` (se o gravado não é o exportado) e só então apaga o que deixou de ser usado (`cleanUp`, que também remove das pastas de pacote regravadas os arquivos que só a versão antiga tinha, `removeSpecFile`, recalculados pela listagem da pasta e repetidos na gravação seguinte se falharem; falha vai para o Diagnóstico). O `mapping.json` em disco nunca aponta para um arquivo já apagado (durante a regravação de um pacote a pasta pode ter arquivos da versão nova enquanto o `mapping.json` ainda cita a antiga, mas nada some); arquivos removidos vão para uma `trash` em memória (numa pasta, o `File` lido deixa de ser legível quando o arquivo é apagado) até nenhum snapshot do histórico os referenciar.
- **Conferência** (`syncProject`, por `sync`): conflito aberto → `unchanged`; gesto → `busy`; `saving` (gravação agendada ou enfileirada e ainda não iniciada: ela mesma confere antes de gravar) → `busy`. Uma `sync()` pedida durante uma gravação em curso é um trabalho atrás dela: roda depois e responde pelo que encontra (em geral `unchanged`, o arquivo é o que a sessão acabou de gravar). Se a data mudou, lê: igual → só atualiza a data; vazio sem pendência → `unchanged` (editor escrevendo); diferente com a **gravação em erro** (a pendência não chega ao disco sozinha; um arquivo vazio de vez também cai aqui) → abre o `conflict` e devolve `conflict`; diferente sem pendência → `loadProject` e, se ainda `idle()` (edições são síncronas e podem entrar entre os `await`; a guarda é relida antes de trocar o projeto), `adopt` → `reloaded`. Depois do trabalho, fora da fila, `proposals.scan()` (a fila das propostas pode esperar pela da sessão, no `flush` de aplicar aceitas; nunca o contrário).
- **Recarregar** (`resolveConflict('reload')`): `loadProject` em `try/catch`; falha → `reloadFailed`; senão `adopt` (troca o projeto do store, zera o histórico, `saver.reset()`, apaga os órfãos de `pendingFiles`) e confere as imagens. Nunca rejeita. A recarga externa (a Conferência também chama `adopt`) leva as "Só eu" da memória para o projeto do disco (`carryLocalPerspectives`), reconciliadas por `reconcilePerspective` do projeto de antes ao novo; um arquivo com outro `project.id` não leva nenhuma, e as chegadas (`arrivals`) do estado da UI são zeradas.
- **Manter as minhas** (`resolveConflict('keep')`): adota a revisão do disco (uma leitura que lança segue como arquivo sumido), `written = null`, fecha o conflito e grava por cima; se o disco está travado, o resultado é `status = 'error'`, não uma rejeição.

**Arquivo vazio para sempre** (um editor que morreu depois de truncar): "Erro ao salvar"; "Tentar de novo" repete as tentativas e falha de novo; três saídas: Exportar (leva o confirmado), apagar o arquivo por fora (a próxima tentativa grava) e o diálogo de conflito, que a conferência abre com a gravação em erro ("Manter as minhas" grava por cima; Recarregar dá `reloadFailed`).

**Contratos.** `flush(): Promise<FlushResult>` nunca rejeita e entra na fila; `ok: true` ⇔ o projeto confirmado do instante da chamada está no disco; `ok: false` ⇔ a pendência continua (`saveStatus === 'error'`), com a causa em `error` (`ExternalChangeError` ⇔ conflito aberto). Uma edição durante a conferência (`store.apply`) agenda a gravação de forma síncrona (`saving`), então a conferência em curso devolve `busy` e nunca adota o arquivo de fora entre a edição e o `flush`. `onChanged` (`SessionOptions`) é chamado pela gravação do `mapping.json` com conteúdo ainda não exportado e por cada gravação de `proposal.json` (`createProposalStore({ onChanged })`); o controller o usa para o indicador "Alterações não exportadas" (o IndexedDB guarda o mesmo flag em `saveMapping`/`writeProposal`). `collectFiles()` devolve `saved: false` quando o zip leva um confirmado que o disco ainda não tem. `close()` espera a fila (uma conferência ou recarga em curso) antes de gravar o pendente e fechar.

**Perspectivas na sessão** (etapa #659; modelo em `src/model/perspective*.ts`, formato em [`FORMAT.md`](FORMAT.md), "Campos da v16"). Cada perspectiva é "Para todos" ou "Só eu", e o **Quem vê** só decide onde ela mora:

- **Para todos** vai no `mapping.json` (`perspectives[]`, mais `arrivals[]` e `project.id`, v16). **Só eu** fica no IndexedDB deste navegador, em banco próprio (`mapping-perspectivas`, `storage/localPerspectives.ts`: um store `perspectives`, `project.id` → lista, no mesmo formato de um item de `perspectives`, validada com zod por entrada), para não pedir uma versão nova do banco dos projetos locais (o motivo dos recentes de pasta). Sem IndexedDB (`openLocalPerspectives` devolve `null`) a opção fica indisponível: `createPerspective` com `local` e `setPerspectiveLocal(id, true)` falham com `local-unavailable`.
- **Na memória as duas moram juntas** em `project.perspectives`, para o desfazer, os gestos e a reconciliação valerem para ambas; o que as distingue é `session.perspective.localIds`. A sessão abre juntando as "Só eu" que o controller leu do IndexedDB (`mergeLocalPerspectives`, `store/localPerspectiveSync.ts`: cada uma passa por `reconcilePerspective` do projeto a ele mesmo, só para limpar; um id que o arquivo já tem vale o do arquivo). Tudo o que grava ou exporta usa `fileProject(p, localIds)` (`store/perspectives.ts`): `persist`, `onDisk` e `collectFiles` (o zip) nunca levam uma "Só eu", e é a sessão, como sempre, a única que grava o `mapping.json` (`revision + 1`). `attachLocalSync` observa o projeto confirmado e, quando a lista das "Só eu" muda (por identidade dos objetos), enfileira `save(project.id, lista)` no IndexedDB, sem bloquear; a falha vai para o Diagnóstico e a próxima mudança tenta de novo.
- **Trocar o Quem vê** (`perspectiveActions.setPerspectiveLocal`, fora do desfazer; recusa com `read-only`, `reviewing` e `gesture-active`) segue uma ordem que nunca perde dado. _Para todos → Só eu_ (`makeLocal`): grava no IndexedDB primeiro (`persistIncluding`; se falha, `local-unavailable` e nada muda), só então entra em `localIds` e o arquivo é regravado sem ela. _Só eu → Para todos_ (`makeShared`): `hold` mantém o id no IndexedDB, sai de `localIds`, o arquivo é regravado **com** ela e o `flush` espera o `mapping.json`; se falha, volta a "Só eu" (`save-failed`), e só com o arquivo gravado o `release` deixa o IndexedDB esquecê-la. Como o projeto não muda, `rewriteFile` zera `written` e agenda a gravação. Criar com `local` põe o id em `localIds` no mesmo lote do `apply`, então o `mapping.json` nunca chega a citar uma "Só eu"; duplicar herda o Quem vê da original.
- **A perspectiva aberta** é estado da UI (`session.perspective.id`; `null` é a Principal), fora do desfazer, guardada no `localStorage` por `project.id` (`mapping.openPerspective`, blob versionado e validado com zod, as 20 mais recentes, por `safeStorage`). Abrir um projeto retoma a guardada. Se a perspectiva aberta deixa de existir no confirmado (apagada aqui, desfeita, apagada noutro navegador ou por uma recarga externa), um `effect` volta à Principal e mostra o aviso `removed` com o nome; o mesmo aviso sai ao abrir se a guardada já não existe. Trocar de perspectiva não entra no desfazer nem grava nada.

**Interface.** `useExternalChanges` (montado em `Editor.tsx`) chama `session.sync()` a cada ~3 s com a janela visível e, ao voltar o foco, `sync({ images: true })`; `reloaded` mostra "Projeto atualizado por fora". O diálogo de conflito (`EditorDialogs`) usa `Dialog` com `closable={false}`: sem o X, e Esc e o clique no fundo não fazem nada. Seleção, camadas visíveis e viewport são estado da UI e ficam como estão (a seleção só é limpa se o item sumiu: `session.reloads`). Só a **pasta** implementa `statMapping`/`statImage` (`session.watchable`); o projeto local não é observado. As imagens trocadas por fora são achadas pelo carimbo (`tamanho:lastModified`) de cada arquivo, conferido ao voltar o foco e depois de recarregar, e `onImagesChanged` faz o controller chamar `display.invalidate(path)`.

**Nomes internos antigos.** O produto se chama "Mapping", mas dois nomes invisíveis ao usuário mantêm o antigo `mapeador`, para não exigir migração dos dados já guardados nos navegadores: o banco IndexedDB dos projetos locais (`mapeador-imagens`, em `storage/local.ts`; o dos recentes de pasta, criado depois, já é `mapping-folders`) e os caches do service worker (`mapeador-…`, em `pwa/sw.js`). As chaves do `localStorage` já usam o prefixo `mapping.`. Nos arquivos, `app: "mapeador-imagens"` e `format: "mapeador-spec"` ainda são lidos; o `app` é normalizado para `"mapping"` ao ler, então a próxima gravação já usa o valor novo.

## Espaços, pertencimento e gestos

**Dois espaços de coordenadas.** Uma marcação vive no espaço do **container** (`containerId` preenchido; `rect` em pixels
da imagem original, dentro dela) ou no do **canvas** (`containerId: null`, a marcação do canvas; `rect` em unidades do
canvas, inteiras, até negativas). `spaceOf(p, marking)` (`src/model/hierarchySettle.ts`) devolve o espaço (`placement` e
limites); `toCanvasRect`/`fromCanvasRect` (`geometry.ts`) convertem de um para o outro. As conversões de tela ficam em
`src/canvas/`, como sempre; as de espaço, que mudam o dado gravado, ficam no modelo.

**O pertencimento é derivado e gravado.** `parentId` da marcação e do container nunca é escolhido: `settleHierarchy(p)` (puro,
idempotente, devolve o mesmo objeto se nada muda) o recalcula pela geometria e, antes, decide o espaço de cada marcação
não flutuante (o container que a contém inteira, senão o canvas; se mudou, converte o `rect` e as descendentes vão junto).
As regras estão em [`FORMAT.md`](FORMAT.md), "Campos da v13 (pertencimento)": dentro é totalmente contido, o pai é a menor do
mesmo espaço, o pai do container é a menor marcação do canvas que o contém, e as flutuantes ficam fora da árvore. Nos empates
(retângulos iguais; candidatas de mesma área a pai, também para o container) **a relação atual vale** e a ordem do array só
decide o empate novo: dentro de um grupo de retângulos iguais a ordem de fora para dentro é a ordenação topológica dos
`parentId` atuais (o pai antes do filho; entre as livres, a que vem antes no array; quem não tem pai no grupo entra pelo array;
ciclo é quebrado pela que vem antes), e entre candidatas de mesma área o `parentId` atual fica se for uma delas (de cada grupo
conta só a de dentro), senão ganha a que vem por último. Reordenar irmãs nunca muda pais, nem no assentar seguinte; o assentar
continua determinístico, idempotente e sem mudar a ordem dos arrays, mas o resultado depende do `parentId` atual nos empates. Os membros (`membersOf`, `projectIndex.members`/`canvasRoots`) saem do `parentId` e nunca são gravados. **O pertencimento é só da Principal**: uma perspectiva (v16) não decide quem contém quem, só quais raízes aparecem e onde (ver "Perspectivas", abaixo).

**Quando assenta.** No fim de **toda** operação do modelo que mexe na geometria (desenhar, mover, redimensionar marcação,
mover/redimensionar/trocar/excluir container, aplicar proposta: `applyAccepted` assenta depois do patch). **Não** assenta na
leitura, na migração nem na abertura (ler nunca grava e nunca muda dado), e a operação aceita `settle: false`, usado **só**
nas prévias de gesto. Sem a tolerância: o modelo só conhece "totalmente contido"; a ferramenta (a interação) é que ajuda a pessoa
a chegar lá.

**Reconciliação das perspectivas.** No fim do assentar (`settleHierarchy`, salvo `settle: false`), `reconcilePerspectives(before, after)`
(`src/model/perspectiveReconcile.ts`) mantém `perspectives[].items` e `arrivals[]` coerentes com a geometria nova, sem mover nada na
tela: a raiz apagada sai; a que deixou de ser raiz (entrou noutra marcação) dá lugar à raiz nova, posta de modo que o item continue
onde estava; o item que virou raiz entra onde estava, pela posição de `before`; sem raiz repetida (vale a primeira); `hiddenLayers` só
com camadas que existem; posição de marcação inteira. A marca "Veio de…" sai quando a raiz some, deixa de ser raiz ou muda de lugar na
Principal. Sem nada a mudar devolve o mesmo objeto. O `before` vem de `SettleOptions.before` (`src/model/hierarchySettle.ts`): as
actions o preenchem com `settleOptions(base)` (`src/store/project.ts`), o projeto do **início da operação**; no fim de um gesto, o
projeto do **início do gesto** (a prévia já mexeu em `items`, e comparar com ela perderia a mudança de raiz). Um `before` explícito vale
mais que o do assentar, que sem ele usa o projeto que entra (uma operação do modelo chamada por outra, ou a "Só eu" reconciliada ao
abrir, onde antes e depois são o mesmo e só limpa). `pruneHiddenLayers` tira das perspectivas as camadas que o projeto perdeu.

**O gesto.** Ao arrastar ou redimensionar, o canvas chama `beginGesture`, e cada movimento do ponteiro vira uma prévia com
`settle: false`: o pertencimento fica **congelado** enquanto o ponteiro se move e o canvas desenha o resultado sem recalcular a
árvore. Ao soltar, o canvas calcula o **encaixe** e a **absorção** e chama a ação `finish…` da mesma operação (`finishMarkingMove`,
`finishMarkingRect`, `finishImagePlacement`), que repete a operação com os valores finais e `settle: true` (e `before` = o projeto do início do gesto, para reconciliar as perspectivas) sobre o projeto do início
do gesto; só então `commitGesture`: **uma** entrada de desfazer com geometria, espaço e pertencimento juntos. A operação final
nunca falha (se falhar, assenta a última prévia válida).

- **Encaixe:** ao mover, o container de destino acende e a marcação solta quase toda dentro dele é puxada para dentro, para a
  pessoa não ter de acertar o pixel.
- **Absorção:** ao redimensionar uma marcação, o que ficou **quase** inteiro dentro dela acende e, ao soltar, a
  marcação cresce até cobri-lo; o item passa a ser membro. A tolerância é `ABSORB_TOLERANCE` (em pixels de tela, em `src/canvas/`):
  é regra de **interação**, nunca do modelo, e por isso nunca é gravada nem aplicada por uma proposta ou pelo MCP.
- Mover uma marcação **dentro de um container** leva as descendentes; no **canvas** mexe só nela (os membros ficam onde estão e o
  pertencimento é refeito). Nada prende a marcação ao container: ela pode sair dele e virar marcação do canvas, ou entrar em
  outro container com o `rect` convertido.

**Seleção múltipla e arrasto conjunto.** `ui.selection` continua sendo o item **principal** (alças, Detalhes); `ui.selectionGroup`
guarda os **outros** itens presos ao objeto do principal, então qualquer escrita direta em `ui.selection` desfaz o grupo sem
código extra; `selectedItems(ui)` junta os dois. Shift+clique (e Ctrl+clique ou Cmd+clique, que valem o mesmo no canvas, inclusive
sobre alça, e na Árvore; no macOS o Ctrl+clique é o clique direito e não junta; na revisão de propostas nenhum dos três vale), o duplo
clique e "Selecionar com o conteúdo" (`selectionWithContents`, `src/model/multiSelection.ts`) montam o grupo. O arrasto conjunto é a operação pura `moveItems`: tudo ou
nada (trava ou sobreposição com container que não se move falham), com o deslocamento em unidades do canvas; a marcação de
container o recebe dividido pela escala e preso ao container, e o item levado por outro (marcação dentro de container movido,
descendente) não recebe deslocamento à parte. As prévias usam `settle: false`; ao soltar, a ação final repete a operação com o
assentar e há **uma** entrada de desfazer. O arrastar da Paleta usa `componentDropTarget` (`src/ui/componentTarget.ts`, puro: slot,
container ou canvas, e o que acender) e o hook `useComponentDrop`, com o MIME `application/x-mapping-component`; o botão
**Adicionar** usa o mesmo alvo pela seleção.

As setas do teclado movem a seleção pela operação pura `nudgeItems` (`src/model/multiSelection.ts`): 1 px, ou 10 px com Shift, no
espaço próprio de cada item (marcação de container em pixels da imagem, em qualquer escala; marcação do canvas, flutuante e container
em unidades do canvas). Container leva as marcações, marcação de container leva as descendentes e a seta (traço) não anda. É tudo ou
nada, como em `moveItems` (trancado, sair do container ou container sobrepondo outro: nada se move, sem aviso). O movimento é um
gesto do store: a primeira seta chama `beginGesture`, cada repetição `updateGesture` (prévia com `settle: false`) e `commitGesture`
fecha com o assentar numa só entrada de desfazer. Apertar e soltar é um gesto de um passo; segurar a tecla (repetição) é um gesto
só, fechado no keyup, na perda de foco da janela ou ao apertar outra tecla. A tecla só vale com o foco no canvas ou em nenhum controle
(`body`); não vale em campo de texto, Árvore, menu, abas etc., com `defaultPrevented`, em somente leitura, na revisão de propostas nem
com um gesto de ponteiro em andamento, e vale em Navegar e Desenhar. Alt+↑/↓, Alt+Shift+↑/↓ e Ctrl+Shift+setas seguem com os usos
que já tinham.

O **retângulo de seleção** (SM2) é o Shift+arrasto em qualquer modo (Navegar e Desenhar): o gesto em `src/canvas/input/pointer.ts`
vira a intenção `select-rect` e desenha o retângulo (borda tracejada `cv-select`, preenchimento `cv-select-fill`) em `state.marquee`,
pela camada de sobreposição, sem prévia ao vivo nem rolagem automática. Sobre item selecionado ou alça no Navegar o Shift+arrasto
continua movendo ou redimensionando, e o que não passa do limiar de arrasto segue sendo o Shift+clique. Ao soltar, a função pura
`marqueeItems` (`src/canvas/input/marquee.ts`) escolhe os itens **inteiramente** dentro do retângulo e eles são **somados** à
seleção (nunca tira item; mantém o principal, ou, sem seleção antes, o primeiro dos novos na ordem da Árvore). Vale a regra "só os de
fora": reaproveita `movingItems`, então marcação de um container que entrou, ou descendente dela, não entra (já vai com o container),
e container dentro de uma marcação do canvas que entrou entra. Itens invisíveis (camada escondida, visibilidade, modo visualização) não
entram, setas só com "Mostrar setas" ligado, e os trancados entram. Esc ou ponteiro cancelado apaga o retângulo sem mudar a seleção.
O gesto não altera o projeto e não gera entrada de desfazer.

**Marcação pai (Envolver).** `wrapItems` (`src/model/multiSelection.ts`) cria uma marcação que envolve a seleção, com uma ou mais
itens (uma marcação não flutuante ou um container sozinhos também: a nova fica em volta dele com a margem de 8 px, limitada ao
container e ao pai atual). Entram marcações não flutuantes e containers (setas e notas ficam fora do pertencimento). O modelo não
escolhe pai: cria a nova com o **pai atual** do conjunto no `parentId` (a relação que o desempate estável mantém) e assenta, e o
assentar confere o resto. Onde aparece: o botão **Envolver** do resumo da seleção múltipla, o atalho **Ctrl/Cmd+G**
(`useEditorShortcuts`) e a entrada **Envolver** do menu de contexto do canvas e do ⋯ da linha da Árvore (`WrapMenuItem` em
`src/ui/CopyActions.tsx`). Os quatro passam por `src/app/wrapSelection.ts`: `currentWrapItems` diz o que envolver agora (a
seleção atual; ou, num menu, só o item da linha quando ele está fora da seleção), `canWrapNow` confere (fora do somente leitura
e da revisão, e se algum item entra) e `wrapItemsNow` chama a action `wrapItems`, seleciona a marcação nova e avisa
`multi.wrapFailed` se o modelo recusar. O atalho só assume a tecla quando `canWrapNow` vale e nunca com o foco num campo de
texto; senão o evento segue para o navegador.

- **Espaço:** se tudo o que entra são marcações do mesmo container, a nova é desse container; senão é do canvas, com o
  retângulo em unidades do canvas arredondado para fora, e a marcação de um container conta pelo **container inteiro** (só o
  container pode ser filho de uma marcação do canvas).
- **Pai atual:** entre as marcações do mesmo espaço que contêm o conjunto (fora da seleção e dos descendentes dela), a que o
  assentar escolheria (`enclosingAmong` em `src/model/hierarchySettle.ts`): o pai comum das selecionadas de topo, se é uma das de
  menor área; senão, a de dentro da cadeia de retângulos iguais. Nunca o último do array, que depois de reordenar marcações de
  mesmo retângulo pode ser o de fora (#549).
- **Retângulo:** o que envolve tudo, com margem de `MIN_MARKING_SIZE` (8 px) de cada lado, limitado ao container e ao **pai atual**
  do conjunto, para a nova nunca tirar o conjunto de dentro do pai que ele já tinha.
- **Posição no array:** antes da primeira marcação selecionada. A nova não tem relação com as selecionadas, então o empate de
  retângulo igual com elas é novo e o array decide: a de antes é a de fora. A nova nasce com o **pai atual** de `parentId`: ela
  cabe nele e nenhuma menor a contém, e mesmo com o retângulo igual ao dele a relação atual o mantém de fora, venha ele antes ou
  depois no array. Assim a nova fica filha do pai que as selecionadas tinham e mãe direta delas. Marcações não
  selecionadas que caem dentro do retângulo também passam a ser filhas: é a geometria.
- **Depois:** uma entrada de desfazer; a nova fica selecionada sozinha, sem nome e sem anotações. A trava não impede, porque
  nenhuma geometria existente muda, só o `parentId`.

**Perspectivas: gestos e restrições** (etapa #659, decisões 5 e 8; `src/store/perspectiveGestures.ts`). Com uma perspectiva aberta o
canvas desenha `perspectiveView(project, perspectiva)` e chama as **mesmas** actions de `project.ts` com coordenadas **da vista**; é a
action que as traduz, e o canvas não sabe de perspectiva além de não começar o que é só da Principal (`IntentContext.perspectiveOpen`).
As funções `…InView` devolvem `null` na Principal ou quando vale a regra de sempre, e a action cai na operação do modelo.

- **Arrastar muda a posição, não o dado.** Mover uma raiz (container ou marcação do canvas, flutuante inclusive) muda só o item dela em
  `perspectives[].items` (`moveRootsInPerspective`): o `placement`/`rect` do projeto fica, e o gesto é **uma** entrada de desfazer como
  sempre. Marcação do canvas filha de outra, ou container dentro de uma marcação do canvas, arrasta a **raiz inteira**. Dentro de um
  container (marcação de container, arrastar, redimensionar) vale a regra da Principal. Mudar a escala de um container raiz grava só a
  escala no projeto; a flutuante redimensionada grava o tamanho no projeto e a posição no item. A trava e a sobreposição na vista
  (`image-overlap`) valem como na Principal, e o encaixe em container ao soltar é da Principal. O arrasto conjunto e as setas do teclado
  (`itemsMoveInView`) andam as raízes na perspectiva e, na mesma operação, o resto como de sempre.
- **"Só na Principal"** (`principal-only`, código de `StoreErrorCode`; `principalOnly` diz à interface quando desabilitar o comando com a dica):
  desenhar marcação do canvas que não é flutuante (a operação criadora inteira é recusada), a rota de seta (`setArrowRoute`,
  `previewArrowRoute`: as pontas da seta continuam), **Arrumar**, **Excluir** uma raiz e redimensionar marcação do canvas que não é
  flutuante (mover continua). O ponteiro já não começa o gesto: sem container sob o ponto o modo Desenhar vira pan, e só as pontas da seta
  têm alça. Desenhar dentro de um container funciona.
- **Criar raiz fora da Principal.** A raiz nova (container ou flutuante) entra na perspectiva onde foi criada, na posição que tem no
  projeto, e **chega à Principal** (`creationInPerspective` → `arriveInPrincipal`, `src/model/perspectivePlace.ts`): o lugar na Principal é
  calculado na vista da perspectiva (perto da raiz de referência, a outra ponta de uma seta que a liga; o livre mais próximo se
  ocupado; senão a área de chegada), a raiz é movida, o projeto assenta, e só então entra a marca `Veio de…` em `arrivals` (o assentar
  tiraria a marca de quem mudou de lugar). `kind` e `referenceId` não são gravados: vão em `session.perspective.arrivals` (`onArrival`),
  para o aviso dos Detalhes, e `dismissArrival` tira a marca.
- **Setas entre raízes diferentes** não levam os pontos de passagem para a vista (a vista usa a rota automática, `points: []`); entre
  as de uma mesma raiz os pontos andam com ela.
- **Conversas:** o ponto do canvas (fora de container) só tem pino na Principal (`pinPlaces(…, principal)`); o ponto de container segue o
  container, que a vista já traz ou não.

**Trava.** Trancar uma marcação do canvas trava o `placement` dos containers dentro dela (`canEditImagePlacement`); a
herança continua em `markingLockStates`, que o cadeado da Árvore e do canvas leem.

## Especializações no projeto e anotações tipadas

O formato do arquivo está em [`SPEC-FORMAT.md`](SPEC-FORMAT.md) e o do projeto (ids estáveis, referências `ref`, pendências) em
[`FORMAT.md`](FORMAT.md). Aqui ficam as regras de comportamento que o código aplica.

**Ciclo de vida** (`model/specializations.ts`; cada operação é uma entrada de desfazer):

- **Aplicar:** valida o arquivo, copia para `specs/` e cria as camadas da especialização no fim da lista. Com o mesmo `id` já no
  projeto: `version` maior oferece **Atualizar**; igual ou menor avisa e não faz nada.
- **Atualizar versão:** substitui a cópia em `specs/`; camadas novas são criadas, as existentes mantêm cor e anotações e o nome
  segue o da nova versão; as que sumiram viram **camadas livres**. Anotação que ficou inválida (campo obrigatório novo, opção ou
  tipo removido, relação não permitida, etiqueta removida de um alvo) **não é alterada**: aparece como incompleta, com o motivo.
  Tipo removido deixa a anotação somente leitura, com a ação "Converter em anotação livre".
- **Remover:** ou **apaga os dados** (as camadas, as anotações delas **e as vinculadas a elas em outras camadas**, com
  confirmação por contagem), ou **converte em camadas livres**: as anotações tipadas viram livres (`type` e `values` nulos) com os
  valores em texto em `entries` (na ordem dos campos, campos vazios omitidos, `table` achatada como `parametros[1].nome: origem`,
  `ref` como o rótulo do alvo), o nome do tipo vira o `name` quando este está vazio, e vínculos e `inherit` são mantidos. Nos
  dois casos a cópia em `specs/` sai. As referências de outras especializações que apontavam para dados removidos ou
  convertidos ficam quebradas (pendências), e a confirmação diz quantas.
- **Camadas da especialização** não podem ser excluídas nem renomeadas (só removendo a especialização); a cor pode ser trocada;
  mostram o selo da especialização e podem ser reordenadas, ocultadas (qualquer camada pode ser escondida, até todas; não há camada ativa).

**Anotações tipadas na interface:**

- **Criar:** em camada de especialização, "+ Anotação" lista os tipos daquela camada. Tipo com `requiresOwner` pede o **dono**
  primeiro (anotação da mesma marcação cujo tipo aceita este filho); sem dono possível, a mensagem diz o que criar antes. A partir
  do dono, o editor oferece um botão por tipo de `allowedChildren`, que cria a filha já vinculada na camada do tipo filho (se a
  camada estiver oculta, cria e oferece torná-la visível). Campos com `default` vêm preenchidos.
- **Editores por tipo de campo:** `string` e `number` em campo de texto, `date` no seletor nativo, `enum` em botões segmentados
  (até 3 opções) ou lista, `table` em linhas que se adicionam, removem e reordenam, `ref` com o alvo atual e as ações Escolher,
  Limpar e Ir para o alvo (o seletor lista **só os alvos aceitos**, agrupados por anotação, com a busca; sem alvo, a mensagem
  explica o que falta). Não há campo para chaves extras.
- **Referências recebidas:** a anotação que é alvo mostra quem aponta para cada tupla ou linha (`name ← Input input_nome (Nome)`),
  e excluir um alvo avisa quantas referências vão quebrar.
- **Pendências** (`model/issues.ts`, calculadas, nunca gravadas; salvar incompleta é sempre permitido): obrigatório vazio
  (inclusive coluna de tabela), valor incompatível, opção ou tipo inexistente, dono ausente ou de tipo não permitido, referência
  quebrada e alvo não aceito (perdeu a etiqueta ou deixou de ser livre). Aparecem como alerta na anotação, junto aos indicadores da
  marcação no canvas e no filtro **Incompletas** da Lista.
- **Exibição** (`model/typedDisplay.ts`, funções puras; a interface passa os textos traduzidos): título "nome do tipo · rótulo da
  instância" (rótulo: `name`, senão o `labelField`; sem rótulo, só o tipo); valores na ordem dos campos com o `label`, opcionais
  vazios omitidos e obrigatórios vazios como `id: —` na cor de alerta; `table` em resumo no zoom semântico (`atributos: 3 linhas`)
  e completa no painel e na lista; `ref` como `dado: → User.name`, ou `dado: → (referência quebrada)` em alerta.

## Entrada e otimização de imagens

Vale para toda imagem que entra pela app (arquivo, câmera, colar, arrastar e trocar). A decisão é função pura em
`model/imageOptimization.ts`; a recodificação (canvas, `toBlob`) fica em `storage/imageImport.ts`.

- **Otimização na importação, antes de existir marcação:** a imagem otimizada passa a ser a "original", e as coordenadas nascem
  nela. O lado maior é limitado a `MAX_IMAGE_SIDE` (2560 px, sem opção na interface; imagem menor não é ampliada). O formato é
  WebP: com perdas (qualidade `LOSSY_QUALITY`, 0,85) para fotos e **sem perdas** para origem PNG; se o navegador não gera WebP,
  JPEG para fotos e PNG para origem PNG. Se a imagem não precisou ser reduzida, o recodificado só substitui o arquivo se for menor;
  se foi reduzida, vale sempre a versão reduzida. A recodificação remove os metadados (GPS inclusive); a normalização EXIF vem
  antes. No zip as imagens entram sem compressão (`STORE`). Imagens de projetos anteriores e arquivos já existentes numa pasta
  usada para criar o projeto ficam intocados.
- **Colar** (Ctrl/Cmd+V com o foco fora de campo de texto; em campo de texto o colar continua sendo de texto) adiciona a imagem no
  centro da área visível ou, se sobrepuser outra, no espaço livre mais próximo. O nome gerado é `img-AAAAMMDD-HHMMSS.<ext>`, com
  sufixo `-2`, `-3`… em colisão.
- **Arrastar e soltar** (`app/imageIntake.ts`): arquivo(s) em área vazia entram no ponto de soltura (ou no espaço livre mais
  próximo); **um único** arquivo sobre uma imagem existente a **troca** (mesma proporção: direto; proporção diferente: aviso e
  `needsReview`); vários arquivos sempre entram como novos; o que não é imagem é ignorado com aviso. O alvo acende durante o
  arrasto.

## Desempenho

- **Índice e estado derivado** (`model/projectIndex.ts`, `store/derived.ts`): `projectIndex(p)` é memoizado em
  `WeakMap<Project, ProjectIndex>` (funciona em Node), então `issues`, `refs`, `hierarchy` e a listagem usam mapas por id em vez de
  `find`/`filter` em laços. `derived.ts` separa o que depende do **projeto e da UI** do que depende do **viewport**: pan e zoom só
  atualizam a transformação do stage e o que depende de escala (texto do zoom semântico, espessuras).
  O stage recebe posição e escala numa chamada só (`stage.setAttrs({ x, y, scaleX, scaleY })` em `CanvasController.render`): o Konva
  agrupa os atributos numa cascata só, e cada atributo de transformação aplicado à parte limparia o cache de transformação de todos
  os nós (milhares, num projeto grande) e dispararia `absoluteTransformChange` neles; o zoom passou de 3 cascatas por quadro para 1
  (`tests/canvas/CanvasController.test.ts` conta: zoom 1, pan 1, edição 0).
- **Orçamentos** (medidos em testes, ligados por `npm run test:perf` e desligados com `--coverage` porque o código instrumentado
  é mais lento): índice, pendências, indicadores e visibilidade de um projeto grande (500 marcações, 1.500 anotações, metade
  tipadas, e 500 referências) em menos de 8 ms (`tests/model/performance.test.ts`, mediana de várias rodadas, cada uma numa versão
  nova do projeto); uma renderização do canvas com o projeto já indexado em menos de 16 ms (`tests/canvas/renderPerformance.test.ts`,
  Konva em jsdom com contexto 2D falso). Cada teste repete uma vez para separar ruído do runner de regressão real.
  O teste do canvas com 200 setas mede como os irmãos: 3 rodadas de aquecimento descartadas e a mediana de 15, uma por métrica
  (pan, zoom, edição), com a métrica no `expect`. No `npm test` os 3 arquivos de orçamento (`tests/model/performance.test.ts`,
  `tests/canvas/renderPerformance.test.ts`, `tests/store/reviewPerf.test.ts`) rodam em projetos próprios do Vitest (`perf-model`
  e `perf-app`, em `vite.config.ts`), com `sequence.groupOrder` maior que o dos demais e um arquivo por vez: começam depois do
  resto da suíte, sem disputar CPU com ela.
- **Testes de crescimento** (`npm run test:scale`): medem a mesma operação com n = 1.250 e 4n = 5.000 marcações do fixture
  `buildScaleProject` (`tests/model/scaleProject.ts`), pela mediana de rodadas após o aquecimento, cada rodada numa versão nova do
  projeto, e exigem a razão entre as medianas abaixo de 5× (linear dá ~4×, quadrático ~16×). Passar do teto é defeito a corrigir,
  não teto a subir. Rodam por `vitest.scale.config.ts` (projetos `scale-model`, `scale-app` e `scale-mcp`, arquivos `tests/scale/**/*.scale.ts`, um por vez),
  fora do `npm test` e da cobertura, num passo do job `build` do CI depois do `test:perf`; cada teste repete até duas vezes (`retry: 2`: as operações de poucos ms oscilam em torno de 4× e chegam a 5–7× numa rodada) e imprime no
  log n, 4n, as duas medianas e a razão. O auxiliar é `tests/support/growth.ts` (coleta o lixo antes de cada rodada; os workers sobem com `--expose-gc` e `--max-semi-space-size=128`, porque com o semi-espaço padrão o _scavenge_ do V8 inflava a razão para 5 a 8× sem laço quadrático nenhum). O que se mede (cada linha é um caso, n = 1.250 e 4n = 5.000, e o log mostra a razão de cada um):
  - **Modelo** (`scale-model`, Node): `validateProject`; `serialize` + `deserialize`; índice, pendências, indicadores e visibilidade;
    `buildListing`; `perspectiveView` de cada perspectiva (`tests/scale/model/`).
  - **Sessão, estado derivado e visualizador** (`scale-app`, jsdom; `tests/scale/app/`): gravar um projeto já aberto (conferir
    `revision` e conteúdo, gravar `revision + 1`, num armazenamento falso) e abrir o projeto; o estado derivado do editor
    (`createEditorDerived`: camadas visíveis, indicadores, visibilidade, pendências, lista) a cada versão nova do projeto; o
    visualizador, que monta a cena de n e 4n instâncias e atualiza uma delas já montada (contexto 2D falso).
  - **MCP** (`scale-mcp`, Node; `tests/scale/mcp/`): `get_project`, `list_markings`, `get_marking`, `get_annotation`, `find_by_code`,
    `find_by_source` e `list_threads`, em processo (`createServer` + `InMemoryTransport`), sobre o projeto de escala gravado numa
    pasta temporária (com `specs/` e uma conversa a cada 25 marcações em `comments/`). O servidor lê o projeto do disco a cada
    chamada, e é esse o custo medido de uma chamada por item num projeto grande.
    O auxiliar tem a versão assíncrona (`expectLinearGrowthAsync`) para a sessão e o MCP. O `test:scale` inteiro leva cerca de 90 a
    100 s. Assentar e editar ficam nos orçamentos do `test:perf`.

Só o modelo existe por enquanto: a app e o MCP passam a usá-lo nas fases seguintes da etapa.

### `mcp/` (servidor MCP)

Servidor em Node (stdio) fora de `src/`, com `tsconfig.json` próprio (sem DOM). Só pode importar `src/model/`: o ESLint recusa `src/ui`, `src/canvas`, `src/app`, `src/storage`, `src/store`, `src/i18n`, `src/theme`, `src/utils`, as bibliotecas de navegador e qualquer módulo de rede (`node:http`, `fetch`…). `npm run build:mcp` (`mcp/build.mjs`, esbuild) gera `dist-mcp/mapping-mcp.js`: um arquivo CommonJS único, com as dependências e a documentação (`?raw`) embutidas, mais um `dist-mcp/package.json` `{"type":"commonjs"}` (este repositório é `"type": "module"`).

- `main.ts` lê os argumentos (`args.ts`, `--root` repetível) e liga o transporte stdio; `server.ts` cria o `McpServer`, registra as tools (`tools.ts`) e os recursos de documentação (`docs.ts`: `mapping-docs://AGENT-GUIDE.md`, `FORMAT.md` e `SPEC-FORMAT.md`).
- **Caminhos** (`paths.ts`): `Roots` é o único ponto que transforma o que o agente digitou em caminho de disco. Recusa `..`, absoluto fora das raízes e link simbólico que sai delas (compara o `realpath`); `resolveProjectFile` aplica o mesmo a arquivos citados dentro de um `mapping.json` (`images/…`, `specs/…`), que é entrada não confiável. O `root` do `create_project` é resolvido como o `main.ts` resolve o `--root` (a partir do diretório de trabalho), pelo caminho real ou pelo nome da pasta, se único; com `path` absoluto, ele precisa conter o caminho (`invalid-arguments`). `isWithin` recebe a API de caminho (o teste usa `path.win32`). A gravação é atômica (`writeFileAtomic`: temporário na mesma pasta + renomear).
- **Projetos** (`projects.ts`): `discoverProjects` acha pastas com `mapping.json` em qualquer profundidade (não segue links simbólicos, ignora pastas ocultas e `node_modules`, não entra em projeto achado); `findProject` aceita nome da pasta, caminho relativo a uma raiz ou absoluto e devolve as candidatas se o nome se repete; `loadProject` lê `mapping.json` e `specs/` e valida tudo por `deserialize` do `src/model/` (migrações em memória; **ler nunca grava**). `createProject.ts` cria a pasta (`mapping.json` e `.gitignore`; `images/` nasce na app, com a primeira imagem).
- **Referências** (`items.ts`): `Refs` monta as referências `mapping://` (só a URL; `ref` e `bare` dão o mesmo texto) com `shortCode`/`formatRef`; os nomes e caminhos legíveis (`Imagem › Pai › Marcação`, via `markingPath`/`label`) vão só nos campos próprios das respostas, nunca no texto da referência; `resolveItem` interpreta com `parseRef` o que o agente colou (referência completa, `m/código` + `project`, id) e procura num projeto ou em todos. Ambiguidade vira erro com as candidatas.
- **Visões** (`views.ts`, `markingList.ts`): montam as respostas JSON compactas só com funções do modelo (`projectIndex`, `projectIssues`, `getBacklinks`, `refsOf`, `markingLockStates`…), sem regra de negócio própria.
- **Escrita em lote**: `operations.ts` é o esquema (zod) das operações de `plan_changes`; `batch.ts` as aplica em ordem sobre uma cópia do projeto, **só com as operações puras do `src/model/`** (invariantes, travas, especializações, vínculos e referências são do modelo; o lote só traduz o que o agente informou: referências, apelidos `$nome`, camadas e tipos por nome, valores `ref` e tabelas no formato do agente), guarda o erro de cada operação sem parar (a que depende de um apelido de uma operação que falhou recebe `alias-unavailable`) e monta o resumo legível; `modelErrors.ts` explica cada `ModelErrorCode` (`Record` exaustivo). `changes.ts` roda o lote sobre o projeto lido da pasta (`prepareBatch`) e monta a resposta comum do `plan_changes` (prévia, **sem gravar nada**) e do `propose_changes`. **Nenhum caminho do servidor grava o `mapping.json`** (o `apply_changes` não existe mais): o servidor só grava o projeto vazio do `create_project` e `proposals/`.
- **Propostas**: `proposals.ts` (`Proposals`) implementa `propose_changes`, `list_proposals`, `get_proposal`, `get_proposal_review` e `withdraw_proposal` sobre as funções puras de `src/model/` (`buildProposal`, `reviewTree`, `changeStatuses`, `reviewProgress`, `compareProposals`, `supersedeProposal`, `withdrawProposal`); não há regra de negócio própria. `proposalStore.ts` é o único módulo que grava no disco: cria `proposals/<id>/` (imagens novas antes, `proposal.json` por último, sem sobrescrever; a pasta criada é removida se algo falha) e atualiza uma proposta existente relendo o arquivo imediatamente antes de gravar e gravando `revision + 1` (a app pode estar decidindo ao mesmo tempo; após 3 tentativas, `revision-conflict`). `proposalRefs.ts` resolve `mapping://<projeto>/p/<código>` (o código curto vem de `shortCodesFor`, a mesma regra dos itens); `proposalViews.ts` monta as visões compactas (estado de cada mudança, níveis, progresso, notas). `sourceTools.ts` (`find_by_source`, `find_types_by_source`) e `specValidation.ts` (`validate_specialization`: os erros vêm de `parseSpecText`, a mesma função da importação da app; os avisos, de `specWarnings` em `src/model/specWarnings.ts`).
- **Imagens** (`mcp/image/` e `imageTools.ts`, fase 3a.4): `get_marking_image` e `get_container_file` leem o arquivo original do projeto (pelo `resolveProjectFile`, então só dentro das raízes), decodificam, recortam, reduzem, desenham os contornos e codificam, e devolvem um conteúdo `image` (base64) precedido do texto JSON que o descreve (`respondWithImage` em `tools.ts`). Os **codecs** (`codecs.ts`) são os do `@jsquash` (libpng, mozjpeg e libwebp compilados para WebAssembly), cujos `.wasm` entram no arquivo único como bytes pelo plugin `wasm:` do `mcp/build.mjs` (nome virtual por causa dos `.d.ts` ao lado de cada `.wasm`; a lista fica em `mcp/wasmFiles.mjs`, que o `vite.config.ts` também lê para os testes). São instanciados sob demanda a partir dos bytes (`new WebAssembly.Module`), sem ler arquivos nem rede; o WebP é codificado sem SIMD, direto da fábrica do codec, porque o `init` do pacote escolhe a variante com um `import()` dinâmico que o arquivo único não carrega. **Recorte, redução e contorno** (`raster.ts`) são TypeScript puro sobre RGBA: a redução é a média da área coberta por pixel (ponderada pela opacidade) e o contorno é desenhado **depois** da redução, por dentro do retângulo e com halo escuro, para ter a mesma espessura em qualquer escala; `compose.ts` junta as etapas e `formats.ts` detecta o formato e lê as dimensões **pelo cabeçalho** (PNG, JPEG e WebP) antes de decodificar, recusando arquivos de mais de 64 MB ou 100 megapixels (uma "bomba de descompressão" em disco não esgota a memória). O JPEG é decodificado com a orientação EXIF aplicada, como o navegador faz na app. Arquivo com dimensões diferentes das do `mapping.json` não derruba a tool: as coordenadas são ajustadas na proporção e a resposta traz um `warning`. `orientation.ts` gira os pixels pela orientação EXIF (as 8), aplicada pelo `decodeImage` no JPEG. Para clientes que não mostram `image` no chat, `mcp/imageServer.ts` entrega cada imagem gerada também por URL local: um servidor HTTP em loopback (`127.0.0.1`, porta aleatória, token aleatório por processo no caminho) que guarda as imagens só em memória (LRU de 64 imagens e 64 MB), sobe na primeira imagem pedida, não segura o processo (`unref`) e se desliga com `--no-http`; as tools acrescentam `url` e `markdown` à resposta. É a única exceção à regra "sem rede" do ESLint, e só para escutar: o servidor não faz requisição de saída e nada vai para o disco.
- **Adição de imagens**: `imagePrepare.ts` repete a importação da app (`storage/imageImport.ts`) sobre os mesmos codecs, com as decisões do modelo (`planOutputSize`, `chooseOutputFormat`, `shouldUseEncoded`, `withExtension`): imagem já girada pelo EXIF, lado maior até 2560 px (`resize`) e WebP (sem perdas se a origem é PNG).
- **Código das especializações**: `codeViews.ts` monta as visões (`code` por plataforma numa forma só, `{ symbol, definition, params?, values?, notes? }`, com a `definition` do `path` resolvida — `url` e `ref` do `repo` da especialização, `localFile` e `exists` pelo clone local do projeto —, por `typeCodeView` e `packageCodeView` (o `get_component`), e as chamadas de `get_code_hints`: `types` por `specId/typeId`, `repos` e, na árvore, só `args`, `values` e `linked` por anotação) e `findByCode.ts` a busca de `find_by_code` (os tipos e as anotações deles); ambos usam as funções puras de `src/model/` (`codeLink`/`repoLink`, `codeLocalPath`, `codeBlueprint`, `findByCode`). `codeFiles.ts` é o único módulo que toca o disco por caminho de código, e só com `stat`/`realpath` (o servidor **nunca lê nem grava código**, garantido por `tests/mcp/noCodeRead.test.ts`); a conferência fica confinada ao diretório de trabalho do cliente (`Roots.workDir`), porque o `localPath` pode subir acima das raízes e o `path` vem de um arquivo editável por terceiros.
- **Distribuição**: o push na `main` (o merge do épico) dispara `.github/workflows/mcp-release.yml`: o job `decide` publica só se a tag `mcp-v<versão>` de `SERVER_VERSION` (`mcp/version.ts`) ainda não existe (lógica em `scripts/release/stableRelease.mjs`; o job `epic` do `ci.yml` falha o PR do épico que muda as entradas da release, `scripts/release/releaseInputs.mjs`, sem subir a versão), e o job `release` cria a tag e a Release juntas, depois de rodar lint, typecheck e testes, gera `dist-mcp/mapping-mcp.js`, o executa copiado para fora do repositório (`--version`) e o anexa à Release com o `.sha256`. Uma tag `mcp-v<versão>` criada à mão dispara o mesmo workflow (plano B). Instalação e uso para quem consome o servidor: `docs/MCP.md`.
- **Respostas**: JSON compacto só no texto (sem `structuredContent`, que dobraria o contexto gasto); falha esperada é `ToolError` e vira `isError` com `{"error": {"code", "message", …}}`. O código é `ToolErrorCode` (`errors.ts`): a união literal do registro `MCP_ERROR_CODES` com os `ModelErrorCode`; todo código do registro está na seção "Erros" do `docs/AGENT-GUIDE.md` (`tests/mcp/errorCodes.test.ts`).
- **Quem grava**: só `paths.ts` (`writeFileAtomic`), `createProject.ts` (a pasta, o `.gitignore` e o `mapping.json` novo; `images/` nasce na app, com a primeira imagem) e `proposalStore.ts` (`proposals/`). A regra é dupla: o ESLint recusa importar as funções de escrita do `node:fs` nos outros módulos de `mcp/**`, e `tests/mcp/staticGuards.test.ts` varre `mcp/**/*.ts` recursivamente conferindo quem chama que função de escrita e quem cita o `mapping.json`. As constantes da pasta (`MAPPING_FILE`, `IMAGES_DIR`) e o texto do `.gitignore` (`gitignoreWithBackups`) vêm do modelo, os mesmos da app. Os arquivos novos de uma proposta usam temporário + `link` (nunca sobrescreve); sem hard link (`EPERM`, `ENOTSUP`, `ENOSYS`, `EXDEV`: exFAT, compartilhamentos de rede), `writeFile` com `wx`; nos dois caminhos, apagar o temporário é melhor esforço (`removeTemp`: recusado por antivírus ou pasta montada, vira aviso no stderr e o `.tmp` fica, ignorado pela app e pelo servidor), para nunca dar erro com o arquivo já gravado. Os nomes de `images/` reservados por outras propostas seguem o que ainda pode ser aplicado (`reservedImages`): numa aberta, as pendentes e as aceitas; numa substituída (e na anterior de um `supersedes`), só as aceitas.
- **Limites conhecidos** (aceitos e documentados):
  - **Janela no `proposal.json`**: o servidor (ao substituir ou retirar) e a app (ao decidir) releem o arquivo e comparam o texto imediatamente antes de renomear por cima, mas nenhum dos dois trava o arquivo. Uma decisão gravada pela app no intervalo de microssegundos entre a releitura e o `rename` do servidor se perde em silêncio (a app depois adota a versão do disco). Só acontece numa mudança de `status` com a app gravando no mesmo instante; se um dia doer, o `status` pode ir para um arquivo-marcador em vez de reescrever o JSON.
  - **Gravar a nova antes de marcar a anterior**: o `propose_changes` com `supersedes` grava a proposta nova e só depois marca a anterior como `superseded`. Se o processo morre entre as duas, ficam duas propostas `open`, com o `supersedes` da nova apontando para a anterior (o `list_proposals` já mostra `supersededBy`). Se marcar falha sem queda, qualquer que seja o erro, a resposta traz o aviso `supersede-failed` e a nova continua gravada. Derivar "substituída" do `supersedes` da nova também para `open` (como a app já faz para `applied`) fica como evolução.
- Testes em `tests/mcp/` (projeto `mcp` do Vitest, ambiente `node`). Um `globalSetup` gera o bundle uma vez; `images.test.ts` sobe o mesmo bundle sobre um projeto com imagens PNG, JPEG e WebP geradas no teste (`imageFixtures.ts`, com pixels dados por fórmula) e confere dimensões, `padding`, `maxSize`, cores, contornos e legenda das filhas, e roda o arquivo copiado para uma pasta sem `node_modules`; `write.test.ts` cria pelo MCP o projeto inteiro do roteiro 13.9 (num lote só, com apelidos, enviado como proposta e aplicado por `applyAccepted`, como a app) e o compara com `cadastroProject`, além de conferir lote inválido, travas, caminhos fora das raízes, imagens e o projeto v5; `proposals.test.ts` cobre a importação inteira, a revisão simulada (decisões e notas editadas no arquivo com as funções do modelo, `proposalSupport.ts`), a nova proposta com `supersedes`, conflito, trava, `source` e a garantia de que o agente nunca altera o `mapping.json`; `specValidation.test.ts` confere que `validate_specialization` devolve os mesmos erros que `parseSpecText`; `proposalStore.test.ts` testa a conferência de `revision` da proposta; `imagePrepare.test.ts` testa a orientação EXIF e a otimização (imagens de `images.ts`); `imageOps.test.ts` testa `raster`, `compose`, `formats` e os codecs diretamente; `proposalDisk.test.ts` provoca as corridas da gravação das propostas (o `mapping.json` mudando no meio do cálculo, a anterior mudando a cada leitura, falha de disco, `link` sem suporte, `rm` do temporário recusado) com um gancho de disco (`fsHooks.mjs`, carregado por `node --import` só nos testes, que troca funções de `node:fs/promises` no processo do servidor e nunca entra no bundle); `staticGuards.test.ts`, `errorCodes.test.ts` e `version.test.ts` são as catracas da escrita, dos códigos de erro e da versão × docs; `read.test.ts` sobe `dist-mcp/mapping-mcp.js` por stdio com o cliente do SDK, sobre uma pasta temporária (`workspace.ts`) com o projeto do roteiro 13.9 e variações (sem cópias de `specs/`, schema v5, `mapping.json` hostil, link simbólico para fora, ids que colidem).

### `src/storage/`

- `folder.ts` (pasta, e `ensureGitignore`, que grava `backups/` no `.gitignore` ao criar um projeto em pasta), `local.ts` (IndexedDB), `zip.ts` (exportar/importar, com `proposals/` e `comments/`), `autosave.ts`, `imageImport.ts` e `exif.ts` (leitura e otimização de imagens), `existingImages.ts`, `share.ts`.
- `localPerspectives.ts` (as perspectivas "Só eu" no IndexedDB, banco `mapping-perspectivas` por canal, uma lista por `project.id`; fora de `ProjectStorage`, aberto uma vez por app pelo controller), `loadProject.ts` (ler e validar `mapping.json` + `specs/`, ao abrir e ao recarregar; devolve também `libraryIssues`, os níveis 1 e 2 do validador sobre cada pacote `specs/<id>/`, via `specPackage.ts`), `loadProposals.ts` (ler e validar `proposals/`), `loadThreads.ts` (ler e validar `comments/`), `imageCrop.ts` (recorte em PNG para copiar).
- Todos implementam a interface `ProjectStorage` (`types.ts`); a sessão não sabe se é pasta ou local. Só a pasta tem `folderName`, `statMapping` e `statImage` (o que a app confere por fora).
- **Recentes de pasta**: o navegador não deixa guardar o caminho de uma pasta, mas deixa guardar o **handle** (`FileSystemDirectoryHandle`, serializável no IndexedDB) e pedir a permissão de novo. `local.ts` (`openFolderLibrary`) guarda cada pasta aberta num banco à parte, `mapping-folders`, e não no banco dos projetos locais: um store novo lá pediria uma versão nova do banco, e uma aba antiga aberta bloquearia a atualização. São dois stores: `folders` (a linha da lista: id, nome do projeto, nome da pasta e último uso) e `handles` (id → handle). Nunca há caminho. A lista (`list`) **não lê nenhum handle**: a tela inicial nunca depende de o navegador conseguir reconstruir um; o handle só é lido ao clicar em **Abrir** numa visita nova (`handle(id)`; `app/recents.ts` guarda em memória os handles desta visita) e, ao guardar, só os das entradas com o mesmo nome de pasta, para o `isSameEntry`. `remember` compara com `isSameEntry` (a mesma pasta atualiza a entrada em vez de duplicar; com `replaceId`, "Localizar pasta…", a entrada passa a apontar para a pasta escolhida e, se ela já estava na lista, as duas viram uma). `folder.ts` dá `isReopenable` (o handle tem `queryPermission`, `requestPermission` e `isSameEntry`), `ensurePermission` (consulta `readwrite` e, se não `granted`, pede) e `isOriginPrivate`. **Uma pasta do OPFS** (`navigator.storage.getDirectory()`, reconhecida por `isSameEntry`/`resolve` da raiz) **nunca é guardada**: o seletor de pastas não a devolve (só os testes e2e a usam no lugar dele), e o Chromium 1243 (o `chrome` completo e o headless shell) derruba a página ao ler de volta do IndexedDB um handle do OPFS (`get` ou `getAll`; gravar, `structuredClone` e `postMessage` passam). Isso foi medido no CI; com handles do seletor de verdade não dá para medir no CI, então o roteiro manual confere o reabrir no Chrome real. Sem esses recursos, sem IndexedDB ou sem o modo pasta (`showDirectoryPicker`), nada é guardado e a lista mostra só os projetos deste dispositivo. Todo acesso em `try/catch`: uma falha ao guardar vai para o Diagnóstico e não impede o projeto de abrir. Nada disso toca o `mapping.json`. `LocalLibrary.list()` não ordena: a ordem da tela inicial é a de `recentProjects`.
- **Pasta do clone dos documentos externos** (`docRepoFolders.ts`): o `doc` de um tipo pode ser `{ repo, path }`, um `.md` de um repositório declarado em `docRepos` da especialização (formatVersion 11). A app lê o arquivo da pasta do clone que a pessoa conecta **uma vez por máquina** (`showDirectoryPicker`, num clique). O handle fica no IndexedDB, num banco só dele, `mapping-doc-folders` (nome por canal: o preview acrescenta `-preview`, como os demais), no store `folders`, com a `url` do repositório normalizada como chave (sem `/` final nem `.git`: `normalizeRepoUrl`). A leitura consulta `queryPermission` em modo **leitura** e devolve `permission` se não for `granted`; quem renova é o botão "Permitir acesso a <repo>", porque `requestPermission` só vale num clique. Um `Map` em memória guarda o mesmo handle: sem IndexedDB (ou se ele não abrir em 3 s), a pasta vale até fechar a aba. Todo acesso em `try/catch`, com a falha no Diagnóstico. **Fica fora do `mapping.json`** porque a pasta é desta máquina e deste navegador: o handle não serializa em JSON e não deve ir no zip, no commit nem pelo MCP. O que o projeto guarda é o `docRepos[<id>].localPath`, um caminho relativo que o MCP usa para ler o documento no disco (Configurações › Repositórios › Documentos). O link "Abrir no repositório" da página do componente é só navegação (`<a>` para o `urlTemplate`): a CSP e o `connect-src 'none'` não mudam, e a app continua sem requisição de rede. Sem seletor de pasta ou sem `urlTemplate`, a seção mostra só o link ou `<repo>: <path>`.
- **Cópia do projeto (`ProjectStorage.copyId`)**: a chave do estado por dispositivo que pertence a uma cópia (o retomar da revisão, `store/review.ts`). Local: o id do projeto (`LocalLibrary.open(id)`). Pasta: o id da entrada dos recentes, que é por pasta física (`isSameEntry`) e sobrevive ao **Localizar pasta…** (a entrada fundida com outra da mesma pasta passa a ter o id daquela). Pasta fora dos recentes (sem IndexedDB, handle sem `isSameEntry`, OPFS, falha ao guardar): um id por nome de pasta **por aba** (`sessionCopyId` em `app/recents.ts`, no `sessionStorage` por `safeStorage`, com um `Map` de reserva). É definido na criação do storage, **antes** de a sessão abrir, e nunca muda; só os storages de leitura (abrir, conferir a pasta escolhida) não têm. O schema não tem id de projeto, e um não resolveria a mesma proposta em duas cópias (o zip importado e a pasta descompactada dele).

### `src/canvas/`

- `CanvasController.ts`: orquestrador fino; monta o quadro, agenda a renderização e conecta os módulos. O projeto desenhado (`drawnProject`) vem do projeto à vista (`review.derived.shownProject`): fora da revisão, o do store com a prévia do gesto, recortado por `projectInPerspective` da perspectiva aberta (`options.perspective`); a prévia da proposta (com `proposedDisplay`) na visão Proposto; o canvas não decide Atual/Proposto nem a perspectiva. O ponteiro recebe `perspectiveOpen` (`input/pointer.ts`, `input/intents.ts`): com uma perspectiva aberta não começa o que é só da Principal (desenhar no vazio do canvas, os pontos de passagem da seta, o encaixe em container) e lê o projeto desenhado, não o do store; `commentPins.ts` só põe pino de ponto do canvas na Principal. `CanvasHost.tsx`: ponte com o Preact.
- `renderers/`: `images`, `markings`, `semanticCard`, `overlay` (seleção, alças, etiqueta do nome, rascunho, alvo de soltar). Recebem dados prontos e só atualizam nós do Konva (com pool de nós reaproveitado). Nenhuma cor, família de fonte, opacidade, raio ou tamanho de alça fixos: tudo vem de `frame.tokens`; `tests/theme/canvasLiterals.test.ts` procura literais.
- **Setas no canvas** (v13; modelo em `model/arrows.ts`): `canvas/arrowGeometry.ts` (puro) monta o desenho de cada seta a partir de `arrowRoute` — a polilinha (`straight`, `elbow`) ou a curva (`curve`: Hermite por trecho, com as tangentes das pontas perpendiculares ao lado da marcação e Catmull-Rom nos pontos de passagem, amostrada; o mesmo traço serve ao desenho e ao toque) — e o guarda por seta (mesmo objeto enquanto a seta, as duas marcações e os containers delas são os mesmos). `visibleArrowShapes(projeto, visibilidade)` lista as setas com as duas pontas à vista (memoizado; mesmo array enquanto nada muda) e o `CanvasController` a lê do projeto **desenhado** (com a prévia do gesto e, na visão Proposto, as setas propostas), vazia com "Mostrar setas" desligado fora do modo visualização (no modo, só o item Setas decide, com `canvasVisibility`); por isso não é um derivado de `derived.ts` (o derivado do editor não vê a prévia do gesto). `renderers/arrows.ts` é um grupo próprio entre os componentes e as marcações (a mesma camada do Konva das marcações, desenhado antes delas: o palco tem cinco camadas, porque o Konva avisa no console a partir de seis) com **um nó só** que pinta todas as setas em quatro passagens (halo do traço, halo da ponta, traço, ponta; espessura e ponta em px de tela, divididas pelo zoom na hora de pintar), então o zoom não toca nenhum nó e o número de operações de pintura não cresce com o de setas (o desenho por zoom é guardado, o traço é afinado pelo espaçamento em tela); só o rótulo (o `name`) é um nó por seta nomeada. A seleção fica na sobreposição (`overlay.ts`): realce (primária e secundárias), alças da primária (pontas, pontos de passagem, meio dos trechos, `arrowHandles`), cadeado da trancada, a **alça de ligação** da marcação selecionada (`linkHandlePoint`, fora da borda direita) e a seta provisória do gesto (`InteractionState.arrowDraft`, com a marcação de destino, que acende como o alvo de soltar). O toque (`input/intents.ts`): `hitChain` põe as setas (a até `ARROW_HIT_TOLERANCE` px de tela do traço) depois das flutuantes e antes das marcações e dos containers; as intenções `arrow-link` e `arrow-handle` vêm das alças, e a seta trancada dá `locked` sobre o traço. O rótulo do nome acima do container (retângulo do texto medido pelo `ImageRenderer`, `titleRects`; acerto por `containerTitleAt`) entra na cadeia logo depois das setas e seleciona o container mesmo coberto de marcações; com o container selecionado, arrastá-lo pelo rótulo o move. Os gestos (`gestures.ts`/`pointer.ts`) são `arrow-link` (sem gesto do store: soltar sobre uma marcação chama `addArrow` e seleciona a seta), `arrow-route` (mover um ponto de passagem ou arrastar o meio de um trecho para criar um: `previewArrowRoute`, os pontos gravados no espaço de `arrowPointsSpace` por `fromCanvasPoint`, arredondados) e `arrow-end` (trocar a ponta com `previewArrowEndpoint`; sobre a mesma marcação troca o lado pelo `nearestSide`; soltar no vazio cancela); cada um é uma entrada de desfazer, e o clique duplo num ponto de passagem o remove (`setArrowRoute`). **Canto (`elbow`)**: `arrowRoute` devolve a polilinha ortogonal do roteador (`elbowRoute`, puro, em `model/arrows.ts`: trechos horizontais e verticais, saída e chegada perpendiculares aos lados, `points` = um por segmento do meio, `route.lanes`); as alças são as pontas e o segmento do meio (`segment`, o segmento inteiro pega o toque), o gesto `arrow-route` em modo `segment` o move em paralelo (`previewArrowRoute` com um ponto por segmento, `elbowLanePoints`), o clique duplo nele volta à rota padrão, e o renderer traça o canto com junção em esquadro (`ArrowStrokes.corners`). Tokens: `cv-arrow`, `cv-arrow-select`, `cv-arrow-label`, `cv-arrow-label-bg`, `size-arrow-stroke`, `size-arrow-stroke-selected`, `size-arrow-head`. O `CanvasController` publica `data-arrows` (setas desenhadas) no container.
- `components/`: `componentLayer` (camada Konva dos desenhos, diff por identidade), `renderScene`, `screenRenderer` e `konvaMeasurer` (ver "Componentes" abaixo).
- `input/`: `pointer` (eventos → `gestureMachine` → intenções), `keyboard`. `gestureMachine.ts` é uma máquina de estados pura e testada.
- `viewportController.ts`, `viewport.ts`: pan, zoom, enquadrar, centralizar. `viewState.ts`: os signals que a interface lê (viewport, tamanho, área das imagens e cursor em pixels da imagem); o controller os escreve, e o cursor só muda uma vez por quadro. `minimap.ts`: as contas do minimapa (funções puras).
- `markingGeometry.ts`, `imageGeometry.ts`, `semanticText.ts`, `theme.ts`: geometria, zoom semântico (só o nome no cabeçalho da marcação grande; as anotações ficam no painel direito) e leitura dos tokens do tema. `readCanvasTokens` lê do CSS (`--cv-*`, `--color-card`, `--opacity-*`, `--t-cv-*`, `--font-sans`, `--radius-*`, `--size-handle`, `--size-lock-badge`) e é relido quando o tema muda; `canvasTokensFrom(leitor)` é a versão pura, usada nos testes. Linha da marcação: `cv-line` (ou a cor escolhida para a imagem) sobre um halo `cv-halo` por fora e por dentro; selecionada, `cv-select` com a etiqueta do nome (`cv-name-tag`). ### Foco e teclado

O modelo de foco mora em `ui/focus.ts`. Três ideias sustentam as regras abaixo: abrir um modal é síncrono com a renderização que o põe no DOM (não há quadro com `<dialog>` fechado e sem retorno); a origem do foco é guardada **uma vez por slot**; e cada jeito de fechar tem **um** dono que decide para onde o foco vai (o retorno do modal só age com o foco perdido, depois de qualquer dono explícito).

- **Modal** (`Dialog`, `RefPicker`, por `useModal`): `showModal`, foco inicial, contagem em `modalOpen` e registro do retorno acontecem num `useLayoutEffect`, no mesmo commit que põe o `<dialog>` no DOM. Um `<dialog>` no DOM está sempre aberto, com o foco dentro e com o retorno registrado, mesmo que saia antes do próximo quadro. `modalOpen` (signal) diz se há modal aberto; os atalhos do editor e o colar de imagens o leem, em vez de procurar `dialog[open]` no documento.
- **Retorno ao fechar** (`restoreFocus`, chamado numa microtarefa depois da renderização que fecha, porque o Preact desmonta o diálogo antes de aplicar o resto da mesma renderização): só age com o foco perdido (no `body` ou dentro do modal que saiu); então vai a quem abriu; se quem abriu saiu do DOM, ao alvo explícito (`returnFocus`, elemento ou função lida ao fechar); **sem** alvo explícito, ao contêiner focável mais próximo de quem abriu; por último, ao primeiro controle de `data-focus-root` (`App.tsx`). Com alvo explícito o modelo não adivinha contêiner. O fallback de contêiner pode focar uma janela de ferramenta (`section.tool-window[tabindex=-1]`) em vez de um controle: é aceitável e fica assim.
- **Origem no slot do host** (`useDialogSlot`): o editor (`useEditorDialogs`), a tela inicial e os passos de criação de `AnnotationsPanel` têm um slot de diálogos (um por vez). A origem do foco é guardada no gesto que abre o primeiro diálogo e uma troca no mesmo slot a herda (Configurações › Ver atalhos, tipo › dono); o host envolve o slot com `DialogSlotContext` e o primeiro `Dialog` montado sob ele reivindica a origem (`useFocusOrigin`). Diálogos abertos por cima (os passos do `SpecsDialog`) e os avulsos guardam a sua na renderização.
- **Um dono por fechamento**: para cada jeito de fechar, um só código decide o foco. Quem fecha e leva o foco a outro lugar faz isso até o commit (síncrono ou em `useLayoutEffect`), antes do retorno do modal, que então não mexe. Exemplos: a tela inicial fecha o Excluir e o Remover da lista **depois** da ação e passa `returnFocus` para a linha que ficou; sem diálogo (Remover da lista na linha), a própria Home leva o foco à linha no commit da lista nova. O "ir para a anotação" (backlinks, pendências, criação, Ctrl+Enter no seletor) é do painel (`AnnotationsPanel`, no commit que desenha o cartão). O diálogo de exportação devolve o foco ao botão **Exportar** da barra (`buttonRef`, exposto por `dialogs.exportButton`), porque o zip é gerado com ele desabilitado.
- **Avisos da especialização** (etapa #486, `formatVersion` 10): o aviso (`notices` no tipo, no campo e na coluna de `table`) só informa; não é pendência (`AnnotationIssueCode` e Incompletas não mudam) e nada bloqueia por causa dele. Os dados vêm de duas funções puras de `src/model/`, sem DOM e memoizadas pela versão do projeto como o `projectIndex`: `noticeUsage(p)` (`notices.ts`: cada aviso das especializações carregadas com as anotações que ele afeta — a do tipo, a que tem valor não vazio no campo, a que tem valor não vazio na coluna em alguma linha) e, sobre ela, `src/model/noticeList.ts` (`buildNoticeList` e `noticeCounts` para a janela, `noticedCount` e `noticesByAnnotation` para a aba e a barra, `changeNotices` para a revisão). `store/derived.ts` só aplica os filtros da UI (`noticeKind`, `noticesInUseOnly`, `noticesVisibleOnly`, em `store/ui.ts`) e as camadas visíveis sobre a lista memoizada (`noticeList`, `noticeCounts`, `noticedCount`), sem `find`/`filter` em laço e sem recalcular em pan ou zoom. A janela **Avisos** (`src/ui/NoticesView.tsx`, inferior, `Ctrl+Shift+8`, aba entre Incompletas e Diagnóstico — a ordem das abas é a de `TOOL_WINDOWS`, não a do número) agrupa por aviso (`removed`, `deprecated`, `diverges`, `pending`; depois a ordem das especializações, camadas e tipos), com o selo, o lugar, a mensagem, o `since` e a contagem no cabeçalho do grupo e uma linha por anotação (marcação, camada, anotação, valor); escolher a linha leva à anotação pelo mesmo caminho de Incompletas. A aba mostra quantas anotações têm algum aviso e a barra de status, "Avisos: N" (escondido com N = 0; o clique abre a janela). Na revisão, o `ChangePopover` mostra, abaixo dos valores da mudança, os avisos que a mudança traz (`ui/review/ChangeNotices.tsx`, lidos da prévia com todas as mudanças, `fullPreview`); Aceitar e Aplicar não dependem deles.
- **Janelas de ferramenta** (`ui/toolWindowLayout.ts`): quem abre (`openToolWindow`: faixa, aba, atalho, `Ctrl+L` e os caminhos programáticos: `openReview` e `useShowProblem` da revisão, `updateFeedback` do `SpecsDialog` e o "ir para a anotação" de Incompletas em `EditorWindows`) guarda o `document.activeElement` por janela, num `Map` de UI (nunca no store, não persistido); uma janela aberta desde o carregamento não tem origem. Quem fecha é `closeToolWindow` (o X, `hide-window`, `toggle-window` e o clique na faixa passam por ela): só age com o foco dentro da janela e, ainda com a janela no DOM (sem quadro com o foco no `body`, sem microtarefa), foca o primeiro que existir e estiver fora dela: quem abriu → botão da janela na faixa (`data-strip-window`) → canvas (`data-canvas-area`). Abrir uma janela que esconde outra do mesmo lado aplica a mesma ordem à que saiu. Na janela inferior, trocar de aba remonta a seção (chave por id) e perderia o foco da aba: `openToolWindow` leva o foco à aba ativa da nova janela, numa microtarefa que se soma à de `showAndFocusToolWindow` na lista de exceções ao `useFocusRequest`. Abrir por código continua sem mover o foco. No `SpecsDialog` a origem guardada fica dentro do diálogo e sai do DOM quando ele fecha, então ao fechar a Incompletas vale o botão da faixa (aceito). Abrir a revisão a partir da Lista (janela inferior) troca a Lista por Propostas e o foco vai à aba ativa, não ao `body`. Quando quem abriu some do DOM (o **Revisar** sai quando a lista de Propostas vira a árvore da revisão), vale o botão da faixa (`data-strip-window`), nunca o `body`; e quem abriu só é a origem se de fato abriu a janela (a Incompletas não abre Detalhes que já estavam abertos). **Trava de lint:** `no-restricted-imports` (com `importNames`) proíbe importar `showToolWindow`, `hideToolWindow` e `toggleToolWindow` de `store/toolWindows` em `src/ui/**` e `src/app/**`, exceto em `ui/toolWindowLayout.ts` (`tests/tooling/` prova que a regra recusa). **Intencionais** (decisão do dono, 2026-11-02): o `Ctrl+Shift+N` em dois toques (com a janela aberta e o foco fora dela, o primeiro toque só a foca e o segundo fecha, como numa IDE) e o Catálogo, que ao fechar não restaura a Árvore nem as Camadas.
- **Menus e popovers** (`ActionMenu`, `MenuPopover`, `Popover`): em todo fechamento (Esc, escolha, clique fora, rolagem), `returnFocusToTrigger` leva ao gatilho o foco que estava no menu, antes de ele sair do DOM; na escolha, antes da ação do item, para um diálogo aberto por ela guardar o gatilho como quem o abriu. Se o clique fora pôs o foco em outro lugar, ele fica lá. O menu de contexto do canvas, sem gatilho, devolve o foco a quem o tinha ao abrir. O `Popover` aceita ser controlado (`open`/`onOpenChange`): o marcador da revisão abre pelo hover e pelo foco, e um painel guarda qual marcador está aberto; com `scroll="follow"` ele se reposiciona em vez de fechar quando a página rola (a rolagem que leva o marcador focado à vista não o fecha). **Limite:** o `Popover` acha o gatilho pelo primeiro controle focável do host fora do painel (uma heurística que serve aos usos de hoje: a paleta de cor, o menu das linhas de camada e o menu de copiar referência e recorte); um host com outro controle antes do gatilho precisaria de um `ref`.
- **Foco depois da renderização: um idioma só.** `useFocusRequest()` guarda o pedido e o cumpre no `useLayoutEffect` da renderização seguinte do dono (a alça da linha movida, a linha nova da tabela, o "+ Par" depois de descartar um par). Nada de `requestAnimationFrame`, `useEffect` ou microtarefa para foco, com estas exceções: o retorno do modal (acima), que o menu de contexto do canvas também usa (`restoreFocusAfterRender`, uma microtarefa); o **Alt+N** (`useEditorShortcuts.ts`), que abre Detalhes e clica no "+ Anotação" num `requestAnimationFrame`, depois que a janela desenha; `showAndFocusToolWindow` (função de módulo; a renderização agendada pelo signal roda numa microtarefa anterior) e o **Localizar** da Árvore (`TreeWindow`): `revealInTree` abre os ancestrais da seleção por signal, a Árvore só desenha as linhas novas na renderização que esse signal agenda, e o `afterPaint` (`MarkingTree.tsx`, um `requestAnimationFrame`) espera esse desenho para achar a linha `aria-current` dentro do próprio `ref` e focá-la. O mesmo `afterPaint`, sem foco, rola a Árvore até a seleção que muda por fora.
- **Sem seletores entre componentes**: um componente não acha outro pelo DOM global nem pela classe dele. Use `ref` (`buttonRef` em `Button`/`IconButton`, `inputRef` em `TextField`, `triggerRef` no `ActionMenu`), `returnFocus`, um signal, ou `[data-…]`/`[role=…]` dentro do próprio `ref` (`data-dialog-body`, `data-grip`, `data-cell-value`, `data-recent-open`, `data-tooltip`). Regra ESLint (`no-restricted-syntax` em `src/ui/**` e `src/app/**`, `eslint.config.js`): `document.querySelector*`/`getElementById`/`getElementsBy*` e seletor com `.` em `querySelector(All)` e em `closest` são erro (a janela e a coluna da esquerda são achadas por `[data-window]`, `[data-tool-column]` e `[data-panes]`); exceções nominais `ui/focus.ts` (`data-focus-root`) e `ui/toolWindowLayout.ts` (`data-window`), e o Alt+N de `useEditorShortcuts.ts` com `eslint-disable` justificado. `tests/tooling/focusRules.test.ts` prova que a regra recusa o padrão antigo.

**Política de teclado:**

- **Enter num campo de texto confirma e o foco fica no campo** (`CommitInput`, o Valor dos pares); uma guarda impede que o `change` que o navegador dispara em seguida grave de novo (uma entrada de desfazer). A guarda vale só enquanto o valor externo (no par, o par gravado) ainda é a base daquela gravação e é zerada quando ele muda: depois de desfazer, o mesmo texto grava de novo; depois da renderização, o campo mostra o valor externo e o `change` duplicado não tem o que gravar, mesmo com um `onCommit` que normaliza o texto. Gravado, o rascunho passa a ser o texto gravado, então desfazer mostra o valor de antes, não o rascunho. Exceção: **Enter na Chave** de um par leva ao Valor. Enter num `<form>` de diálogo envia; Enter e ↑↓ no seletor de referência e nos níveis da revisão seguem o que cada um faz.
- **Alt+Enter**: nova linha / novo par.
- **Esc num campo**: com o que reverter, volta ao valor gravado e **para aí** (`preventDefault` + `stopPropagation`: não fecha o diálogo nem o menu em volta); sem o que reverter, **sobe** (fecha o menu ou o diálogo; no editor, os atalhos ignoram campos de texto). Esc num par novo o descarta e o foco vai ao "+ Par".
- **Menus e popovers** devolvem o foco ao gatilho em todo fechamento (acima).
- **`aria-keyshortcuts` sempre na sintaxe ARIA** (`Control+E`, `Control+Shift+Z`, `Alt+Enter`, `F1`), gerado por `ariaKeys(rótulo)` (`app/shortcuts.ts`) a partir do rótulo humano (`Ctrl+E`), que fica só na dica; rótulo que não é tecla ("Ctrl+clique") não vira atributo. `IconButton`, `Segmented` e `DecisionControl` aplicam `ariaKeys`; `tests/tooling/focusRules.test.ts` exige literal ARIA ou `ariaKeys(…)` em todo `aria-keyshortcuts=`.

### Estilos (`src/theme/`)

`tokens.ts` é a fonte única dos tokens de design (cores nos temas claro e escuro, espaço, raio, tipografia, tamanhos, opacidades, durações, z-index, sombras, breakpoints e a paleta de camadas). O plugin `tokensCss` (`vite.config.ts`) a entrega como `virtual:tokens.css`, importado primeiro por `main.tsx`, e não existe arquivo `tokens.css` para editar. A densidade também é token: os papéis `--control-height` (28px), `--control-height-sm`, `--control-radius`, `--control-icon` (16px) e `--control-check`, com um valor só (sem troca por largura). ### Componentes

Uma biblioteca (`formatVersion` 4) traz, por tipo de anotação, um arquivo de componente ([`COMPONENT-FORMAT.md`](COMPONENT-FORMAT.md)). A app desenha esses componentes no canvas, sobre containers sem arquivo ou, se a pessoa quiser, sobre fotos.

**Regra: desenho derivado, nunca gravado.** O `mapping.json` não guarda nada do desenho: nenhuma cena, caixa, cor resolvida ou fonte. Ele guarda só o que sempre guardou (imagens, marcações e anotações com os valores dos campos) e, nos containers sem arquivo, `file: null` e `background` (schema v10). O desenho sai da marcação, do pacote aplicado e dos valores, a cada vez; exportar, zipar e reabrir dão o mesmo desenho porque os dados são os mesmos. A marcação desenha a **primeira anotação tipada própria** (na ordem do array `annotations`) cujo tipo tem componente na versão aplicada (`markingComponent`, `src/model/componentCatalog.ts`); só as anotações da própria marcação desenham. Sem catálogo ou sem componente, a marcação é comum e nada muda.

- **Catálogo e fontes em memória** (`src/store/componentLibrary.ts`, criada pela sessão). Para cada especialização aplicada com pacote em `specs/<id>/`, a biblioteca lê os componentes e as fontes uma vez por `id@versão` (aplicar, atualizar, desfazer e recarga externa invalidam). O catálogo (`ComponentCatalog`) fica num signal; componentes que não carregam viram `problems` e não derrubam o resto. As fontes viram `FontFace` a partir dos **bytes** do arquivo (`src/storage/fonts.ts`; a CSP bloqueia fonte por URL, mas aceita `ArrayBuffer` em memória). Cada registro terminado sobe `fontsEpoch`, e os desenhos remedem. Fonte ausente cai na fonte do sistema, com aviso no Diagnóstico.
- **Catálogo da biblioteca**: a página de cada componente (`CatalogView`, `src/ui/catalog/`, só apresentação) aparece em dois lugares, com a mesma regra de dados: o `Catalog` vem de `buildCatalog` (`src/model/catalog.ts`, puro) sobre os arquivos do pacote já lidos para a memória, e nada é gravado. **Sem projeto**: a tela inicial tem **Abrir biblioteca** (pasta pelo `showDirectoryPicker`, senão zip); `openLibraryPackage` (`src/app/controller.ts`) lê o pacote com os limites do `specPackageImport`, `openLibraryPreview` (`src/store/libraryPreview.ts`) monta o catálogo e registra as fontes do pacote (tiradas ao fechar), e `App` mostra `CatalogScreen` (`layout="split"`, `project={null}`: sem Adicionar à tela nem links de repositório) em vez da `Home`; um pacote com erros abre mesmo assim, com os problemas no topo. **Dentro do projeto**: a janela **Catálogo** (`src/ui/CatalogWindow.tsx`, esquerda, `Ctrl+Shift+9`, no lugar da antiga janela Biblioteca, cujo id `library` salvo no `localStorage` migra para `catalog`) tem as abas **Componentes** (`layout="list"`; a página abre num diálogo) e **Paleta**. Os catálogos vêm de `session.catalogs` (`src/store/projectCatalogs.ts`): montados **sob demanda** quando a aba Componentes monta, a partir da cópia em memória da sessão ou de `specs/<id>/`, uma vez por conjunto de `id@versão` e invalidados junto com `components.invalidate()`; com a janela fechada não custam nada. Aqui o `project` é passado (links de código) e **Adicionar à tela** usa o alvo de `componentTarget` (seleção primeiro) e `actions.addComponent`, como a paleta.
- **Medidor de texto** (`src/store/textMeasure.ts`). `textMeasurer` começa no medidor aproximado (testes e Node); o `CanvasController` troca para o `konvaMeasurer` ao montar (`src/canvas/components/konvaMeasurer.ts`) e os desenhos remedem na hora. No navegador a medida é real; no Node e no servidor MCP é sempre a aproximada (por isso o MCP nunca arruma, ver abaixo).
- **Derivado** (`src/store/derived.ts`, com a lógica pura em `src/model/componentDrawings.ts`). `componentScenes` é o mapa por marcação de um `ComponentDrawing` (cena instanciada na caixa da marcação, avisos e `overflow`), em ordem de desenho (pais antes das filhas, irmãs na ordem do array). `drawingsOf(p)` faz o mesmo para o projeto da revisão (visão Proposto) pelo mesmo cache, e só a marcação que mudou é reinstanciada; as demais devolvem o **mesmo objeto**. `drawnMarkings` é o conjunto das marcações cujo desenho está visível. Mexer no retângulo, num valor, no catálogo, no medidor ou em `fontsEpoch` redesenha; pan e zoom não. Na visão Proposto, o catálogo que o derivado lê (`review.components`, `src/store/proposedCatalog.ts`) é o da biblioteca aplicada mais os pacotes de especialização que a proposta aberta cria ou atualiza, lidos de `proposals/<id>/<pasta>/` quando a proposta abre (não quando a visão muda nem quando se decide) e sem gravar nada em `specs/`; na visão Atual, o catálogo é o da biblioteca (`session.components`), o próprio objeto. A pendência `component-overflow` ("O componente não cabe") é produzida aqui, juntada às do modelo, e por isso entra em Incompletas e na contagem.
- **Camada Konva** (`src/canvas/components/componentLayer.ts`, `renderScene.ts`, `screenRenderer.ts`). Fica entre as imagens e as marcações, com um nó por marcação que desenha (o `slot` do componente não desenha contorno no produto, `showSlots: false`; só testes e o visualizador mostram o reservado) e **diff por identidade** do `ComponentDrawing` (mesmo objeto, nó intocado). O `CanvasController` publica `data-components` no container, ao lado de `data-fits` e `data-images`, para os testes e2e esperarem o quadro. A marcação que desenha tem a **borda só em hover e seleção** (`renderers/markings.ts`), e o **zoom semântico** mostra o desenho no lugar do nome dela. O container sem arquivo sempre desenha; sobre foto, só com a opção por pessoa **Mostrar componentes sobre fotos** (`showComponentsOnPhotos` em `src/store/settings.ts`, `localStorage` por `safeStorage`, nunca no projeto). O filtro "Marcações sem anotação" (esmaecer e ocultar) não se aplica à marcação que desenha: `drawnMarkings` é calculado primeiro (sem depender da visibilidade) e entregue a `markingVisibility` como `alwaysShown`, então ela fica por inteiro, desenhada, e o ancestral dela não vira só borda.
- **Tamanho mínimo e ordem.** O `minSize` do componente vale para a marcação que o desenha: criar, editar o retângulo e o MCP recusam com `rect-too-small`; o canvas prende o redimensionar no mínimo em vez de recusar no meio do gesto. A **ordem entre irmãs é a ordem do array `markings`** (sem campo novo): a última é desenhada por cima; `reorderMarking`/`siblingPosition` (`src/model/markings.ts`), campo **Ordem** nos Detalhes e `position` na proposta.
- **Arrumar** (`src/model/componentArrange.ts`, `src/ui/arrange.ts`). Recalcula e grava os retângulos das filhas de um componente com slot pelo `layout` do slot (o componente `hug` cresce; a filha cujo componente é `hug` num eixo é remedida nesse eixo, com texto novo ela encolhe ou cresce, nunca abaixo do `minSize`; tamanho fixo só avisa), numa única entrada do histórico. Só roda por **ação da pessoa** (`Alt+Shift+A`, botão nos Detalhes, menu de contexto do canvas): nunca na carga, no MCP nem ao aplicar uma proposta. O resultado vem num aviso curto (Arrumado, com avisos, ou Nada a arrumar).
- **Container sem arquivo** (`file: null`, `background`; invariante `container-content`): sem arquivo, sem bitmap, não recodificado nem trocado, fora do zip como arquivo; criado pelo diálogo **Novo container** (`src/ui/ContainerDialog.tsx`, `containerForm.ts`) ou pela operação de proposta `add_container` (`add_blank_image` segue aceita, com aviso); o quadro o organiza como as imagens. O diálogo oferece **Personalizado**, **Tamanho da seleção** (o retângulo da marcação selecionada) e os tamanhos `containers` das especializações aplicadas (`formatVersion` 6), agrupados pelo nome da especialização; o núcleo não traz tamanhos de dispositivo. A aba **Paleta** da janela **Catálogo** (`src/ui/LibraryPalette.tsx`, `Ctrl+Shift+9`) lista os tipos com componente e o Adicionar (`useAddComponent`, comum ao Catálogo) cria a marcação com a anotação tipada (valores de `preview`), com a regra **seleção primeiro** (`componentTarget`, `src/ui/componentTarget.ts`): dentro do componente com slot selecionado; senão no container da seleção (o selecionado ou o da marcação selecionada), centrado no centro da vista se ele cai nele, ou no centro do próprio container; sem seleção, no container sob o centro da vista (sem container ali, o Adicionar fica desabilitado). Depois de criar, se a marcação nova ficou fora da área visível, `CanvasController.revealSelection` faz o pan mínimo até ela, sem mudar o zoom (já à vista, a vista não se mexe).
- **Bibliotecas embutidas e a de notas.** Um pacote de biblioteca comum pode vir dentro do build: `libraries/<id>/index.ts` importa cada arquivo da pasta com `?raw` e entrega um `BundledLibrary` (`id`, `specFile`, `files`); `libraries/notas/` é a biblioteca de notas (camada Notas, versão 3: tipos flutuantes `nota` e `tabela`, componentes no estilo post-it; o da `tabela` usa o nó `repeat`, `formatVersion` 2 do componente). `src/model/bundledLibrary.ts` é puro (`applyBundledLibrary`, `hasBundledLibrary`, `bundledLibraryDiskFiles`): aplica o pacote ao projeto como uma aplicação de especialização comum e diz quais arquivos vão para `specs/<id>/`; quem grava é a sessão. A aplicação é **por padrão** e só na criação e na migração (`withDefaultNotes`, `src/app/controller.ts`): projeto novo (pasta ou neste dispositivo) nasce com ela e **grava os arquivos no armazenamento** junto com o primeiro `mapping.json`; projeto aberto de um schema anterior ao 13 a ganha em memória, sem entrada de desfazer, e a sessão a grava na primeira gravação, junto com o backup da migração, pela opção `stagedPackages` (`src/store/session.ts`); projeto **já v13 sem ela** (removida pela pessoa ou criado sem) fica como está, e remover por Especializações › Remover é definitivo. O servidor MCP usa o mesmo módulo no `create_project` (`notes`). Uma pasta de `libraries/` **sem** `index.ts` (hoje `libraries/kotlin/`) é uma biblioteca pronta para uso que não entra no build: a pessoa a aplica por Especializações (pasta ou zip), e um teste em `tests/model/` a valida.
- **Tipo flutuante na Paleta.** Tipo com `floating: true` cria **marcação flutuante** (`containerId` nulo, `floating: true`, fora do pertencimento nos dois sentidos, desenhada acima de tudo). O Adicionar (`componentTarget`, `src/ui/componentTarget.ts`) ignora a seleção e cria sempre no canvas, no centro da vista, com o rótulo "Adicionar no canvas"; o arrasto da Paleta (`componentDropTarget`) solta onde cair, sem procurar container nem slot. O texto de um campo `string` da anotação é editado por `StringEditor` (`src/ui/FieldEditors.tsx`), que abre em várias linhas quando o valor tem quebra ou passa de 60 caracteres, ou ao apertar Shift+Enter; a célula de tabela continua de uma linha.

Onde ficam: o motor puro (`instantiate`, `layout`, `scene`, `arrange`) em `src/model/components/`; o catálogo, os valores, o cache e o Arrumar em `src/model/component*.ts`; o que depende do Konva em `src/canvas/components/`; as fontes em `src/storage/fonts.ts`.

### Content Security Policy

O `dist/index.html` carrega esta política num `<meta http-equiv="Content-Security-Policy">`, logo depois do `charset` (ela só vale para o que vem depois dela):

```
default-src 'none';
script-src 'sha256-…';   style-src 'sha256-…';
img-src 'self' data: blob: https: http:;   connect-src 'none';
worker-src 'self';   manifest-src 'self';
object-src 'none';   frame-src 'none';   form-action 'none';   base-uri 'none';
require-trusted-types-for 'script';   trusted-types default
```

Esta é a política do perfil `app` (o `index.html`). `pwa/csp.ts` tem dois perfis, `CspProfile = 'app' | 'static'`, parâmetro obrigatório de `buildCsp`, `injectCsp`, `verifyCsp` e `applyCsp`. O perfil `static` (o guia `public/guia/`, gerado por `scripts/guia.ts`, e a demo do visualizador, `viewer/demo/`) tem `img-src 'self' data: blob:` e não exige Trusted Types. O guia monta o painel com `innerHTML` não vazio (dados do exemplo, escapados) e a demo não carrega a política `default`; nenhum dos dois mostra imagem remota, então neles a imagem para fora continua barrada pelo navegador. O resto desta seção descreve o perfil `app`.

**Por que existe.** A app já não faz nenhuma requisição de rede com dados do usuário, mas isso era só uma promessa do código. Com `connect-src 'none'` (e `default-src 'none'`) o navegador passa a recusar `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, fontes e frames de qualquer origem, inclusive a nossa: um bug, uma dependência comprometida ou um JSON malicioso aberto na app não conseguem tirar o projeto do dispositivo por esses caminhos. **Imagens são a exceção:** o `img-src` libera `https:` e `http:` (um componente pode exibir uma imagem por URL, de qualquer origem; ver "Modelo de ameaças (imagens remotas)" abaixo), e o que impede a imagem de virar canal de saída deixa de ser só a CSP. `form-action 'none'` e `frame-src 'none'` fecham os caminhos por formulário e `iframe`; `base-uri 'none'` impede reescrever as URLs relativas; `object-src 'none'` desliga plugins.

**Como é gerada.** `pwa/csp.ts` (funções puras) e o plugin `contentSecurityPolicy` do `vite.config.ts`. O plugin roda **depois** do vite-plugin-singlefile (que tem `enforce: 'post'` e embute o JS e o CSS no `generateBundle`) e **antes** do `serviceWorker()`, porque o hash do build que o `sw.js` carrega precisa enxergar o HTML já com a política. Para cada bloco `<script>` e `<style>` do HTML final ela calcula o SHA-256 do conteúdo exato (com CRLF normalizado, como o navegador faz) e o põe em `script-src`/`style-src`. Por isso a política **não pode ser escrita à mão no `index.html` de origem**: qualquer mudança no bundle muda o hash. No `npm run dev` não há CSP (o Vite injeta scripts inline para o HMR); ela só existe no build, que é o que é publicado e o que os testes E2E abrem.

**O build falha** (`verifyCsp`, chamado por `applyCsp`) se: a CSP faltar; uma diretiva fixa for alterada; houver `'unsafe-*'`; algum bloco embutido não tiver hash correspondente (ou sobrar hash sem bloco); houver `<script src>`, `<link rel="stylesheet">`, `style=""` ou handler inline no HTML. No perfil `app` ele acusa também: `img-src` diferente de `'self' data: blob: https: http:`, falta de `require-trusted-types-for 'script'` ou de `trusted-types default`, e a ausência de `<meta name="referrer" content="no-referrer">` no `index.html`. No perfil `static` a conferência é a de antes (`img-src 'self' data: blob:` exato) e as diretivas de Trusted Types são acusadas, porque não podem estar lá. `tests/app/cspBuild.test.ts` cobre cada caso.

**O que a CSP permite e por quê.**

| Diretiva                                             | Valor                    | Motivo                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `script-src`, `style-src`                            | só os hashes dos blocos  | O app é um arquivo só: um JS e um CSS embutidos. Estilos aplicados por JS (CSSOM: `el.style.x = …`, `style.setProperty`, o objeto `style` do Preact e o Konva) **não** são bloqueados; o atributo `style=""` e `setAttribute('style', …)` são.                         |
| `img-src 'self' data: blob: https: http:`            | próprio, data, blob, web | Ícones (`./icons/…`), imagens do projeto (URLs `blob:`), imagens embutidas e, imagens por URL de qualquer origem. Fixo: o interruptor de `http:` é da app (política de URL), não da CSP; não há variável de build. `createImageBitmap` e o canvas não passam pela CSP. |
| `require-trusted-types-for 'script'`                 | —                        | Os sinks de HTML e de script (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `script.src`, `navigator.serviceWorker.register`…) só aceitam valores de uma política de Trusted Types. Ver "Trusted Types" abaixo.                                    |
| `trusted-types default`                              | só a política `default`  | Criar qualquer outra política (`trustedTypes.createPolicy('x', …)`) é recusado pelo navegador.                                                                                                                                                                         |
| `connect-src 'none'`                                 | nada                     | A regra central. O service worker não é afetado: ele roda em outro contexto e a política da página não vale para ele.                                                                                                                                                  |
| `worker-src 'self'`                                  | `./sw.js`                | Registro do service worker (só em `https:`; em `file://` não há service worker e a diretiva fica sem uso).                                                                                                                                                             |
| `manifest-src 'self'`                                | `./manifest.webmanifest` | O `<link rel="manifest">` é inserido por `attachManifest()` só em `https:`.                                                                                                                                                                                            |
| `object-src`, `frame-src`, `form-action`, `base-uri` | `'none'`                 | Sem plugins, sem frames, sem envio de formulário (os formulários da app usam `onSubmit` com `preventDefault`) e sem `<base>`.                                                                                                                                          |

#### Trusted Types

A política `default` fica em `src/app/trustedTypes.ts`, importada **antes de qualquer outro código** em `src/main.tsx`. Ela aceita só o que a app usa de fato:

- `createHTML`: apenas a string vazia (o Konva faz `container.innerHTML = ''`; o Preact só usa `innerHTML` com `dangerouslySetInnerHTML`, que o código não usa);
- `createScriptURL`: apenas exatamente `'./sw.js'` (constante `SERVICE_WORKER_URL`). O Chromium trata `navigator.serviceWorker.register` como sink de `TrustedScriptURL`; sem isso o service worker não registraria. É a única exceção à regra "só a string vazia", decidida pelo dono em 2026-10-31;
- sem `createScript`.

Qualquer outro HTML, script ou URL de script é recusado pelo navegador (`TypeError` e violação `require-trusted-types-for`), e outra política (`createPolicy` com outro nome) também (`trusted-types default`). Navegador sem Trusted Types: a política não é instalada e o resto da CSP continua valendo. **Regra prática:** nada de `innerHTML`, `outerHTML`, `insertAdjacentHTML` nem `dangerouslySetInnerHTML` com conteúdo, nem `script.src`; monte o DOM por JSX ou `textContent`. Se aparecer um uso novo legítimo, pare e registre no PR em vez de afrouxar a política.

#### Referrer

O `index.html` leva `<meta name="referrer" content="no-referrer">`: nenhum pedido que a página faça (imagem remota incluída) informa de qual endereço ela veio. O `verifyCsp` exige a meta no perfil `app`.

#### Imagens remotas: política, consentimento e carregador

O nó `image` de um componente (`src` literal ou exatamente `{ "$field": "<campo>" }`, campo `string` ou coluna `string` da `table`
num `repeat`; `$concat`, `$switch` e outras expressões no `src` são erro do parser, para o componente não montar uma URL com valores
de outros campos e enviar dados do projeto a quem escreveu a especialização) pede uma imagem por URL. `width`/`height` `hug` é erro: a
arrumação nunca depende da imagem baixada. A especialização não declara origens.

- **Primeira porta, a política** (`model/remoteImages.ts`, pura, só `URL`): `checkRemoteImageUrl(value, { allowHttp,
allowLocalNetwork })` devolve `{ ok: true, url, origin, local }` ou `{ ok: false, reason }` (`empty`, `invalid`, `insecure`,
  `credentials`, `too-long`, `private-host`). Só `https:` (e `http:` com o interruptor ligado), sem usuário e senha, até 2048
  caracteres; IP literal, `localhost`, nome sem ponto e sufixos `.local`, `.localhost` e `.internal` são recusados enquanto o
  interruptor de rede local estiver desligado.
- **Segunda porta, o consentimento** (`storage/imagePermissions.ts`): por **origem** (esquema incluído, então `http://a.com` e
  `https://a.com` são origens diferentes), por navegador, só no `localStorage` com try/catch. **Nunca** vai para o projeto, a
  especialização, o zip nem a proposta (um projeto de terceiros não pode se autorizar, e um `id` de especialização reaproveitado não
  herda permissão) e nunca é automático. A faixa acima do canvas (estado derivado em `store/derived.ts`) lista as origens novas do
  projeto aberto, com **Permitir estas** e **Agora não** (o padrão, válido para a sessão); uma origem nova que apareça depois
  (edição, MCP, proposta) a faz voltar só com ela. Configurações › Privacidade lista as origens permitidas com **Revogar** e tem
  três interruptores, todos desligados por padrão e com aviso: **qualquer origem** (sem faixa; a rede local continua pedindo
  consentimento próprio), **imagens sem criptografia (`http:`)** (separado do anterior) e **rede local**. Um quarto, **servidores
  sem CORS**, permite a tentativa descrita abaixo. Vale igual no somente leitura e nas duas visões da revisão.
- **Carregador** (`canvas/components/imageLoader.ts`, o único lugar que cria `Image` para URL remota): `crossOrigin = 'anonymous'`
  e `referrerPolicy = 'no-referrer'`; até 6 em paralelo, 20 s de tempo limite, recusa acima de 8192 px de lado ou 40 MP, exibe um
  bitmap reduzido a 2048 px no lado maior, cache em memória por URL (64 entradas, `close()` adiado para o quadro seguinte) e falha
  não repetida na sessão. Estados por imagem: `loading`, `loaded`, `opaque`, `blocked-consent`, `invalid`, `failed`, `too-large`;
  todos menos `loaded` e `opaque` desenham o reservado. `canvas/components/remoteImages.ts` faz a ponte (política, consentimento,
  carregador) para o canvas principal e para a galeria do Catálogo; falhas vão ao Diagnóstico, uma vez por URL.
- **Sem CORS:** com o interruptor ligado, o carregador tenta primeiro com `crossOrigin` e, se falhar, **uma vez** sem ele; a imagem
  fica `opaque`. Imagem `opaque` só é desenhada no canvas principal. **Toda leitura de pixel** (`toDataURL`, `toBlob`,
  `getImageData`, `toCanvas`) usa o reservado no lugar dela: a única leitura sobre camada com imagem é a da galeria do Catálogo
  (`canvas/components/exampleImages.ts`, sempre `pixelSafe: true`); o minimapa não lê pixel e os recortes só leem imagens do
  projeto (`blob:`). `tests/canvas/pixelReads.test.ts` falha se aparecer uma leitura nova fora dessa lista.
- **Limites conhecidos:** na app publicada em `https:`, o Chrome e o Edge tratam `http:` como conteúdo misto (tentam `https:` e,
  sem ele, a imagem fica `failed`) e podem bloquear o acesso de um site público à rede local ou pedir permissão própria; ambos
  funcionam de fato pelo `file://`. A app não contorna.
- **MCP e visualizador:** o servidor **nunca baixa** imagem: desenha o reservado em `get_marking_image` e devolve a URL como texto
  nos valores (o agente só grava URL que veio da origem do trabalho ou do dono, nunca uma inventada). O visualizador embutível tem a
  opção `remoteImages`, desligada por padrão; ligada, segue a política de URL e recebe do hospedeiro uma função
  `allowOrigin(origin)` (padrão recusar tudo), sem consentimento próprio; a CSP é do site hospedeiro.

#### Modelo de ameaças (imagens remotas)

Uma imagem só é pedida à rede quando as **duas portas na app** concordam: a URL passa na política (`src/model/remoteImages.ts`; `http:` só com o interruptor ligado) **e** a origem tem consentimento neste navegador (ou o interruptor "Permitir imagens de qualquer origem" está ligado). A CSP fica por cima, liberando `https:`/`http:`. Quem cobre cada ameaça:

| Ameaça                                                                                                                 | Quem a cobre                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T1. Vazamento de dados do projeto por código injetado ou bug (`new Image().src = 'https://x/?d=…'`)                    | O navegador já não bloqueia a imagem para fora. Cobrem: `script-src` só com hashes (nenhum script injetado roda) e Trusted Types (nenhum HTML injetado), um só criador de imagem (regra de lint); `src` restrito a literal ou `{ "$field" }`. `connect-src 'none'` continua. |
| T2. Rastreamento de quem abre o projeto (IP, hora) por quem escreveu a especialização, a proposta ou a anotação        | Consentimento por origem, por navegador; `no-referrer`; sem credenciais.                                                                                                                                                                                                     |
| T3. URL maliciosa num valor de campo (agente pelo MCP, proposta, edição)                                               | Política pura no modelo: só `https:`, sem usuário e senha, até 2048 caracteres, sem host privado.                                                                                                                                                                            |
| T4. Exaustão de memória (imagem enorme) e excesso de requisições                                                       | Carregador com limite de concorrência, tempo limite, tamanho máximo decodificado e bitmap de exibição reduzido; cache só em memória, com despejo.                                                                                                                            |
| T5. Canvas contaminado quebrando a galeria do Catálogo                                                                 | `crossOrigin = 'anonymous'` por padrão; servidor sem CORS: a imagem não carrega e fica o reservado. Com o interruptor de CORS ligado, a imagem `opaque` só é desenhada no canvas principal e nunca é lida de volta.                                                          |
| T6. Rede privada (roteador, `localhost`, serviços internos)                                                            | Interruptor de rede local desligado por padrão: IP literal, `localhost`, nome sem ponto e sufixos `.local`, `.localhost`, `.internal` são recusados na política (`private-host`); ligado, cada origem local pede consentimento próprio, nem o "qualquer origem" a cobre.     |
| T7. Persistência e reenvio de conteúdo de terceiros                                                                    | A imagem nunca é gravada: nem no projeto, nem no zip, nem no IndexedDB, nem no cache do service worker (`pwa/sw.js` já ignora pedido de outra origem). Só a URL (texto) fica no `mapping.json`.                                                                              |
| T8. Servidor MCP fazendo requisições em nome do agente                                                                 | O MCP **nunca** baixa imagens: desenha o reservado e devolve a URL como texto.                                                                                                                                                                                               |
| T9. Imagem por `http:` (a URL, com tokens, e a imagem trafegam sem criptografia e podem ser lidas ou trocadas na rede) | Interruptor desligado por padrão, consentimento separado da origem `http`, aviso na faixa e em Privacidade; a imagem trocada não roda código (é decodificada como imagem, sem script).                                                                                       |
| T10. Cookies do site em imagem sem CORS                                                                                | Interruptor desligado por padrão, aviso, `no-referrer` e uma só nova tentativa.                                                                                                                                                                                              |

**Um só criador de imagem.** A regra `imageCreationSyntaxRules` do `eslint.config.js` proíbe `new Image`, `createElement('img')`, atribuição a `.src`/`.srcset`, `setAttribute('src'|'srcset')` e `fromURL` em `src/**` e `viewer/**`, exceto em `src/canvas/components/imageLoader.ts` (o carregador) e em `src/storage/**` (as imagens do projeto, por `blob:`). Teste em `tests/tooling/imageCreationLint.test.ts`. Assim nenhum código novo monta URL de imagem por fora da política.

**Ameaça residual.** Um bug no nosso código que ponha dados numa URL de imagem não é mais barrado pelo navegador (antes era). Quem controla uma origem consentida fica sabendo quando e de qual IP o projeto é aberto e quais marcações aparecem na tela. E um agente ou uma proposta pode pôr uma URL de origem nova: ela só é pedida depois do consentimento daquela origem, ou na hora se o interruptor "qualquer origem" estiver ligado.

**Download, compartilhamento, área de transferência e arrastar e soltar** não dependem da CSP: baixar o zip usa o "Salvar como" do sistema (`showSaveFilePicker`, gravado pelo `createWritable` do handle) onde ele existe (Chrome e Edge, inclusive em `file://`) e, sem ele, um clique em `<a download href="blob:…">` (navegação/download não é governada por `default-src`); `navigator.share` e `navigator.clipboard` são APIs do navegador (copiar a referência grava o texto primeiro, com `writeText`, sempre permitido, e só acrescenta o formato personalizado quando `clipboard-read` já está concedida, porque gravar formato `web …` exige essa permissão e a app não pede permissão ao copiar); arrastar, soltar e colar chegam como `File`/`DataTransfer` dentro da página. O aviso "Alterações não exportadas" de um projeto neste dispositivo (`markExported` em `app/controller.ts`) só sai quando o arquivo saiu: pelo seletor, depois do `close()` da gravação; pelo compartilhamento, quando a promessa de `navigator.share` resolve. Cancelar o seletor ou o compartilhamento (`AbortError`) não muda nada, e uma falha de gravação mostra o erro no diálogo. Pelo `<a download>` a app não sabe se a pessoa salvou: o aviso sai no clique e o diálogo avisa que, se ela cancelar o salvamento, precisa exportar de novo (`app/ExportDialog.tsx`, `storage/share.ts`).

**Dependências.** O zod 4 testa `Function('')` para gerar validadores compilados; sob a CSP isso vira uma violação (capturada, mas registrada no console e emitida como `securitypolicyviolation`). `src/utils/zodConfig.ts` (importado primeiro por `main.tsx`) liga `jitless`, e o zod usa o caminho interpretado, sem `eval`. JSZip só usa `new Function` num _fallback_ de `setImmediate` que não é alcançado nos navegadores suportados.

**Para quem mexer na app.** Estilo dinâmico: use propriedades CSS (`--var`) pelo objeto `style` do Preact; não use `dangerouslySetInnerHTML` com `style=""`, `<style>` injetado em runtime, `eval`, `new Function`, `import()` de URL externa nem `fetch`. Também não use `innerHTML` com conteúdo nem `script.src` (Trusted Types), e não crie imagem por URL fora do carregador. Se uma funcionalidade nova precisar de rede, ela exige decidir de novo a política (e o que se promete ao usuário no README), não afrouxar a diretiva.

**Testes.** `tests/e2e/csp.spec.ts` (Playwright): a `<meta>` vem antes de qualquer recurso; `fetch`, XHR, WebSocket, EventSource, imagem externa, `eval`, `<script>` inline e `setAttribute('style')` são bloqueados e nenhum pedido sai da página; o fluxo principal (criar projeto, adicionar imagem, marcar, anotar, copiar ID, arrastar e colar imagens, exportar o zip) termina com **zero** eventos `securitypolicyviolation`; o compartilhamento do zip (Web Share simulado) e a abertura por `file://` também. `tests/e2e/cspServiceWorker.spec.ts`: servidor `https` local (como o GitHub Pages) com a versão principal em `/` e um build de preview (`VITE_CHANNEL=preview`) em `/preview/`: instalação do service worker, precache, uso offline, aviso de "Nova versão disponível" ao mudar o `sw.js`, e os dois service workers convivendo, sem violações. Esse teste usa `openssl` e `--ignore-certificate-errors` (o service worker não registra com certificado autoassinado sem ele).

### Build e PWA

`vite.config.ts` usa `vite-plugin-singlefile` (um só `index.html`) e carimba `pwa/sw.js` com um hash do build, que é o que faz o navegador detectar "nova versão". `VITE_CHANNEL=preview` (ver `src/utils/channel.ts`) separa armazenamento, manifest e service worker do preview.

**Preview isolado.** O deploy publica a `main` em `/` e o branch em `/preview/` no mesmo artefato do Pages; a produção nunca é substituída (um push na `main` publica só a `main`). O build do preview, com `VITE_CHANNEL=preview`, acrescenta o sufixo `-preview` ao nome do banco IndexedDB e o prefixo `preview:` às chaves do `localStorage` (assim nunca migra nem apaga os projetos da versão principal), mostra uma faixa fixa avisando que os dados são separados, usa o nome "Mapping (preview)" no manifest (`PREVIEW_APP_NAME`, `pwa/build.ts`) e registra o service worker no escopo de `/preview/`.
