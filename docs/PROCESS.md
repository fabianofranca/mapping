# Delivery process

Rules of the delivery workflow: issue planning, epics, phases, tester, code review and model use (the step by step and the messages are in [`docs/FLOW.md`](FLOW.md) and in the skills). Whoever does delivery work reads this file and `CLAUDE.md`, in the sections that apply; the tester reads only `docs/TESTING-NUVEM.md`; code subagents receive the rules in the briefing.

## Workflow

- The owner uses Claude Code from a phone; the **session start** is in `CLAUDE.md`, "Workflow (summary)".
- **Issue planning** (owner's decision of 2026-11-02): the roadmap and the stage plans live in issues of `fabianofranca/mapping`, never in a repository file. No PR exists only for a plan.
  - **Labels:** `roadmap` is an idea, improvement, migration or pending item without a plan; `bug` is a defect: what contradicts the specification or the docs (including `docs/TESTING.md`), an accessibility failure, a flaky test, a doc or script that does not match the app, or raising the `dist/index.html` ceiling above the limits (a review request to the owner, `severity: low`; `docs/FLOW.md`, item 6); `ready` is the detailed stage (plan, decisions, `step`s and model table); `in-progress`, the stage whose epic has started; `step`, the sub-issue of a phase; `severity: high|medium|low` belongs to the `bug` (see "Bugs and visual evidence"); `impact: high|medium|low`, to the `roadmap` (see "Impact"), and stays on it in `ready` and `in-progress`. `code-review` marks the code reviewer's issues (round and `bug`s; see "Code review"). `via-rapida` marks a released fast track: a `roadmap` or `bug` that the queue runs in a slot, as `/via-rapida #<n> fila=<id>` (the owner sets it, or the fast-track session on a conflict, with a `Via rápida: espera #N` comment); the session removes it when it starts or is refused, and re-adding it after a refusal brings the issue back to the queue; `detalhar-backlog` skips it. `observador-da-fila` marks #1644 and the issues the observer opens (`roadmap` with `impact:`). A new issue is `roadmap` **or** `bug`, never both. `bug`, `code-review` and `observador-da-fila` are a **type**, not a state: they stay until the issue closes, even in `ready` and `in-progress`. The cycle is `roadmap` or `bug` → `ready` → `in-progress`; nothing is implemented before `ready` (or `in-progress`, when resuming), except the fast track, which takes the issue straight to `in-progress`.
  - **Impact:** every open `roadmap` has exactly one impact label, set on creation, with the line `Impacto: <level> — <why>` in the body; the `bug` does not carry one (it has the severity). It measures how much the item changes the use of the tool (app, MCP, agents' workspace) and the recurring cost of the delivery workflow; the size of the work does not count:
    - `impact: high`: a new or unlocked capability at the core of the tool (marking, organizing, annotating, saving, mapping through the MCP), or a change that weighs on every use or every stage of the workflow;
    - `impact: medium`: a noticeable improvement in a frequent flow; accessibility; or lower recurring cost of the delivery workflow (tester, sessions, CI);
    - `impact: low`: polish, migration or refactoring without a perceived gain, or a rare or unreproduced observation;
    - when in doubt between two levels, the higher one applies, with the reason in the body. Whoever changes the impact swaps the label and comments why (the agent proposes, the owner decides).
  - **Detailing a stage:** the `roadmap` or `bug` issue becomes the stage issue (swap `roadmap` for `ready`; the `bug` and the `impact:` stay; a `ready` issue created directly, if it is not a `bug`, gets the impact; or the new `ready` cites and closes the `roadmap` or `bug` as a duplicate). The body has the goal, what stays out, numbered decisions, the epic (`epic/<name>`), the versions (schema, formats, MCP) and the table of models and effort (an **Orquestrador** row, one per phase, a Tester column; see "Automated flow"). Each phase is a `step` sub-issue (`parent_issue_number`) with the table row, the **Toca em:** (files, or a pattern with a prefix, and sections, never a folder or a whole document: `docs/TESTING.md#R12` per script; the `.md` files of `docs/` and of the root and the `SKILL.md`s by the `##`, `docs/ARCHITECTURE.md#performance` and `CLAUDE.md#<slug>`; `docs/TESTING-NUVEM.md#full-round-in-blocks` for the block table; the section of `.claude/skills/spec-author/SKILL.md` and of `docs/AGENT-GUIDE.md` in a trigger of the "Agent impact"; details in `detalhar-backlog`), the checkboxes and the acceptance criteria. The **last phase** has the **Testador** section, with the scripts and the line "Passada visual: `<list>`" (or "Passada visual: nenhuma").
  - **During the stage:** each phase's PR starts with "Parte de #<sub-issue>" (a PR to the epic does not close an issue by itself); the phase agent ticks the checkboxes in the sub-issue and closes it (`completed`) after the merge into the epic. A decision that changes the plan is edited into the issue body and commented with the reason. The epic's PR to `main` carries "Closes #<stage issue>".
  - **Defect found during the stage**: a defect that appears in the implementation (in a phase session, in the tester's report — ❌ or an observation that is a defect — or in the closing) is **fixed in the stage itself**, with no `bug` issue, when it does not need an owner decision. It also applies to a defect that predates the stage.
    - **Needs an owner decision** (not fixed alone): the expected behavior is not in a decision of the issue, doc, spec or script, or there is more than one reasonable reading (a product decision); the fix changes a decision already made in the issue; it touches the schema or a format; it does not fit in a fix (it would need phases of its own); or the defect is about data loss, `mapping.json` integrity or security (that one calls the owner immediately).
    - **Where it is fixed:** in the phase where it appears, if it fits what the phase touches, with test first and the item under "Fixed outside the plan" in the PR Summary; otherwise the phase lists it under "Defeitos pendentes" in the notice to the orchestrator, and it enters the fix phase with the ones from the report.
    - **It becomes an issue** only if it needs an owner decision (the body says what the decision is, with the options) and the defect found after the fix phase (there is only one per stage). If an open issue already exists for the fixed defect, the PR cites it and the closing closes it (`completed`).
    - The closing lists in the stage issue the defects fixed outside the plan (origin and PR); what is noticed in the app or in the MCP goes under `## Corrigido` in the `changelog/`. The owner's standalone round (without a stage) fixes nothing.
  - **Closing:** the closed issue is the history. The closing comments on it the decisions of the PRs, the test reports and what was left for later; each item left for later becomes a `roadmap` issue (with the impact label) or a `bug` (a defect, with the evidence; only when it needs an owner decision, see "Defect found during the stage").
  - **Project:** the agent cannot reach the Project "Mapping - Backlog" (the issue enters by auto-add or through the owner). Every agent text on GitHub ends with the attribution footer.
- **Bugs and visual evidence:** a defect is a `bug` issue, never `roadmap`; the image that shows it goes in the orphan branch `evidencias`, because the GitHub API does not attach an image to an issue. A defect found during a stage follows "Defect found during the stage": it only becomes an issue if it needs an owner decision.
  - **Before creating, look for duplicates** among the open and closed issues, by label and by keyword. Identical (same behavior, same cause): do not create; comment the new origin on the existing one. Groupable and not yet `ready`/`in-progress`: it enters it as a numbered item; already `ready`/`in-progress`: a new issue with "Relacionada: #N". Regression of a closed issue: a new issue that cites it, without reopening. The body records the search ("Duplicadas: nenhuma (busca: <terms>)" or "Relacionada: #N"). The cases and the commands are in [`docs/FLOW.md`](FLOW.md) ("Bug: duplicate search").
  - **Severity:** every open `bug` has exactly one severity label, set on creation (only `bug` carries it; `roadmap` carries `impact:`, and the `bug` never does; a `roadmap` that becomes a `bug` swaps the `impact:` for the `severity:`):
    - `severity: high`: data loss, a corrupted `mapping.json`, a save that fails silently, a project that does not open, a security flaw, or a flow that cannot be completed without a workaround (on the report scale of `docs/TESTING.md`: **blocks** and **high**);
    - `severity: medium`: there is a workaround, but whoever has not read the guide trips; it includes an accessibility failure with a workaround, a flaky test and a broken test helper (**medium**);
    - `severity: low`: cosmetic, text, or a doc or script that does not match the app without leading to an error (**low**);
    - an issue that groups several defects carries the highest severity among them (each item states its own); when in doubt between two, the higher one, with the reason in the body. Whoever changes the severity swaps the label and comments why.
  - **Bug body and evidence:** what happens; the expected behavior and where it comes from; steps to reproduce; branch and commit; origin; severity and why; the duplicate search. A visible defect carries a cropped PNG capture, with no personal data or secret; what cannot be seen carries the test output or the DOM excerpt. Details in [`docs/FLOW.md`](FLOW.md) ("Bug: body and evidence").
  - **Procedure:** the issue is created first, to get the number; the image goes to `<issue>/<name>.png` in the `evidencias` branch (`<issue>` is the issue or sub-issue where it first appears) and the issue body cites it with `![short description](https://github.com/fabianofranca/mapping/blob/evidencias/<issue>/<name>.png?raw=true)`. The commands are in [`docs/FLOW.md`](FLOW.md) ("Bug evidence"). The worktree of that publication is the exception to "Session start".
  - **No push:** if it is not possible (permission, network), the issue describes in text what the capture shows, says it was sent in the session chat, and the file goes to the chat (`SendUserFile`).
- **Everything reaches `main` through an epic.** Each stage (or front that should only reach `main` after being validated whole) is a branch `epic/<name>` with a PR to `main`, open until the end. Each phase, or part of a phase, is a short branch and a PR **based on the epic branch**, with the usual description; once merged, it goes away. A small stage is an epic of one part. The epic PR's description is finalized once, when the owner decides to merge. `main` enters the epic by merge (never rebase or force-push).
- **Fast track:** a small process tweak goes in an epic of one PR, without `ready` or phases (`.claude/skills/via-rapida/SKILL.md`).
- **Changelog per epic:** each epic has a file in `changelog/` (rule, format and order in [`changelog/README.md`](../changelog/README.md); English, Keep a Changelog format): the epic creates `changelog/<name>.md` (`<name>` is the branch without `epic/`, with `[Não lançado]` in the title) and the closing renames it to `changelog/AAAA-MM-DD-<name>.md`, with the date in the title; the `epic` job of `ci.yml` fails if the epic's PR to `main` does not carry one of the two names.
- **Design system per epic:** the design system is the **Mapping** artifact of Claude Design, curated by hand and outside the repository; its record is [`docs/DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md) (URL, component → code map, triggers) and, per epic, `docs/design-system/<name>.md`. Every phase declares the **DS impact** in the PR and, with impact, records the pending item under `## Pendências` of that file in the same PR (the epic's first PR creates it with `[Não lançado]` in the title). Only the **epic closing** writes to the DS (`DESIGN-SYSTEM.md` › "When writing"; the index is read right before): it writes the pending items, fills in `## Sincronização`, moves what it did not write to `## Ficou sem gravar` and renames the file to `docs/design-system/AAAA-MM-DD-<name>.md` (the `epic` job fails without one of the two names). The `/design-sync` skill **does not apply**: it expects the `dist/` of a published library.
- **`main` only accepts PRs from `epic/*`:** the `epic` job of `ci.yml` fails for any other origin (except `dependabot/*`) and is a required check in the "main protegida" ruleset. CI runs only on PRs, once per commit (editing the PR does not run CI): a branch without a PR has no CI. There is only one preview, the one from the last green PR ([`docs/FLOW.md`](FLOW.md), "CI and preview"). `ci-rerun.yml` reruns the CI of an abandoned runner.
- **MCP version per epic** (`mcp/version.ts`, one per epic): each PR based on an `epic/**` generates a snapshot (`mcp-snapshot-pr<N>`); the release candidate (`mcp-v<version>-rc.<n>`) comes out only on the merge of the PR with the `mcp-rc` label, the last phase's (that phase's agent sets it; if missing, run the MCP pre-release workflow); the stable `mcp-v<version>` comes out by itself on the merge of the epic into `main` when the version is new (`mcp-release.yml`, which deletes the rcs). The version is provisional until the closing, which picks the next free one on `origin/main` and swaps the changelog title. The epic PR fails, in the "Versão do MCP" step of the `epic` job, if what goes in the release changed without raising the version (the list is in `scripts/release/releaseInputs.mjs`).
- **Automated flow**. The ready-made messages and the orchestrator's step by step are in [`docs/FLOW.md`](FLOW.md) ("Orchestrator — step by step"); the rules stay here. Three chats, and each one is a subject:
  1. **Roadmap:** the agent creates a short `roadmap` issue (with the impact label and the `Impacto:` line) or `bug` (problem or idea, origin, what is known), without phases or a plan; the `bug` follows "Bugs and visual evidence".
  2. **Detailing** (Fable/Opus): the `roadmap` or `bug` becomes `ready` as in "Detailing a stage", with the `step` sub-issues and the model table (an **Orquestrador** row and a Tester column). A product decision is asked of the owner in that chat.
  3. **Implementation:** the owner opens the chat on the model of the Orquestrador row (default Sonnet), in **Auto** mode, and asks for the stage. The **orchestrator** only implements a `ready` issue, swaps `ready` for `in-progress`, creates the `epic/<name>` from the updated `main` and runs the phases in order, one child session per phase (the table's `model`, never `permission_mode: plan`), and moves to the next only after the previous one's notice (fallback check by `send_later`).
  - **Tester:** after the last phase, the orchestrator creates the tester session in the "Mapping - testes" environment with the scripts and the visual pass of the last phase's sub-issue. The full round goes in **one session per block** (`bloco k de n`, `docs/TESTING-NUVEM.md`); the directed one with more than 40 steps without R0 goes in groups (`round-guide.mjs --grupos`, up to 5 sessions, `grupo k de n`). The summary goes in the sub-issue without rewriting the reports; the findings carry the code `k.n`. The tester ([`docs/TESTING-NUVEM.md`](TESTING-NUVEM.md)) builds the app and the MCP of the commit, posts the report as a **comment on the sub-issue** and notifies the orchestrator by `send_message`. No Windows/Edge coverage; the on-demand scripts are the owner's.
  - **With ❌ or a pending defect** (the "Defeitos pendentes" of the phase notices and the report observations that are defects and do not need an owner decision), it opens **one** fix phase and retests only the steps that failed and the steps the fixes affect, **in a single session** with the findings of all groups or blocks. With the findings **all of low severity** (low; owner's decision, 2026-11-13), the fix goes to the closing **without a retest** (the check before and after is enough); in a mixed round the retest covers only the high and medium ones, and a low one that the fix does not reproduce gets a retest of just that. An observation that is a defect and a pending defect get a severity from the scale in section 7 of `docs/TESTING.md`, the higher one when in doubt. The orchestrator calls the owner if the fix fails again, if the finding is about data loss, `mapping.json` integrity or security, or if it needs a product decision.
  - **Without ❌ and without a pending defect,** it does the closing ("Closing", above, plus the changelog and the DS record renamed with the date and the "Closes #<stage>" in the final description of the epic's PR).
  - **Merge:** the orchestrator notifies the owner on the phone (`PushNotification`) and merges the epic into `main` **only after the owner answers "pode mesclar" in the chat** (if the "main protegida" ruleset requires an approval the agent cannot give, the owner presses the button). After the merge, it checks the MCP Release (`docs/FLOW.md`; on failure, it notifies the owner with the link and the plan B of `docs/MCP.md`); outside the automated flow, whoever merges checks the same way.
  - **The phase session** opens the PR to the epic ("Parte de #N"), follows the CI and, with a green CI, **merges its own PR into the epic**; then it ticks the checkboxes, closes the sub-issue and notifies the orchestrator by `send_message` (a session that ends well does not notify by itself). A product decision outside the sub-issue goes to the orchestrator, who calls the owner; a defect found along the way follows "Defect found during the stage".
  - **Limitations:** a child session does not have more permission than the orchestrator and, if it asks for permission, it stalls; that is why the implementation chat stays in **Auto** mode.
  - **Outside the automated flow** (a manual stage), the owner opens each phase, the first phase's agent swaps `ready` for `in-progress`, and the last one's creates the tester and reads the report: without ❌, the round is accepted; with ❌, it talks to the owner before fixing (the pending defects enter that conversation). The epic PR stays with the owner.
- **Code review** (owner's decisions of 2026-11-08 and 2026-11-10; how it runs in [`docs/FLOW.md`](FLOW.md), "Code review"): every epic merged into `main` without a `/code-review high` of the whole epic at the closing (`riskTriggers.mjs` gave `nenhum gatilho`) is reviewed whole, overnight, by the "CR por épico" schedule, in one reviewer session per epic. The reviewer only reads the code: the output is a round issue (`roadmap` + `code-review` + `impact:`) and one `bug` (+ `code-review` + `severity:`) per confirmed high or medium defect; the low ones stay in the round issue. The `code-review` issues follow the usual cycle.
- **Test scripts (`docs/TESTING.md`, section 8):** the main scripts (R0 to R17) are made for the cloud tester agent to run **alone**; every new or changed step needs a way for the cloud agent to do it (the cloud recipe of appendix A, Playwright over CDP, shell, an MCP client over stdio). A test that needs the owner and is **not very relevant** goes to the on-demand (manual) scripts. If it is **very relevant** (data loss, `mapping.json` integrity, security), the agent does not decide alone: it warns the owner in the conversation and in the PR, and the step is marked as pending a decision.
- Every PR description contains:
  1. **Summary** of what changed;
  2. **How to test**: objective manual steps on the desktop, remembering that the preview is published by itself with a green CI;
  3. **Decisions made** that were not in the issue (the ones that change the plan also go as a comment on the stage issue);
  4. **DS impact**: `none`, or the design system components, sections, tokens and icons that the change affects. Cross the phase's "Toca em:" with the triggers of [`docs/DESIGN-SYSTEM.md`](DESIGN-SYSTEM.md) (without opening the artifact); whatever is not `none` enters as a pending item in `docs/design-system/<name>.md`, in the same PR.
  5. **Agent impact**: `none`, or what changes in the `spec-author` skill (`.claude/skills/spec-author/SKILL.md`) and in [`docs/AGENT-GUIDE.md`](AGENT-GUIDE.md), the two sources that reach the workspaces' agents (the guide is embedded in `mapping-mcp.js`; the Mapping repository is not). The update goes **in the same PR**. Triggers:
     - **skill:** format of the specialization, the component or the library (`formatVersion`, field type, new key, validation rule, cited error message, migration);
     - **guide:** an MCP tool, parameter or operation, an error code, or a new modeling pattern.
     - The usage rules stay in the guide and the skill, never only in `examples/workspace/AGENTS.md`, which does not update itself in the workspaces.
     - What breaks: `tests/tooling/agentDocs.test.ts` (the skill and the guide say "A versão atual do formato é a N"; "13. Versão" of the skill lists `formatVersion` 1 to N; `docs/SPEC-FORMAT.md` has the row for each version) and `tests/mcp/agentGuideCoverage.test.ts` (every tool and every batch `op` in backticks in the guide).
- An ambiguous or infeasible issue: record the doubt in a comment on the issue and in the PR, instead of inventing a big behavior; a small detail, decide, carry on and document.

## Model use (saving quota without losing quality)

The owner wants to spend little of the most expensive model's quota: quality comes from the closed specification and the tests, not from the model that types.

- **A new session per subject.** Each turn rereads the whole session; once a topic is closed (PR open and described), the next one starts in another session. In the automated flow, each chat and each phase session is a subject; the PR, the stage issue and the `README`s are the input context.
- **The main model (Fable/Opus) does only what requires judgment:** understanding the request, deciding format and architecture, writing the subagents' briefing, reviewing what comes back, integrating and talking to the owner.
- **Sonnet subagents produce the rest** (code from a specification, components and examples, tests, documentation, PR description, scripts, CI log triage), at `medium` (`high` only for review or checking), always with a briefing that states the goal, the files to read, what stays out and the validation commands (`npx vitest run <files>`, `npx eslint`, `npx prettier --check`, `npx tsc --noEmit`) that must pass before returning. The briefing also requires **test first**: for a behavior change or a fix, the subagent writes the test that reproduces the behavior, runs it, sees it fail for the expected reason and only then changes the code; the return brings the test name and the failure seen. If an honest test is impractical, it says so in the return and the coordinator decides. Refactoring without a behavior change, documentation and mechanical work do not require a new test, but they require the existing tests to pass before and after.
- **Haiku for the mechanical** (renaming, formatting, sweeping logs, updating counts in tests). A small change and PR text also go through a subagent, from the briefing: size is not an exception.
- **Fewer round trips of the main model:** validate in batch (the gates once, at the end), one screenshot per delivery, short answers that stand on their own.
- **Never delegate without context:** the subagent only knows what is in the briefing; point to the files and the `CLAUDE.md` rules that apply.
- **Coordinator and effort defined per phase.** Each phase has a coordinator model (Fable, Opus, Sonnet or Haiku, from the most expensive to the cheapest): the one of the main session, which writes the briefings, reviews and integrates. Before starting, the session checks the model it runs on (`session_context.model` of `get_session` of `claude-code-remote`, if it exists; otherwise the identity in the system prompt). A model above the defined one: it does not run the phase, says which one is defined and asks the owner to switch; below: it warns and only continues if the owner confirms. With no model defined, the default of this section (Fable/Opus coordinates); the subagents do not change with the coordinator (Sonnet produces, Haiku does the mechanical). Each phase also defines the effort (`low`, `medium`, `high`, `xhigh`, `max`) of the coordinator and of the subagents; with no effort defined, `medium` for everything. The subagents' effort goes explicitly in the briefing, read from the sub-issue; the coordinator's goes in the `effort` of `create_session` (checked by the `effort_level` of `get_session`; if refused, the session is born without it); from `high` up it becomes the level of the `/code-review` of the phase's diff before the PR (`docs/FLOW.md`). The stage table also has the **Orquestrador** row (model of the implementation chat; default Sonnet) and the Tester column (default Sonnet, medium) and lives in the stage issue, with each phase's row repeated in the sub-issue. In the automated flow, the child session is already born on the table's `model`, and the refusal by model still applies.

## Stages

- **In progress:** the open `in-progress` issue and the open PR from `epic/*` to `main` (without an open `in-progress` issue, there is no stage in progress). **Ready:** the open `ready` ones. **Future:** the open `roadmap` ones, or `bug` without `ready`/`in-progress`; none is implemented before becoming `ready` with the phases, except the fast track.
- **Completed:** `changelog/` summarizes each delivery, one file per epic; the plan and the decisions stay in the closed `in-progress` issues; what came before (up to 2026-11-02) is in the git history. The "Uso real" (real use) milestone was reached on 2026-10-16.
- **Principle:** the core is generic, with nothing specific to Figma or another origin; platforms, languages and code components enter only through specializations (no platform name in the core code).
- **Tests:** [`docs/TESTING.md`](TESTING.md); the cloud tester's prompt, in [`docs/TESTING-NUVEM.md`](TESTING-NUVEM.md).
