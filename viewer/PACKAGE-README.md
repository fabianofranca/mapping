# mapping-viewer

Embeddable Mapping viewer: it draws **one screen** of components (a design system's library plus a screen description) in a container on your site, read-only, with real-time updates. The core does not depend on any framework; there is an optional React wrapper.

## Installation

Inside `dist-viewer/` (the folder generated by `npm run build:viewer` in the Mapping repository):

```bash
npm pack
# generates mapping-viewer-0.10.0.tgz
```

In the project that will use it:

```bash
npm install ./mapping-viewer-0.10.0.tgz
```

You can also copy the whole `dist-viewer/` folder into the project and import `mapping-viewer.js` by path.

## Core (no framework)

```ts
import { createViewer, loadLibrary, parseScreen } from 'mapping-viewer';

const library = loadLibrary(files); // files: { path, text?, bytes? }[]
const screen = parseScreen(JSON.parse(screenJson));

const viewer = createViewer(document.getElementById('preview')!, {
  library,
  screen,
  onClick: (id) => console.log('clicked', id),
});

viewer.update({ screen: newScreen }); // redraws only what changed
viewer.setSelection(['i-card']); // selection coming from your panel
viewer.dispose(); // when unmounting
```

The container must have a size; the framing redoes itself when it changes.

## React

```tsx
import { MappingViewer } from 'mapping-viewer/react';

<MappingViewer
  library={library}
  screen={screen}
  selection={selection}
  onClick={(id) => setSelection(id ? [id] : [])}
  fontsVersion={fontsVersion}
/>;
```

`konva` is a peer dependency (the range comes from Mapping's `package.json`): only for the types, because `ScreenRenderer` exposes `Konva.Group` in the declarations. npm 7 or newer installs it on its own and your project compiles with `skipLibCheck: false`; the code uses the copy of Konva embedded in the bundle.

`react` is an **optional** peer dependency: only whoever imports `mapping-viewer/react` needs it (18 or newer).

## Screen from an external JSON

When the screen comes from a backend (for example, a server-driven UI JSON), the specialization declares how to read it: `origins` (width, height, roots and the node keys) and `sources` on the types and fields (which external type each type corresponds to and from which `props` path each field comes). Instead of `screen`, pass the already parsed JSON in `source`:

```ts
const viewer = createViewer(el, {
  library,
  source: JSON.parse(json), // wins over `screen`
  sourceSystem: 'sdui', // optional: without it, the first origin
  onSource: ({ screen, warnings, error }) => showWarnings(warnings, error),
});

viewer.update({ source: otherJson }); // a new object recomputes; the same object does not
viewer.screen(); // the computed and drawn screen
```

In React: `<MappingViewer library={library} source={json} sourceSystem="sdui" onSource={...} />`. The screen is recomputed when the library or `source` change and on `redraw()`. With `error` (a JSON without width/height, for example) nothing is drawn; the warnings (unknown property, value outside the options, type without an annotation type) arrive in `warnings`.

To get the screen without drawing it, use `screenFromSource(library, json, { system?, measure })` (it returns `{ screen?, warnings, error? }` and never throws). `translateSource` returns only the tree without geometry (`LayoutScreen`) and `layoutScreen` lays it out by sizes.

## Screen from a file format

From `formatVersion` 22 a specialization has no `origins`: the **plugin of a file format** (`fileFormats`, with its `parse` function) reads the external file instead. `mapping-viewer/formats` is a separate entry that runs that plugin and gives the screens the viewer draws; the core does not change and only the host that imports it pays for it. The plugin runs in a sandbox of the host page (a hidden `<iframe sandbox="allow-scripts">` with a `blob:` Worker) that has no network, storage or access to the page, whatever the page's CSP: the sandbox document carries a CSP of its own. The page needs the three entries of the next section.

```ts
import { createViewer, konvaMeasurer, loadLibraryFromUrl } from 'mapping-viewer';
import { screenFromFormat, disposeFormatSandbox } from 'mapping-viewer/formats';

const library = await loadLibraryFromUrl('/libraries/sdui-backend/'); // also fetches each format's plugin
const result = await screenFromFormat(library, fileText, {
  format: 'sdui-backend/sdui', // <specId>/<formatId>
  measure: konvaMeasurer, // the one that draws, so the boxes match the drawing
  // fonts: the same `fonts` you give createViewer (default: the viewer's own, which is also createViewer's default)
});
if (result.error) showError(result.error.code, result.error.message);
else createViewer(el, { library, screen: result.screen }); // one `Screen` per container with components: `result.screens`
```

In React, the same call in an effect (the last one wins, and the sandbox goes away with the page):

```tsx
const [result, setResult] = useState<FormatScreenResult>();
useEffect(() => {
  let current = true;
  screenFromFormat(library, text, { format, measure: konvaMeasurer }).then(
    (r) => current && setResult(r),
  );
  return () => {
    current = false;
  };
}, [library, text, format]);
// …<MappingViewer library={library} screen={result?.screen} />
// A host that unmounts the page, once: disposeFormatSandbox().
```

`screenFromFormat(library, text, { format, measure })` returns a `Promise` that **never rejects**: `{ screens, screen?, warnings, error? }`. Each container that has component markings becomes a `Screen` (its size and boxes in the container's pixels divided by its density, ids that survive a re-read of the same text); `screen` is the first. `warnings` has the plugin's and the drawing values'. With `error` (`code`, `message` and, where the plugin threw, `line` and `column`), `screens` is empty:

| `error.code`                                                               | When                                                                                                                                          |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `format-not-found`                                                         | `format` is not `<specId>/<formatId>` of a format the library declares (the message lists them), or its plugin did not come with the library. |
| `spec-invalid`                                                             | The specialization of the library does not validate.                                                                                          |
| `plugin-failed`, `plugin-timeout`, `plugin-limit`, `plugin-output-invalid` | The plugin threw (with `line` and `column`), went past the 5 s limit, a size limit, or answered something invalid.                            |
| (the applier's code, e.g. `unknown-type`)                                  | The plugin's operations were refused (`operation <i> (<op>) refused: …`).                                                                     |
| `nothing-to-draw`                                                          | The file has no container with component markings.                                                                                            |
| `sandbox-unavailable`                                                      | The page's CSP or Trusted Types refuse the sandbox (next section). The rest of the viewer keeps working.                                      |

Only one plugin call runs at a time. The page is also a **secure context** (https or `localhost`): the plugin's result is applied with `crypto.randomUUID()`. `source`, `sourceSystem` and `onSource` of `createViewer` are unchanged and keep reading `origins` of specializations up to `formatVersion` 21.

`disposeFormatSandbox()` removes the iframe the entry made (one per page, created at the first call and kept): call it when a single-page host unmounts; the next call makes another. Load one copy of `mapping-viewer/formats` per page: a second copy asks for the `mapping-viewer` policy again, which a host without `'allow-duplicates'` in `trusted-types` refuses (the result is `sandbox-unavailable`).

## Content Security Policy of the host

The sandbox of the section above needs three things from the host's CSP; `FORMAT_SANDBOX_CSP` (exported by `mapping-viewer/formats`) has the exact values:

1. **`script-src`: the hash of the sandbox's only script**, `'sha256-0Fot2/lUbTdR3FiiVQdAaKvHyEBgTK6ZQgIXa8WcuKI='` (`FORMAT_SANDBOX_CSP.scriptSrc`). The iframe is a `srcdoc` one and inherits the page's policy; its script is allowed by hash, never by `'unsafe-inline'`. The hash changes when the package does: copy it from `FORMAT_SANDBOX_CSP.scriptSrc` of the version you install.
2. **`worker-src`: `blob:`** (`FORMAT_SANDBOX_CSP.workerSrc`): the plugin runs in a Worker made from a `blob:` URL.
3. **With Trusted Types, `trusted-types mapping-viewer default`** (`FORMAT_SANDBOX_CSP.trustedTypes`): `mapping-viewer` is the policy through which the viewer gives the iframe its document (it accepts only that document and nothing else), and `default` is the one the iframe's own document creates for its Worker. The host's own `default` policy, if it has one, is never used or touched by the viewer.

An example policy for a host with Trusted Types:

```
default-src 'none';
script-src 'self' 'sha256-0Fot2/lUbTdR3FiiVQdAaKvHyEBgTK6ZQgIXa8WcuKI=';
worker-src blob:;
img-src 'self' data: blob:;
require-trusted-types-for 'script';
trusted-types mapping-viewer default
```

The sandbox document **narrows** whatever the host allows: it has its own CSP (`default-src 'none'; script-src <hash> blob:; worker-src blob:; connect-src 'none'`), enforced together with the host's, so the plugin has no network (`fetch`, `WebSocket`, `WebTransport`, a dynamic `import()`) even in a host whose `connect-src` or `script-src` allows it. It has an opaque origin (no `allow-same-origin`): no access to the host's storage, DOM or cookies.

A host without one of the three gets `error.code = 'sandbox-unavailable'` from `screenFromFormat`, with a message that lists them, **nothing in the console**, and everything else in the viewer works as before (a `screen` the host passes still draws). The `mapping-viewer` and `default` entries only matter if the host already uses `require-trusted-types-for`; without Trusted Types the plain document is assigned.

## Loading the library

`loadLibrary(files)` receives the list of files of the design system folder: the specialization (`"format": "mapping-spec"`), one `.json` per component and the fonts (`bytes`). If the files are on a server, use `loadLibraryFromUrl`:

```ts
import { loadLibraryFromUrl } from 'mapping-viewer';

const library = await loadLibraryFromUrl('https://my-site.com/ds/material3.spec.json');
if (library.problems.length > 0) console.warn(library.problems);
```

It fetches the specialization, the components and the fonts it points to (paths relative to the specialization's URL). A file that fails to arrive is left out and shows up in `library.problems`; a specialization that fails to arrive throws `Error`. Options: `{ fetch, fonts }` (your own `fetch`, for example with authentication; `fonts: false` does not fetch the fonts).

## Fonts

The core does not load fonts. Two ways:

- **CSS:** declare the families with `@font-face` on your site;
- **Through the library:** `await registerLibraryFonts(library)` registers, via `FontFace`, the fonts the specialization declares (with the loaded bytes) and returns the status of each one (`loaded`, `missing`, `failed`).

### Token mode

A specialization with `tokens` (`light`, `dark`…) draws with the first entry of each axis. For another one, pass `drawingMode: 'dark'` (a string sets that entry on every axis that declares it) or a map with one entry per axis, `drawingMode: { theme: 'dark', density: 'compact' }`, to `createViewer` (or the `drawingMode` prop of `<MappingViewer/>`). An axis left out, or an entry it does not declare, falls back to its first entry. Changing it later, with `viewer.update({ drawingMode: 'light' })`, redraws without reloading the library or the screen; an equal selection (another key order, a default entry spelled out) does not redraw. With `source`, an origin whose `screen.background` is a token (`{ "$token": "surface" }`) draws that background in the same selection, so the screen background changes with `drawingMode` too. `font-sans` and `font-mono` (built in) resolve to the host's font in any mode.

When the fonts finish loading, re-measure the texts: `viewer.redraw()` in the core, or change the value of `fontsVersion` in `<MappingViewer/>`.

## Package images

A component's `image` node can cite an image file of the library package (`.png`, `.jpg`, `.jpeg` or `.webp`, by its path relative to the package root). The viewer draws it from the **bytes you pass to `loadLibrary`** (the `bytes` of the `TextFile` of that file, next to the specialization and the components). There is no option to turn it on, no network request and no CSP change: `img-src` is not involved, because the viewer creates no URL and no `<img>`; it decodes the bytes with `createImageBitmap`, which the host browser must provide (without it, the placeholder stays). Each image is limited to 1 MB and 2048 px per side, and the format is checked by the file header; an image over the limits, one that cannot be decoded or a file that is not there is the placeholder (a decode failure also reports the `image-decode-failed` warning, and an image over the limits or not in the format of its extension the `package-image-refused` one; a missing file has no warning). Like the remote images, none of them taints the canvas, so `viewer.toDataURL()` stays valid.

`loadLibraryFromUrl` fetches only the specialization, the components, the icons and the fonts: it does **not** fetch image files, so a library loaded that way draws the placeholder for its package images. To show them, read the image files yourself and call `loadLibrary` with their `bytes`. Passing another library to `update({ library })` frees the decoded images of the previous one.

## Remote images

A component can have an `image` node whose URL comes from a field (`mapping-component` format 3). The viewer **requests no image by default**: without the `remoteImages` option, the component draws the placeholder (a gray rectangle with the image stroke) and nothing goes to the network.

```ts
createViewer(container, {
  library,
  screen,
  remoteImages: true,
  // Your site decides, per origin. Without this function, everything is refused.
  allowOrigin: (origin) => origin === 'https://cdn.example.com',
});
```

(In React: `<MappingViewer remoteImages allowOrigin={...} />`. `remoteImages` applies only at creation; `allowOrigin` is read on every request, so a new function on every render does not recreate the viewer. With `createViewer` directly, the function passed at creation is the one that applies.)

With `remoteImages: true`, the image is only requested when the **two gates** agree:

1. **The URL passes Mapping's policy:** only `https:`, no username and password, up to 2048 characters and no local network host (literal IP, `localhost`, a name without a dot, `.local`, `.localhost`, `.internal`). `http:` and the local network have **no switch** in the viewer.
2. **Your `allowOrigin(origin)` function returns `true`** for the origin (`https://cdn.example.com`). Throwing an exception is the same as refusing. The viewer stores no consent and shows no prompt: the host site decides.

How it loads: `crossOrigin = 'anonymous'` and `referrerPolicy = 'no-referrer'` (no cookies and no `Referer`), at most 6 concurrent requests, a 20 s timeout, an image of up to 8192 px per side and 40 million pixels, a bitmap downscaled to 2048 px and an in-memory-only cache (the image is never stored). The image server must send `Access-Control-Allow-Origin`; without CORS the image does **not** show up: the viewer never asks without CORS, so a server without CORS always draws the **failure look** (the gray fill, the X and a dashed outline in `palette.failedLine`, `#d9480f` by default; override it through the `palette` option). The neutral placeholder (gray X, no dashed outline) stays for a field with no URL, a refused origin and an image still loading. Check a server with `curl -sI <url>` and look for the `access-control-allow-origin` header. That is why `viewer.toDataURL()` stays valid with remote images: none of them taints the canvas.

**The CSP belongs to the host site.** The viewer defines no policy. If your site has a CSP, `img-src` must allow the image origins (for example `img-src 'self' data: blob: https://cdn.example.com`); without that the browser blocks the request and the component stays on the placeholder, even if `allowOrigin` accepts it. If the site uses Trusted Types (`require-trusted-types-for 'script'`), Konva needs a `default` policy that accepts the empty string in `createHTML`.

## Instance tree

`screenTree(screen, library)` returns the roots (in drawing order) with nested children; each node carries `id`, `parentId`, `depth`, `label` (the instance's label), `typeId`, `typeName`, `instance` and `children`. `flattenTree(tree)` gives the same tree as a list, in pre-order (the drawing order), ready for a list indented by `depth`. Selection and highlight go back to the canvas through `setSelection` and `setHover`.

## Notes

- The core and the React bundle are **self-contained**, with Konva and the engine inside. Use `mapping-viewer` **or** `mapping-viewer/react` on the same site; the two together load two copies of Konva. `mapping-viewer/formats` has no Konva (the host passes `konvaMeasurer` of the bundle that draws) and goes with either; it is ~830 kB, about twice the core, which is why it is a separate entry.
- The React bundle leaves `react`, `react/jsx-runtime` and `react-dom` out: your site provides its own React.
- The package is ESM (`"type": "module"`) and ships minified, with source maps (`.js.map`).
- Remote images: off by default (section above); `AllowOrigin` is the type of the `allowOrigin` function.
- `loadLibraryFromUrl` uses `fetch`: the host site must allow the request (CORS and, if there is one, CSP `connect-src`).
