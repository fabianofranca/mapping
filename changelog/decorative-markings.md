# Decorative markings (Frame, Bracket, Line) — [Não lançado] (épico `epic/decorative-markings`, PR #2922, MCP 0.62.0, schema v25)

## Adicionado

- The format has a new optional `markings[].decorative` flag (schema v25, written only when `true`, right after `floating`). A decorative marking is a child like any other but is never a parent: the parents of the other markings and containers are the same as without it. Migration v24 → v25 only changes the version number, so an earlier app opens a file that holds one read-only instead of dropping the flag.
- The model settles a decorative marking into the smallest non-decorative marking that contains it, refuses to make a marking both decorative and floating (`decorative-floating`) and checks the new invariants `parent-decorative` and `decorative-floating`, with a repair for each. A marking created decorative is drawn below its siblings.
- A specialization can declare `decorative: true` on an annotation type (`formatVersion` 25): a marking created from the type is born decorative and drawn below its siblings. The validator refuses it together with `floating` or `structural` and on an arrow-only type, and the specialization help, `docs/SPEC-FORMAT.md`, the JSON schema and the `spec-author` skill describe it. Proposals can carry the flag too (proposal `formatVersion` 13, written only when a proposal uses it); the review shows a `decorative` change like any marking field.
- MCP: `create_marking.decorative` (absent takes the annotation type's value, `false` makes an instance of a decorative type ordinary) and `update_marking.decorative` (errors `locked` and `decorative-floating`); `get_marking` and the `list_markings` rows carry `decorative`, and `list_markings` filters by it. `wrap_items` takes a decorative marking like any member. The agent guide and `docs/MCP.md` say when to use a decorative marking and that it is never a parent.
