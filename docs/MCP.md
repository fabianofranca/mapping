# Mapping MCP server

The MCP server lets an agent (Claude Code, Claude Desktop or another MCP client) **read Mapping projects stored in a folder and propose changes to them**, with the same rules as the app (invariants, locks, references, specializations). The agent **never writes `mapping.json`**: every change arrives as a **proposal** in `proposals/`, which the user reviews in the app (accepting or rejecting at any level, with notes) and applies. Since 0.25.0 it also **converses**: it reads the conversations that people open on items, asks when a decision is not its own and replies in `comments/` (see "Change in 0.25.0"); it never resolves or deletes a conversation. Since 0.26.0 it also **reads the project's perspectives** (crops by audience; see "Change in 0.26.0"), without ever creating or changing them. It runs locally, over stdio, in Node (≥ 20), and makes no network requests (the local image server only listens on 127.0.0.1).

Only **folder** projects are within the MCP's reach; projects stored in the browser are not. To use the server, create or open the project in the app as a **folder**.

## Installation

1. Download `mapping-mcp.js` from the [latest `mcp-v*` Release](../../../releases) (there is also a `mapping-mcp.js.sha256` to check it: `sha256sum -c mapping-mcp.js.sha256`). To test something not yet published, download from a pre-release: `mcp-snapshot-pr<N>` (the build of a phase PR, before it enters the epic) or `mcp-v0.41.0-rc.<n>` (the epic's release candidate, generated on the merge of the last phase). They announce the version with a suffix in `--version` (`0.8.0-snapshot.pr172+abc1234`, `0.8.0-rc.1`).
2. Copy the file to `tools/` in the app's repository. It is self-contained (dependencies, image WebAssembly and documentation embedded): no `npm install` needed.
3. Register the server in a `.mcp.json` at the repository root:

   ```json
   {
     "mcpServers": {
       "mapping": {
         "command": "node",
         "args": ["tools/mapping-mcp.js", "--root", "design/mappings"]
       }
     }
   }
   ```

4. Open Claude Code (or another client) in the repository and approve the `mapping` server. The tools show up as `mcp__mapping__…`.

> **Repository with `"type": "module"` in `package.json`:** the file is CommonJS. Put a `package.json` with `{"type":"commonjs"}` next to it, in `tools/`; without it `node` reads it as an ES module and fails.

Test outside the client: `node tools/mapping-mcp.js --version` and `--help`.

**Signature extractor (optional).** To import the parameters of a Kotlin/Compose, SwiftUI or Figma component (see "Signature extractor" below), also download `mapping-signature.mjs` and `mapping-signature.mjs.sha256` from the same Release, check them (`sha256sum -c mapping-signature.mjs.sha256`) and copy to `tools/`. The workspace's `setup.sh` already installs it at `tools/mapping-signature.mjs`; without a workspace, this is the manual plan B, the same as for `mapping-mcp.js`. It is an ES module (`.mjs`): it runs with `node` in any repository, with no `package.json` next to it and no `npm install`.

> **Central mappings folder.** To keep several projects in a single folder, ready for any MCP client (Claude Code, Cursor, Gemini CLI, Copilot, Codex), copy [`examples/workspace/`](../examples/workspace/): `setup.sh` downloads the server, the `spec-author` skill and the `AGENTS.md` rules block from the release, checks the `sha256` of all of them before replacing any file and updates itself (`--no-self-update` turns that off); `AGENTS.md` explains the folder to the agent. The line to update an old workspace (run it once) is in the folder's `README.md` and below, in "Publishing a version".

## Roots

`--root <folder>` defines where the server may read and write; repeat it for more than one. Relative paths are resolved from the client's working directory (the repository, when the `.mcp.json` belongs to the project). The `root` argument of `create_project` accepts the root the same way: as written in `--root` (relative, with `./` or a trailing slash), absolute, as listed in `roots` by `list_projects`, or by the folder name, if only one root has it. The server looks for projects (folders with `mapping.json`) at any depth inside the roots. `--no-http` turns off the local image server (the image tools answer without `url`/`markdown`).

Security: the server only reads and writes inside the roots. It refuses `..`, absolute paths outside them and symbolic links that leave them (`outside-roots`); it does not follow links when looking for projects; and it writes atomically (temporary file + rename) the empty project and the updates to a proposal; the new files of a proposal go through a temporary file + hard link, which never overwrites (on a disk without hard links, such as exFAT, it writes directly, still without overwriting). Deleting the temporary file is best effort (since 0.3.4): if the system refuses (Windows antivirus, a folder mounted in a VM), the written file stands, the server writes a warning to stderr and the `.<file>.<x>.tmp` stays in the proposal folder; neither the app nor the server reads it, and it can be deleted by hand. What it writes: the empty project of `create_project`, the `proposals/` folder (proposals and their images) and, since 0.25.0, the conversations in `comments/<id>.json` (a new conversation through a temporary file + hard link, which never overwrites; an appended message through an atomic write after rereading the file). It **never** writes to `comments/resolved/` (resolving is done by a person, in the app). The only socket it opens is the local image server's: it listens only on 127.0.0.1, on a random port, with a random token in the path, serves only the images generated by the tools in this session, kept in memory, and is turned off with `--no-http`. **`mapping.json`, the `specs/` copies and `images/` are written only by the app**, when it applies a proposal; resolved, reopened and deleted conversations are also the app's alone. Reading never writes, not even to migrate a project with an old schema: the migration (with a backup in `backups/`) belongs to the app, on the first write; the proposal is computed over the project migrated in memory. The only exception to "only inside the roots" is the check of the **existence** of code files, which looks only at metadata (`stat`) and is confined to the client's working directory (see "Instantiation code of specializations"), and the reading of the `.md` of a **document in an external repository** by `get_component` (see "Change in 0.18.0"), confined to the same directory.

## References

Ctrl+C (Cmd+C) in the app, with a marking, container or annotation selected, copies the reference:

```
mapping://<project>/<m|i|a|p|l|c>/<code>
mapping://<project>/a/<code>/f/<field>
mapping://<project>/a/<code>/e/<code>
mapping://<project>/a/<code>/f/<field>/r/<code>
```

- `<project>`: the project's folder name, encoded as in a URL (`A-Z a-z 0-9 - . _ ~` stay as they are; everything else becomes `%XX`, in UTF-8: `My Project (v2)` is `My%20Project%20%28v2%29`). If there are two folders with the same name, the server returns the candidates and asks for the path.
- `m` marking, `i` **container** (the letter did not change when the image became a container, so references already pasted keep working), `a` annotation, `p` **proposal** (the one that `propose_changes` and `list_proposals` return), `l` **layer** and `c` **conversation** (the one that `list_threads` and `open_thread` return). After the code of an **annotation** a part may follow: `/f/<field>` (the `key` of the typed field, encoded like the project), `/e/<code>` (a pair of the free-form annotation) and, after a `table` field, `/r/<code>` (a row). The full grammar is that of [`COMMENT-FORMAT.md`](COMMENT-FORMAT.md), "References and citations".
- `<code>`: the first 8 hexadecimal characters of the id (12, 16… if there is a collision).
- The reference is **only the URL**: it carries no readable path or anything after the code (the name comes from `resolve`; the readable path, from the `path` of `get_marking`, `get_container` and `get_annotation`). Anything after the code (the ` (path)` of the old format, `?`, `#`, a space) or an unencoded project is `invalid-ref` (see "Change in 0.21.0").

Every tool that takes an item (`ref`) accepts the full reference, just `m/3f2a9c1e` with `project` given separately, or the full id. Paste the reference into the chat and the agent resolves it without needing the project. In the proposal tools, `ref` is `mapping://project/p/3f2a9c1e`, `p/3f2a9c1e` (with `project`) or the proposal id; the code is unique among the project's proposals. In the conversation tools, `ref` is `mapping://project/c/5d0e8a41`, `c/5d0e8a41` (with `project`) or the conversation id. `resolve` understands all the forms and returns `kind` `marking`, `arrow`, `container`, `annotation`, `layer`, `thread`, `field`, `entry` or `row` (field, pair and row carry `annotation`, `key` and `value`). `get_annotation` and the other item tools accept a field, pair or row as the annotation that contains it; in a marking or container tool a part is `wrong-kind`, a layer or conversation in an item tool is also `wrong-kind`, a suffix the grammar does not know is still `invalid-ref` and a field, pair or row that does not exist in the annotation is `not-found`. The old references (`m`, `i`, `a`, `p`) work as always. **Ctrl+Alt+C** copies the marking's crop as a PNG.

### Instantiation code of specializations (stages 3b, 9 and Instantiation code)

Specializations can declare **platforms** (targets in which the agent writes the solution: Android, iOS, the BFF) and say, in `code`, which code creates an instance of each annotation type on each one: `symbol` is what is called, `path` is the file that defines it (to read the signature), `params` and `values` say how to pass the fields and `notes` gives guidance. The **repository belongs to the library**, hence to the specialization (`platforms[].repo`: `url`, `urlTemplate?`, `ref?`); the project only overrides the local clone (`platformRepos[<platform>].localPath`). The mapping stores nothing about the solution (there has been no `codeRef` field since 0.4.0). Format details are in [`FORMAT.md`](FORMAT.md) and [`SPEC-FORMAT.md`](SPEC-FORMAT.md). The agent's flow is in [`AGENT-GUIDE.md`](AGENT-GUIDE.md): `mapping://` reference → `get_marking` and `get_marking_image` → `get_code_hints` → read the `definition` of each type → write the calls.

In specialization 9, `code` can have `variants` (the variant changes the `symbol`, like `Button` and `OutlinedButton` in Compose): `get_marking` and `get_annotation` deliver the code **already resolved** for each annotation's variant, `get_code_hints` carries it on the `tree` annotation (`types` is the raw base), and `get_specialization` and `get_component` the raw one.

In `get_marking`, `get_annotation`, `find_by_code`, `get_component` (field `code.<platform>`) and in `types` of `get_code_hints`, each `code` entry has the same shape, with the `definition` (the file that defines the `symbol`) resolved alongside:

```json
{
  "symbol": "com.app.ds.DSButton",
  "definition": {
    "path": "app/src/main/java/com/app/ds/DSButton.kt",
    "url": "https://github.com/org/app-android/blob/v3/app/src/main/java/com/app/ds/DSButton.kt",
    "ref": "v3",
    "localFile": "app/src/main/java/com/app/ds/DSButton.kt",
    "exists": true
  },
  "params": { "label": "text", "style": "style" }
}
```

- `url` and `ref`: from the specialization's `repo`. `url` is built from the `urlTemplate` (`null` without it); the path has no line. Without `path`, `definition` is `null`.
- `localFile`: the platform's `localPath` (the project's override, relative to the project folder) plus the `path`, **relative to the client's working directory** (the server process's; in Claude Code, the repository). `exists` says whether the file is there. Without `localPath`, both are `null` (a platform without a local clone is not a problem: the agent opens the `url`). In `get_component` by `path` (a package without a project), `localFile` and `exists` are always `null`.
- **Signatures (specialization `formatVersion` 16).** With `signature`, `ignore`, `calls` and `formats` in the specialization's `code`, the entry gains those keys, **as they are in the specialization, already resolved by case** (in `variants`, the case's `signature` and `ignore` replace the base's; `params`, `values`, `calls` and `formats` add up key by key) and the `unmapped`:

```json
{
  "symbol": "androidx.compose.material3.Button",
  "signature": "signatures/button.compose.json",
  "ignore": ["modifier"],
  "calls": { "colors": "androidx.compose.material3.ButtonDefaults.buttonColors" },
  "formats": { "width": "{value}.dp" },
  "params": {
    "title": "#0",
    "containerColor": "colors.containerColor",
    "width": "width"
  },
  "unmapped": [
    { "name": "onClick", "role": "callback", "type": "() -> Unit", "required": true },
    {
      "name": "enabled",
      "role": "value",
      "type": "Boolean",
      "required": false,
      "default": "true"
    },
    {
      "name": "content",
      "role": "slot",
      "type": "@Composable RowScope.() -> Unit",
      "required": true
    }
  ]
}
```

- `unmapped`: the sheet's parameters, **in the sheet's order**, that no field links and that `ignore` does not dismiss: `{ name, role, type, required, default? }`. A parameter with some factory field linked by path (`colors.containerColor`) counts as linked. `callback`, `modifier`, `state` and `slot` are also included, so the agent knows, for example, that `onClick` is required. It only appears when the type has `signature` **and** the server can read it; otherwise the key does not exist.
- **The server reads only the sheet's JSON**, in the applied package (`specs/<id>/signatures/…`), never the code: the sheet is a file of the library, derived from the code by whoever wrote it (format in `mapping-docs://SIGNATURE-FORMAT.md`).
- In `get_code_hints`, `types["<spec>/<type>"]` carries the `code` with `calls` and `unmapped`; each item of `args` is `{ field, name, value }`, the positional one (`#0`) is `{ field, position, value }`, and a factory's argument is `{ name, call, args: [{ field, name, value }] }`, which only exists when some field of the factory is filled in (an empty field is left out). The value goes through `formats` (`16.dp`).
- `find_by_code` answers "which types are instantiated with this file or symbol, and where are they marked" (format in [`AGENT-GUIDE.md`](AGENT-GUIDE.md)).
- **The server never reads or writes code files**: it only builds the path and checks existence (`stat`), which is covered by a test. The agent reads the file with its own tools.
- **Safety limit**: the `localPath` can climb folders (`../../..`) and the `path` comes from a file that other people can edit. So the check only looks **inside the client's working directory**, also after following symbolic links. If the computed path leaves it, the `definition` carries `localFile: null`, `exists: null` and `localFileProblem: "outside-workdir"` (without touching the disk); a symbolic link that leads outside counts as `exists: false`. For `localFile` to appear, open the client at the root of the cloned repository.
- `get_project` carries, on each platform declared by the applied specializations, `repos` (the `repo` of each specialization that declares it, with `specId`) and `localPath` (or `null`); `platformRepos` carries only the `localPath`. There are no more repository warnings: a platform without a local clone is not a problem.

### Importing the signature (`plan_signature_import`)

`plan_signature_import({ path, type, platform? | system?, variant?, signature? | signatureFile? })` turns a component's `mapping-signature` **sheet** (format in `mapping-docs://SIGNATURE-FORMAT.md`) into fields, `code` or `sources` and warnings of a library type. It **writes nothing**: it returns the preview and the whole specialization already imported, and the agent writes the files and runs `validate_library`. The rule is deterministic (the same sheet gives the same answer) and lives in `src/model/signatures/` (`planSignatureImport`); the server only reads JSON.

- **Input.** `path` is the package folder (or the specialization file inside it), inside the roots; `type` is the type id; `platform` (code target, the id in `platforms`) **or** `system` (design target, like `figma`, in the type's `sources`); `variant` is the value of the `variants` field when the sheet is a case's (only with `platform`). The sheet comes in `signature` (inline object) **or** in `signatureFile` (a `.json` inside the roots): exactly one of the two.
- **Output.** `fields` (the fields the import creates), `links` (each parameter linked to the field: `via` is `params`, `name` or `new`), `code` (or `sources`), `notices` (all with the sheet's `ref`, the `message` starting with `<platform>:` and the place: the type or the field), `unmapped` (the parameters without a field, as in `get_code_hints`), `changes` (relative to the sheet saved in the package: `added`, `removed`, `changed` and `renamed`), `suggestedMigrations` (`remove-field` and `rename-field`: the agent only writes them into `migrations` if the person asks; the import **never** writes them nor removes a field), `versionBump` (the contract changed: a new field or option; raise the `version`), `signaturePath` (where to save the sheet), `previous` (there was a saved, valid sheet; if the `code`, the case or the `source` cites a sheet absent from the package or invalid, `previousProblem` gives the reason and the import goes on without a previous one; without the problem, the key does not exist) and `spec`.
- **The previous sheet** is the one that the type's `code` (of the case, with `variant`) or `sources` cites in `signature`, read from the package; without it, it is the first import.
- **Errors** (`detail` and `hint`): `signature-invalid` (the sheet does not pass `parseSignature`; `issues` carries the path inside the sheet), `type-not-found`, `platform-not-declared`, `signature-mismatch` (the sheet's symbol and file, or the system, differ from those of the `code` or `source`), `variant-not-found` (the `code` does not declare the case, or `variant` was passed with `system`) and `invalid-spec` (the specialization predates `formatVersion` 16: raise it by hand first, because `params` starts being interpreted).
- **The server never reads code.** A `signatureFile` that is not `.json` is refused before any disk access, and what is not a sheet is `signature-invalid`. Extract the sheet with `mapping-signature.mjs` or write it by hand (`source.extractor: "agent"`).

#### Signature extractor

`mapping-signature.mjs` (code in `signature/`) reads a Kotlin file (a `@Composable` function), a Swift file (a SwiftUI `struct`) or a Figma node's JSON and writes the component's sheet. It runs **in the library's clone, by the agent**; the server still does not read code and only reads the JSON sheet that the agent writes into the library.

```bash
node tools/mapping-signature.mjs kotlin --file <file.kt> --symbol <name> --path <relative to the repo> --ref <commit> \
  [--also <file.kt>]... [--overload <n>] --out signatures/<type>.<platform>.json
node tools/mapping-signature.mjs swift --file <file.swift> --symbol <name> --path <relative to the repo> --ref <commit> \
  [--also <file.swift>]... [--init <n>] --out signatures/<type>.<platform>.json
node tools/mapping-signature.mjs figma --file <nodes.json> --node <id> --out signatures/<type>.<system>.json
node tools/mapping-signature.mjs --help
```

- `--symbol` is the name of the `@Composable` function (simple or with the `package`); `--path` is the file's path relative to the repository root and `--ref` the commit pinned in `platforms[].repo` (they go in `source.path` and `source.ref`). `--also` points to other `.kt` files where the `enum class`es and `XDefaults.f()` factories that the main file uses live.
- **Ambiguous overload:** with more than one candidate, the command exits with an error (code 1), lists the candidates with their index and asks for `--overload <n>`.
- Deterministic output (same input, same bytes), no dependency and no network; it only writes to `--out`, and only after validating the sheet. Exit codes: 0 ok, 1 extraction error, 2 usage error.
- **Swift:** `--symbol` is the `struct` (`ProfileCard` or `DS.ProfileCard`); the written `init` comes from `--init <n>` (saved in `source.init`) and, without a written `init`, the memberwise one applies (the stored properties without `@State`, `@Environment` and the like). With more than one `init`, the command exits with an error, lists the `init`s with their index and asks for `--init <n>`. The external label goes in `label` (`_` is the positional, the `#0` of `get_code_hints`).
- **Figma:** `--file` is the saved JSON in which the node carries `id`, `type` and `componentPropertyDefinitions` (the response of `GET /v1/files/:key/nodes`, the whole file's or the loose node; the format that Figma's MCP returns has not been checked) and `--node` the id of the `COMPONENT_SET` or `COMPONENT` (`12:34` or `12-34`). The sheet is a design one (`source.kind: "design"`): `plan_signature_import` links it to the type's `sources` (pass `system: "figma"`), not to `code`.
- The three readers give sheets of the same format (`source.extractor: "mapping-signature/<reader>@1"`); a source without an extractor (React, Storybook, Flutter) remains by hand (`source.extractor: "agent"`).

- **The importer's warnings** (`pending` for each `value` parameter without a field, `removed`, `diverges`) show up in `types["spec/type"].notices` of `get_code_hints`, alongside the curated ones, with the sheet's `ref`; the `unmapped` of the same `code` is the trace of what the screen still does not model. The generated `pending` and the `unmapped` say the same thing in two ways: the warning stays in the specialization, the `unmapped` comes out of the sheet.
- Read-only, minor version (0.39.0).

### Preview and catalog in the batch (0.25.1)

The same goes for `addComponentMarking` in the model, which used to skip the `preview` when it received `values`.

### Anchor between markings (schema v20, 0.40.0)

- **Operations.** `create_marking` and `update_marking` accept `anchor` (`{ to, side?, align?, offset?: { main, cross } }`; `to` is the anchor's reference, id or alias; `side` `top`, `bottom`, `start` or `end`; `align` `start`, `center` or `end`; `offset` in container pixels). `null` in `update_marking` removes the anchor; absent does not change it. `create_marking` with `anchor` and **without `rect`** (with `annotation` of a type with a component) is born at the measured size, **snapped** to the anchor by the component's defaults (the `anchor` key at its root) and by what `anchor` says. The **`snap_to_anchor`** op (`{ "op": "snap_to_anchor", "marking": <ref> }`) snaps an already anchored marking again, keeping its size; the summary gives the rectangle before and after, or says nothing changed. It works in `plan_changes` (the preview), in the batch and in a proposal (the review shows the anchor as "Anchor" and the snap as the Position).
- **Moving and deleting.** Moving the anchor is `update_marking` with `move` (the `move_marking` op only reorders siblings and takes no one along): it takes the anchored ones (and their descendants) along, even locked; resizing the anchor does not. Deleting the anchor sets `anchor: null` on the anchored ones. **An anchored marking that leaves the target's space** (goes to another container or to the canvas, by `update_marking` with `container`) **is released**: `anchor: null`, and the `rect` stays where the step put it; a target that leaves the anchored one's space releases the anchored ones the same way.
- **Reading.** `get_marking` **always** returns `anchor` (with `to` as a reference; `null` without an anchor) and `anchoredBy` (the references of the anchored ones; `[]` when no one is anchored to it); `get_code_hints` returns `anchor: { marking, side, align }` on the anchored marking (at the top and on the `tree` node).
- **Model errors.** There is no `snap_to_anchor` tool: it is a batch op (`plan_changes`/`propose_changes`), like `fit_marking`. An `anchor.to` that is a reference or id **of a marking that does not exist** comes out as `not-found` ("marking not found") and an alias `$x` without a prior creation, as `unknown-alias`, when the step is resolved; the model's `anchor-missing` applies to a hand-edited `mapping.json` (the folder becomes unreadable, `invalid-project`). `anchor-missing`, `anchor-self`, `anchor-cycle`, `anchor-other-space` (the anchor counts in the batch's state at that point), `not-anchored` (`snap_to_anchor` without an anchor) and `locked` (locked geometry that would change). List and causes in `AGENT-GUIDE.md`.
- **Component.** `anchor` at the file root and the `$anchor.*` pseudo-fields only in `formatVersion` 4 (`docs/COMPONENT-FORMAT.md`, "Anchor"); the specialization does not go up a version (the proposal does, see "Proposals").

### Reading direction (schema v20, 0.40.0)

- **Operations.** `update_project` accepts `direction` (`"ltr"` or `"rtl"` writes, `null` removes and goes back to `ltr`, absent does not change); `add_container` and `update_container` accept `direction` (`"ltr"`/`"rtl"` pins the container's; `null` goes back to following the project). A value outside the set is refused by the operation's schema (`invalid-arguments`). In the batch summary it appears as `direction "rtl"` (or `project direction`, when going back to following the project).
- **Reading.** `get_project` returns `direction` (the project's; `ltr` when none is written, because that is what applies) and, in each container, the pinned `direction` (`null` = follows the project) and the `effectiveDirection`; `get_container` likewise; `get_marking` carries the same in the item's `container`.
- **Image.** `render_marking` and `render_container` gain `direction` (`ltr`/`rtl`), which pins the direction across the whole drawing, including in the containers that pin their own (like `drawingMode`). The response carries `direction` (`null` when each container used its own effective one). In `rtl` the rows, grids and `start`/`end` positions mirror and `mirror` icons flip; text aligns by `start` but glyphs come out in text order, without bidi (a known limit).
- **Code.** `get_code_hints` returns `direction` (the effective one of the marking's container) at the top and on each `tree` node; there is no parameter in `code`. Whoever writes the code applies it per platform (`docs/AGENT-GUIDE.md`, decision 3).
- **Proposals.** The project's and the container's direction go in proposal `formatVersion` 8 (`docs/PROPOSAL-FORMAT.md`); proposals without direction do not go up.
- **Proposals with an anchor.** A proposal that writes `anchor` (a marking's field, or the `anchor` in the value of a created marking) goes up to `formatVersion` 9 (`PROPOSAL_ANCHOR_FORMAT_VERSION`); an earlier app or MCP refuses the file instead of discarding the anchor. The `snap_to_anchor` op alone does not raise the version (it is only the Position), and a proposal without an anchor does not go up.

### Container density (schema v19)

- **Operations.** `add_container` and `update_container` accept `density` (a number from 0.5 to 8: image pixels per component unit; `null` in `update_container` goes back to 1; absent does not change). Outside the range it is the model error `container-density`, with `detail` ("received 12; from 0.5 to 8") and `hint` ("from 0.5 to 8; 3 for a 1080 px capture of a 360 dp phone…").
- **Reading.** `get_container`, `get_project` (the container list) and `get_marking` (the item's `container`) return `density` (1 when not declared).
- **Drawing and proof.** `render_marking`, `render_container` and `get_marking_image` draw with the density's scale, with no new parameter (`zoom` is still the image's). The component's `minSize` counts × `density` (`rect-too-small` and resizing) and `component-overflow.missing` is in image pixels; `plan_changes` with `update_container` `density` re-checks the container's markings.
- **Proposals.** The container's `density` field goes in proposal `formatVersion` 7 (`docs/PROPOSAL-FORMAT.md`).

### Drawing mode (schema v18)

- **Operations.** New `update_project` with `drawingMode` (a string writes, `null` removes, absent does not change); `add_container` and `update_container` accept `drawingMode` (a string pins, `null` goes back to following the project). A name outside `[a-z0-9][a-z0-9-]*` fails with `invalid-name`.
- **Reading.** `get_project` returns `drawingMode` (`null` without a mode) and, in each container, the pinned one and the `effectiveDrawingMode`; `get_container` likewise; `list_markings` carries `effectiveDrawingMode` on each row. The effective one is the container's, else the project's, else the first mode declared in `tokens.modes` by the specializations, else `null`.
- **Proposals.** The mode change becomes the `project` entity (and the container's `drawingMode` field) in the proposal, which is then written in `formatVersion` 6 (`docs/PROPOSAL-FORMAT.md`); proposals without the mode stay on 4 (creation) and 5 (revision).

### Arrows and `near` (ME4)

- **`create_arrow`** (`from`, `to`, `style?`, `name?`, `as?`), **`update_arrow`** (`arrow`, `name?`, `style?`, `locked?`) and **`delete_arrow`** (`arrow`), operations of `plan_changes` and `propose_changes`. The arrow links two markings (never another arrow or a container: `arrow-endpoint`; the same end twice: `arrow-self`), with `style` `straight`, `curve` (default) or `elbow`. **Never `points`**: the route belongs to the person, and `points` in `create_arrow` or `update_arrow` fails with `invalid-arguments`. The proposal carries only the creation and removal of the arrow (`create-arrow`, `delete-arrow`); `update_arrow` on an arrow that already exists works in the preview (`plan_changes`) and warns with `ignored-argument` that it does not go into the proposal.
- **The arrow's reference**: arrow ids and marking ids share the space, so the arrow uses the letter `m` (`mapping://project/m/<code>`). `get_marking` and `resolve` with it return `kind: "arrow"`, `from`, `to` (in `get_marking`: reference, name and path; in `resolve`, only the reference), `style`, `lock` and the annotations by layer; `create_annotation` accepts the arrow's reference in `marking`.
- **`appliesTo` is enforced.** `create_annotation` with a type that does not apply to the item (a marking-only type on an arrow, or an arrow-only type on a marking) fails with `type-not-applicable` and a `hint`; `update_marking` and `delete_marking` with an arrow's id fail with `wrong-kind` and the `hint` points to `update_arrow` or `delete_arrow`. An annotation that stopped applying after a specialization update becomes a pending item (`type-not-applicable`), not an error; the update's preview lists the change as `changed-applies-to` (additive).
- **`get_marking`** of a marking carries `arrows: { outgoing, incoming }` (when there are any): `ref`, `id`, the other end (`to` on outgoing, `from` on incoming), `name`, `style` and `locked`.
- **`get_marking_image`** refuses the arrow with the `arrow` error (and a `hint`) and the canvas marking with `canvas-marking`.
- **`near`** in `create_marking` (reference, id or alias of a container or a marking): only for a floating annotation type (without `container`); the marking is born in a free spot on the target's margin (to the right, stacked from top to bottom with a 24-canvas-unit gap, without overlapping containers or other floating markings; if it does not fit, left, below, above). The `rect`, if given, supplies only the size (x and y are ignored). On a non-floating type or marking, `near` is ignored with an `ignored-argument` warning.
- `changes` of `plan_changes`/`propose_changes` gains `arrows` (created, changed, deleted) and `created` carries `kind: "arrow"`.

### Change in 0.38.0 — variables in format 4 (`let` and `$var`)

### Change in 0.35.0 — `fit_marking` and the instance at the measured size (MC3, Measured by content)

- **Op `fit_marking`** of `plan_changes` and `propose_changes` (`marking`: reference, id or alias): fits a component's marking to its content, the same **Arrange** as the app on a marking without a slot. Each axis whose `sizing` is `hug` (or an expression that gives `hug` or px) becomes the measured size with the annotation's values **in the batch's state at that point** (an integer rounded up, between the `minSize` and the limits of the component's root, never below a marking's minimum); the top-left corner stays, the `fill` axis, the absent one and the one stretched by the parent's `stretch` do not change and the result never exceeds the image. Membership comes out of the geometry afterwards (the response's `membership` says who changed parent). The step's summary carries the rectangle before and after (`120×40 px at (20, 20) → 120×96 px at (20, 20)`) or "nothing changes".
- **Errors:** `not-fittable` (no axis depends on the content, the marking is not a component's or is a component with markings in the slot, which the app's Arrange handles; the `hint` points to the `sizing` in `get_component`), `locked` (locked geometry that would change), `not-found` and the usual reference ones.
- **There is no new tool:** the server still does not write the project. "Direct" is `plan_changes` with the op (the preview, writing nothing); sending is `propose_changes`, where the review shows the fit as the usual **Position** change (X, Y, Width and Height), next to the value that changed, and the user can accept one and reject the other. The rule in `AGENT-GUIDE.md` ("Fitting to the content"): after changing a value that alters the content of a fittable component, call `fit_marking` on the same marking, in the same batch or the same proposal, also when revising a proposal and when answering a conversation. Editing the value alone does not change the rectangle.
- **`create_marking` without `rect`** with `annotation` of a type whose component has a content-dependent `sizing` (and no slot) **is born at the measured size** with the component's `preview` and the step's `values` (text, number and empty; table and reference stay at the `default`), in the usual free spot (0.34.1). With `rect`, the `rect` rules. A component with a slot is born at its `size`. It also applies to `near` and `inside` without `rect`.
- Minor version, compatible (one new op; no tool or argument changed); `formatVersion` and schema unchanged. The epic's version is `0.35.0` (the final one is chosen at closing).

### Change in 0.34.1 — `create_marking` without `rect` is born in a free spot

- **`create_marking` with `annotation` of a type with a component and without `rect`** (and without `inside` or `near`) is born in the free spot closest to the container's center (on the canvas, to 0,0), **without covering or coinciding** with other markings of the same space (on the canvas, nor with containers), with a gap of 8 units, the same placement as the app's **Add to canvas**. Before, all were born at the center, overlapping: the second identical component became a child of the first and a large component adopted the markings it covered. Two identical components in the same batch are born side by side, both without a parent.

### Change in 0.23.0 (Fix in the same proposal)

Schema v14 and specialization (`formatVersion` 11) unchanged; the proposal gains **format 5** (`docs/PROPOSAL-FORMAT.md`, "Agent revision"), which **only the revision writes** (creation stays on format 4).

- **New tool `revise_proposal(ref, project?, { operations?, drop?, dryRun? })`**: the agent fixes the open proposal in the proposal itself, instead of sending another with `supersedes`. It needs `drop` or `operations` with at least one item (otherwise `invalid-arguments`); a result that changes nothing is `no-changes`.
  - `drop`: change ids (`c3`, as `get_proposal` shows) to remove. It follows the dependencies: removing the creation removes what depends on it; removing the removal of a cascade removes that of whoever causes it. An id that does not exist: `change-not-found`.
  - `operations`: the same vocabulary and the same validation as `propose_changes`, applied over the **whole proposed state** (the current project plus all the changes that remained, with any decision, including the rejected ones), after the `drop`. That is why an item the proposal itself creates is edited by its final id (`mapping://…` reference). The `$name` aliases apply. A batch with an error writes nothing and carries `errors` per operation.
  - `dryRun: true` computes and returns the result without writing (`revised: false`, `dryRun: true`).
- **Each change leaves the revision as one type only:** _untouched_ (identical: id, `from`, `to`, decision and notes), _replaced_ (same id and `from`, new `to`; the decision goes away, back to no decision; the notes stay; gets the "Revised" mark), _new_ (a `c<n>` id never used, without a decision, with the mark) or _removed_ (leaves `changes`; its notes go up to the proposal level, with the same text and date). Only the decisions of the replaced and removed ones change; dependents rejected along with them stay rejected (Partial item in the review).
- **What is accepted stays frozen.** A change that is **accepted** and not yet applied is not replaced or removed: if the batch would touch one, the whole call is refused, without writing, with `change-frozen` (the ids come in the error). The `hint` says that the user already accepted those changes: ask them to clear the decision or send a new proposal with `supersedes`.
- **When it can:** `open` proposal with `applied` empty. With something already applied: `proposal-applied` (use `propose_changes` with `supersedes`); in another status: `not-open`; read-only project: `read-only`. A proposal that no longer applies to the current project (`entity-missing`, `entity-exists`, `field-mismatch` or an invariant) is refused with `proposal-not-applicable`, with the problems and the change ids; the `hint` says to remove them in `drop` or send a new proposal.
- **Library package** (specialization in a folder) new or replaced in a revision: `revise-unsupported` (it goes in a new proposal). Removing the change of a package that is already in the proposal is allowed, and its files leave the proposal folder.
- **Images:** the new file swap writes the image in `proposals/<id>/images/` without overwriting any; the image of a removed swap leaves the folder (best effort: a failure becomes a warning on stderr and the revision stands).
- **Response:** `revised` (`false` in `dryRun`, which also carries `dryRun: true`), `proposal` (`ref`, the same; `id`, `title`, `status`), `revision` (that of `proposal.json`, already +1), `counts` (`changed`, `added`, `dropped`), the lists `changed`, `added` and `dropped` (each item with `id` and a readable `summary`), `created` (the final references of the created items, as in `propose_changes`), `warnings` and `hint`.
- **Reads that change:**
  - `get_proposal`: each change with the mark carries `revised: { at, kind: "changed" | "added", previous?: { to, state } }` (`previous` only on the replaced one; `state` is `"rejected"` or `null` = no decision), and only while the change is **undecided** (deciding removes the mark, as in the app), and the root carries `revisions: { count, last: { at, changed, added, dropped } }` (only when there are revisions).
  - `get_proposal_review`: `revisable` (open and nothing applied) and a `hint` that points to `revise_proposal` or, when not possible, `propose_changes` with `supersedes`; `awaitingUser` (the replaced and new ones still without a decision: `change`, `target`, `revised`), which do **not** count as rejected; and the notes that went up to the proposal come out in the general notes with `fromDroppedChange` (the summary of the removed change they came from).
  - `list_proposals`: `lastRevisedAt` per proposal (absent if it was never revised).
- **New errors:** `change-frozen`, `change-not-found`, `proposal-applied`, `proposal-not-applicable` and `revise-unsupported` (list in `AGENT-GUIDE.md`).
- **Compatibility:** an old app in cache refuses the format 5 file and does not overwrite it; an old MCP server lists the proposal in `broken`. `mapping.json` is never changed by the tool.

### Change in 0.22.0 (Stable tie-break)

No change in the format of `mapping.json` (schema v14), of the specialization (`formatVersion` 11) or of the proposal (format 4), and no new tool. What changes is the result of reordering and of applying a proposal: the hierarchy settle now **prefers the current relation** in ties, and the order of the `markings` array only decides a new tie.

- **Reordering no longer swaps parents.** `move_marking` (and the app's Details **Order**) only changes the order among siblings: two markings with the same rectangle where one is the parent of the other stay that way, even if the reordering puts the child first in the array; and, among candidates of the same area for a parent, the current parent stays. This also holds in the following settle (a `move_marking` or a gesture later), which could previously invert parent and child.
- **Equal rectangles:** the order from the outside in, within the group, is that of the current `parentId`s (the parent before the child); whoever has just arrived at the rectangle, without a parent in the group, enters by the array (the earlier one is the outer one), as always.
- **The applied proposal equals the proposed one, also with `move_marking` in the batch.** Applying all the changes of a `propose_changes` gives the same parents (markings and containers) and the same order among siblings that the `membership` and the Proposed view showed, with or without `move_marking` (end of the "Known exception (#549)" of earlier versions). Two supporting adjustments: the `insertBefore` anchor is chosen so that ties come out as in the proposed state, and the review no longer shows an extra position change when two new markings enter the same place. Known limit (#625): a tie between markings that already existed, decided in the batch by an intermediate step that the proposal does not record, follows the base's relation and may give another parent (about 1 batch in 1,000 in a fuzz); check with `get_marking` after applying.
- **The `parentId` read remains the source of truth:** the agent checks the hierarchy with `get_marking` and does not deduce the parent from the position in the array.

### Component library (0.5.0)

Specialization `formatVersion` 4 is a **package** (a folder with the specialization, `components/`, `docs/`, `examples/` and `fonts/`; see [`SPEC-FORMAT.md`](SPEC-FORMAT.md), "Library: the package"). The server **validates, reads and carries the package in a proposal**; whoever applies it (copies the folder to `specs/<folder>/`) is the app, in the review.

- `validate_library({ path, previous?, level? })`: `path` is the package folder or the specialization file inside it (relative to a root or absolute inside them). It reads the folder (text only from `.json` and `.md`; fonts and other files count as present, without reading the content; symbolic links are not followed; at most 2000 files and 32 MB of text, otherwise `package-too-large`) and calls `validateLibrary`, the same function as the app and the skill. `previous` is the earlier version's specialization file and turns on the version contract (a break without `migrations` is an error); `level` (1, 2 or 3, default 3) limits how far to validate. The response carries `valid` (without any `error`), `path`, `spec` (a summary with counts of components, documents, examples, fonts, origins and migrations), `summary` (the level that ran and the package's counts), `errors` and `warnings` (each `{ file, path, message, severity }`; at most 100 of each, with `moreErrors`/`moreWarnings` when there are more) and `hint`. **An error prevents use, a warning allows use.** A folder without a specialization returns `valid: false` with the reason. It applies nothing to any project.
- `validate_specialization` accepts `formatVersion` 4 but validates only the **file**; the summary gains `components`, `docs`, `examples`, `fonts`, `origins` and `migrations`, and the `hint` says to use `validate_library` for the package.
- `list_components` and `get_component` read the **applied** library (`project` + `specId`: the copy in `specs/<folder>/`, the folder of the specialization's `file`) or any package (`path`). `list_components` returns, per type with a component, `type`, `name`, `layer`, `size` and `minSize` (px), `hasDoc` and `examples` (count). `get_component` returns, for a `type` (id or name): `doc` (the markdown), `fields`, `examples` (`values`, or `system` + `file` with the external example's `json` when it is up to 16 KB), `code`, `sources` and `component` (the file's JSON). A type without a component or document is not an error: `hasComponent: false` and a `hint` come. A nonexistent type: `unknown-type`.
- `get_specialization` returns the whole v4 (nothing is discarded) and, when the project's copy is a `specs/<id>/` folder, `package: { dir, files }`.
- `plan_library_update({ project, path })`: the **read-only** preview of applying or updating the library at `path` (the new package's folder or the specialization file inside it; also a v1 to v3 file) in the `project`. Returns `specId`, `from` (applied version, `null` if it is not applied) and `to`, `decision` (`apply`, `update` or `not-newer`), `validation` (`valid`, `errors`, `warnings`; on update the applied copy is the `previous`) and, on `update`: `additive` (only adds, without a break and without `freedLayers`: a layer that disappears, even without annotations, is not additive; the `hint` asks for the person's confirmation), `refused` (a break without a migration) with `missingMigrations`, `changes` (`code`, `kind`, `path`, `message`), `steps` (the `step` with `op` and keys, and `annotations`, `values`, `converted`, `deleted`, `refs`, `lossCount` and the step's `losses`), `losses` (`reason`, `message`, the annotation and the marking in text and in reference, `field`, `rowId` and `value`), `pending` (the annotation, `code` and `field`), `brokenRefs`, `addedLayers`, `freedLayers` and a `hint`. Lists above 100 items are cut, with the total in `changesTotal`, `lossesTotal`, `pendingTotal`, `stepsTotal` and `missingMigrationsTotal`.
- **`apply_specialization` and `update_specialization` accept the v4 package folder** in `file` (or the specialization file inside it; v1 to v3 still go by file). The server reads the folder (binaries included, up to 500 files and 64 MB, the app's limit), validates with `validateLibrary` (on update, with the applied copy as `previous`) and: a validation error → `invalid-library` (with the first errors); a version not greater → `spec-not-newer`; a break without a migration → `spec-missing-migrations` with `missingMigrations`. Warnings go on and come back in `warnings` (`library-warning`). The proposed project comes from the model (`packageSpecName` = the specialization file, the `specs/<id>/` folder; the update runs the `migrations` on the annotations), and **the package's files are written to `proposals/<id>/specs/<folder>/…`** (the same principle as `proposals/<id>/images/`; `files.packages` in the response lists the folders and the file count). On apply, the app **copies** the folder to `specs/<folder>/` and validates the package; the server never writes `specs/` or `mapping.json`. The operation's description summarizes the migration (steps, changed values, converted or deleted annotations, lost values, pending items) and the proposal carries the `values.*` changes of each migrated annotation.
- **Change in 0.5.0**: new tools (`plan_library_update`), v4 package accepted in the proposal (applying and updating with the folder), and the operations and fields of screens with components (next section); nothing that existed changed format. Use 0.5.0 with the app of the same period (schema v10): a v9 project is migrated on reading, in memory.

### Containers with components (0.5.0)

Schema v10 introduced the **container without a file** (`file: null`, with `width`, `height` and `background`) and the component library draws instances in it. The server reads the components of the specializations in a folder (`specs/<id>/`) once, when loading the project, and uses them only to **measure and check**; it **never arranges** the children of a component with a slot (whoever uses Arrange is the person, in the app) and never writes drawing: `mapping.json` stores nothing of it.

- **New operations** of `plan_changes`/`propose_changes` (fields in [`AGENT-GUIDE.md`](AGENT-GUIDE.md)): `add_container` (called `add_blank_image` in 0.5.0; see "Change in 0.8.0"; `width`, `height`, `background`, `name?`, `source?`, `center?`) and `move_marking` (`marking`, `index`: position among the siblings, 0 = underneath).

Markings carry `order` (position among the siblings; in `get_marking`, `{ index, count }`) and, when they draw a component, `component` (`specId/typeId`) and `minSize`.
- **`get_marking_image` on a container without a file** draws the crop: the background and, in drawing order, the components that cross the region, with the same drawing as `render_container` (`drawing: "rendered"` in the response; see "Drawing image").

### Proposals (stage 4)

Every change made by the agent arrives as a **proposal**, a kind of pull request inside the tool. The file format and the review rules are in [`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md); the agent's flow, in [`AGENT-GUIDE.md`](AGENT-GUIDE.md).

```
my-project/
├── mapping.json                 # only the app writes it
├── images/
└── proposals/
    └── 8c1f2d9e-…/              # proposal id (reference: mapping://<project>/p/8c1f2d9e)
        ├── proposal.json
        └── images/              # new or swapped images, until they are accepted
            └── checkout.webp
```

- **`propose_changes`** applies the operations to a copy of the project (the same code as `plan_changes`, with only the pure operations of `src/model/`), compares before and after entity by entity, field by field (`buildProposal`) and writes the proposal: one change per creation, per removal and per changed field, with the value before (`from`) and after (`to`) and the **final ids** of the created items. An invalid batch writes nothing; a batch that changes nothing is refused (`no-changes`: the re-export matches the project).
- **Images** that are new or swapped wait in `proposals/<id>/images/` (already optimized, as in the app) and only go to `images/` when the user accepts and applies. The file name does not collide with `images/` or with what another proposal may still apply: in an open one, the pending and accepted images; in a superseded one, only the accepted ones (its pending ones can no longer be applied). The operations' `base64` content is not copied into `proposal.json` (which keeps the operations only for reference). By `base64`, each image can be up to 16 MB and the whole message up to ~24 MB (what passes through the protocol's stdin); larger images, up to 64 MB, go by `file`. A message above that ceiling shuts the server down with `mapping-mcp: message larger than N bytes` on stderr.
- **`mapping.json` is never changed by the agent** (neither the migration of an old schema, nor `specs/`): the review, the application of the accepted ones and the writing of the project belong to the app, which uses the same pure functions of the model (`applyAccepted`). There is an integration test over stdio that checks the file's hash after each tool.
- **User review**: decisions (accepted, rejected, no decision) at four levels (proposal, container, item, change) and notes, written by the app in `proposal.json` itself. The file has its own `revision`, with the same check as `mapping.json`: when the server updates a proposal (superseded, withdrawn or revised), it rereads the file immediately before writing, tries again if the app wrote in the meantime and writes `revision + 1`; if the file keeps changing, it refuses with `revision-conflict`.
- **Fixing in the same proposal** (`revise_proposal`): while the proposal is `open` and nothing has been applied, the agent replaces, removes and adds changes in the proposal itself (see "Change in 0.23.0"). Who writes what: the agent writes `changes`, the `decisions` of the replaced and removed ones (which go back to no decision), the `notes` of the removed ones (they go up to the proposal), `revisions` and `formatVersion` 5; the app writes the person's decisions and notes. An accepted change is not touched (`change-frozen`).
- **Superseding** (`supersedes`), for when the fix does not fit in the same proposal (something is already applied, or a new library package): the previous proposal, if still **open**, becomes `superseded` and keeps its decisions and notes. If its review still had changes **without a decision or accepted but not applied**, the response carries the `superseded-incomplete` warning, with the counts and what the new proposal repeats (`same`), changes (`different`) or leaves out (`missing`). A previous one already `applied` stays `applied` (it is history): the response carries `superseded: { status: "applied", note }` and the app shows on it "Applied · superseded by" the new one, derived from the new one's `supersedes`. The count matches changes by origin (`source`), by entity and field and, in creations without an origin (annotations, markings), by the readable path (image › parent › name), even with new ids.
- **Conflicts and lock**: `get_proposal` recomputes each change against the **current** project: if the current value does not match the `from`, the change comes with `conflict` (and the current value); geometry or removal changes on a locked item come with `locked`. Accepting overwrites the current value; rejecting keeps it.
- **In the app**, the proposal appears in the **Proposals** window (Ctrl+Shift+7; on a phone, the Panels menu) and opens in review mode: the canvas shows the project as it would be, the project becomes read-only and the decisions and notes are written in the proposal itself. "Apply accepted" is the only path for changes to enter `mapping.json`. To test the review without an agent, open `examples/proposta-exemplo.zip` in the app.

### Concurrency with the app

`mapping.json` has a `revision`, but the agent does not write it. The proposal keeps the `revision` it was computed on (`baseRevision`); `propose_changes` checks that `mapping.json` did not change while computing and, if it did, refuses with `revision-conflict` (send again). `revise_proposal` rereads `proposal.json` immediately before writing and, if the app wrote in the meantime (a decision by the person), **recomputes everything on the new version** (a replaced change that the person has just accepted becomes `change-frozen`); it also checks that `mapping.json` did not change during the computation (`revision-conflict`) and writes `revision + 1`, with 3 attempts before refusing with `revision-conflict`. If the project changes **after** the proposal, nothing is lost: the affected changes appear as a **conflict** in the review, with the current value, the before and the after, without losing the decisions already taken. In **conversations** (`comments/<id>.json`) the rule is the same: `post_message` and the `propose_changes` message with `thread` reread the file immediately before writing, redo the operation on the disk's version if the app changed it in the meantime (the `after` guard applies to it too) and write `revision + 1`, with 3 attempts before the `revision-conflict`; an unreadable file is not overwritten (`invalid-thread`). The app open on the same folder notices the new proposal (the folder is checked together with `mapping.json`); if there are local changes not yet saved, it asks what to do ("Project changed outside the app") when the project file changes.

### The 60 s limit and `wait_for_comment` (spike of decision 37)

`wait_for_comment` is a tool that **keeps waiting**, and MCP clients cut a call that takes long. Before fixing the deadline, the stage measured what happens, on 2026-11-07, with a test MCP server over stdio (a `wait(seconds)` tool that sleeps and replies):

| Client                                                                    | Wait requested                                             | Result                                                                                           |
| ------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| SDK (`@modelcontextprotocol/sdk` 1.32.1, `Client.callTool`)               | 30 s                                                       | Passes.                                                                                          |
| SDK                                                                       | 70 s                                                       | `MCP error -32001: Request timed out` at 60.0 s (`DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`).        |
| SDK                                                                       | 70 s, with progress, without `resetTimeoutOnProgress`      | Times out at 60 s the same way.                                                                  |
| SDK                                                                       | 70 s, with `onprogress` and `resetTimeoutOnProgress: true` | Passes (70.0 s).                                                                                 |
| Claude Code 2.1.319 (`claude -p … --mcp-config … --strict-mcp-config`)    | 30 s, with and without progress                            | Passes.                                                                                          |
| Claude Code                                                               | 120 s and 600 s, with and without progress every 15 s      | `MCP server "spike" tool "wait" timed out after 60s`: **progress does not extend the deadline**. |
| Claude Code with `MCP_TOOL_TIMEOUT=900000` (ms) in `claude`'s environment | 120 s                                                      | Passes (the tool went to the background and returned `{"waited":120.0}`).                        |

**Conclusion (path (b) of decision 37):** with Claude Code's default, a tool only passes below 60 s. That is why `wait_for_comment`'s `timeoutSeconds` has a **default of 45 and a maximum of 50**, and the agent **repeats the call** (the loop is in "Conversations" of `AGENT-GUIDE.md`). The server sends progress every 15 s to the clients that use it (the SDK's with `resetTimeoutOnProgress` gets the extended deadline), but does not count on it. Whoever raises `MCP_TOOL_TIMEOUT` only gains the convenience of repeating fewer times: the server **never goes past 50 s** in a call.

## Publishing a version (maintainers)

The server's version is **one per epic**: `SERVER_VERSION` in `mcp/version.ts` (today `0.41.0`) is the only `x.y.z` in the code, and the channels below only add a suffix to the build (`MCP_BUILD_SUFFIX`, which `mcp/build.mjs` validates). The workflow `.github/workflows/mcp-prerelease.yml` takes care of the first two; `mcp-release.yml`, of the third.

**Files of each release.** The snapshot, the rc and the stable publish the same files, assembled by `scripts/release/workspaceAssets.mjs` (a single script, one pass per job that compiles; it exits with an error if `examples/workspace/AGENTS.md` does not have exactly one managed block, with the `mapping:begin` and `mapping:end` markers in order). Each has a `.sha256` in the `sha256sum` format (also checked by `shasum -a 256 -c`):

| File                    | What it is for                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `mapping-mcp.js`        | The MCP server.                                                                                                               |
| `setup.sh`              | Copy of `examples/workspace/setup.sh`: installs or updates the workspace at the release's version.                            |
| `SKILL.md`              | The `spec-author` skill from the same commit as the release (copy of `.claude/skills/spec-author/SKILL.md`).                  |
| `AGENTS.mapping.md`     | The managed block of `examples/workspace/AGENTS.md`, between `mapping:begin` and `mapping:end` (markers included).            |
| `watch-comments.mjs`    | Copy of `examples/workspace/watch-comments.mjs`, the conversation watcher: `setup.sh` installs it at the workspace root.      |
| `mapping-signature.mjs` | The Kotlin, Swift and Figma signature extractor (`signature/`, ESM): `setup.sh` installs it at `tools/mapping-signature.mjs`. |

Releases earlier than this one do not have the five files after the server (`watch-comments.mjs` only comes from the first stable with the watcher, and `mapping-signature.mjs` from the first with the extractor; with an older tag, `setup.sh` warns and goes on). Workspaces that still have the old `setup.sh` update once, with the transition line (after the first stable with the new files; before that, replace `latest/download` with `download/<rc tag>` and pass the tag to `./setup.sh`), which also goes in each release's notes:

`setup.sh` downloads those files through the release's direct download and, if GitHub answers 5xx or 429 or does not answer, tries again and uses the assets API (`api.github.com/repos/…/releases/assets/<id>`, without a token), checking the `sha256` the same way; the final error carries the HTTP code (stage #877).

```bash
curl -fsSL https://github.com/fabianofranca/mapping/releases/latest/download/setup.sh -o setup.sh && chmod +x setup.sh && ./setup.sh
```

- **Snapshot per PR (automatic).** Every PR based on an `epic/**` generates a test build in the fixed pre-release `mcp-snapshot-pr<N>` (version `0.41.0-snapshot.pr<N>+<sha>`), overwritten on each push and **deleted (release and tag) when the PR closes**, merged or not (closing cancels a snapshot in progress). The PR's code is compiled in a read-only job (`snapshot-build`); a second job (`snapshot-publish`), without a checkout, is the only one that writes to the Release. Installation: `./setup.sh mcp-snapshot-pr<N>` (see `examples/workspace/`) or download the Release's files.
- **Release candidate by the `mcp-rc` label (automatic).** The merge, into an `epic/**`, of a PR with the `mcp-rc` label (the one of the epic's last phase; the agent of that phase puts the label on when opening the PR) generates the pre-release `mcp-v0.41.0-rc.<n>` (`n` = the version's largest existing rc + 1) from the merge commit, after lint, typecheck and tests. Without the label, the merge does not generate an rc. If it is forgotten, run the "MCP pre-release" workflow by hand (`workflow_dispatch`) on the epic's branch. They are **deleted (release and tag) when the stable is published**.
- **Stable (automatic on the epic's merge).** The stable `mcp-v0.41.0` comes out by itself when the epic enters `main` with a `SERVER_VERSION` that does not have a tag yet; no one creates the tag. On the push to `main`, the workflow `.github/workflows/mcp-release.yml` runs two jobs:

  1. **`decide`** reads `SERVER_VERSION` at the merge commit and checks on the remote whether `mcp-v<version>` exists (`scripts/release/stableRelease.mjs`). If it exists (an epic without a new version, a Dependabot merge), it ends green with the notice "mcp-v<version> already published; nothing to do" and `release` is skipped.
  2. **`release`** (only if the tag does not exist) runs lint, typecheck and tests (without the performance budgets), generates `dist-mcp/mapping-mcp.js`, tests it outside the repository (`--version` prints only the version, e.g. `0.41.0`) and creates the tag and the Release together (`gh release create --target <merge commit>`; a tag created only by the `GITHUB_TOKEN` would not trigger another workflow), with the 10 files and the checksum. The title is the tag's name. Finally, it deletes the pre-releases `mcp-v<version>-rc.<n>`. Two consecutive pushes with the same new version do not publish twice (`concurrency` per tag): the second only attaches the files. An rc tag (`mcp-v<version>-rc.<n>`) pushed by hand does not trigger the stable (`!mcp-v*-*`).

  **Lock on the epic's PR.** The "MCP version" step of the `epic` job (`ci.yml`) fails the PR from `epic/*` to `main` that changes what goes in the release (the entries of `scripts/release/releaseInputs.mjs`: `mcp/`, `src/model/`, the embedded documentation, the `libraries/notas/` library and the sources of the workspace files) and keeps a version that already has a stable: raise `SERVER_VERSION` in `mcp/version.ts` (and the docs that cite it). A new version passes, as long as it is greater than the last stable; without a changed entry, it passes with the notice that the merge does not publish. `package-lock.json` stays out (a Dependabot merge never publishes).

  **Checking the Release after the merge.** Whoever merges the epic (in the automated flow, the orchestrator) finds the "MCP release" run of the merge commit and waits for it. With a new version, it checks that the Release `mcp-v<version>` exists, is not a pre-release, has `mapping-mcp.js`, `setup.sh`, `SKILL.md`, `AGENTS.mapping.md`, `watch-comments.mjs` and `mapping-signature.mjs`, each with its `.sha256`, and that the version's rcs are gone; without a new version, that `release` was skipped.

  **Plan B (manual).** If the workflow failed or the Release was left without the files, fix the cause and create the tag by hand on `main` (`git tag mcp-v0.41.0 && git push origin mcp-v0.41.0`, or Releases › Draft a new release with the new tag), which triggers the same workflow (a Release created earlier through the UI receives the files). For a tag that already exists, run Actions › **MCP release** › Run workflow, with the tag (e.g. `mcp-v0.41.0`): the workflow uses the tag's code and only attaches the files, without deleting or recreating the Release.
