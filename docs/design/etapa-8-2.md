## 3. Retomar a revisão: blob v2 (P2/R3, P3, P5, O5)

### O que fica no `localStorage` (`mapping.reviewResume`)

```ts
interface ResumeBlob {
  readonly v: 2;
  /** `${scope}|${proposalId}` de toda proposta já aberta neste dispositivo. Sem limite, sem LRU. */
  readonly seen: readonly string[];
  /** Posição, visão, filtros e conflitos conhecidos, por `${scope}|${proposalId}`. LRU por cópia. */
  readonly resume: Readonly<Record<string, ReviewResume>>;
}
// ReviewResume = { selected, view, filters, knownConflicts } — o mesmo de hoje (zod, sem mudança).
```

- Validado por zod (`v: z.literal(2)`, `seen: z.array(z.string())`, `resume: z.record(z.string(), resumeSchema)`), sempre em try/catch (via `safeStorage`).
- **Versão ≠ 2, texto corrompido ou formato antigo (o `Record` plano de hoje) → `{ v: 2, seen: [], resume: {} }`**; a primeira gravação substitui o blob. As entradas legadas (`folder:loja|checkout-figma`, as chaves só com o id) **são descartadas**, não migradas (decisão 5 de "Decisões a confirmar": só existem nos dispositivos do dono). Consequência visível, uma vez por dispositivo: toda proposta sem decisão nem nota volta a **Nova** e a revisão reabre na primeira pendente, visão Proposto.
- `MAX_KNOWN_CONFLICTS = 500` continua.
- **LRU do `resume`, por cópia**: ao gravar, as entradas com o prefixo `${scope}|` são reordenadas (a gravada por último) e só as `MAX_RESUME_PER_COPY = 12` mais recentes **dessa cópia** ficam; as de outras cópias não são tocadas. Tamanho do blob limitado a 12 × número de cópias usadas no dispositivo (~300 bytes por entrada; com as ~20 cópias do dono, < 100 KB). Sem teto global.
- **`seen` não tem LRU** nem teto: só ids (`copyId|proposalId`, ~50 bytes). Evictar uma entrada de `resume` **nunca** mexe em `seen` (o teste de eviction da §10 garante). Uma proposta apagada do disco continua em `seen` (inofensivo).

### A chave da cópia: `copyId` (contrato com a 8.4)

- **Tipo esperado** em `ProjectStorage`: `readonly copyId?: string`, **string não vazia**, estável para a mesma cópia física do projeto entre sessões (local: o id do IndexedDB; pasta: o id da entrada dos recentes, que sobrevive a "Localizar"; pasta sem recentes: um id por sessão), **preenchido antes de `openSession` e imutável** durante a sessão. **[D1]** A 8.4 (PR #130, nota aprovada) define o campo em `src/storage/types.ts` exatamente assim e o preenche; **esta fase não edita `src/storage/types.ts`**.
- **Como a 8.2 lê**, com tipagem local em `src/store/review.ts`, sem depender de o campo existir no tipo:

  ```ts
  function copyIdOf(storage: ProjectStorage): string | null {
    const id = 'copyId' in storage ? storage.copyId : undefined; // narrowing do TS: `storage.copyId` é `unknown`
    return typeof id === 'string' && id !== '' ? id : null;
  }
  export function resumeScope(storage: ProjectStorage): string {
    return copyIdOf(storage) ?? legacyScope(storage);

  ```

  Quando a 8.4 mergear, `'copyId' in storage` continua compilando (o campo passa a existir no tipo) e nada mais muda; o `legacyScope` sai nessa hora (ver abaixo).

- **Sem `copyId`** (até a 8.4 mergear, ou numa `ProjectStorage` de teste): `legacyScope(storage)` = `storage.id` se ela for a local (`'id' in storage`, string), senão `storage.folderName ?? ''`. Por que não só `folderName`, como o `PLAN.md` resume: no projeto local não há `folderName`, e cair em `''` faria **todas** as cópias locais compartilharem uma só revisão enquanto a 8.4 não entra. - A **chave final** é `${scope}|${proposalId}` (o id da proposta nunca tem `|`, `PROPOSAL_ID_RE`). Não existe mais `kind:` no prefixo (o `copyId` já distingue as cópias) nem reconhecimento de chave legada: `entriesOf`, `known: null` e o ramo `previous ?? all[id]` somem.

## 5. Conflitos novos (P6)

- `newConflicts = computed(() => conflictIds − knownAtOpen)` enquanto aberta: um conflito que surge **durante** a revisão (recarga externa, `session.sync → reloaded`) aparece como **Conflito novo** na hora, na lista e nos Detalhes (hoje só os da abertura).
- Ao fechar, passam a conhecidos: `knownAtOpen ∪ { conflitos atuais que a pessoa decidiu }`. Decidir um conflito é a prova de que ela o viu; um conflito novo que ficou sem decisão **volta como novo na próxima abertura** (hoje é engolido). Não há estado novo a rastrear (a decisão já está na proposta).
- O teste `tests/store/review.test.ts:484` ("um conflito que aparece durante a revisão já é conhecido na abertura seguinte") **fixa o comportamento errado** e é reescrito: o conflito surgido aparece como novo durante a revisão; decidido, é conhecido na próxima abertura; sem decisão, é novo de novo.

## 6. Aplicar aceitas: `proposal.json` falha depois do `flush` (P7)

Hoje (`proposalActions.ts`, `applyAcceptedChanges`): `before` copia as imagens → `store.apply` (entrada com `HistoryLink`) → `deps.flush()`; se o `flush` falha, `abandoned = true`, `store.undo()`, `discardRedoOf`, `rollback()` e `save-failed`. Mas se o `flush` **passa** e `storage.writeProposal` **falha** (`proposals.ts`, `runMutation` → `write-failed`), nada compensa: o projeto fica aplicado em memória e no disco, a proposta sem `applied`, reaplicar dá `blocked`, imagens duplicadas.

### Desenho (decisão 3 de "Decisões a confirmar": compensar como no `save-failed`)

`MutationPlan` ganha **`compensate?: () => Promise<void>`**: "desfaz o que `before` fez, quando a gravação da proposta falha depois dele". `runMutation`: no `catch` de `writeProposal`, `reportError('proposals.write')`, **`await plan.compensate?.()`** (erro dele só vai ao `reportError`, nunca propaga) e devolve `write-failed`, como hoje. As outras mutações (decidir, anotar, desfazer/refazer a aplicação) não definem `compensate`: nada muda para elas.

Em `applyAcceptedChanges`, `compensate`:

1. `abandoned = true` (o `HistoryLink` deixa de mexer na proposta no desfazer/refazer);
2. `if (applied !== null && store.project.peek() === applied) store.undo()` (a memória volta ao projeto de antes; a sessão vê `committed !== written` e **agenda sozinha** a regravação, contrato §4 da `docs/design/etapa-8-1.md`);
3. `store.discardRedoOf(id)`;
4. **`const saved = await deps.flush()`**: confirma que o disco voltou ao projeto de antes (`revision + 2`). **A ordem importa**: o `mapping.json` em disco ainda cita `images/nova.webp` até esta gravação, e a regra da sessão é "o disco nunca aponta para um arquivo já apagado";
5. se `saved.ok`: `rollback()` (as cópias saem de `images/` por `dropProjectImage`; se o `cleanUp` da sessão já as tirou, `stored.delete` devolve `false` e nada é feito duas vezes). Se `!saved.ok`: as cópias **ficam** (o disco ainda as cita); a gravação continua pendente na sessão ("Erro ao salvar / Tentar de novo") e, quando passar, o `cleanUp` as remove por não estarem no projeto gravado.

Resultado: `{ ok: false, error: 'write-failed' }` (texto existente `proposal.error.writeFailed`, "Não foi possível gravar a proposta."); a proposta no disco é a de antes (as aceitas continuam "aguardando aplicação"), `proposals/<id>/images/…` intacto (`after` não roda), a revisão continua aberta e **aplicar de novo conclui** quando o armazenamento volta. Nenhum estado novo na sessão; o `flush` é chamado duas vezes na mesma mutação, o que o contrato da 8.1 permite ("a direção `proposals → saver` é a permitida").

## 7. Regra de negócio para `src/model/proposalView.ts` (P8, P10, P11)

- **`levelType(level: ReviewLevel, id: string | null, changes: readonly Change[]): ChangeType | null`**: o tipo dominante de um nível (hoje o laço de `levelTypes` em `derived.ts:451-481`): item e imagem pelo tipo da própria entidade, na ordem criada > removida > trocada > alterada, "movida" só se a posição é a única coisa que muda; sem mudança própria, "alterada" se algo dentro mudou; proposta e projeto pelo dominante de tudo. `derived.levelTypes` passa a chamar `levelType` por nó (a memoização continua no `computed`).
- **`proposalListStatus(p: Proposal, progress: ReviewProgress, fresh: boolean): { flag: 'new' | 'inReview' | 'superseded' | 'applied' | 'withdrawn' | null; action: 'review' | 'continue' | 'view'; primary: boolean }`**: o `proposalStatus` de `ProposalRow.tsx:28-70` sem `t()` e sem `showNew` (§4). `ProposalRow` só traduz `flag` → tom + texto.
- **`needsExitReminder(status, acceptedPending)`** sai de `ExitReviewDialog.tsx` para o modelo (trivial; `app/useExitReview.ts` e o diálogo importam do modelo).
- `conflictsOf` (cache por `(changes, applied, project)`) fica em `derived.ts`: é memoização, não regra; a regra é `changeStatus` do modelo.
- **P8**: em `ReviewDetails`, `suggest` da seção Notas = `summary.rejected > 0` (nível) ou `levelState === 'rejected'` (mudança); `partial` deixa de sugerir (O9).
- **P11**: `decide` passa por `withOpen` (sem revisão aberta devolve `{ ok: false, error: 'unknown-proposal' }`, sem mudar a assinatura); `record` recebe o id da proposta em vez de `proposalId.peek() ?? ''`; `close` com proposta apagada por fora não grava resume (§3).
