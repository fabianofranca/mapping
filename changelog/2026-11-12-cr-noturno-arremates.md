# Nightly CR: scheduling finishing touches — 2026-11-12 (epic `epic/cr-noturno-arremates`, PR #1760, MCP 0.38.1 unchanged, schema v19)

## Alterado

- The "How it runs" of the per-epic CR (`docs/FLOW.md`, "Code review") gains six finishing touches for whoever drives the flow. The coordinator finds the round's issue through a REST listing of the `code-review` issues (one call per page of 100, without `search/issues`, which accepts only 30 calls per minute) before running `riskTriggers.mjs`, in a single shell loop; the epics that already have an issue do not even go through `git checkout`. Each reviewer gets one attempt per epic: at the 90-minute fallback check, the `status_bucket` decides (`working` waits longer, `blocked` warns the owner, `failed` or no issue becomes the round's issue "A revisão automática falhou", created by the coordinator with the `cr-epic` marker, and the review goes to the backlog). Step 1 records that `main` accepts only a merge commit. The "Known limitations" say that the trigger criterion does not check whether the `/code-review high` ran at closing (owner's decision of 2026-11-12), that the search accepts 30 calls per minute and that the script of step 3 runs every night on the epics with a trigger, locally. The scheduling prompt changes only through the coordinator's conversation (`update_trigger` with `prompt` is refused in another session): whoever changes the reviewer block or the steps puts the whole new prompt in the epic's PR description, with the line "Dono: aplicar este prompt no CR por épico", and the owner applies it. The reviewer's MODEL MESSAGE does not change. `tests/tooling/epicCodeReview.test.ts` checks the new text (listing before the script, `status_bucket`, one attempt per epic, merge commit and the same date in every `--shallow-since`).
