# Servidor MCP do Mapping

O servidor MCP deixa um agente (Claude Code, Claude Desktop ou outro cliente MCP) **ler projetos Mapping guardados em pasta e propor alterações a eles**, com as mesmas regras da app (invariantes, travas, referências, especializações). O agente **nunca grava o `mapping.json`**: toda alteração chega como uma **proposta** em `proposals/`, que o usuário revisa na app (aceita ou rejeita em qualquer nível, com notas) e aplica. Ele roda localmente, por stdio, no Node (≥ 20), e não faz nenhuma requisição de rede.

Só projetos **em pasta** ficam ao alcance do MCP; projetos guardados no navegador, não. Para usar o servidor, crie ou abra o projeto na app como **pasta**.

## Instalação

1. Baixe `mapping-mcp.js` da [última Release `mcp-v*`](../../../releases) (há também um `mapping-mcp.js.sha256` para conferir: `sha256sum -c mapping-mcp.js.sha256`). Para testar algo ainda não publicado, baixe de uma pre-release: `mcp-snapshot-pr<N>` (o build de um PR de fase, antes de entrar no épico) ou `mcp-v0.5.0-rc.<n>` (a release candidate do épico, gerada no merge da última fase). Elas anunciam a versão com sufixo em `--version` (`0.5.0-snapshot.pr172+abc1234`, `0.5.0-rc.1`).
2. Copie o arquivo para `tools/` no repositório do app. Ele é autocontido (dependências, WebAssembly de imagem e documentação embutidos): não precisa de `npm install`.
3. Registre o servidor num `.mcp.json` na raiz do repositório:

   ```json
   {
     "mcpServers": {
       "mapping": {
         "command": "node",
         "args": ["tools/mapping-mcp.js", "--root", "design/mapeamentos"]
       }
     }
   }
   ```

4. Abra o Claude Code (ou outro cliente) no repositório e aprove o servidor `mapping`. As tools aparecem como `mcp__mapping__…`.

> **Repositório com `"type": "module"` no `package.json`:** o arquivo é CommonJS. Coloque ao lado dele, em `tools/`, um `package.json` com `{"type":"commonjs"}`; sem isso o `node` o lê como módulo ES e falha.

Teste fora do cliente: `node tools/mapping-mcp.js --version` e `--help`.

> **Pasta central de mapeamentos.** Para guardar vários projetos numa pasta só, pronta para qualquer cliente MCP (Claude Code, Cursor, Gemini CLI, Copilot, Codex), copie [`examples/workspace/`](../examples/workspace/): o `setup.sh` baixa o servidor da release, confere o `sha256` e traz a skill `spec-author`; o `AGENTS.md` explica a pasta ao agente.

## Raízes

`--root <pasta>` define onde o servidor pode ler e gravar; repita para mais de uma. Caminhos relativos valem a partir do diretório de trabalho do cliente (o repositório, quando o `.mcp.json` é do projeto). O argumento `root` do `create_project` aceita a raiz do mesmo jeito: como está no `--root` (relativa, com `./` ou barra final), absoluta, como listada em `roots` pelo `list_projects`, ou pelo nome da pasta, se só uma raiz o tiver. O servidor procura projetos (pastas com `mapping.json`) em qualquer profundidade dentro das raízes.

Segurança: o servidor só lê e grava dentro das raízes. Recusa `..`, caminhos absolutos fora delas e links simbólicos que saem delas (`outside-roots`); não segue links ao procurar projetos; e grava de forma atômica (arquivo temporário + renomear) o projeto vazio e as atualizações de uma proposta; os arquivos novos de uma proposta vão por arquivo temporário + hard link, que nunca sobrescreve (num disco sem hard link, como exFAT, grava direto, ainda sem sobrescrever). Apagar o temporário é melhor esforço (desde a 0.3.4): se o sistema recusa (antivírus do Windows, pasta montada numa VM), o arquivo gravado vale, o servidor escreve um aviso no stderr e o `.<arquivo>.<x>.tmp` fica na pasta da proposta; nem a app nem o servidor o leem, e ele pode ser apagado à mão. O que ele grava: o projeto vazio do `create_project` e a pasta `proposals/` (propostas e as imagens delas). **O `mapping.json`, as cópias de `specs/` e `images/` só a app grava**, ao aplicar uma proposta. Ler nunca grava, nem para migrar um projeto de schema antigo: a migração (com backup em `backups/`) é da app, na primeira gravação; a proposta é calculada sobre o projeto migrado em memória. A única exceção ao "só dentro das raízes" é a conferência de **existência** de arquivos de código, que olha só metadados (`stat`) e fica confinada ao diretório de trabalho do cliente (ver "Código das especializações").

## Referências

O Ctrl+C (Cmd+C) na app, com uma marcação, imagem ou anotação selecionada, copia a referência:

```
mapping://<projeto>/<m|i|a|p>/<código> (<caminho legível>)
```

- `<projeto>`: nome da pasta do projeto. Se houver duas pastas com o mesmo nome, o servidor devolve as candidatas e pede o caminho.
- `m` marcação, `i` imagem, `a` anotação, `p` **proposta** (a que `propose_changes` e `list_proposals` devolvem).
- `<código>`: os 8 primeiros caracteres hexadecimais do id (12, 16… se houver colisão).
- `(<caminho legível>)`: só para leitura humana; o servidor o ignora.

Toda tool que recebe um item (`ref`) aceita a referência completa, só `m/3f2a9c1e` com `project` informado à parte, ou o id completo. Cole a referência no chat e o agente a resolve sem precisar do projeto. Nas tools de proposta, `ref` é `mapping://projeto/p/3f2a9c1e`, `p/3f2a9c1e` (com `project`) ou o id da proposta; o código é único entre as propostas do projeto. **Ctrl+Alt+C** copia o recorte da marcação como PNG.

### Código das especializações (etapas 3b e 9)

As especializações podem declarar **plataformas** e dizer como cada tipo de anotação vira código nelas (`code`: o componente, o arquivo que o define, os parâmetros e as orientações), e o projeto guarda o repositório de cada plataforma (`platformRepos`: `urlTemplate` e `localPath`). O mapeamento guarda só o que ajuda a **gerar** código; desde a 0.4.0 (schema v9) não há mais o campo `codeRef` (onde a instância foi implementada). Detalhes do formato em [`FORMAT.md`](FORMAT.md) e [`SPEC-FORMAT.md`](SPEC-FORMAT.md). O fluxo do agente está em [`AGENT-GUIDE.md`](AGENT-GUIDE.md): referência `mapping://` → `get_marking` e `get_marking_image` → `get_code_hints` → implementar.

O `path` do `code` de um tipo (o arquivo que define o `symbol`) volta no `code` de `get_marking` e `get_annotation`, na anotação de `get_code_hints` e no `code` de `find_by_code`, com o endereço e o arquivo local ao lado:

```json
{
  "symbol": "com.app.ds.DSButton",
  "path": "app/src/main/java/com/app/ds/DSButton.kt",
  "url": "https://github.com/org/app-android/blob/main/app/src/main/java/com/app/ds/DSButton.kt",
  "localFile": "app/src/main/java/com/app/ds/DSButton.kt",
  "exists": true
}
```

- `url`: do `urlTemplate` da plataforma (`null` sem ele); o caminho não tem linha.
- `localFile`: o `localPath` da plataforma (relativo à pasta do projeto) mais o `path`, **relativo ao diretório de trabalho do cliente** (o do processo do servidor; no Claude Code, o repositório). `exists` diz se o arquivo está lá. Sem `localPath`, os dois são `null`.
- `find_by_code` vai do arquivo (ou símbolo) para os tipos que o usam e as anotações desses tipos (formato no [`AGENT-GUIDE.md`](AGENT-GUIDE.md)).
- **O servidor nunca lê nem grava arquivos de código**: só monta o caminho e confere a existência (`stat`), o que é coberto por teste. O agente lê o arquivo com as próprias ferramentas.
- **Limite de segurança**: o `localPath` pode subir pastas (`../../..`) e o `path` vem de um arquivo que outras pessoas podem editar. Por isso a conferência só olha **dentro do diretório de trabalho do cliente**, também depois de seguir links simbólicos. Se o caminho calculado sai dele, a resposta traz `localFile: null`, `exists: null` e `localFileProblem: "outside-workdir"` (sem tocar no disco); um link simbólico que leva para fora vale `exists: false`. Para o `localFile` aparecer, abra o cliente na raiz do repositório do app (o que o `.mcp.json` do projeto já faz).
- `get_project` traz `platforms` (as declaradas pelas especializações aplicadas), `platformRepos` e `warnings` (`missing-repo`: plataforma em que algum tipo tem `path`, sem `urlTemplate` nem `localPath`; `types` diz quantos tipos). `plan_changes` e `propose_changes` repetem os `warnings` do projeto resultante.
- **Mudança incompatível da 0.4.0**: as respostas não trazem mais `codeRefs`; `find_by_code` devolve tipos (com as anotações deles) em vez de entradas de `codeRef`; o aviso `missing-repo` conta `types` em vez de `entries`; um valor para o campo removido no lote falha com `unknown-field`. Use a 0.4.0 com a app da mesma época (schema v9): um projeto v8 é migrado na leitura, em memória.

### Biblioteca de componentes (0.5.0)

A especialização `formatVersion` 4 é um **pacote** (uma pasta com a especialização, `components/`, `docs/`, `examples/` e `fonts/`; ver [`SPEC-FORMAT.md`](SPEC-FORMAT.md), "Biblioteca: o pacote"). O servidor **valida, lê e leva o pacote numa proposta**; quem aplica (copia a pasta para `specs/<pasta>/`) é a app, na revisão.

- `validate_library({ path, previous?, level? })`: `path` é a pasta do pacote ou o arquivo da especialização dentro dela (relativo a uma raiz ou absoluto dentro delas). Lê a pasta (textos só de `.json` e `.md`; fontes e outros arquivos contam como presentes, sem ler o conteúdo; links simbólicos não são seguidos; no máximo 2000 arquivos e 32 MB de texto, senão `package-too-large`) e chama `validateLibrary`, a mesma função da app e da skill. `previous` é o arquivo da versão anterior da especialização e liga o contrato de versão (quebra sem `migrations` é erro); `level` (1, 2 ou 3, padrão 3) limita até onde validar. A resposta traz `valid` (sem nenhum `error`), `path`, `spec` (resumo com contagens de componentes, documentos, exemplos, fontes, origens e migrações), `summary` (o nível que rodou e as contagens do pacote), `errors` e `warnings` (cada um `{ file, path, message, severity }`; no máximo 100 de cada, com `moreErrors`/`moreWarnings` quando há mais) e `hint`. **Erro impede usar, aviso deixa usar.** Uma pasta sem especialização devolve `valid: false` com o motivo. Não aplica nada a projeto algum.
- `validate_specialization` aceita a `formatVersion` 4 mas valida só o **arquivo**; o resumo ganha `components`, `docs`, `examples`, `fonts`, `origins` e `migrations`, e a `hint` manda usar `validate_library` para o pacote.
- `list_components` e `get_component` leem a biblioteca **aplicada** (`project` + `specId`: a cópia em `specs/<pasta>/`, a pasta do `file` da especialização) ou um pacote qualquer (`path`). `list_components` devolve, por tipo com componente, `type`, `name`, `layer`, `size` e `minSize` (px), `hasDoc` e `examples` (quantidade). `get_component` devolve, para um `type` (id ou nome): `doc` (o markdown), `fields`, `examples` (`values`, ou `system` + `file` com o `json` do exemplo externo quando tem até 16 KB), `code`, `sources` e `component` (o JSON do arquivo). Um tipo sem componente ou documento não é erro: vem `hasComponent: false` e uma `hint`. Tipo inexistente: `unknown-type`.
- `get_specialization` devolve a v4 inteira (nada é descartado) e, quando a cópia do projeto é uma pasta `specs/<id>/`, `package: { dir, files }`.
- `plan_library_update({ project, path })`: a prévia, **somente leitura**, de aplicar ou atualizar a biblioteca de `path` (a pasta do pacote novo ou o arquivo da especialização dentro dela; também um arquivo v1 a v3) no `project`. Devolve `specId`, `from` (versão aplicada, `null` se não está) e `to`, `decision` (`apply`, `update` ou `not-newer`), `validation` (`valid`, `errors`, `warnings`; na atualização a cópia aplicada é o `previous`) e, em `update`: `additive`, `refused` (quebra sem migração) com `missingMigrations`, `changes` (`code`, `kind`, `path`, `message`), `steps` (a `step` com `op` e chaves, e `annotations`, `values`, `converted`, `deleted`, `refs`, `lossCount` e as `losses` do passo), `losses` (`reason`, `message`, a anotação e a marcação em texto e em referência, `field`, `rowId` e `value`), `pending` (a anotação, `code` e `field`), `brokenRefs`, `addedLayers`, `freedLayers` e uma `hint`. Listas passam de 100 itens cortadas, com o total em `changesTotal`, `lossesTotal`, `pendingTotal`, `stepsTotal` e `missingMigrationsTotal`.
- **`apply_specialization` e `update_specialization` aceitam a pasta do pacote v4** em `file` (ou o arquivo da especialização dentro dela; v1 a v3 seguem por arquivo). O servidor lê a pasta (binários inclusive, até 500 arquivos e 64 MB, o limite da app), valida com `validateLibrary` (na atualização, com a cópia aplicada como `previous`) e: erro de validação → `invalid-library` (com os primeiros erros); versão não maior → `spec-not-newer`; quebra sem migração → `spec-missing-migrations` com `missingMigrations`. Avisos seguem e voltam em `warnings` (`library-warning`). O projeto proposto vem do modelo (`packageSpecName` = o arquivo da especialização, a pasta `specs/<id>/`; a atualização executa as `migrations` nas anotações), e **os arquivos do pacote são gravados em `proposals/<id>/specs/<pasta>/…`** (o mesmo princípio de `proposals/<id>/images/`; `files.packages` na resposta lista as pastas e a contagem de arquivos). Ao aplicar, a app **copia** a pasta para `specs/<pasta>/` e valida o pacote; o servidor nunca grava `specs/` nem o `mapping.json`. A descrição da operação resume a migração (passos, valores alterados, anotações convertidas ou apagadas, valores perdidos, pendências) e a proposta traz as mudanças `values.*` de cada anotação migrada.
- **Mudança da 0.5.0**: tools novas (`plan_library_update`), pacote v4 aceito na proposta (aplicar e atualizar com a pasta), e as operações e campos das telas com componentes (próxima seção); nada do que existia mudou de formato. Use a 0.5.0 com a app da mesma época (schema v10): um projeto v9 é migrado na leitura, em memória.

### Telas com componentes (0.5.0)

O schema v10 tem a **tela em branco** (imagem sem arquivo: `file: null`, com `width`, `height` e `background`) e a biblioteca de componentes desenha instâncias nela. O servidor lê os componentes das especializações em pasta (`specs/<id>/`) uma vez, ao carregar o projeto, e os usa só para **medir e conferir**; ele **nunca arruma** os filhos de um container (quem usa Arrumar é a pessoa, na app) e nunca grava desenho: o `mapping.json` não guarda nada dele.

- **Operações novas** de `plan_changes`/`propose_changes` (campos em [`AGENT-GUIDE.md`](AGENT-GUIDE.md)): `add_blank_image` (`width`, `height`, `background`, `name?`, `source?`, `center?`) e `move_marking` (`marking`, `index`: posição entre as irmãs, 0 = por baixo).
- **Operações mudadas**: `update_image` aceita `background`, `width` e `height` numa tela em branco (numa foto, `not-blank`); `create_marking` aceita `annotation` (`type`, `name?`, `values?`; cria a marcação e a anotação tipada de uma vez) e `annotationAs`, e, quando o tipo tem componente, dispensa `rect` (tamanho inicial do componente, dentro do slot do `parent` ou no centro da imagem); `create_marking` e `update_marking` com `rect` respeitam o `minSize` do componente (`rect-too-small`, com o mínimo na mensagem).
- **Leitura**: `get_project`, `get_image` e `get_marking_image` dizem que a imagem é uma tela em branco (`blank: true`, `file: null`, `background`); `get_image_file` numa tela em branco falha com `blank-image`. As marcações trazem `order` (posição entre as irmãs; em `get_marking`, `{ index, count }`) e, quando desenham um componente, `component` (`specId/typeId`) e `minSize`.
- **`get_marking_image` numa tela em branco** desenha o recorte: o fundo e, em ordem de desenho, os componentes que cruzam a região, num **desenho simplificado** (`drawing: "simplified"` na resposta): formas com cantos arredondados, elipses e caminhos preenchidos; gradiente vira a cor do primeiro stop; imagem vira um reservado cinza; sombras e tracejado são ignorados; e **o texto vira barras** (uma por linha, na cor do texto), porque o servidor não tem fontes. O texto é medido por um medidor aproximado, então as quebras de linha podem diferir da app. Serve para conferir posição, tamanho e hierarquia, não o acabamento.
- Tudo desta seção faz parte da 0.5.0 (a Biblioteca sai numa versão só, por épico).

### Propostas (etapa 4)

Toda alteração feita pelo agente chega como uma **proposta**, uma espécie de pull request dentro da ferramenta. O formato do arquivo e as regras da revisão estão em [`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md); o fluxo do agente, em [`AGENT-GUIDE.md`](AGENT-GUIDE.md).

```
meu-projeto/
├── mapping.json                 # só a app grava
├── images/
└── proposals/
    └── 8c1f2d9e-…/              # id da proposta (referência: mapping://<projeto>/p/8c1f2d9e)
        ├── proposal.json
        └── images/              # imagens novas ou trocadas, até serem aceitas
            └── checkout.webp
```

- **`propose_changes`** aplica as operações a uma cópia do projeto (o mesmo código do `plan_changes`, só com as operações puras do `src/model/`), compara o antes e o depois entidade por entidade, campo por campo (`buildProposal`) e grava a proposta: uma mudança por criação, por remoção e por campo alterado, com o valor antes (`from`) e depois (`to`) e os **ids definitivos** dos itens criados. Um lote inválido não grava nada; um lote que não altera nada é recusado (`no-changes`: a reexportação coincide com o projeto).
- **Imagens** novas ou trocadas esperam em `proposals/<id>/images/` (já otimizadas, como na app) e só vão para `images/` quando o usuário aceita e aplica. O nome do arquivo não colide com `images/` nem com o que outra proposta ainda pode aplicar: numa aberta, as imagens pendentes e aceitas; numa substituída, só as aceitas (as pendentes dela não podem mais ser aplicadas). O conteúdo `base64` das operações não é copiado para o `proposal.json` (que guarda as operações só para referência). Por `base64`, cada imagem tem até 16 MB e a mensagem inteira até ~24 MB (o que passa pelo stdin do protocolo); imagens maiores, até 64 MB, vão por `file`. Uma mensagem acima desse teto encerra o servidor com `mapping-mcp: mensagem maior que N bytes` no stderr.
- **O `mapping.json` nunca é alterado pelo agente** (nem a migração de um schema antigo, nem `specs/`): a revisão, a aplicação das aceitas e a gravação do projeto são da app, que usa as mesmas funções puras do modelo (`applyAccepted`). Há teste de integração por stdio que confere o hash do arquivo depois de cada tool.
- **Revisão do usuário**: decisões (aceita, rejeitada, sem decisão) em quatro níveis (proposta, imagem, item, mudança) e notas, gravadas pela app no próprio `proposal.json`. O arquivo tem `revision` própria, com a mesma conferência do `mapping.json`: quando o servidor atualiza uma proposta (substituída ou retirada), relê o arquivo imediatamente antes de gravar, tenta de novo se a app gravou no meio e grava `revision + 1`; se o arquivo não para de mudar, recusa com `revision-conflict`.
- **Substituir** (`supersedes`): a proposta anterior, se ainda **aberta**, passa a `superseded` e mantém as decisões e notas. Se a revisão dela ainda tinha mudanças **sem decisão ou aceitas sem aplicar**, a resposta traz o aviso `superseded-incomplete`, com as contagens e o que a proposta nova repete (`same`), altera (`different`) ou deixa de fora (`missing`). Uma anterior já `applied` continua `applied` (é histórico): a resposta traz `superseded: { status: "applied", note }` e a app mostra nela "Aplicada · substituída por" a nova, derivado do `supersedes` da nova. A contagem casa as mudanças pela origem (`source`), pela entidade e campo e, nas criações sem origem (anotações, marcações), pelo caminho legível (imagem › pai › nome), mesmo com ids novos.
- **Conflitos e trava**: o `get_proposal` recalcula cada mudança contra o projeto **atual**: se o valor atual não bate com o `from`, a mudança vem com `conflict` (e o valor atual); mudanças de geometria ou remoção num item trancado vêm com `locked`. Aceitar sobrescreve o valor atual; rejeitar o mantém.
- **Na app**, a proposta aparece na janela **Propostas** (Ctrl+Shift+7; no celular, menu Painéis) e abre no modo revisão: o canvas mostra o projeto como ficaria, o projeto fica somente leitura e as decisões e notas são gravadas na própria proposta. "Aplicar aceitas" é o único caminho para as mudanças entrarem no `mapping.json`. Para testar a revisão sem um agente, abra `examples/proposta-exemplo.zip` na app.

### Concorrência com a app

O `mapping.json` tem `revision`, mas o agente não o grava. A proposta guarda a `revision` sobre a qual foi calculada (`baseRevision`); o `propose_changes` confere que o `mapping.json` não mudou enquanto calculava e, se mudou, recusa com `revision-conflict` (envie de novo). Se o projeto mudar **depois** da proposta, nada é perdido: as mudanças afetadas aparecem como **conflito** na revisão, com o valor atual, o antes e o depois, sem perder as decisões já tomadas. A app aberta na mesma pasta percebe a proposta nova (a pasta é conferida junto com o `mapping.json`); se houver alterações locais ainda não gravadas, pergunta o que fazer ("Projeto alterado fora da app") quando o arquivo do projeto mudar.

## Solução de problemas

A tabela abaixo cobre o que costuma aparecer na instalação e no uso; a lista completa dos códigos de erro e de aviso, com o significado de cada um, está em [`AGENT-GUIDE.md`](AGENT-GUIDE.md), seção "Erros" (o registro é `mcp/errors.ts`).

| O cliente não lista as tools                                                 | Confira o caminho de `args` (relativo ao diretório de trabalho do cliente), a versão do Node (`node --version` ≥ 20) e se aprovou o servidor. Rode `node tools/mapping-mcp.js --help`.                                                                    |
| `SyntaxError: Cannot use import statement` / `require is not defined`        | O repositório declara `"type": "module"`: ponha `{"type":"commonjs"}` num `package.json` em `tools/` (veja Instalação).                                                                                                                                   |

Crie-a ou corrija o `--root`.                                                                                                                                                    |

Ao substituir ou retirar: o `proposal.json` não parava de mudar (a app está gravando decisões); tente de novo.                                               |

## Publicar uma versão (mantenedores)

A versão do servidor é **uma por épico**: `SERVER_VERSION` em `mcp/version.ts` (hoje `0.5.0`, a da etapa Biblioteca) é o único `x.y.z` do código, e os canais abaixo só acrescentam um sufixo ao build (`MCP_BUILD_SUFFIX`, que o `mcp/build.mjs` valida). O workflow `.github/workflows/mcp-prerelease.yml` cuida dos dois primeiros; o `mcp-release.yml`, do terceiro.

- **Snapshot por PR (automático).** Todo PR com base num `epic/**` gera um build de teste na pre-release fixa `mcp-snapshot-pr<N>` (versão `0.5.0-snapshot.pr<N>+<sha>`), sobrescrita a cada push e **apagada (release e tag) quando o PR fecha**, mesclado ou não. Instalação: `./setup.sh mcp-snapshot-pr<N>` (ver `examples/workspace/`) ou baixe os arquivos da Release.
- **Release candidate pelo rótulo `mcp-rc` (automático).** O merge, num `epic/**`, de um PR com o rótulo `mcp-rc` (o da última fase do épico; o agente dessa fase põe o rótulo ao abrir o PR) gera a pre-release `mcp-v0.5.0-rc.<n>` (`n` = maior rc existente da versão + 1) a partir do commit do merge, depois de lint, typecheck e testes. Sem o rótulo, o merge não gera rc. Se esquecerem, rode o workflow "MCP pre-release" à mão (`workflow_dispatch`) no branch do épico. Elas são **apagadas (release e tag) quando a estável é publicada**.
- **Estável (o dono).** Depois do merge do épico na `main`:

1. Confirme que `SERVER_VERSION` em `mcp/version.ts` (`0.5.0`) e as versões desta seção batem (o teste `tests/mcp/version.test.ts` confere) e que isso já está na `main`.
2. Crie a tag `mcp-v0.5.0` na `main`: `git tag mcp-v0.5.0 && git push origin mcp-v0.5.0`, ou crie a Release pela tela do GitHub (Releases › Draft a new release, tag nova `mcp-v0.5.0` na `main`), que cria a tag junto.
3. O workflow `.github/workflows/mcp-release.yml` confere que a tag bate com `SERVER_VERSION` (tags de rc e de snapshot nunca o disparam), roda lint, typecheck e testes (sem os orçamentos de desempenho), gera `dist-mcp/mapping-mcp.js`, o testa fora do repositório (`--version` imprime só `0.5.0`) e o anexa à Release com o checksum: cria a Release se ela não existe, ou anexa os arquivos à que já existe. O título da Release é o nome da tag. Por fim, apaga as pre-releases `mcp-v0.5.0-rc.<n>`.
4. Confira que a Release tem `mapping-mcp.js` e `mapping-mcp.js.sha256`. Se ficou sem eles (o workflow falhou), corrija a causa e rode de novo pela tela: Actions › **MCP release** › Run workflow, com a tag (ex.: `mcp-v0.5.0`). O workflow usa o código da tag e só anexa os arquivos, sem apagar nem recriar a Release.
