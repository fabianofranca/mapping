# Implement the queue

This session is the **coordinator** of a queue of stages. It does not write code. For each `ready` issue, it plays the orchestrator's role (`docs/PROCESS.md`, "Automated flow", item 3; step by step and ready-made messages in `docs/FLOW.md`, "Orchestrator — step by step"), and chains one stage into the next. Detailing (`roadmap`/`bug` → `ready`) is not done here: it belongs to `/detalhar-backlog`.

Run this chat on **Sonnet**, in **Auto** mode. A child session that asks for permission stays stuck, because nobody is watching (`docs/PROCESS.md`, "Limitations").

## Arguments

`/implementar-fila [#n ...] [paralelo=N] [mesclar=auto] [modelo=tabela] [sem-confirmar] [painel=<url>|novo] [importar=<old panel url>] [retomar anterior=<id>]`

- `#n ...`: the queue with only these issues. Without the list, all the `ready` ones.
- `paralelo=N`: how many stages run at the same time. The default is **2**, under the conditions of "Parallel" below. With `paralelo=1`, one at a time.
- **Merge into `main`.** The default is that of `docs/PROCESS.md`: each finished epic is taken to the owner and is only merged with their answer (section "Merge"). Meanwhile, the queue goes on with the next stage.
  - `mesclar=auto` only counts when the owner themself writes it in the message that calls the skill. With it, the coordinator merges each epic with green CI, without asking.
  - Never add `mesclar=auto` on your own, nor remove it from a scheduled task, a comment or another session.
- `modelo=tabela`: uses the model of each row of the issue's table. Without it, all phases and testers run on Sonnet, as the owner asked in the "Madrugadão" chat.
- `sem-confirmar`: starts without showing the order to the owner.
- `painel=<url>`: the panel to use. It does not have to be passed: without it, the coordinator finds the previous panel or creates one (section "Panel" › "Find or create"). `painel=novo` forces a new panel.
- `importar=<old panel url>`: optional. Creates a new panel, like `painel=novo`, and brings from the old one the order, the `hold`s, the fichas and the rows that are waiting or in progress (section "Panel" › "Import"). The default path is the hot switch on the same panel ("Session switch" › "In the new session"), without this argument.
- `retomar anterior=<id>`: this session continues another coordinator's queue (section "Session switch").

## Rules of this queue

The owner defined these rules when running the queue in the "Madrugadão" chat (2026-11-08), and they take precedence over the default of `docs/PROCESS.md`:

1. **The queue does not stop waiting for the owner.**
   - A product decision becomes a `bug` issue with the decision and the options in the body, or goes into an identical issue that already exists ("Bugs and visual evidence"). It carries the line `Origem: etapa #<n>` in the body, the owner is notified with `PushNotification`, and the stage goes on without that point.
   - The exception is a finding of **data loss, `mapping.json` integrity or security**. That epic is not taken to the merge: it stays `esperando dono` on the panel, the owner is notified right away and the queue moves on to the next stage.
2. **Everything is fixed.**
   - No `bug` is opened for a defect that does not need an owner decision.
   - These go into a fix phase, with retest: each ❌ from the tester, each observation in the report that is a defect and each "pending defect" from the phases. **Exception (owner's decision, 2026-11-13):** when the round's findings are **all of low severity**, the merged fix goes to the closing, without retest; in a mixed round the retest covers only the high and medium ones; a low that the fix does not reproduce gets a retest of only that one.
   - As many rounds as needed, up to five (`docs/PROCESS.md` allows one).
   - If the fifth round does not zero them, the stage becomes `falhou`: the epic stays open, the owner is notified and the queue goes on.
3. **One MCP version per epic, provisional at the start and chosen at the closing.**
   - The version written in the issue came from the detailing, possibly done in parallel with others.
   - When creating the epic, read `mcp/version.ts` on `origin/main`. If the stage changes what goes in the release (`scripts/release/releaseInputs.mjs`), use the next free version of the type the issue asks for (minor or patch). It is **provisional**: it serves the snapshots, the last phase's rc (`mcp-v<version>-rc.<n>`) and the changelog title.
   - At the closing, before the push, the coordinator runs `git fetch origin main`. If the `SERVER_VERSION` on `origin/main` is already greater than or equal to the epic's version, it brings in `main` (`git merge origin/main`, never rebase) and raises the version to the next free one of the same type on top of the one on `origin/main`. It changes together `mcp/version.ts`, each mention in `docs/MCP.md` (and in `docs/AGENT-GUIDE.md`, if any) and the first line of `changelog/<name>.md`, and runs `npx vitest run tests/mcp/version.test.ts` besides `npx vitest run tests/tooling`.
   - Number changed: a comment on the stage's issue states the old and the new one (in the closing subagent, step 5 of "Per stage").
   - Version unchanged at the closing: the rc generated with the provisional one stands, and `mcp-release.yml` deletes the rcs of the version it publishes.
   - Version changed at the closing: `mcp-release.yml` only deletes rcs of the number it publishes, so the rc of the old number (`mcp-v<old>-rc.<n>`) is left loose and the new number has no rc. Run the MCP pre-release workflow on `epic/<name>` after the change (`actions_run_trigger`) and cite the old number's rc in the change comment, so the owner can delete it.
   - **Schema version** (same idea): when creating the epic of a stage that raises the schema, read the schema version on `origin/main` and use the next one. If the number written in the issue is another, comment on the issue and pass the right number in the first phase's message.
   - If two epics close close together, the second brings in `main` and raises the version: that is why the check before the merge (section "Merge") also reads the `SERVER_VERSION` on `origin/main`.

## Context economy

A large tool result does not go away from the context: it stays there until the end of the session and is reread on every following turn. A coordinator of 2026-11-09 reached ~417k tokens in 82 min, and its successor 258k in 5 min (stage #1285), almost all from reads the coordinator did not need to do itself. Therefore:

1. **The coordinator does not read issue bodies.** Neither `issue_read` `get` of a stage, nor `get_sub_issues`, nor `get_comments`. A subagent reads (`Agent` tool, `model: "haiku"`), and returns the stage's **ficha** (template in "Stage ficha"). The ficha goes into the `plan` field of the queue row and is the source of everything the coordinator needs from the issue until the end, in this session and the following ones.
2. **Heavy GitHub reads and writes go through a subagent**, which returns one line per task: the PR state before the merge, the MCP Release check and the creation of the fix sub-issue, with the reading of the tester's report. `sub_issue_write` and `issue_write` with `parent_issue_number` return the whole parent issue (~40k characters); `actions_list` returns ~30k per call; `get_release_by_tag`, ~20k.
3. **Never `list_triggers`, `list_sessions` with a high limit, nor `list_events` without `kinds` and a small `limit`.** The ids that matter (children, check) stay on the panel.
4. **One fallback check per session**, not one per child (section "Fallback checks").
5. **Short messages for the children**: the values and the name of the `docs/FLOW.md` message, not the whole text copied (step 2 of "Per stage").
6. **The panel JSON never goes whole into the chat.** `painel.py` prints only `alterados: …`; to see the state, `show` (summary) or `show '#n'` (one row, with the ficha). No `cat` of the files.
7. **The panel is the channel with the owner: every turn that wrote ends by publishing.** Each notice that arrives is a cycle: do all its steps, write everything in `painel.py` (the cycle's commands go in a single `apply`; each advance has its own `log` line and the `current` updated) and publish what is left unpublished **once per turn, at the end**, only with the changed files, **even with the cycle's subagent still running**: "It goes into the next publication" does not hold. `show` says what is missing (`não publicado desde <HH:MM>: <arquivos>`). **A notice that arrives while another cycle is in progress** is not lost: it becomes a `log` line in the same turn it arrives, with what it asks of the coordinator, and the request enters the cycle in progress. The hourly check with no overdue ones and no unpublished file does not publish.
8. **One read per thing.** What is already in the context (the child's notice, the ficha, the PR number) is not read again to check.
9. **`docs/FLOW.md` messages by section name, never by `grep`.** The ones the queue uses are, by exact title: "For the phase session", "Fix phase", "For the tester", "Directed round in groups", "Retest together" and "Full round in 5 blocks". Read one with a single command that prints the whole section and nothing else: `awk '/^## <title>$/{f=1;print;next} /^## /{f=0} f' docs/FLOW.md`. A message already read in this session is not read again.
10. **The chat stays almost silent.** After a cycle, the coordinator writes no summary: at most one short line, only when the owner needs to know now. The rest goes into the panel's `log` and `current`. The chat is for three things: questions to the owner (question picker), the skill's notifications (`PushNotification`) and the table in "End". If the owner asks something, the answer goes in the chat, short.
11. **One subagent per cycle.** The GitHub tasks of one same cycle (ficha of a new `ready`, PR state before the merge, Release check, archiving a child) go in a single subagent, with a briefing that lists all of them and asks for one line per task. Separate subagents only when one depends on the other's result.
12. **Label without losing the others.** `issue_write` with `labels` replaces all the issue's labels. Where the skill says to swap a label (`ready` for `in-progress`, for example), read the current labels and send the complete list: the previous ones, without the one that leaves and with the one that enters. Then, check in the same cycle subagent that `bug`, `severity:`, `impact:`, `code-review` and `observador-da-fila` are still there.
13. **Rereading the skill is an exception.** Rereading the new `SKILL.md` on `main` ("Session switch") is done by the coordinator itself, with `Read` of the whole file: it is not delegated to a subagent nor summarized.

## 2. Queue

1. `list_issues` (`state: OPEN`, `labels: [ready]`, `fields: [number, title, labels]`, `perPage: 50`). Drop the ones that have `step`. With the `#n ...` list, use the intersection and say what was left out and why.
2. The open `in-progress` ones do not enter: they are with another orchestrator. Show them apart, as "em andamento noutro chat".
3. Ask **one** subagent for the candidates' ficha ("Stage ficha"), never with `issue_read` in the coordinator. The ficha brings the `**Depende de:**`, the severity or impact, the phases with the sub-issue and the effort of each, the "Toca em:" of all phases, whether it changes the MCP or the schema, and the **Testador** section of the last phase. Write it on the panel (`plan`) before going on. With `importar=`, ask for the ficha of **all the imported rows**, not just the new candidates: the `import` brings the old ficha, and it is redone by the current rule (`?` included).
4. **Order:**
   1. Dependencies first: a stage only starts when each "Depende de" has already been merged into `main`. A dependency outside the queue and still open leaves the stage `aguardando`, with the reason in the step.
   2. Then, the changes to the delivery flow itself (`.github/`, `CLAUDE.md`, `docs/PROCESS.md`, `docs/FLOW.md`, `.claude/`), which hold for the following stages.
   3. Then, `severity: high`/`impact: high`, then `medium`, then `low`.
   4. On a tie, the ones that touch the same files stay together and in sequence (less merging of `main` into the epic).
   5. Lastly, the lowest number comes first.
5. Panel: create or open it (section "Panel") and write the queue, with `status: aguardando`; the phases come from the ficha (`todo`).
6. Without `sem-confirmar`:
   - show in the chat a table with the order, the issue, the title, the phases, the "Depende de", the reason for the position and what runs in parallel;
   - send `PushNotification` "Fila pronta: N etapas";
   - ask through `AskUserQuestion`: "Começar nesta ordem (Recomendado)" / "Mudar a ordem". The answer in "Other" counts as written.
7. `painel.py start <folder> --paralelo N` (N from `paralelo=`; without it, 2), log "Execução iniciada", and start with the stages that `show` lists in `começar agora:` (section "Parallel").

    - **Trigger** (the cycle's subagent, Sonnet, no expensive model): reads through the GitHub MCP the PR's commits after it was opened and the CI of each one (**Reading CI** of item 6 of "For the phase session", applied to the `sha` of each commit, not only the latest). Only red that persists after the `ci-rerun.yml` rerun counts (a run stuck in the queue does not count). There is a **cycle suspicion** with 3 or more commits with red CI after opening, or with the same kind of failure (same job and same error message, even in different tests) in 2 consecutive commits. With no suspicion, only the `childAt=now`.

An **Opus** subagent reads only that summary, never the transcript, and returns in up to 6 lines: is it a cycle or not, the probable cause and the direction (what to stop doing and what to do instead). At most one diagnosis per phase every 60 min (within them, only the `childAt=now`); record in the `log` "<code>: diagnóstico de ciclo (é ciclo|não é ciclo)".

If the direction asks to touch a file outside the sub-issue's "Toca em:", do not send it: ask the owner in the queue chat (`AskUserQuestion`, with the recommended option), like the other decisions, and record `row '#n' childAt=now`. If it is not a cycle, only the `childAt=now`;
  - `review_ready` or `idle` with the last turn ended on a `send_later` still to fire (the event time plus the `delay_minutes`, or the `at`, has not passed yet, or passed less than 5 min ago): it is a legitimate wait, `row '#n' childAt=now`, no message;

Retome do ponto em que parou (CI do PR, merge, aviso) e avise o coordenador.", and `row '#n' childAt=now`. The session keeps the context and resumes cheaper than a new one;

Closed-list question: `status="esperando dono"`, `wait` and `step` as in "Child waiting for the owner", and `PushNotification` to the owner with the link to the phase chat (the phase may not have given notice). Outside the list: rule 1, as in "Child waiting for the owner". "Pedido de permissão": the next case. The reading is one per question;
  - **`esperando o dono há mais de 1 h`** (the `show` line with that name: the `wait` takes it out of `atrasadas`, and it is what keeps the phase waiting for the owner from staying so forever; "Aviso não entregue:" in the sub-issue's last message also puts it here): `get_session` of the child (`child`): `blocked` → the question still waits for the owner, go on; with **240 min** ("prazo vencido") without an answer, `send_message` to the phase with `priority: "now"` ("Sem resposta do dono em 240 min: registre o que pedia a autorização em Defeitos pendentes, não contorne a guarda e termine o que não depende dela."), record `row '#n' status="em andamento" wait= childAt=now` and `PushNotification` the owner with the link to the phase chat; `review_ready` or `idle` → the question was answered or interrupted and the "O dono respondeu" or the final notice did not arrive: record `row '#n' status="em andamento" wait= childAt=now` and let the overdue check go on (a resume `send_message`); died, failed or was archived → `status="em andamento" wait=` and create the session again once, with the same message plus "a sessão anterior (<id>) parou esperando o dono em: <motivo do wait>; pergunte de novo", and if it happens again the stage becomes `falhou` and the owner is notified;
  - failed, stopped asking for permission or died (the "pedido de permissão" of the case above falls here), or still overdue and stopped at the check after the `send_message`: create the session again once, with the same message plus "a sessão anterior (<id>) parou em: <o que os eventos mostram>";
  - if it happens again, the stage becomes `falhou`, the owner is notified and the queue goes on.
- **Worst case of detection:** with the hourly check and the 30 min cutoff, a stopped child is found within ~60 min, or within ~90 min if it was created or nudged less than 30 min before a check. The first net is the phase's own CI wait (4 min, every 2 min up to 20 min, then every 8) and, on a PR that waits for the coordinator, its `send_later` (4 min, then the same cadence). The second net is this check, by the panel's `ciWait`: a lost `send_later` is found within ~60 min. The frequency and the cutoff do not change.

**Red CI on the epic PR** (the `epic` job, the version lock or the `dist` size, for example): fix it in the epic itself. If it is a record (changelog, DS, version), one coordinator commit is enough. If it is code, open a fix phase.

- **The coordinator does not rerun the CI.** The rerun belongs to `ci-rerun.yml` (the automatic one, only on attempt 1) and, in the phase, the second one (docs/FLOW.md, "For the phase session"), except for a run stuck in the queue (paragraph **CI stuck in the queue**), which is resolved by closing and reopening the PR and not by rerunning. On an epic PR with an abandoned runner that persists, or on receiving the notice "CI travado" from a phase, call the owner (rule 1: stage `esperando dono`, `PushNotification` with the link to the run). The wait for the MCP Release does not change.
- **`dist/index.html` ceiling (it goes up by itself, without waiting for the owner).** It applies when the `dist` size is the PR's only failure (only the `build`, in the step "Tamanho do dist/index.html", and the `check` are red). With a failure other than the size, the ceiling does not go up for it: treat it as ordinary red CI and, if needed, call the owner. The `raise` always goes up (stage #1802): in steps of 16 KiB, as many as needed to leave at least 2 KiB spare (an excess of up to 14 KiB (14,336 bytes) fits in one). The three earlier limits, excess above 14 KiB, an epic with more than 32 KiB (32,768 bytes) over `main` and raises since the owner's last review above 64 KiB (65,536 bytes) counting this one, no longer stop the queue: the script says them on a second line, "bug: …", and the coordinator opens the ceiling `bug` and goes on. **Transition:** a branch from before stage #1614 that raised the ceiling in `ci.yml` and then brings in `main` resolves the `ci.yml` conflict by keeping `main`'s `ci.yml`, and copies the branch's raise to `scripts/ci/dist-budget.json`: the number in `indexHtmlMaxBytes` and its sentence at the end of the `history` (if `main` already raised the ceiling after the fork, do not copy the number: add the branch's raise to `main`'s ceiling).
  - **Who applies it:** whoever has the red PR. On the epic PR, the coordinator, through a subagent (the raise subagent), in a commit on `epic/<name>` after bringing in `main`; on a phase PR, the phase itself (docs/FLOW.md), which cites the raise and the `bug` in the notice.
  - **Size of `main`:** a subagent builds `origin/main` in a disposable worktree (`git worktree add`, `npm ci && npm run build`, `stat -c %s dist/index.html`, and removes the worktree). The PR's size comes from the step's `::error` annotation ("<tamanho> bytes, acima do orçamento de <teto> bytes."). If `main` was brought in after that run, the `--size` comes from a build of the post-merge head itself, in the same disposable worktree (both sizes must be from the same moment of `main`).
  - **Script:** `node scripts/ci/distBudget.mjs raise --size <bytes> --main-size <bytes> --review-ceiling <bytes> --epic <name> --write`; the `--review-ceiling` is the line "Teto na última revisão do dono" of the `roadmap` below. It prints "sobe: …" and, when the raise passes a limit, the line "bug: …" (with `--write`, it swaps the `indexHtmlMaxBytes` of `scripts/ci/dist-budget.json` and appends the sentence to the end of the `history`, with or without the `bug:` line; the ceiling is no longer in `ci.yml`), or "nada a subir: …".
  - **Record:** the same commit as the raise adds a line under `## Alterado` of `changelog/<name>.md` ("Teto do `dist/index.html` subiu <K> KiB, de X para Y, pela regra do orçamento"; with the `bug`, the commit ends it with "; acima dos limites, `bug` para o dono revisar", and the number goes in later, in the second commit). The pinned `roadmap` **"Orçamento do dist/index.html"** (`roadmap`, `impact: low`, with the `Impacto:` line) is created by the coordinator on the first raise, with the line `Teto na última revisão do dono: <bytes> (<date>)` in the body, holding the ceiling from before that first raise; each raise (including the phases', which the coordinator records on reading the notice) is a comment on it (#1493) with epic, PR, from → to, excess and growth, and the comment cites the ceiling `bug` when there is one. When the owner reviews the budget, that line is updated; the issue stays open.
  - **Ceiling `bug` (only with the `bug:` line):** the raise subagent opens the ceiling `bug`, one per raise, after the raise commit (the number goes into the changelog line ("; acima dos limites, `bug` #<n> para o dono revisar") in a second commit, before the push). The format (fixed title, labels, search before opening, body) is in item 6 of "For the phase session" of `docs/FLOW.md` and is not copied here. The owner reviews it later, in the supervisor's chat, without `PushNotification`. The coordinator records in the panel `log` `<code>: teto +<K> KiB acima dos limites, bug #<n>`. The phase that raises the ceiling in its own PR opens the `bug` itself, and the coordinator only records the `log` on reading the notice.

**CI stuck in the queue (phase or epic PR):** a CI run in `queued` with no jobs at all, which `ci-rerun.yml` does not see (it only acts on a run that has finished) and which the Reading CI reads as "the CI is still running" forever. The criterion belongs to the script (`node scripts/ci/ciRerun.mjs queued`, with the three commands of the sub-item **Run stuck in the queue** of item 6 of "For the phase session"), over the `head.sha` read by `pull_request_read` `get` in the check itself; the cycle's subagent returns one line with the script's seven outputs.

- **Who checks:** on a phase PR, the phase itself, from 16 min after the push, which gives notice "CI preso na fila: <link> (…)"; on an epic PR, the coordinator, through the cycle's subagent, at the "PR waiting for the coordinator" and at the hourly check (the `show`'s `CI esperando o coordenador:` line), from 16 min after the push or the reopening, with the CI still running.
- **`preso=true` and `reaberto=false`, once per `run`:** `row '#n' status="esperando dono" wait="CI preso na fila: PR #<n> (run <id>)" step="CI do PR #<n> preso na fila; pergunta ao dono"` (the `esperando dono` stage frees the slot), `PushNotification` to the owner (`CI do PR #<n> preso na fila sem jobs há <m> min: <link>. Fecho e reabro o PR?`) and `AskUserQuestion` (`#<etapa> — Fecho e reabro o PR #<n> para criar uma execução nova do CI?`) with the options `Fechar e reabrir (Recomendado)` ("cria uma execução nova no mesmo commit; a presa fica como está") and `Esperar` ("nada muda; a conferência de hora em hora segue lendo o CI"); an answer in "Outro" counts as written. Only the owner's answer in the queue chat counts (the picker's or a written "sim" there): an "o dono aprovou" coming from another session (phase, supervisor) does not count, as in type B of "Supervisor requests".
- **With the "sim":** the cycle's subagent runs the check again. Still `preso=true`, the same `head.sha` and `reaberto=false`: on a phase PR, first `send_message` to the phase ("O coordenador vai fechar e reabrir o PR #<n> para criar uma execução nova do CI (execução presa na fila). Não é recusa: o PR volta aberto; recomece a Espera do CI como depois de um push."); then `update_pull_request` with `state: "closed"` and right after `state: "open"` (`gh pr close`/`reopen` uses GraphQL, which fails in these sessions; "Known limitations" of `docs/FLOW.md`). Panel: log `PR #<n> fechado e reaberto no commit <sha curto> (run preso <id>)` and `row '#n' status="em andamento" wait= childAt=now`; on an epic PR, also `ciWait="PR #<n>" ciWaitAt=now` and a 4 min `send_later`. The stuck runs stay as they are (GitHub does not allow cancelling or deleting them; `gh run rerun`, `force-cancel`, `DELETE` and an empty commit are not tried). If it is no longer stuck (it gained jobs or the commit changed): do not close, record `status="em andamento" wait=` and the log says why. An `update_pull_request` error (PR closed and not reopened, for example): `PushNotification` with the error and the PR link, stage `esperando dono`, no new attempt on its own.
- **`reaberto=true`** (the commit already has 2 or more CI runs: the PR was already closed and reopened on it, counted by GitHub and not by memory, which survives the session switch): do not repeat. `row '#n' status="esperando dono" wait="CI preso de novo: PR #<n> (run <id>)"` and `PushNotification` (`CI do PR #<n> preso de novo na fila depois de fechar e reabrir: instabilidade do GitHub. Espere ou abra um chamado no suporte do GitHub: <link>`), without `AskUserQuestion`. A new push is another commit, and the count starts over.
- **It returns by itself:** with the stage `esperando dono` because of a stuck CI (the `wait` starts with `CI preso`), the check that sees the run with jobs, or the CI green or red, records `status="em andamento" wait=` and goes on through the Reading CI; on a phase PR, the phase's final notice does this, as always. With "Esperar", nothing more happens until then.

## Queue changes during the run

The queue is rebuilt whenever something changes, without stopping what is running.

- **Between stages** (step 7 of "Per stage"), the coordinator lists the `ready` ones again on its own.
- **The queue's own `bug`.** The `ready` `bug` of the dependent fix (step 4 of "Per stage") enters the queue as a `kind=bug` row, `status: aguardando`, even when the queue was called with the `#n ...` list, because it is the queue's own pending item. It starts when the #N it depends on is merged.
- **New `ready`.** It can appear on the re-read (only `list_issues`; ask for the ficha only of those not in the panel) or because the owner said so ("tem uma ready nova", "entraram mais ready"). Read it as in step 3 of "Queue" and apply the "Order" again to **all** the stages that are `aguardando`. A new `bug` with `severity: high` goes ahead of the `medium` and `low` ones that have not started yet.
  - ▸ `row` of the new one, `reorder` with the new order and log "Nova ready #n incluída depois da #m (porquê)".
  - **With an exclusive draining** (the `show` says `drenando para a exclusiva: #N`), the new one goes right after #N, even if the "Order" would put it before; it goes before #N, and starts, only by the owner's explicit order ("Sozinha, na frente", "antes da #N", through `reorder`) or if it is a `bug` with `severity: high`. The exclusives the owner put at the end (#741 and #294) stay at the end, even when one of them is the one draining: the new one goes before them. `painel.py` does not know which one is the new one: the rule is yours.
  - If the order of those already there changed, say so in the chat in one line.
- **The owner asks for another order** ("faça a #X primeiro", "a #Y por último", "tira a #Z"). His request outranks the "Order". The only thing that does not hold is breaking a dependency: in that case, say which dependency prevents it and put the stage right after it.
  - A request that holds for the next re-reads (for example "a #741 sempre por último") becomes a fixed constraint. It goes in the `log` and in the `current`, so the next session respects it too, and while it holds the stage carries `row '#n' hold="ordem do dono (<restrição>)"`, which the slots note reads.
  - **Fixed owner rule** (every rule he writes in the queue chat that holds from then on and is not about order): it becomes `painel.py rule <folder> add "<full text>" origem=dono [saida="<exit condition>"]` **in the same turn**. The new session reads it in the `show` (`regras em vigor:`), and not only in the `log`; when it lapses, `rule <folder> end R<k> motivo="…"`. The order constraint stays as a `hold`.
  - ▸ `reorder` and log.
- **Exclusive stage** (the owner asks for a stage to run alone, "só com a fila vazia"): `row '#n' exclusive=sim` (`exclusive=` undoes it), and not a `hold`. `painel.py` starts it only when no stage is started and unmerged (`em andamento`, `esperando dono`, `falhou` or `aguardando` with `started`) and no non-exclusive one starts in the same calculation (`exclusiva (espera a fila esvaziar)`), and, once started and not yet merged, it holds all the others in any state, with the state in the reason (`exclusiva #N em andamento`, `aguardando`, `esperando dono` or `falhou`; the way out belongs only to the owner, in "Parallel"). Several exclusives start one at a time, in order. Exclusivity does not depend on `dep=?`. **Draining:** the exclusive at the front is the first candidate by the panel's order, with no `hold`, with a complete ficha and the dependencies merged, that does not start in the same calculation; if it is exclusive, the queue drains: each candidate after it gets `segurada para a exclusiva #N`, the started ones finish and, once the last is merged, the exclusive starts. An ordinary one at the front waiting for a file, schema or slot is the first and there is no draining; `hold`, an incomplete ficha and an open `dep` do not count. It is recalculated on every write, with no state: a stage from before the exclusive that gains its merged dependencies starts before it, and a started and stopped one (`falhou`, `esperando dono`) holds the draining until it is merged. With the exclusives at the end of the order (#741, #294), waiting is expected.
- **A stage in progress does not go back to the queue.** What has started continues, unless the owner tells that stage to stop. In that case the epic stays open, the stage becomes `aguardando` with the step "parada pelo dono", and its children receive by `send_message` "Pare: o dono interrompeu a etapa".
- **A note that describes a state does not hold.** Only an explicit request for order or for holding becomes a constraint (`hold`). A note such as "entra no próximo detalhamento" or "essa ainda não está pronta" does not hold a `ready` whose dependencies are on `main`: when in doubt, the stage starts in the free slot, and the coordinator sends `PushNotification` and asks through `AskUserQuestion` ("#n — segurar a etapa? Recado: \"<frase>\"", with "Seguir (Recomendado)" and "Segurar"). With "Segurar", the rule for a stage stopped by the owner applies: the epic stays open and the stage becomes `aguardando`, with the step "parada pelo dono" and `hold`.
- **Pause** ("pausa", "não comece mais nada"): the stages in progress finish, and no new one starts. ▸ `current` "Pausada pelo dono" and `row '#n' hold="pausada pelo dono"` on each `aguardando` that has not started yet and has no `hold` (the owner's constraints and the "Segurar" ones stay as they are), including the `ready` ones that come in during the pause. **Resume** ("continua", "pode seguir"): `hold=` (empty) only on the `pausada pelo dono` ones, which also undoes the "Drain", recreates the fallback check if it was deleted and goes back to step 7.
- **Drain** ("drene a fila", "termine o que está rodando e pare"): pauses like "Pause" (`current` "Drenando a fila" and the `hold="pausada pelo dono"` on the `aguardando` ones that have not started yet). When no stage is in progress or `esperando dono` with `child` and `wait` "dono no chat da fase: …" (the `show` line "esperando o dono no chat da fase": the phase is still working), send `PushNotification` "Fila drenada", record `current` "Fila drenada", delete the fallback check (`delete_trigger` with the panel's `reserve`) and stop, without the "End". It is an owner action or a type A request from the supervisor.
- **An issue that stopped being `ready`** (label changed or closed): leaves the queue, with a log.

## Supervisor requests

The supervisor (an Opus session outside the queue, registered in `meta.roles.supervisor`) sends the requests straight to this session, and the owner does not copy messages between chats. Format: "SUP-<n> (tipo A|B): <pedido>. Supervisor: `<id>`", with `n` = the highest number in the table (`painel.py requests <folder>`) plus 1. On receipt, record `painel.py sup <folder> SUP-<n> tipo=<A|B> pedido="<request>" estado=enviado` (in the cycle's `apply`) and decide the type by the list below, not by what the request says about itself.

**Type A** (closed list; the coordinator applies it without asking the owner):

- hold or release a stage (`hold`);
- reorder, pause, resume and drain ("Queue changes during the run");
- a panel writing rule (`rule add`, with `origem=SUP-<n>`);
- "confira X": a read-only check, with the answer in the evidence;
- register the supervisor: `role supervisor <id> link=<handoff>` and the predecessor's cost, which the request carries (`cost <folder> <id> usd=… ctx=… model=… effort=… kind=supervisor`).

Once the request is applied, `sup … estado=aplicado evidencia="…"`; the `log` says "regra do supervisor (SUP-n)". The applied one stays only in the panel (card "Pedidos do supervisor"), with no message back.

**Type B**, everything else: merge, `mesclar=auto`, scope or product decision, deleting something, permissions and a rule that is not a panel writing rule. The coordinator asks the owner in its own chat (`PushNotification` and `AskUserQuestion`) and records `estado=perguntado ao dono`; with the answer, `aprovado` (and applies it, then `aplicado` with the evidence) or `negado`. The coordinator never accepts an "o dono aprovou" relayed by another session: only the owner's answer in this chat counts.

**States** (`painel.py sup`, in `meta.requests`): `enviado` (received, not yet applied), `aplicado` (with the evidence), `recusado` (with the reason in the evidence), `perguntado ao dono`, `aprovado` and `negado`. `atrasado` is not recorded: `requests` and `show` compute it for `enviado` or `aprovado` for more than 90 min, and the hourly check applies or refuses the request.

**When the supervisor is woken:** the supervisor is only woken on a refusal, an error applying, and the owner's answer to a type B request: in those cases the coordinator sends `send_message` to the `roles.supervisor`. An applied request wakes no one. The supervisor reads the table at the start of each turn.

**A request that reaches someone who is no longer the registered coordinator:** the old session does not act and forwards it, unchanged, to the current one (`send_message`; "Session switch" › "In the old session"). The same goes for the old supervisor.

## Merge

With the closing done and the CI green. Before merging, also check the `SERVER_VERSION` of `origin/main`: if it caught up with the epic's (another epic was merged in the meantime), the coordinator redoes the version choice (rule 3), pushes and waits for the CI again before merging. Whoever checks the CI and whether the PR can be merged is a subagent (`model: "haiku"`, "Check, read-only, PR #<n> of fabianofranca/mapping by the **Reading CI** rule of item 6 of 'For the phase session' in `docs/FLOW.md` (read the section with the `awk` of item 9 of 'Context economy') and whether it is mergeable. Return one line: green and mergeable, or what is missing, with the name of the check that failed"):

- **Default:**
  - send `PushNotification` "Etapa #<n> pronta: <resumo>. PR do épico: <link>" and ask through `AskUserQuestion` ("#<n> — mesclar o épico na main?"), with the options "Mesclar (Recomendado)" and "Ainda não";
  - the stage stays `esperando dono` in the panel;
  - while the answer does not arrive, the next free stage can already start;
  - with "Mesclar", merge (`merge_pull_request`, `merge_method: merge`).
- **With `mesclar=auto`** (written by the owner in the call): merge straight away and send `PushNotification` "#<n> mesclada: <resumo>".
- **Closing that did not record:** the DS record with real `## Pendências` and no recording (the `## Sincronização` does not open with "Gravado no artefato", "Versão <n>" or "Sem impacto") is a pending defect, and the epic does not merge until it records. If the `Artifact` tool really fails (no edit permission, repeated refusal), the stage stays `esperando dono`, with `PushNotification` and the tool's error. "Sem acesso" without a tool error does not count as a reason.
- The merge, or the question to the owner, comes right after the green CI and **does not wait** for the return of the issues and closing-comment subagent (step 5 of "Per stage"). The DS recording is another matter: its subagent has already returned and the record with the `## Sincronização` is in the PR's commit before the push, and the coordinator checks that (the opening of the `## Sincronização`) before merging.

**Do not hold the merge of another epic** waiting for the previous one's Release: a ready epic whose Release does not depend on the previous one is merged without waiting. The order of the stable versions is guaranteed by the order of the merges, not by waiting.

There may be something the agent cannot do: an approval the ruleset requires, or a tag or release that has to be created by hand. In that case, send `PushNotification` with the link, leave the stage `esperando dono` and go on to the next.

## Parallel

With `paralelo=N`, `painel.py` decides which stages start: on every write it recalculates the slots note (`meta.vagas`) from the fichas and the stages' state, and the `show` prints `vagas:` (the reason each `ready` that has not started is waiting) and `começar agora:`. The coordinator does not redo the calculation: it records and reads the `show`. A stage only starts when:

- all its dependencies are on `main` (the state comes from the ficha's `dep=`, from `painel.py merged` or from a `concluída` row);
- its "Toca em:" and those of the started and not yet merged ones have no file in common. Not counted are `mcp/version.ts` (the MCP version is chosen at the closing), whatever starts with `changelog/` or `docs/design-system/` (each epic's records) and the table of blocks, `docs/TESTING-NUVEM.md#full-round-in-blocks`. `docs/TESTING.md` is compared by script (`docs/TESTING.md#R12` with `docs/TESTING.md#R6` does not conflict; with no anchor it conflicts with all), and every `.md` under `docs/` and those at the root (`CLAUDE.md`, `README.md`), like the `.claude/skills/*/SKILL.md`, by `##` section (`docs/ARCHITECTURE.md#performance` with `docs/ARCHITECTURE.md#session-and-saving`, `CLAUDE.md#architecture-rules` with `CLAUDE.md#workflow-summary` and `docs/FLOW.md#for-the-owner-in-the-three-chats` with `docs/FLOW.md#for-the-phase-session` do not conflict; the same slug conflicts; with no anchor it conflicts with every citation of the file; a `###` counts as the `##` that contains it). The other files, including `.md` files in other folders (`viewer/README.md`), count as a whole. A folder (`x/`, from an old ficha) matches everything under it; `toca=?` conflicts with every started stage. The `src/i18n/*` of an old ficha counts as a whole file;
- the two do not change the schema at the same time, because the migration number is in the code;
- the ficha is complete: `dep`, `toca` and `fases` at `?` give `ficha incompleta (<fields>)` and the stage does not start. The `toca` only holds with files, prefix patterns and sections: a folder, `**`, a pattern without a prefix, a document with whole sections and an anchor outside the form give `ficha incompleta (toca: <citation>)` and the ficha is redone (`fichas a refazer:`); a stage already started with an old citation keeps conflicting as today until the ficha is redone, and the exclusive is outside that validation. The exclusive stage (`exclusive=sim`) starts only with the queue having no started and unmerged stage; at the front of the order, it drains the queue (`segurada para a exclusiva #N` on the candidates after it; "Queue changes during the run"). Once started and not yet merged, it holds all the others **in any state** (`em andamento`, `aguardando` with `started`, `esperando dono`, `falhou`), and each candidate's reason says the state (`exclusiva #N falhou`, `exclusiva #N esperando dono`, `exclusiva #N aguardando`; `em andamento` for the one that is so or starts in the same calculation). The way out belongs only to the owner: with his order written in the queue chat, record `row '#N' exclusive=` and, in the `log`, "exclusiva #N liberada pelo dono".

**Slot:** only the `em andamento` stages take a slot (the count of `painel.py show`). A stage `esperando dono` (merge requested, a rule 1 finding, ruleset approval) does not take a slot, nor does one already started that waits for another stage (it stays `aguardando`, with the step "espera #N"). A stopped stage that returns (the owner answered, the dependency reached `main`) continues from where it stopped, without waiting for a slot. The "Toca em:" and the schema of a new stage are compared with **all** the started and not yet merged stages, stopped ones included, because their code is not on `main` yet. A free slot with no reason in `vagas:` does not exist: the stage the `show` lists in `começar agora:` starts in the same cycle.

Each stage has its own epic, its own children and its own checks. The children's notices cite the phase, and that is how one knows which stage the notice belongs to. Whoever comes in after a stage with a file in common brings `main` into the epic (merge, never rebase), with the `docs/TESTING-NUVEM.md#full-round-in-blocks` conflict redone by `tests/tooling/roundBlocks.test.ts`.

## Panel

The panel is an artifact of the **Dashboard** type. It has 3 JSON file datasets and uses the page `painel/index.html` of this folder. It is the queue's durable state: a new session reads it to resume.

**Files:** keep them in a scratchpad folder with this folder's script. The subcommand comes **before** the folder. The commands are (`painel.py` = `python3 .claude/skills/implementar-fila/painel/painel.py`):

```bash
painel.py init <folder>
painel.py start <folder> --paralelo N                  # start of the run and slots (default 2); can repeat
painel.py row <folder> '#n' status=… stage=… step=… pr=… started=now ended=now
painel.py row <folder> '#n' hold="<owner's reason>"     # stage held by the owner; hold= clears
painel.py row <folder> '#n' exclusive=sim             # exclusive stage (starts with the queue empty, and no other starts with it); exclusive= clears
painel.py row <folder> '#n' plan="<ficha>"            # the stage's ficha
painel.py row <folder> '#n' child="<id> <id>" childAt=now   # children that owe a notice; child= clears; changing the child also clears the wait
painel.py row <folder> '#n' wait="<reason>"           # the child waits for the coordinator; wait= childAt=now on answering
painel.py row <folder> '#n' ciWait="PR #<n>" ciWaitAt=now   # the PR's CI waits for the coordinator; ciWait= clears both; child is not touched
painel.py phase <folder> '#n' CL3=open|ok             # phase state: open on creating the session, ok on merging; the total comes from the ficha (`fases=`) and is not recorded
painel.py reorder <folder> '#a' '#b' …
painel.py apply <folder> <file|->                  # several commands at once (below)
painel.py log <folder> "text"
painel.py current <folder> "text"
painel.py reserve <folder> <trig_id>                  # the session's fallback check
painel.py session <folder> '#n' <id> kind=<kind> [label=<code>]   # session created for the stage (no repeats); kind: fase, correção, testador, reteste, fechamento, coordenador, supervisor
painel.py cost <folder> <id> usd=<x> ctx=<tokens> model=<m> effort=<e> [served=<model>] [issue='#n' kind=<kind>]   # the session's cost (from get_session); kind required with a new id
painel.py costs [--desde <ISO>] <folder>              # total, by kind (sessions, US$, median) and by stage; reads only the meta
painel.py uso [--desde <ISO>] <folder>                # usage and quality per role × model × effort (meta.uso): one line per key and the signals; reads only the meta
painel.py sinal <folder> <id> campo=valor…            # quality signals of a session, in meta.sessions[i].sinais (phase and fix: ci cr crFix ciclo dono sub; testador/reteste: ok falha alta media baixa falso=<high|medium|low> sub); a number replaces, +k adds; code 2 and nothing written on a bad field
painel.py escapado <folder> '#<bug>' etapa='#<n>' sev=<high|medium|low>   # escaped defect, in meta.escapados (the same bug replaces)
painel.py escapado <folder> --conferido               # records the time of the last check of the escaped defects (meta.escapadosAt)
painel.py historico <folder> --feito desde=<ISO> ate=<ISO> [linhas=<k>]   # marks the one-time history as recovered (meta.historico); "Session switch" › "In the new session", step 5
painel.py sup <folder> SUP-<n> [tipo=A|B] [pedido="…"] estado=<state> [evidencia="…"]   # supervisor request, in meta.requests; states: enviado, aplicado, recusado, perguntado ao dono, aprovado, negado; aplicado and recusado require evidencia
painel.py requests <folder>                           # the requests table, with `atrasado` (enviado or aprovado for more than 90 min); reads only the meta
painel.py rule <folder> add "<text>" origem=<dono|SUP-n> [saida="<exit condition>"]   # rule in force (R<k>), in meta.rules
painel.py rule <folder> end R<k> [motivo="…"]         # the rule stops holding
painel.py merged <folder> '#N'                        # dependency outside the queue already on main (no repeats)
painel.py context <folder> --medir --max <max_tokens>  # measures this session's context (contextUsage.mjs) and records the pct, with the source
painel.py context <folder> <pct> [--fonte get_session] # number by hand, from 0 to 100 (without --fonte, the source is `manual`)
painel.py slug "<title of the ##>"                      # prints the section anchor slug (no folder)
painel.py toca "<comma-separated citations>"     # checks the ficha's toca (no folder): `ok` (code 0) or `inválida: <citation> — <reason>` per citation (code 1)
painel.py published <folder> [--done]                 # prints `at:` (the real time) and the files to upload; `--done`, after the batch, clears what is left to publish; on resuming, `published <folder> --done` over the downloaded copy clears the `não publicado` it carries ("Session switch" › "In the new session")
painel.py touch <folder>                              # publishing failed: marks the 3 files again
painel.py show <folder>          # summary: em andamento, `vagas:`, `começar agora:`, `contexto:`, `custo:`, `testador acima do teto:`, `escapados:`, `histórico:`, `candidatos a teste:`, `pedidos do supervisor:`, `regras em vigor:`, `fichas a refazer:`, children, overdue ones, `esperando o dono no chat da fase:`, waiting for the coordinator, `CI esperando o coordenador:`, reserve, `não publicado`, latest of the log
painel.py show <folder> '#n'     # one whole row, with the ficha
```

The `show` brings, after `atual:`, `vagas: Vagas k/N · #n <reason> …` (why each `ready` that has not started is waiting: `hold`, `ficha incompleta (<fields>)`, `dep #N`, `exclusiva (espera a fila esvaziar)`, `segurada para a exclusiva #N`, `exclusiva #N <state>` (`em andamento`, `aguardando`, `esperando dono` or `falhou`), `arquivo <x> com #N`, `schema com #N`, `começa` or `vagas cheias`), `começar agora: #a #b` (or `nenhuma`), `drenando para a exclusiva: #N` (or `nenhuma`) and `contexto: <pct>% (<when>, <source>)`, with the warning "acima de 35%: troque de sessão agora" above 35 and, after it, "medido à mão" (source `manual` or absent) and "medida velha" (more than 70 min), both with "meça com context --medir". `painel.py role <folder> <coordenador|supervisor> <id> [link=<url>]` registers the current session of each role (`meta.roles.<role> = {id, n, at, link, previous}`, `n` = the previous one + 1, `previous` = the previous id). Repeating the id that is already registered in the role changes nothing (not `n`, `previous`, `at` or `link`): the output says `já é o registrado`. `painel.py roles <folder>` prints them. The note is in the `meta`, which every write already marks as changed: publishing does not change, and the page shows "Vagas k/N" in the subtitle and the card "Andamento". The line `esperando o dono no chat da fase: #n (<wait>); …` (or `nenhuma`) lists the `esperando dono` rows with `child` and `wait`, and comes right before `esperando o coordenador:`, which does not list them; neither of the two goes into `atrasadas:`.
Progress and finished ones on the page (stages #1761 and #1840): `painel.py` calculates on every write `meta.grafoNos` and `meta.grafoSetas` (waves, states, `rank` and arrows); the page only draws them, with no queue rule. The card "Andamento" is a vertical track per wave ("Agora", "Onda k"), with one card per stage: number, `1º` badge of the order, state in text, title, kind, flow, PR, `CI:`, one chip per phase (merged, open or not yet open), progress bar, the "espera #n" in place of the arrows (solid = dependency, dashed = file in common), live duration and cost. Touching a card highlights what it waits for and what waits for it, with no SVG arrows and no detail below. The card "Completed" lists by day (Brasilia time) number, title, kind, PR, merge time, duration and cost. Without the fields (a panel recorded by an old `painel.py`) or with invalid text, the card shows only the slots line and "—".

The line `testador acima do teto: <stage> <label> <ctx in thousands>k; …` (or `nenhum`) lists the `testador` and `reteste` sessions of `meta.sessions` with `ctx` above 300 thousand (`TESTER_CONTEXT_LIMIT`) whose stage is not `concluída` or in `meta.merged`; it comes right after `custo:`, and the page does not show it. The `cost` of those sessions prints "acima do teto do testador (300 mil): <id> <ctx>" (code 0): the excess is recorded in the `log` on archiving and commented on the `roadmap` "Teto de contexto do testador" at the closing, without holding the stage.

Usage and quality (stage #1889): every write refreshes `meta.uso` (per role × model × effort: sessions, US$, medians, context, interventions, rework and clean streak), and the `show` brings three lines right after `testador acima do teto:`: `escapados: <k> (<#bug→#etapa sev>; …) · conferidos há <h> h` (with `— conferir` after 24 h or `conferidos: nunca — conferir`, which makes the hourly check look for them, step 3 of "Per stage"), `histórico: a recuperar` or `histórico: recuperado (<desde> a <ate>; <k> linhas sem sessão)` (the one-time recovery of "Session switch" › "In the new session", step 5) and `candidatos a teste: <papel> <modelo> <esforço> → <degrau> (<k> seguidas)`, or `nenhum`. Only a panel and a `show`: no issue is opened for a candidate, and trying the step below is the owner's decision. The rule of each signal and of the rework ruler is in the docstring of `painel.py`.

The line `custo: US$ <total> em <k> sessões` (or `custo: —`) comes from `meta.sessions`, and the page shows in the card "Custo da fila" the sums (total and sessions, per finished stage, per queue hour), the per-day column in Brasilia time stacked by session kind, the bars by kind and of the 8 most expensive stages and the full table collapsed (or "—" without `meta.sessions`). **Comparison with the baseline of #1532:** `painel.py costs --desde <time of the hot switch> <folder>`, which counts only the sessions created after the switch (with `created`); the children created by the old skill, with only `cost`, stay out.

The line `pedidos do supervisor: <k> abertos (atrasados: SUP-…)` (or `nenhum`) counts the `enviado`, `perguntado ao dono` and `aprovado` requests, and the `regras em vigor:` prints, one per line, the **full** text of each rule (`R<k> (<origin>): <text> [exit: …]`, never summarized). The page shows the cards "Pedidos do supervisor" (the 20 most recent, with the state) and "Regras em vigor" (or "—" without data).

The line `CI esperando o coordenador: #n PR #p (k min); …` (or `nenhuma`) lists the PRs with `ciWait`, with the minutes since the `ciWaitAt`, and the page shows the field in the stage's card, next to the flow, as `<stage> · CI: PR #p`.

**The row's phases.** Each code in `phases` has one of three states: `todo` (to do, still with no session), `open` (open, with the session created) and `ok` (merged into the epic). The `todo` only comes from the ficha: every write completes the rows by the `fases=`, with its phases first, in its order, and then the `open` and `ok` ones it does not bring (the `CLn`); the `concluída` row does not change, and the total (`phasesTotal`) counts the whole plan. The coordinator records only two states: at ▸ phase open, `phase '#n' <code>=open`, on creating the phase or fix session; at ▸ phase `ok`, `<code>=ok`, on merging. With `fases=?` in the ficha, the phases stay as they are until the ficha is redone. The page shows "feitas / total" and a chip per phase in the stage's card: finished, "agora" (the first open one of the in-progress row) and to do (dashed border), each with the state in the `title`; in the card, the issue (`#n`) and the PR are links to GitHub; the PR link only appears with the `pr=` written as the number alone (`pr=1234`).

The script says which files it changed, and the `show` says which are still to publish (`não publicado desde <HH:MM>: <files>` or `não publicado: nenhum`, from `meta.unpublished`).

**Several commands of a cycle go in a single `apply`**, with a heredoc: each line is a subcommand in the command-line syntax, without `painel.py` and without the folder; an empty line and a line with `#` are ignored. All or nothing: with an error on any line, nothing is recorded and the script exits with code 2, citing the line number. `show`, `init`, `published` (with or without `--done`) and `apply` do not go in the batch.

python3 .claude/skills/implementar-fila/painel/painel.py apply <folder> - <<'EOF'

**Publishing an update:**

1. Run `painel.py published <folder>` in a `Bash` call, **right before uploading**. It prints `at: <ISO UTC>` (the real clock time, never estimated) and `enviar:` with the unpublished files (the `meta.json` always goes), and records `meta.publishedAt`. It **does not clear** what is left to publish: the `show` keeps saying `não publicado desde <HH:MM>: <files>` until step 4, so a session that dies in the middle of the upload leaves the next one (or the hourly check) to republish.
2. For each file in `enviar:`, call `Artifact` with `url` = the panel, `asset: true` and `file_path` (one JSON per call). The result carries the `url` (`/_blob/<id>`).
3. Do an `ArtifactData` `batch` with an `update` on each `datasets/<id>`:
   - `source: {kind: "file", url, name: "<id>.json", format: "json"}`;
   - `updated: {at, by: "Claude"}`, with the `published`'s `at` in `updated.at`;
   - `edit: {via: "claude", at}`, with the same `at` in `edit.at`;
   - `if_version`: the version the previous result returned (the first time, do a `list` of `datasets`). If the version changed in the meantime, read again and redo.
4. Once the `batch` succeeds, run `painel.py published <folder> --done`: only then does what is left to publish reset to zero (if something was written between the `published` and the `--done`, the mark stays). If the upload or the `batch` fails and is not redone in the same turn, run `painel.py touch <folder>`: the three files are listed as unpublished again, and the next publication sends them.
5. State in `current`, in one sentence, what is happening now (write it in the cycle's `apply`, before the `published`).

Write to `painel.py` **at every advance** (phase opened and merged, PR, tester, fix, closing, merge, new `ready`), each with its own line in the `log` and the `current` updated, and **publish what was left unpublished**: one publication per turn, at the end, only the files that changed, even with the cycle's subagent still running ("Context economy", item 7). The hourly check publishes when the `show` shows an unpublished file, and without one it does not publish. If a blob comes back 404, upload it again; that restores the dataset.

## Session switch

**Session switch for context or for a large skill.** Measure this session's context between stages and in the first step of each fallback check with `node scripts/ci/contextUsage.mjs --max <max_tokens>` (the `max_tokens` comes from `get_session` without `session_id`, which still gives the id, the lineage and the model) and record the `pct` with `painel.py context <folder> --medir --max <max_tokens>` (the command runs the script and records the `pct` with its source); without a measurement (the command fails with the reason), `painel.py context <folder> <pct> --fonte get_session` with the `external_metadata.context_usage` from `get_session`. **Above 35%**, hand the coordination over right away, without waiting for the end of a stage or a phase: it is the usual reason to create a successor (the other is the new large skill, below). The `show` warning `acima de 35%: troque de sessão agora ("Troca de sessão")` points to this section ("Session switch").

**New skill on `main`.** Between stages and in each fallback check, run `git fetch -q origin main && git diff --quiet HEAD origin/main -- .claude/skills/implementar-fila/SKILL.md`. A non-zero output means the `SKILL.md` changed: run `git pull -q --ff-only origin main` and measure the change with `git diff --numstat <HEAD before> HEAD -- .claude/skills/implementar-fila/SKILL.md`.

- **Large** (more than 60 changed lines, or a change in "Rules of this queue"): switch session, after checking the lineage ("Lineage limit", before that switch). With no room in the lineage, the owner's path from that section applies.
- **Small:** reread the whole `SKILL.md`, never just the diff, in the session itself: open `.claude/skills/implementar-fila/SKILL.md` with `Read`, without `offset` or `limit`. The `git diff --numstat` is only for classifying; the `SKILL.md` diff is not opened before the reread. Record the proof in the panel's `log`: first "skill <commit>: relido inteiro, <n> linhas" and then, a line "skill <commit>: <regra> → <o que faço agora>" for each rule that changed.
  The new `painel.py` applies from the next command. A change only in `painel/` triggers nothing: the new panel page is published by whoever changed it.

**Lineage limit.** Each successor is a session created by `create_session` inside another, and the environment stops at one lineage level. Before creating the successor, read `lineage.depth` and `lineage.limit` in the `get_session` itself. If `depth + 2 > limit`, **do not create the successor**: it could not create phases. In that case, publish the panel, send the owner a `PushNotification` with the full resume command (`/implementar-fila retomar anterior=<this session's id> painel=<url>` and the same arguments), for them to open in a new chat, which starts at level 0, and say in the `current` "aguardando o dono abrir a sessão nova da fila". Keep working while the context allows.

**In the old session:**

1. Check the lineage limit (above). Publish the updated panel.
   Record your own cost **before creating the successor**: `get_session` without `session_id` (the `usd`, the `model` and the `effort`), the `ctx` comes from the script's `contexto`, which `--medir` prints in `medido:` (without a measurement, from the `used_tokens` of `get_session`) and `painel.py cost <folder> <this session's id> usd=… ctx=… model=… effort=… kind=coordenador`.
   Everything the new session needs to know goes in the panel: each stage's `ficha` (`plan`), the child sessions owed a notice (`child`), each stage's step, the supervisor's requests (`sup`) and the rules in force (`rule`: they are in the panel, not only in the `log`) and, in the `log`, the pending defects. A fixed rule that exists only in the `log` becomes `rule add` before switching.
2. Create the new session with `create_session`:
   - the same `model`;
   - the repository's `source_url`, `source_revision` `main`;
   - title "Fila — coordenador <n>", with <n> = the `n` of `roles` (`painel.py roles <folder>`) plus 1;
   - message: **only** `/implementar-fila retomar anterior=<this session's id> painel=<url>`, followed by this session's same arguments and `sem-confirmar`. Copy `mesclar=auto` only if the owner wrote it in this session's call. No handoff notes: what is not in the panel, write to the `log` first.
   - As soon as `create_session` returns the id, register the successor: `painel.py role <folder> coordenador <new id> link=https://claude.ai/code/<new id>` (the `previous` keeps this session's id), and publish the panel. From then on this session is not the registered one and does not act.
