# mapping-viewer

Embeddable Mapping viewer: it draws **one screen** of components (a design system's library plus a screen description) in a container on your site, read-only, with real-time updates. The core does not depend on any framework; there is an optional React wrapper.

## Installation

Inside `dist-viewer/` (the folder generated by `npm run build:viewer` in the Mapping repository):

```bash
npm pack
# generates mapping-viewer-0.4.2.tgz
```

In the project that will use it:

```bash
npm install ./mapping-viewer-0.4.2.tgz
```

You can also copy the whole `dist-viewer/` folder into the project and import `mapping-viewer.js` by path.

## Core (no framework)

```ts
import { createViewer, loadLibrary, parseScreen } from 'mapping-viewer';

const library = loadLibrary(files); // files: { path, text?, bytes? }[]
const screen = parseScreen(JSON.parse(screenJson));

const viewer = createViewer(document.getElementById('preview')!, {
  library,
  screen,
  onClick: (id) => console.log('clicked', id),
});

viewer.update({ screen: newScreen }); // redraws only what changed
viewer.setSelection(['i-card']); // selection coming from your panel
viewer.dispose(); // when unmounting
```

The container must have a size; the framing redoes itself when it changes.

## React

```tsx
import { MappingViewer } from 'mapping-viewer/react';

<MappingViewer
  library={library}
  screen={screen}
  selection={selection}
  onClick={(id) => setSelection(id ? [id] : [])}
  fontsVersion={fontsVersion}
/>;
```

`konva` is a peer dependency (the range comes from Mapping's `package.json`): only for the types, because `ScreenRenderer` exposes `Konva.Group` in the declarations. npm 7 or newer installs it on its own and your project compiles with `skipLibCheck: false`; the code uses the copy of Konva embedded in the bundle.

`react` is an **optional** peer dependency: only whoever imports `mapping-viewer/react` needs it (18 or newer).

## Screen from an external JSON

When the screen comes from a backend (for example, a server-driven UI JSON), the specialization declares how to read it: `origins` (width, height, roots and the node keys) and `sources` on the types and fields (which external type each type corresponds to and from which `props` path each field comes). Instead of `screen`, pass the already parsed JSON in `source`:

```ts
const viewer = createViewer(el, {
  library,
  source: JSON.parse(json), // wins over `screen`
  sourceSystem: 'sdui', // optional: without it, the first origin
  onSource: ({ screen, warnings, error }) => showWarnings(warnings, error),
});

viewer.update({ source: otherJson }); // a new object recomputes; the same object does not
viewer.screen(); // the computed and drawn screen
```

In React: `<MappingViewer library={library} source={json} sourceSystem="sdui" onSource={...} />`. The screen is recomputed when the library or `source` change and on `redraw()`. With `error` (a JSON without width/height, for example) nothing is drawn; the warnings (unknown property, value outside the options, type without an annotation type) arrive in `warnings`.

To get the screen without drawing it, use `screenFromSource(library, json, { system?, measure })` (it returns `{ screen?, warnings, error? }` and never throws). `translateSource` returns only the tree without geometry (`LayoutScreen`) and `layoutScreen` lays it out by sizes.

## Loading the library

`loadLibrary(files)` receives the list of files of the design system folder: the specialization (`"format": "mapping-spec"`), one `.json` per component and the fonts (`bytes`). If the files are on a server, use `loadLibraryFromUrl`:

```ts
import { loadLibraryFromUrl } from 'mapping-viewer';

const library = await loadLibraryFromUrl('https://my-site.com/ds/material3.spec.json');
if (library.problems.length > 0) console.warn(library.problems);
```

It fetches the specialization, the components and the fonts it points to (paths relative to the specialization's URL). A file that fails to arrive is left out and shows up in `library.problems`; a specialization that fails to arrive throws `Error`. Options: `{ fetch, fonts }` (your own `fetch`, for example with authentication; `fonts: false` does not fetch the fonts).

## Fonts

The core does not load fonts. Two ways:

- **CSS:** declare the families with `@font-face` on your site;
- **Through the library:** `await registerLibraryFonts(library)` registers, via `FontFace`, the fonts the specialization declares (with the loaded bytes) and returns the status of each one (`loaded`, `missing`, `failed`).

### Token mode

A specialization with `tokens` (`light`, `dark`…) draws in the first mode. For another one, pass `drawingMode: 'dark'` to `createViewer` (or the `drawingMode` prop of `<MappingViewer/>`). Changing it later, with `viewer.update({ drawingMode: 'light' })`, redraws without reloading the library or the screen; a mode the specialization does not declare falls back to the first. `font-sans` and `font-mono` (built in) resolve to the host's font in any mode.

When the fonts finish loading, re-measure the texts: `viewer.redraw()` in the core, or change the value of `fontsVersion` in `<MappingViewer/>`.

## Remote images

A component can have an `image` node whose URL comes from a field (`mapping-component` format 3). The viewer **requests no image by default**: without the `remoteImages` option, the component draws the placeholder (a gray rectangle with the image stroke) and nothing goes to the network.

```ts
createViewer(container, {
  library,
  screen,
  remoteImages: true,
  // Your site decides, per origin. Without this function, everything is refused.
  allowOrigin: (origin) => origin === 'https://cdn.example.com',
});
```

(In React: `<MappingViewer remoteImages allowOrigin={...} />`. `remoteImages` applies only at creation; `allowOrigin` is read on every request, so a new function on every render does not recreate the viewer. With `createViewer` directly, the function passed at creation is the one that applies.)

With `remoteImages: true`, the image is only requested when the **two gates** agree:

1. **The URL passes Mapping's policy:** only `https:`, no username and password, up to 2048 characters and no local network host (literal IP, `localhost`, a name without a dot, `.local`, `.localhost`, `.internal`). `http:` and the local network have **no switch** in the viewer.
2. **Your `allowOrigin(origin)` function returns `true`** for the origin (`https://cdn.example.com`). Throwing an exception is the same as refusing. The viewer stores no consent and shows no prompt: the host site decides.

How it loads: `crossOrigin = 'anonymous'` and `referrerPolicy = 'no-referrer'` (no cookies and no `Referer`), at most 6 concurrent requests, a 20 s timeout, an image of up to 8192 px per side and 40 million pixels, a bitmap downscaled to 2048 px and an in-memory-only cache (the image is never stored). The image server must send `Access-Control-Allow-Origin`; without CORS the image does **not** show up (the placeholder stays). That is why `viewer.toDataURL()` stays valid with remote images: none of them taints the canvas.

**The CSP belongs to the host site.** The viewer defines no policy. If your site has a CSP, `img-src` must allow the image origins (for example `img-src 'self' data: blob: https://cdn.example.com`); without that the browser blocks the request and the component stays on the placeholder, even if `allowOrigin` accepts it. If the site uses Trusted Types (`require-trusted-types-for 'script'`), Konva needs a `default` policy that accepts the empty string in `createHTML`.

## Instance tree

`screenTree(screen, library)` returns the roots (in drawing order) with nested children; each node carries `id`, `parentId`, `depth`, `label` (the instance's label), `typeId`, `typeName`, `instance` and `children`. `flattenTree(tree)` gives the same tree as a list, in pre-order (the drawing order), ready for a list indented by `depth`. Selection and highlight go back to the canvas through `setSelection` and `setHover`.

## Notes

- Each bundle is **self-contained**, with Konva and the engine inside. Use `mapping-viewer` **or** `mapping-viewer/react` on the same site; the two together load two copies of Konva.
- The React bundle leaves `react`, `react/jsx-runtime` and `react-dom` out: your site provides its own React.
- The package is ESM (`"type": "module"`) and ships minified, with source maps (`.js.map`).
- Remote images: off by default (section above); `AllowOrigin` is the type of the `allowOrigin` function.
- `loadLibraryFromUrl` uses `fetch`: the host site must allow the request (CORS and, if there is one, CSP `connect-src`).
