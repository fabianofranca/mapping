# Import a component's parameters through the signature — 2026-11-13 (épico `epic/importar-assinatura`, PR #1755, MCP 0.39.0, schema v19)

## Adicionado

- **Signature sheet (`mapping-signature`, formatVersion 1):** a neutral format for a component's signature (the parameters of a `@Composable` function, the `init` of a SwiftUI view or the properties of a Figma component), with `docs/SIGNATURE-FORMAT.md`, `docs/signature.schema.json` and the `mapping-docs://SIGNATURE-FORMAT.md` resource in the MCP.
- **Specialization `formatVersion` 16:** `fieldModels` at the root (how a source type becomes a field) and, in each platform's `code` and in each `variants` case, `signature` (the sheet in the package), `ignore`, `calls` (factory of a nested argument) and `formats` (value template, like `{value}.dp`); the `params` value can also be a path (`colors.containerColor`) or positional (`#0`); `signature` in the type's `sources`. The new keys stay outside the version contract. `formatVersion` 15 is still accepted.
- **`validate_library` and the app check the cited sheet:** it exists, is a valid `mapping-signature` and has the same symbol and file as the `code`; a mapped parameter that the sheet does not have becomes the notice "parameter outside the signature".
- **`code` in the MCP:** `get_code_hints` builds the nested `args` of a factory (`colors = ButtonDefaults.buttonColors(containerColor = …)`, only with the filled fields), the formatted values (`16.dp`) and the positional ones; the views' `code` (`get_code_hints`, `get_marking`, `get_annotation`, `get_component`, `find_by_code`) brings `unmapped`, the list of the sheet's parameters that did not become a field (name, role, type, whether it is required and the default). Without the new keys, the output is today's.
- **`plan_signature_import` (MCP):** the preview, without writing, of importing a component's signature as the fields of a library type. It receives the sheet (inline or a `.json` inside the roots) and the package, and returns the new fields, the links, the `code` or the `sources`, the notices (with the sheet's `ref` and the message starting with the platform), the `unmapped`, the differences with the stored sheet, the suggested migrations (never written on their own), `versionBump` and the already imported specialization. The errors are `signature-invalid`, `type-not-found`, `platform-not-declared`, `signature-mismatch` and `variant-not-found`; a `signatureFile` that is not a `.json` is refused without being read.
- **Import through the signature:** what becomes a field follows the parameter's role and type (the `fieldModels` models take precedence), composite parameters expand through the factory, the link to existing fields is by `params`, by normalized name or by a new field, and importing the same sheet twice changes nothing. A changed sheet adds only what is additive: a new optional field, a new option and an updated default; what left stays with the `removed` notice, and what diverged, with `diverges`.
- **Guide, skill and test script:** `docs/AGENT-GUIDE.md` gains "Import parameters from the signature" (extract, `plan_signature_import`, write, `validate_library`, sync; never write `migrations` without a request), the `spec-author` skill gains the section "Import the signature" (the sheet by hand for sources without an extractor) and the test script **R26 — Import the signature** (`docs/TESTING.md`, in block 4 of the full round) checks the tool with the sheets in `tests/fixtures/signature/`, with the helper `scripts/testing/assinatura.mjs`.
- **Signature extractor for Kotlin/Compose (`mapping-signature.mjs`):** the command-line script delivered in the Release (with the `.sha256`) and installed in `tools/` by `setup.sh`. It reads a `.kt` file and writes the sheet: the `@Composable` function by name, the `enum class`es and the `XDefaults.f()` factories from the same file or from `--also`, the KDoc `@param` and the overloads (`--overload <n>` when there is more than one). Deterministic, with no dependency and no network; it writes only to `--out`.

- **SwiftUI and Figma extractors (`mapping-signature.mjs swift` and `figma`):** the same script reads a SwiftUI `struct` (the explicit `init` chosen by `--init <n>`, or the memberwise one without `@State`, `@Environment` and the like; the external label in `label` and `_` as positional `#0`; the file's `enum` in `options`, the `.case` default as the option, `@ViewBuilder` as `slot`, `///` and `- Parameter` in `doc`) and the saved JSON of a Figma node (`componentPropertyDefinitions`: `VARIANT` → `enum`, `BOOLEAN`, `TEXT`, `INSTANCE_SWAP` → `slot`; the `#<id>` suffix goes to the parameter's `id`). Each reader refuses the options that are not its own (`--init` only in `swift`, `--node` only in `figma`). The Figma sheet is a design one: the import links it in the type's `sources`, with the `VARIANT`'s `values`, and not in `code`. Test script R26.13 to R26.18.

- **Material 3 (Compose) imported through the signature (version 12, `formatVersion` 16):** the 50 types and the 48 `variants` cases cite the sheet of androidx's own signature (`libraries/material3-compose/signatures/`, 98 sheets extracted by `mapping-signature.mjs` at the pinned commit). 288 parameters come in as fields, with no hand modeling (`shape`, colors, elevations, `horizontal`/`vertical` of the `contentPadding`, `borderWidth`/`borderColor`, `subtitle`, `prefix` and `suffix` of the `text-field` and the `secure-text-field`, among others), the factories' `calls` (`ButtonDefaults.buttonColors`, `outlinedButtonColors`…), the `ignore`s and the `pending` notices for the parameters that are not yet a field; the `fieldModels.compose` brings `Color`, `Shape`, `Dp`, `TextUnit`, `PaddingValues`, `BorderStroke` and the text slots.
- **The Material 3 drawing follows the new fields:** the `button` (radius by the `shape`, `contentPadding`, `containerColor`, `contentColor` and the disabled ones), the `surface` (`borderWidth`/`borderColor` and `shadowElevation`), the `top-app-bar` (`subtitle` in the small style and the colors), the `radio-button` and the `switch` (the colors), the `text-field` and the `secure-text-field` (`prefix` and `suffix`); the `divider`'s `color` was already read. In the other types the field exists and goes to the code, but the drawing does not use it.

## Corrigido

- **Swift external label in `unmapped`:** `unmappedParams` and the "parameter outside the signature" check compared only the parameter's internal name; a `params` that cites the external label (`badge`) now links the parameter, and `ignore` accepts the label or the name.
- **Importer (`plan_signature_import`):** the same parameter without a field in the base and in the case gave two equal `pending` items (error `aviso repetido`; the case's `message` now carries the case); the `ignore` of the `code` and of the case did not prevent the field or the `pending` (and now also applies by the Swift external label); the argument of a factory or of a composite was linked only by name to a field of **another** type (the `border`'s `width` to the size `width`: it becomes a new field `<owner><Name>`); reimporting the base sheet after the case's one reordered the notices; the already reported `removed` came back in `changes` on every reimport; the first import wrote `default` 0 into an existing field that had no `default`.
- **Validator (`parameter outside the signature`):** accepts the `expand` member of the model of the owner parameter's type (`border.width` of `BorderStroke?` with the factory `outlinedButtonBorder(enabled)` in the sheet); only the `expand`'s own members apply (`border.constructor` does not).
- **Import through the signature (fix CL1):** the field that receives the `removed` notice stops citing the parameter that left in the `code`'s `params` (the validator warned "parameter outside the signature"; the `removed` notice stays and survives reimport); the code sheet of another platform is refused (`signature-mismatch`) in the importer and becomes an error in the validator; the validator and the importer now use the same expansion rule for a composite parameter (`expansionOf`): `colors.x` only applies if the importer expands it; every sheet problem of `validate_library` has a `code` from the message catalog (and en-US). In Material 3 (Compose), 11 `parameter outside the signature` notices of the known set go away (`segmented-button`, `time-picker`, `navigation-rail`, `swipe-to-dismiss`).
- **Notices window (fix CL1):** with "Only notices in use" unchecked, the type filter buttons count the listed notices (before they showed 0 because they counted annotations), and the filter's name says "numbers count notices".
- **Bottom window tabs (fix CL1):** the counter sits 4 px from the label (it was 2) and uses the `--t-micro` font; the header's padding moved to the close button, and the six tabs still fit whole at 900 px.
- **Import through the signature (fix CL2):** `plan_signature_import` on a specialization earlier than `formatVersion` 16 now refuses with `invalid-spec` (before it returned a v15 spec that the following validation rejected); the library validator checks the `symbol` and the `path` that a `variants` case swaps against the sheet inherited from the base (`library.signatureSymbolMismatch` and `library.signaturePathMismatch`); the Kotlin extractor strips the backticks from the parameter name (`` `object` `` becomes `object`); and the `formatVersion` 16 messages of `specSignature` go out through the catalog, also in en-US.
