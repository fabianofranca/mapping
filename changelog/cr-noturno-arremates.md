# CR noturno: arremates do agendamento — [Não lançado] (épico `epic/cr-noturno-arremates`, PR #0, MCP 0.38.0 sem mudança, schema v19)

## Alterado

- O "Como roda" do CR por épico (`docs/FLOW.md`, "Revisão de código") ganha seis arremates para quem conduz o fluxo. A coordenadora acha a issue da rodada por uma listagem REST das issues `code-review` (uma chamada por página de 100, sem `search/issues`, que aceita só 30 chamadas por minuto) antes de rodar o `riskTriggers.mjs`, num laço de shell só; os épicos que já têm issue nem passam pelo `git checkout`. Cada revisor tem uma tentativa por épico: na conferência de reserva de 90 min, o `status_bucket` decide (`working` espera mais, `blocked` avisa o dono, `failed` ou sem issue vira a issue da rodada "A revisão automática falhou", criada pela coordenadora com o marcador `cr-epic`, e a revisão vai para o backlog). O passo 1 registra que a `main` só aceita merge commit. As "Limitações conhecidas" dizem que o critério de gatilho não confere se a `/code-review high` rodou no fechamento (decisão do dono de 2026-11-12), que a busca aceita 30 chamadas por minuto e que o script do passo 3 roda toda noite nos épicos com gatilho, de forma local. O prompt do agendamento só muda pela conversa da coordenadora (o `update_trigger` com `prompt` é recusado em outra sessão): quem muda o bloco do revisor ou os passos põe o prompt novo inteiro na descrição do PR do épico, com a linha "Dono: aplicar este prompt no CR por épico", e o dono o aplica. A MENSAGEM-MODELO do revisor não muda. O `tests/tooling/epicCodeReview.test.ts` confere o texto novo (listagem antes do script, `status_bucket`, uma tentativa por épico, merge commit e a mesma data em todo `--shallow-since`).
