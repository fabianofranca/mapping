# Automated flow — ready-made messages

The rules are in `docs/PROCESS.md`; here are the ready-made messages and the step by step (orchestrator, duplicate search and bug evidence, CI and preview). The `<…>` snippets are blanks to fill in.

## For the owner, in the three chats

1. Roadmap or bug (any model):

```text
Create a roadmap issue (or bug, if it is a defect): <idea or problem>. Origin: <where it came from>.
```

Portuguese (what the owner types):

<!-- portuguese-guard:begin what the owner types in the chat stays in Portuguese -->

```text
Crie uma issue roadmap (ou bug, se for defeito): <ideia ou problema>. Origem: <de onde veio>.
```

<!-- portuguese-guard:end -->

For a bug, the agent first looks for an identical issue or one that groups it and sets the severity label (`severity: high`, `severity: medium` or `severity: low`), as `docs/PROCESS.md` says ("Bugs and visual evidence"). The `roadmap` is born with the impact label (`impact: high`, `impact: medium` or `impact: low`) and the `Impacto:` line in the body ("Issue planning" › Impact); the message does not need to ask for it.

2. Detailing (Fable or Opus):

```text
Detail issue #<roadmap or bug> as a stage, with the phases and the models table (Orchestrator row and Tester column). Ask whatever is a product decision. When done, set the label `ready` and remove `roadmap` (`bug` and `impact:` stay).
```

Portuguese (what the owner types):

<!-- portuguese-guard:begin what the owner types in the chat stays in Portuguese -->

```text
Detalhe a issue #<roadmap ou bug> como etapa, com as fases e a tabela de modelos (linha Orquestrador e coluna Testador). Pergunte o que for decisão de produto. Ao terminar, ponha o rótulo `ready` e tire o `roadmap` (o `bug` e o `impact:` ficam).
```

<!-- portuguese-guard:end -->

To detail at once all the `roadmap` and `bug` issues that are not `ready` yet (in a chat in Auto mode): `/detalhar-backlog`. The skill (`.claude/skills/detalhar-backlog/SKILL.md`) creates an Opus subagent (`Agent` tool, in the background) that proposes merging issues into a single epic, to have fewer MCP versions and a single tester round. Then it creates up to 3 Opus detailing subagents at a time and brings their questions to the owner through the question picker, always with a recommended option; the answers go back to the same subagent through `SendMessage`. Since the `Agent` tool accepts `effort`, each unit runs at high effort when the skill's criteria point to it (schema or format, writing of `mapping.json`, cross-cutting architecture, large plan) and at medium otherwise (`alto=#a,#b` forces high, `alto=nenhum` puts everything at medium), with no manual prompt for the owner. Before writing the plan, each detailing checks it against the code of `main` (files, versions, scripts, phases the size of one session, and overlap with the other `ready` and `in-progress` ones). Each stage comes out with the `**Depende de:**` line, which gives the implementation order, and with the "`Toca em:`" of each phase in files and sections, never a folder or a whole document, checked with `painel.py toca`; the `Depende de` covers the `ready` and `in-progress` ones that touch the same files (not counting the records of each epic, `mcp/version.ts` nor the append-only index citations listed in the queue skill's Parallel section; it compares `docs/TESTING.md` per script, every `docs/*.md`, the root `.md` files (`CLAUDE.md`, `README.md`) and the `SKILL.md` files per `##` section (`docs/ARCHITECTURE.md#performance`, `CLAUDE.md#architecture-rules`) and does not count the table of blocks, `docs/TESTING-NUVEM.md#full-round-in-blocks`), and every issue the skill creates carries the line `Origem: etapa #<n>`.

3. Implementation (in the model of the Orchestrator row, in Auto mode):

```text
Implement stage #<stage> in the automated flow. Call me only to confirm the merge.
```

Portuguese (what the owner types):

```text
Implemente a etapa #<etapa> no fluxo automatizado. Me chame só para confirmar o merge.
```

To confirm the final merge, the owner replies in the implementation chat: `pode mesclar`.

To implement all the `ready` ones in sequence (in a Sonnet chat in Auto mode): `/implementar-fila`. The skill (`.claude/skills/implementar-fila/SKILL.md`) orders the queue by the `**Depende de:**` line, by severity and by impact, shows the order and then does, stage by stage, the role of this orchestrator: phases, tester, fixes until the ❌ are zero (the owner's decision becomes a `bug` and the queue goes on) and closing. The "Fila de desenvolvimento" panel is updated at each notice, and the heavy GitHub reads go through a subagent, so the coordinator lasts more hours; the hourly check also checks the context and the switch at 35%. The merge of each epic is requested from the owner by text, in one line in the queue chat (`mesclar #<n>` or `ainda não #<n>`, which keeps the queue going), except when they write `mesclar=auto` in the call. The other questions of the run are asked the same way, by text, and answered with `segurar`/`seguir`, `reabrir`/`esperar`, `soltar`/`esperar`, `refazer`/`tirar` or `ampliar`/`manter` plus `#<n>` (the bare `esperar` is never enough: always `esperar #<n>`), and `aprovar`/`negar SUP-<k>` for a supervisor request. When the Auto mode denies `archive_session`, the coordinator asks by text, without holding the queue: `pode arquivar` makes it archive the pending finished sessions (and the next ones of that session), `não arquive` stops the asks; neither carries over to a successor. Other arguments: `paralelo=N` (default 2, from the slots note `Vagas k/N`), `modelo=tabela`, `sem-confirmar` and `painel=<url>|novo` (without it, the skill reuses the previous "Fila de desenvolvimento" panel). The MCP version at closing: it is provisional when the epic opens and chosen at closing (the next free one on `origin/main`, with `git merge origin/main` if another epic came in before). A fix that can only be resolved with code from another epic does not hold the epic: it becomes a `ready` `bug` with `Depende de: #N`, which the queue itself runs when #N is merged, and the queue only ends with no pending `bug` of its own. Only the stage `em andamento` takes a `paralelo` slot: one that waits for the owner or for another stage frees the slot. A stage held only by stages already in their tester (or correction or closing) starts early, waits as `esperando entrega` (no slot) for their merge and brings `main` in, in a sync session, before its own tester; the panel shows it (`cedo` tag, `esperando merge para testar:`, `pode sincronizar:`). The closing (issues for what was left for later and the comment on the issue) runs through a subagent during the epic's CI, and the merge comes right after the green. The panel has no issues table: it has a card with the link to the GitHub search `Origem: etapa`. The session switch is by context (above 35%, the coordinator hands the queue to a new session, `retomar`, which registers itself on the panel as the coordinator <n> and archives the previous one after checking the archiving with `get_session`; a session that is not the registered one does not act and only forwards to the current one) or by a large new skill: a large new skill on `main` (more than 60 changed lines or a change in "Rules of this queue") becomes a session switch, after checking the lineage; a small one is applied in the session itself (`git pull`, rereading the whole `SKILL.md` with `Read` and proof in the `log`). Near the session lineage limit, the coordinator does not create a successor: the owner opens the new chat with the resume command it sends. The sessions of each delivered stage (phases, testers, fixes) and the previous coordinator are archived.

For a small process tweak (only `.claude/skills/**`, `docs/PROCESS.md`, `docs/FLOW.md`, `docs/TESTING-NUVEM.md`, `CLAUDE.md`, `.github/**`, `scripts/ci/**` and `tests/tooling/**`, up to 80 lines), outside the queue (in a new chat, on Sonnet, in Auto mode, with `effort: high`): `/via-rapida #<n> [mesclar=auto]`. The skill (`.claude/skills/via-rapida/SKILL.md`) takes the `roadmap` or `bug` straight to `in-progress` (never through `ready`), with no detailing, phases or tester, in a one-PR epic, with the usual gates, `/code-review` and CI. With the CI green, it asks about the merge through the picker ("Mesclar" / "Ainda não") (or directly, if you wrote `mesclar=auto` in the call). The supervision (`/supervisionar-fila`) also creates this session when you ask for it in its chat. A released fast track (the `via-rapida` label on the issue) does not need that: the queue runs a released `via-rapida` on its own, in a slot like any stage, as `/via-rapida #<n> fila=<id>` (in queue mode, the session does not merge; the merge follows the queue rule: your `mesclar #<n>` or, with `mesclar=auto` written by you, on its own when the review has no open finding). A refused fast track comes back too: adding the `via-rapida` label again to a refused issue (or detailing it to `ready`) brings it back to the queue by itself; a stage that depends on a refused one waits, and the queue asks you once, by text: `soltar #<n>` starts it without that dependency, `esperar #<n>` keeps waiting.

After the merge, the orchestrator checks the MCP Release: it finds the "MCP release" run of the merge commit (`actions_list`), waits for it (`send_later` of 15 min) and, with a new version, checks that `mcp-v<version>` exists (`get_release_by_tag`), is not a pre-release, carries `mapping-mcp.js`, `setup.sh`, `SKILL.md`, `AGENTS.mapping.md`, `watch-comments.mjs`, `watch-conversations.SKILL.md` and `mapping-signature.mjs` (each with its `.sha256`) and that the rc of the version are gone; with no new version, that the `release` was skipped. On failure, or with the run missing, it notifies the owner with the run link and the manual plan B in `docs/MCP.md`. The result goes into the closing comment and the final notification.

## Orchestrator — step by step

The rules are in `docs/PROCESS.md` ("Automated flow"); the `implementar-fila` skill does the same for a queue of stages. The **orchestrator** (the implementation chat):

- reads the stage issue (which must be `ready`), swaps `ready` for `in-progress`, creates `epic/<name>` from the up-to-date `main` and opens the epic PR to `main` as soon as there is a diff;
- for each phase, in order, creates a child session (`create_session` with the `model` and `effort` from the table, `source_url` of the repository and `source_revision` on the epic; never `permission_mode: plan`) with the phase message, which ends with "`Coordenador: <orchestrator id>`"; schedules a fallback check (`send_later`, 30 to 60 min) and only moves on to the next phase after the previous one's notice;
- after the last phase, finds the "Mapping - testes" environment (`list_environments`) and creates the tester session with the scripts and the visual pass listed in the sub-issue of the last phase (a list of more than 40 steps without R0: runs `node scripts/testing/round-guide.mjs --grupos <scripts>` and creates one session per group, up to 5, as in "Directed round in groups");
- **with ❌** in the report **or with a pending defect**, opens **one** fix phase ("Fix phase") and retests only the steps of the findings and those the fixes affect (never the whole script), **in a single session** with the findings of all groups or blocks ("Retest together"; a fix merged before the retest starts enters it; with no script step affected, the fix's automated test is enough). A round whose findings are **all low severity** (low; owner decision, 2026-11-13) opens the fix and, once merged, goes to closing **without retest**; a mixed round retests only the high and medium ones; a low that the fix does not reproduce gets a retest of its own. It holds for every round, retests included, and a low-only fix counts as one round toward the limit. It calls the owner ("Call the owner", further below) if it fails again, if the finding is about data loss, `mapping.json` integrity or security, or if the fix requires a product decision;
- **with no ❌ and no pending defect**, does the closing: renames the epic file in `changelog/` with the date (`git mv`, and the date in the title), saves the DS pending items in the artifact (`docs/DESIGN-SYSTEM.md` › "When saving") and renames the epic record in `docs/design-system/` with the date, writes the final description of the epic PR with "Closes #<stage>", comments the closing on the stage issue and opens a `roadmap` issue (with the impact label) or `bug` for each item left for later;
- notifies the owner on the phone (`PushNotification`) with the summary and the epic PR link, and merges the epic into `main` **only after the owner replies "pode mesclar" in the chat**;
- after the merge, checks the MCP Release (paragraph "After the merge" above).

**Limits:** `.claude/settings.json` allows in `permissions.allow` the usual commands (gates, `npx`, git without force push) and denies force push, so the phases do not stop on those requests. A phase that does not notify by the fallback check (`send_later`, 30 to 60 min): `get_session` (`status_bucket`) and `list_events`, and then the ladder of the `implementar-fila` skill (hourly check, "For each overdue one"): `working`, schedules another fallback check (`send_later`, 30 to 60 min); `review_ready` or `idle` with no pending `send_later` of the phase, `send_message` to the phase ("Conferência do orquestrador: a fase não avisou. Retome do ponto em que parou (CI do PR, merge, aviso) e avise o coordenador.") and a new fallback check; failed, stopped asking for permission, died, or still stopped at the check after the `send_message`, creates the session again **once**, with the same message plus "a sessão anterior (<id>) parou em: <o que os eventos mostram>"; if it happens again, calls the owner ("Call the owner", right below). It does not relay the owner's answer to an authorization (item 8 of "For the phase session", "Owner authorization"): the question belongs to the phase, in its chat; one that reaches the orchestrator goes back to the phase through `send_message` ("É autorização do dono (item 8 da "Para a sessão da fase"): pergunte no seu chat.") or, coming from the owner in the orchestrator's chat, gets a line with the phase chat link. With the phase stopped on a question (`AskUserQuestion`), it reads the question (`list_events`) before notifying the owner, and one that is not on the closed list is handled like the sub-item "Product decision" of item 8. A phase waiting for the owner does not escape the check: the hourly one rereads it (`esperando o dono há mais de 1 h` from `painel.py show`) and, with 240 min without an answer, interrupts the question (item 8, "Deadline"). The request for a phase to switch by context (`Troca de sessão da fase <código>: contexto <n> mil; passagem em <link>.`, sub-item "Phase context ceiling" of item 3) is answered by the orchestrator itself: it creates the successor with the same phase message and the resume line of the sub-item "Phase context ceiling" (item 3 of "For the phase session"), and archives the previous one (at most 4 switches per phase; the fifth session does not switch). When creating the 4th and 5th sessions it sends `PushNotification` "Fase <código> da #<n> na sessão <k> de 5 por contexto" to the owner, without waiting for an answer.

**Call the owner:** the orchestrator sends `PushNotification` to the owner with the reason and the link (of the session, the PR or the report) and asks in its own chat (`AskUserQuestion`, with the recommended option first). The owner authorization of item 8 of "For the phase session" is not the orchestrator's: the question belongs to the phase, in its chat, and the orchestrator only sends the link to that chat. Inside the queue (`implementar-fila` skill), rules 1 and 2 of "Rules of this queue" apply instead of calling the owner.

## Bug: duplicate search

Before creating a `bug` (`docs/PROCESS.md`, "Bugs and visual evidence"), look for duplicates in the open issues (`list_issues` with the label `bug`, reading title and body, and also the `roadmap`, `ready` and `in-progress` ones) and, by keyword (component, file, script step, error text), in the open and closed ones (`gh api -X GET search/issues -f q='repo:fabianofranca/mapping is:issue <terms>'`):

- **identical** (same behavior, same cause): do not create. Comment on the existing one with the new origin, the branch and commit and the evidence; if the new severity is higher, change the label and say why;
- **groupable** (same component or file, same probable cause, same script step, or fixing one touches the other): if the existing one is not yet `ready` or `in-progress`, the defect goes into it as a numbered item (origin, item severity, evidence), with a comment saying what went in; the title is adjusted if needed. If it is already `ready` or `in-progress`, the plan does not change by itself: create the new issue with "Relacionada: #N" and comment the link on the existing one; the detailing decides whether to merge them;
- **regression** (the defect of a closed issue came back): a new issue that cites the closed one; the old one is not reopened;
- two open ones that are the same defect: the content goes to the more complete one and the other closes as a duplicate (`state_reason: duplicate`, `duplicate_of`), as #405 did with #387 to #390;
- the body (or the comment) records the search: "Duplicadas: nenhuma (busca: <termos>)" or "Relacionada: #N".

## Bug: body and evidence

- **Bug body:** what happens; what was expected and where that comes from (step of `docs/TESTING.md`, doc, spec); steps to reproduce; branch and commit; origin (link to the report or the PR); the severity and why; the duplicate search.
- **Evidence, when possible:** a defect visible on screen gets a PNG capture cropped to the problem area (Playwright `page.screenshot({ clip })` or `import -window root` + `convert -crop`), with no personal data or secrets. A defect that cannot be seen (flaky test, accessibility read from the DOM) gets the test output or the DOM snippet in a code block, in place of the image.

## Bug evidence

The image goes to the orphan branch `evidencias`, at `<issue>/<name>.png`, where `<issue>` is the number of the issue (or sub-issue) where it first appears; the issue is created first, to have the number.

```bash
git fetch origin evidencias
git worktree add <scratchpad>/evidencias origin/evidencias  # the worktree is the exception to "Session start"
cd <scratchpad>/evidencias && git switch -c evidencias-<issue>
mkdir -p <issue> && cp <capture>.png <issue>/<name>.png
git add <issue> && git commit -m "Evidence for #<issue>: <name>"
git push -u origin HEAD:evidencias
```

Afterwards the issue body is edited with `![short description](https://github.com/fabianofranca/mapping/blob/evidencias/<issue>/<name>.png?raw=true)` and the worktree is removed (`git worktree remove`). Push refused because the branch moved: `git pull --rebase origin evidencias` and push again (the commits are still only yours; never force push). `evidencias` only receives images, in one commit per issue; it never becomes a PR nor is merged; images of closed issues are not deleted.

## CI and preview

CI runs only on PRs (`pull_request`), once per commit: a branch without a PR has no CI. When a PR's CI finishes green, `preview-on-pr.yml` (through `workflow_run`) triggers the Deploy with the branch and the SHA, which publishes that commit to the preview (`/preview/`) without validating again; there is only one preview, that of the last PR with green CI. The Deploy's `workflow_dispatch` (without `sha`) remains for publishing another branch, running `ci.yml` first. Editing the PR (title, body or base) does not run CI, and the base of an open PR is not changed: with the wrong base, open a new PR with the right base, whose `opened` runs CI, and close the old one without reopening; no empty commits and no closing and reopening a PR to run CI, except closing and reopening a PR whose run is stuck in the queue (`queued` with no jobs), which the coordinator does once per commit and only with the owner's `reabrir #<n>` in the queue chat (the manual orchestrator still accepts a "sim"; item 6 of "For the phase session", **Run stuck in the queue:**).

## For the phase session

The orchestrator creates the session with `create_session`: `model` and `effort` from the table, `source_url` of the repository, `source_revision` = `epic/<name>`, never `permission_mode: plan`. Message:

<!-- portuguese-guard:begin frozen session-to-session message templates matched by tests -->

```text
Você é o agente da fase <código> — <título> da etapa #<etapa> do repositório `fabianofranca/mapping`, no fluxo automatizado (docs/PROCESS.md, "Automated flow"). The owner does not follow this session: do not ask them anything, except the item 8 authorization, which they answer in this session's chat.

1. Read `CLAUDE.md`, `docs/PROCESS.md` and sub-issue #<phase> with its comments (its plan and any handoffs); it is your plan. Read issue #<stage> **through one subagent** that returns only the sections and numbered decisions the sub-issue cites, plus the stage's "out of scope" section (with no citation, the stage's decisions and acceptance criteria); the main thread never loads the whole stage issue or its comments. Follow the plan; do not reopen decisions already made.
2. Branch `<short branch>`, taken from the up-to-date `epic/<name>`. PR with base `epic/<name>`, title "<code> — <title>", body starting with "Parte de #<phase>" and the usual sections (Summary, How to test, Decisions made, DS impact, Agent impact).
3. Subagents and effort: <from the sub-issue, e.g.: Sonnet medium; mechanical ones Haiku low>. Editing subagents (those that edit from a briefing) run at `medium` (mechanical work stays on Haiku `low`); `high` only for review or check ones. A subagent that goes past ~200k of context is replaced by a new one, with the briefing and what has already been done.
   - **Reading rule:** a source file or doc over ~300 lines is not read whole with `cat` or `Read` in the main thread (`CLAUDE.md` and `docs/PROCESS.md` of item 1 are the exception): use `grep -n` to find the function or section and `sed -n '<a>,<b>p'` (or `Read` with `offset`/`limit`) for the range being changed. A `grep` over docs or over several files ends with `| head -40`.
   - **Phase context ceiling:** the phase does not work far above 300 thousand of context before opening the PR. The measure is `node scripts/ci/contextUsage.mjs`, which reads the usage of the last model call in the session's own local transcript and prints `contexto=`, `mil=` and `acima=` against the 300 thousand ceiling (300,000 tokens); `acima=true` hands over. **Hook:** in cloud sessions, the `PostToolUse` hook of `.claude/settings.json` (`scripts/ci/contextGuard.mjs`) measures after each tool call and, above the trigger of 270 thousand, injects the switch notice into the context (repeated every +10 thousand, with the biggest jumps); the notice counts as `acima=true` (hand over, except with the phase's **last** PR open or in the `5 de 5` session). Its `PreToolUse` call is the **gate**: above the trigger of 270 thousand it refuses to open the PR (`create_pull_request`, `gh pr create` or a POST `gh api …/pulls`) of a phase or fix session, except in the `5 de 5` session, so the phase cannot rush to the PR to be exempt: it hands over and the successor opens the PR. For the queue coordinator (`/implementar-fila` prompt) the same hook injects its own notice from 320 thousand (repeated every +10 thousand), which counts as "above 35%" of "Session switch" in `.claude/skills/implementar-fila/SKILL.md`; the tester gets its own notice from 250 thousand (repeated every +10 thousand; `docs/TESTING-NUVEM.md`, "Context up to 300 thousand"), and `/supervisionar-fila` and `/via-rapida` get none. It is not the `external_metadata.context_usage.used_tokens` of `get_session` without `session_id`: it only changes at the end of a turn, and the phase works in a single turn, so it reads 0 (`get_session` remains in item 8, for the id of the chat link). **Transition:** if the clone does not have the script (epic created before stage #1699 and without `main`), run `git fetch -q origin main && git show origin/main:scripts/ci/contextUsage.mjs > <scratchpad>/contextUsage.mjs` and use the script from there. While `main` does not have it (before the merge of the #1699 epic), `git show` fails and leaves the file empty, and `node` exits with a code other than 0 and 1 or without printing `contexto=`: that is a **missing script** ("script ausente"), which counts as no measurement (reason `script ausente`). **No measurement** (code 1 from the script, or missing script): the phase goes on without the check and says `Contexto: sem medida (<motivo>)` in the final notice. The `<n>` of the switch request and of the handoff is the `mil` from the script. Check at two points, with `node scripts/ci/contextUsage.mjs --teto 270000` (the hook's trigger): (a) before sending a new task to a subagent (editing, review or check); (b) before running the gates of item 5. A third point, (c) before the `/code-review` of item 10 (only in a phase that has item 10), with the same `--teto 270000`: above it, the phase hands over before the review, and the successor runs the review and opens the PR. Without `--teto`, `acima=true` holds only for the 300 thousand. Checks (a), (b) and (c) continue even with the hook: they cover the epic created before stage #1856 and still without `main` (without the hook in the branch's `.claude/settings.json`) and a hook that fails silently. Once the phase PR is open there is no switch: what remains is CI, the merge and the notice, and the phase ends in the same session. The `/code-review` and the fixes of its findings come before the PR and never count as the PR open. That holds only for the phase's **last** PR: a phase that opens several PRs in sequence hands over between a merged PR and the next one when it is above the trigger, even if the earlier PR was open. Above the trigger of 270 thousand (the hook's notice or `acima=true` with `--teto 270000`), the phase hands over:
     1. waits for the running subagents to return, without interrupting any;
     2. commits what is done on the short branch, even with the gates red, with the message `WIP <código>: passagem por contexto`, and `git push -u origin <branch>`. Does not open a PR: a branch without a PR does not run CI (the squash of item 6 takes the WIP out of the epic history);
     3. comments on the phase sub-issue a text that starts with `Passagem da fase <código> (contexto <n> mil):` and carries the branch and the commit; the checkboxes done and those missing (the sub-issue is not ticked here: ticking continues after the merge); the tests seen failing before the code (name and failure), for the PR Summary; the decisions made outside the sub-issue; the files and sections already read, one line each with what matters in them for the rest of the phase; the pending defects so far; the biggest jumps of the hook's last notice (or "no hook notice"); and the next step;
     4. sends the coordinator `Troca de sessão da fase <código>: contexto <n> mil; passagem em <link do comentário>.`, through the Channel of item 7;
     5. Ends the turn. If woken up later (by the queue's check, for example), it only repeats the switch request.

     The one who creates the successor is the coordinator, with this same message and the line `Retomada por contexto (<k> de 5): a sessão anterior (<id>) passou a vez com <n> mil; a passagem está em <link>. Continue no branch <branch>, que já existe (não o recrie da origin/epic/<nome>), e não refaça o que a passagem dá como feito, e não releia o que a passagem dá como lido.` The successor reads the handoff in item 1 (the sub-issue comments) and continues on the branch that already exists, without redoing what the handoff gives as done or rereading what it gives as read: it brings the branch from the origin (`git fetch origin <branch>:<branch>` and `git switch <branch>`, which also works in a single-branch clone) and does not recreate it from the epic's origin (item 2 holds only for the first session). At most 4 switches per phase (5 sessions): the `5 de 5` session does not switch and goes to the end, and the final notice says "passou de 300 mil na quinta sessão". It also holds for the fix phase.
4. Every briefing for a behavior change or a fix follows the `test first` rule of `docs/PROCESS.md` ("Model use"): a test seen failing before the code, and the subagent returns its name and the failure.
5. Before the PR: `npm run lint && npm run typecheck && npm test && npm run build`.
   - **Long local command** (gates, `npm test`, the full suite, build): only with `run_in_background` of the `Bash` tool, which wakes the session when it ends; never `nohup`, `&`, `setsid` or `disown` in a plain call: the harness does not track a detached process, so no notice comes and the turn ends for good. ## Fix phase
```

With ❌ in the report **or with a pending defect** (the "Defeitos pendentes" of the phases' notices and the report observations that are defects and do not need an owner decision; docs/PROCESS.md, "Defect found during the stage"), the orchestrator creates a fix `step` sub-issue (with `parent_issue_number` of the stage, the list of findings with the link to the report comment, the list of pending defects with the origin of each one, and the acceptance criterion "the steps that failed pass, each finding was reproduced before and checked after, and each defect has a test that covers it") and a child session with the same message as the phase, pointing to that sub-issue. The fix **reproduces each finding before touching the code** (the automated test that fails for the reason in the report; for a visual or manual finding, the same check as the report, the recipe, the script or the step, run in the session and seen failing) and **checks again afterwards** that the same check passes, so that a retest is enough; the notice carries the "before" and "after" of each finding, and a finding that was not reproduced is not reported as fixed (it goes to the "Defeitos pendentes" with what was tried).
**Severity and retest (stage #1814):** the subagent that creates the sub-issue records the severity of each finding: the report's (section 10 of `docs/TESTING.md`; a finding without severity does not count as low) and, for an observation that is a defect and for a pending defect, the one from the scale in section 7 of `docs/TESTING.md`, and when in doubt, the higher one. It also records in the **Testador** section of the sub-issue "Reteste: não (todos de severidade baixa)" or the steps of the high and medium findings, and returns `#<number>: <N> achados (<code>:<severity>, …); reteste: sim|não`. With the findings **all of low severity**, the "after" check of the fix itself plays the role of the retest (the acceptance criterion "the steps that failed pass" is read through it), including a fix that changes `src/` (automated test seen failing before; visual finding without an honest test: capture before and after), and the merged notice leads to the closing (`reteste: não`). High or medium severity (`high` or `medium`) is `bloqueia`, `alta` or `média` of the report; `baixa` is `low`. In a mixed round, the retest covers only the high and medium ones; the low ones keep the "before" and the "after". A low that the fix does not reproduce goes to the "Defeitos pendentes" and gets a **directed retest of only its steps** (together with the high and medium ones, if any): the notice prevails over the `reteste:` line recorded earlier, and the orchestrator creates that retest even with `reteste: não` in the sub-issue. The round limit does not change; the fix session merges its own PR into the epic, like the phase (item 6). Only one fix per stage: a defect found after it becomes a `bug` issue. A finding that can only be fixed with code from another epic still outside `main` goes to the "Defeitos pendentes" with "depende de #N" and becomes a `ready` `bug` with `Depende de: #N`, without waiting (skill `implementar-fila`, step 4 of "Per stage"); high severity follows rule 1 and the epic becomes `esperando dono`. What needs an owner decision also becomes a `bug` issue, with the decision and the options in the body, and goes into the "left for later" of the closing. On the second failure, on a finding about data loss, `mapping.json` integrity or security, or if the fix needs a product decision, the orchestrator calls the owner ("Call the owner", in "Orchestrator — step by step").

## Code review

The rules are in `docs/PROCESS.md` ("Code review"). The reviewer only reads the code: it fixes nothing, makes no commit, push or PR, and does not comment on PRs. The output is one issue for the round and the `bug` issues, all with the `code-review` label.

### How it runs

- **Schedule "CR por épico"** (`trig_01NnLQbxT56N2JciyDxdnP4j`), every day at 02:50 (`CRON_TZ=America/Sao_Paulo 50 2 * * *`). It fires into the **coordinator session** `session_01Y37a9rGc6hS2VxVbVDhCcq` ("CR — coordenador (não arquivar)"), not a new session: a session opened directly by a schedule is born without the repository and gets 403 from the GitHub API, and `add_repo` does not exist in it. If the coordinator is archived, the schedule stops working (see "Recreating the coordinator"). The old schedule, `trig_01HVM7XdLhjVuhwHSFz7AiCf`, is disabled, not deleted.
- **The coordinator** does three steps, with the same commands as the schedule's prompt:
  1. **Lists** the epics merged into `main` after the base point of the CR baseline (commit `4532e75`, which stays out of the list), from the history of `main` and not from the API: `git fetch -q --shallow-since=2026-11-08T00:00:00Z origin main && git merge-base --is-ancestor 4532e75 origin/main && git log --reverse --first-parent --format='%H %s' 4532e75..origin/main | sed -nE 's|^([0-9a-f]+) Merge pull request #([0-9]+) from fabianofranca/epic/(.+)$|\2\t\3\t\1|p'`. Each line is an epic, from the oldest to the newest: PR, name and `merge_commit_sha`. The session's clone is shallow, and `--shallow-since` brings the history from the base point. If the command exits with an error (`4532e75` is not in the history of `origin/main`), it warns the owner with the error and stops. `main` only accepts a merge commit (ruleset "main protegida", owner's decision of 2026-11-12): every epic enters the first-parent line with the subject "Merge pull request #N from fabianofranca/epic/<name>".
  2. **Looks for the round issue** of each epic in the list, before running the script, to skip those that already have a `code-review` issue. It lists the `code-review` issues, open and closed, and reads the marker in the body and the number in the title: `gh api -X GET 'repos/fabianofranca/mapping/issues?labels=code-review&state=all&per_page=100&page=1' --jq '.[]|((.body // "")|scan("cr-epic: pr=([0-9]+)")[0]), (.title|scan("^CR épico .* \\(PR #([0-9]+)\\)$")[0])'`. Each line printed is a PR that already has an issue: the epic is skipped. If the page has 100 issues (the same call with `--jq length`), it repeats with `page=2`, `page=3`…, written out in full (`--paginate` does not paginate in this session). The listing costs one call per page and not one search per epic, and the marker finds the issue even after the detailing renames it (#1188, the round of PR #938, was renamed). It also skips the epic that has a "CR épico — <name>" session created by it with `status_bucket` `working` or `blocked` in `get_session` (still running).
  3. **Skips** the ones that already had a CR of the whole epic at closing, deciding by the commit, in a single shell loop (one output line per epic). The safety net of #1324 entered `main` with merge `55b2491` (PR #1381), and `scripts/ci/riskTriggers.mjs`, with merge `63e58b9` (PR #1434). For each epic left, by the `merge_commit_sha`:
     - if `git merge-base --is-ancestor 55b2491 <merge_commit_sha>` fails (merge earlier than the safety net), the epic enters the round;
     - if the merge contains `55b2491` but `git merge-base --is-ancestor 63e58b9 <merge_commit_sha>` fails, it is one of the six merges without the script (only those six: the interval has already closed), decided by the stage's closing comment: PRs #1381, #1343, #1418 and #1417 are skipped and noted as "CR at closing", and PRs #1373 and #1419 enter the round;
     - in the others, it runs in the clone `git checkout -q <merge_commit_sha> && node scripts/ci/riskTriggers.mjs --base <merge_commit_sha>^1`. With at least one `gatilho:` line, the epic had a CR at closing: it is skipped and noted as "CR at closing". With `nenhum gatilho`, the epic enters the round. With any other output or an error, it also enters (when in doubt, reviewing too much costs less than leaving an epic unreviewed), and the notification cites the PR and the output;
     - it goes back to `origin/main` afterwards (`git checkout -q origin/main`).

  Of those left, it creates up to 3 reviewer sessions per night (`create_session` with the repository's `source_url`, Sonnet), the oldest first. The rest wait for the next night. With no new epic, it does nothing. After creating the reviewers, it schedules a fallback check (`send_later`, 90 min). In it, it reads the `status_bucket` (`get_session`) of each reviewer that has not reported yet: `working`, schedules another one of 90 min; `blocked`, warns the owner; `failed`, or `completed` or `review_ready` without the issue, it creates the round issue itself, "CR épico <name> (PR #<pr>)", with the labels `roadmap`, `code-review` and `impact: low`, the line `Impacto: low — the epic's automatic review failed and needs to be redone`, "The automatic review failed: <status and last error>", the session link and, before the footer, the marker `<!-- cr-epic: pr=<pr> sha=<sha> -->`. It is one attempt per epic: the marker takes the epic out of the following nights, and the review goes to the backlog. In the notification to the owner, it says how many epics were skipped for "CR at closing", the PRs for which the script gave another output and the reviews that failed.

- **Each reviewer** deepens the shallow clone and reads the epic's diff (`git fetch -q --shallow-since=2026-11-08T00:00:00Z origin main && git diff <merge>^1 <merge>`), the PR and the stage's issue, and notifies the coordinator by `send_message`. With all the night's notices, the coordinator notifies the owner with the links, the findings, the `bug` issues, the cost and the skipped epics.
- **Recreating the coordinator**, when it is archived or disappears. `update_trigger` does not change a schedule's session, so:
  1. `create_session` with `source_url` `https://github.com/fabianofranca/mapping`, Sonnet and the title "CR — coordenador (não arquivar)";
  2. `create_trigger` with `persistent_session_id` of the new session, name "CR por épico", `cron_expression` `CRON_TZ=America/Sao_Paulo 50 2 * * *` and the prompt read by `get_trigger` from the current schedule, with the new id in step 8 of the template message;
  3. `update_trigger` with `enabled: false` on the old schedule, without deleting it;
  4. a `roadmap` issue to swap the ids in this file (in "How it runs" and in step 8 of the block below).
- **The schedule's prompt** holds the reviewer's TEMPLATE MESSAGE, and the block in "For the per-epic CR reviewer" is its copy, letter by letter. Only the coordinator's conversation changes the prompt: `update_trigger` with `prompt` is refused in any other session ("a routine's instructions (its prompt) can be changed only from the conversation or thread the routine posts into"). Whoever changes the reviewer block or the steps puts the whole new prompt in the epic PR's description, in a `text` block, with the line "Dono: aplicar este prompt no CR por épico"; the closing comments the link to that prompt on the `roadmap` issue opened to apply the prompt (or creates one), and the owner applies it in the coordinator's conversation. CI does not read the schedule: `tests/tooling/epicCodeReview.test.ts` checks only this side, and the epic's closing reviews the change because `docs/FLOW.md` is a risk trigger.

### Known limitations

- `/code-review` only works with a diff. To review whole files (as in the CR baseline), the reviewer reads the files; on a diff, if the skill returns findings from files outside it, they are discarded.
- In these sessions GitHub only works through the REST API: `gh issue create`, `gh repo clone` and GraphQL fail. The commands, and how to write the search, are in item 6 of "For the per-epic CR reviewer".
- The sessions are born with a shallow clone (depth 50): without `--shallow-since`, the list in step 1 comes out short with no error, and the `<merge>^1` of old merges does not exist. `gh api --paginate` does not paginate in these sessions, because the proxy refuses page 2 with 403.
- The high and medium defects are checked by reading the code, not by running the app; the low ones are not rechecked.
- An epic closed **outside the queue** (through the manual flow): if the diff has a trigger, `riskTriggers.mjs` points out `gatilho:` and the nightly CR skips it, even without `/code-review high` at closing, because the safety net only exists in the `implementar-fila` skill. The criterion and the manual flow do not change (owner's decision of 2026-11-11). Even in the queue, the nightly CR does not check whether `/code-review high` ran at closing: the criterion only looks at whether the diff has a trigger (owner's decision of 2026-11-12).
- Search (`search/issues`) accepts 30 calls per minute (`gh api rate_limit`), and two searches per epic went over that on the first night (about 100 calls); that is why step 2 lists the `code-review` issues, one call per page of 100 (the common limit is 15,000 per hour). What still grows every night is the script in step 3, which runs on the epics with a trigger since `63e58b9`, locally and in seconds per epic.

## Queue supervision
