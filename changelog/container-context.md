# Container context — [Não lançado] (épico `epic/container-context`, PR #0, MCP 0.56.0, schema v23, specialization formatVersion 21, proposal formatVersion 11)

## Adicionado

- Specialization `formatVersion` 21: **container classes**. The root key `containerClasses` declares named sets of classes, each one **computed** from the container's size in units (`by: "width"` or `"height"`, with `below` on every class but the last) or **chosen** per container (no `by`); `classes` on a ready-made size of `containers` carries the choice of a chosen set (the Phone size chooses `android`); `appliesIn` on a type lists the classes the type is meant for (any of the listed ones inside a set, all the sets together). The three keys are outside the version contract (no `version` raise, no migration, no `diffSpecs` difference) and versions 1 to 20 behave as before (#2036, #1901).
- Validation of the new keys with the path of each problem (`containerClasses[i].classes[j]`, `containers[i].classes.<set>`, `…appliesIn.<set>`): reserved ids `width` and `height`, `below` rules, unknown sets and classes, empty and repeated lists, and `appliesIn` only on a type that applies to markings in a container. Messages in both languages (#2036).
- Model API `computedClassOf(set, units)` (the class of a computed set for a size in units), `unitsOf(pixels, density)` and `isComputedSet`, pure and tested (`src/model/containerClasses.ts`). Nothing calls them in the app yet (#2036).
- Example package `examples/libraries/sdui-backend/` (`version` 4): the `platform` (chosen) and `window` (by width: `compact` below 600, `medium` below 840, `expanded`) sets, the new Web desktop size (1440 × 900), `classes` on the Phone size and `appliesIn` on `sdui-sheet` and `sdui-fab` (#2036).
- `docs/SPEC-FORMAT.md` (sections "Container classes (`formatVersion` 21)" and "Container classes a type is meant for"), `docs/spec.schema.json`, Help › Specializations, the `spec-author` skill (step "12c. Container classes"), `docs/AGENT-GUIDE.md` and the MCP descriptions of `get_specialization`, `validate_specialization` and the `spec-format` resource (#2036).
- Project schema v23: the container's **`classes`** (`set id → class id`, optional) holds the choice of the specialization's chosen sets. The model has `effectiveContainerClasses` (chosen plus computed from the size in units), `containerClassSets` (the union of the applied specializations' sets) and `undeclaredContainerClasses`, the store action `setContainerClass`, and the error code `container-class` (an id outside `[a-z0-9-]+`); a choice that no specialization declares is kept in the file and left out of the effective classes (#2037).
- Proposal `formatVersion` 11: the container's `classes` field and the `classes` inside a created or removed container; the review text shows the choice by the specializations' names (#2037).
- MCP: `add_container` and `update_container` accept `classes` (`null` removes a set or all of them); `get_container`, `get_project` and `get_marking` return `classes` and `effectiveClasses`; a computed, undeclared or unknown choice is `invalid-arguments` with the `chosenSets` (#2037).
- Pending item **`outside-container-class`**: a marking whose container has a class outside the type's `appliesIn` is incomplete (one item per failing set, with the set, the class and the classes the type is meant for). It counts in **Incomplete**, shows in the Details ("Not meant for Window: Expanded (meant for: Compact, Medium)"), and comes through the MCP in `get_marking`, `get_annotation`, `list_markings` and `issues.new` of `plan_changes` (#2038).
- App: the container **Details** show one selector per chosen set (None and the classes) and a read-only line per computed set with its size in units; the **New container** dialog creates the container with the choice of the ready-made size (Web desktop is born with the platform Web); **Diagnostics** lists a stored choice that no applied specialization declares (#2038).
- Component engine: **`$container.*` pseudo-fields** (component `formatVersion` 4, stays 4): `$container.width` and `$container.height` (the container's size in units) and `$container.<set>` (its class in a set the specialization declares) in the template and in `sizing`; an empty value on the canvas and for a set without a class; any other name is `field does not exist`. They reach the inner instance of a `component` node, the slot `fallback`, the slot's `layout` (Arrange, the slot plan) and the measures (`fit_marking`, creation, Arrange), so what is measured is what is drawn. The MCP `render_marking`/`render_container` and the viewer draw them through the same model, with no new argument (#2039).
- Drawing cache: a component that reads the container is redrawn when the part it reads changes (the class of a set it cites, or the size); a sibling that does not read it keeps the same drawing object (#2039).
- Library proof: a component that reads a set is drawn once without a container and once per class of each set it reads (the sum, not the product); a warning that only a class gives reads `in container window=expanded: …` (pt-BR `no container window=expanded: …`). `validate_library` also refuses `$container.<name>` that is neither `width`, `height` nor a set of the specialization (#2039).
- Example `sdui-backend`: `sdui-column` (component `formatVersion` 4) pads 16 px in a `compact` container and 24 px in the others when the type has no `padding`; the `padding` field lost its `0` default so that the class decides (#2039).
- Specialization `formatVersion` 21: **library documents**. The root key `documents` (`[{ id, name, doc }]`, non-empty, `id` in `[a-z0-9-]+` and unique) declares the library's general documents (conventions, glossary, rules of no single type); `doc` follows the type's `doc` rules (a package `.md` or `{ repo, path }` of `docRepos`). A text document is a cited package file (checked at level 1, no longer "unreferenced") and a `{ repo, path }` one counts as a use of its repository (no `unused-doc-repo`). Outside the version contract (no `version` raise, no migration, no `diffSpecs` difference); the error message `invalid document id; use [a-z0-9-]+` exists in both languages (#2040, #1901).
- MCP: new tool **`get_library_document({ project, specId | path, document })`** (read-only), returning `{ spec, id, name, doc, path }`; an external document is read through the project's clone like a type's, and a file above 1 MiB is not read (`tooLarge: true`); an unknown id is `not-found` with `details.available`. `get_specialization` and `validate_library` carry `documents` (the library counts and the external-document warnings include them) (#2040).
- App: the **Catalog** lists a **Documents** group above the layers (home screen and the project's Catalog window), filtered by the same search; a document opens in its own page that renders the markdown like a type's Document section (#2040).
- Example `analytics` (`version` 3, `formatVersion` 21): `documents` with `docs/conventions.md`; `docs/spec.schema.json`, `docs/SPEC-FORMAT.md`, `docs/MCP.md`, `docs/AGENT-GUIDE.md` and the `spec-author` skill updated (#2040).
