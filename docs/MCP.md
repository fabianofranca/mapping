# Servidor MCP do Mapping

O servidor MCP deixa um agente (Claude Code, Claude Desktop ou outro cliente MCP) **ler projetos Mapping guardados em pasta e propor alterações a eles**, com as mesmas regras da app (invariantes, travas, referências, especializações). O agente **nunca grava o `mapping.json`**: toda alteração chega como uma **proposta** em `proposals/`, que o usuário revisa na app (aceita ou rejeita em qualquer nível, com notas) e aplica. Desde a 0.25.0 ele também **conversa**: lê as conversas que as pessoas abrem nos itens, pergunta quando uma decisão não é dele e responde em `comments/` (ver "Mudança da 0.25.0"); nunca resolve nem apaga uma conversa. Desde a 0.26.0 ele também **lê as perspectivas** do projeto (recortes por público; ver "Mudança da 0.26.0"), sem nunca criá-las nem alterá-las. Ele roda localmente, por stdio, no Node (≥ 20), e não faz nenhuma requisição de rede (o servidor de imagens local só escuta em 127.0.0.1).

Só projetos **em pasta** ficam ao alcance do MCP; projetos guardados no navegador, não. Para usar o servidor, crie ou abra o projeto na app como **pasta**.

## Instalação

1. Baixe `mapping-mcp.js` da [última Release `mcp-v*`](../../../releases) (há também um `mapping-mcp.js.sha256` para conferir: `sha256sum -c mapping-mcp.js.sha256`). Para testar algo ainda não publicado, baixe de uma pre-release: `mcp-snapshot-pr<N>` (o build de um PR de fase, antes de entrar no épico) ou `mcp-v0.36.0-rc.<n>` (a release candidate do épico, gerada no merge da última fase). Elas anunciam a versão com sufixo em `--version` (`0.8.0-snapshot.pr172+abc1234`, `0.8.0-rc.1`).
2. Copie o arquivo para `tools/` no repositório do app. Ele é autocontido (dependências, WebAssembly de imagem e documentação embutidos): não precisa de `npm install`.
3. Registre o servidor num `.mcp.json` na raiz do repositório:

   ```json
   {
     "mcpServers": {
       "mapping": {
         "command": "node",
         "args": ["tools/mapping-mcp.js", "--root", "design/mapeamentos"]
       }
     }
   }
   ```

4. Abra o Claude Code (ou outro cliente) no repositório e aprove o servidor `mapping`. As tools aparecem como `mcp__mapping__…`.

> **Repositório com `"type": "module"` no `package.json`:** o arquivo é CommonJS. Coloque ao lado dele, em `tools/`, um `package.json` com `{"type":"commonjs"}`; sem isso o `node` o lê como módulo ES e falha.

Teste fora do cliente: `node tools/mapping-mcp.js --version` e `--help`.

> **Pasta central de mapeamentos.** Para guardar vários projetos numa pasta só, pronta para qualquer cliente MCP (Claude Code, Cursor, Gemini CLI, Copilot, Codex), copie [`examples/workspace/`](../examples/workspace/): o `setup.sh` baixa da release o servidor, a skill `spec-author` e o bloco de regras do `AGENTS.md`, confere o `sha256` de todos antes de trocar qualquer arquivo e se atualiza sozinho (`--no-self-update` desliga); o `AGENTS.md` explica a pasta ao agente. A linha para atualizar um workspace antigo (rode uma vez) está no `README.md` da pasta e abaixo, em "Publicar uma versão".

## Raízes

`--root <pasta>` define onde o servidor pode ler e gravar; repita para mais de uma. Caminhos relativos valem a partir do diretório de trabalho do cliente (o repositório, quando o `.mcp.json` é do projeto). O argumento `root` do `create_project` aceita a raiz do mesmo jeito: como está no `--root` (relativa, com `./` ou barra final), absoluta, como listada em `roots` pelo `list_projects`, ou pelo nome da pasta, se só uma raiz o tiver. O servidor procura projetos (pastas com `mapping.json`) em qualquer profundidade dentro das raízes. `--no-http` desliga o servidor de imagens local (as tools de imagem respondem sem `url`/`markdown`).

Segurança: o servidor só lê e grava dentro das raízes. Recusa `..`, caminhos absolutos fora delas e links simbólicos que saem delas (`outside-roots`); não segue links ao procurar projetos; e grava de forma atômica (arquivo temporário + renomear) o projeto vazio e as atualizações de uma proposta; os arquivos novos de uma proposta vão por arquivo temporário + hard link, que nunca sobrescreve (num disco sem hard link, como exFAT, grava direto, ainda sem sobrescrever). Apagar o temporário é melhor esforço (desde a 0.3.4): se o sistema recusa (antivírus do Windows, pasta montada numa VM), o arquivo gravado vale, o servidor escreve um aviso no stderr e o `.<arquivo>.<x>.tmp` fica na pasta da proposta; nem a app nem o servidor o leem, e ele pode ser apagado à mão. O que ele grava: o projeto vazio do `create_project`, a pasta `proposals/` (propostas e as imagens delas) e, desde a 0.25.0, as conversas em `comments/<id>.json` (a conversa nova por arquivo temporário + hard link, que nunca sobrescreve; a mensagem acrescentada, por escrita atômica depois de reler o arquivo). **Nunca** grava em `comments/resolved/` (quem resolve é uma pessoa, na app). O único socket que abre é o do servidor de imagens local: escuta só em 127.0.0.1, numa porta aleatória, com um token aleatório no caminho, serve apenas as imagens geradas pelas tools nesta sessão, guardadas em memória, e se desliga com `--no-http`. **O `mapping.json`, as cópias de `specs/` e `images/` só a app grava**, ao aplicar uma proposta; as conversas resolvidas, reabertas e apagadas também são só da app. Ler nunca grava, nem para migrar um projeto de schema antigo: a migração (com backup em `backups/`) é da app, na primeira gravação; a proposta é calculada sobre o projeto migrado em memória. A única exceção ao "só dentro das raízes" é a conferência de **existência** de arquivos de código, que olha só metadados (`stat`) e fica confinada ao diretório de trabalho do cliente (ver "Código de instanciação das especializações"), e a leitura do `.md` de **documento em repositório externo** pelo `get_component` (ver "Mudança da 0.18.0"), confinada ao mesmo diretório.

## Referências

O Ctrl+C (Cmd+C) na app, com uma marcação, container ou anotação selecionada, copia a referência:

```
mapping://<projeto>/<m|i|a|p|l|c>/<código>
mapping://<projeto>/a/<código>/f/<campo>
mapping://<projeto>/a/<código>/e/<código>
mapping://<projeto>/a/<código>/f/<campo>/r/<código>
```

- `<projeto>`: nome da pasta do projeto, codificado como em uma URL (`A-Z a-z 0-9 - . _ ~` ficam como estão; todo o resto vira `%XX`, em UTF-8: `Meu Projeto (v2)` é `Meu%20Projeto%20%28v2%29`). Se houver duas pastas com o mesmo nome, o servidor devolve as candidatas e pede o caminho.
- `m` marcação, `i` **container** (a letra não mudou quando a imagem virou container, para as referências já coladas continuarem valendo), `a` anotação, `p` **proposta** (a que `propose_changes` e `list_proposals` devolvem), `l` **camada** e `c` **conversa** (a que `list_threads` e `open_thread` devolvem). Depois do código de uma **anotação** pode vir uma parte: `/f/<campo>` (a `key` do campo tipado, codificada como o projeto), `/e/<código>` (um par da anotação livre) e, depois de um campo `table`, `/r/<código>` (uma linha). A gramática completa é a de [`COMMENT-FORMAT.md`](COMMENT-FORMAT.md), "Referências e citações".
- `<código>`: os 8 primeiros caracteres hexadecimais do id (12, 16… se houver colisão).
- A referência é **só a URL**: não leva caminho legível nem nada depois do código (o nome vem do `resolve`; o caminho legível, do `path` de `get_marking`, `get_container` e `get_annotation`). Qualquer coisa depois do código (o ` (caminho)` do formato antigo, `?`, `#`, espaço) ou um projeto sem codificar é `invalid-ref` (ver "Mudança da 0.21.0").

Toda tool que recebe um item (`ref`) aceita a referência completa, só `m/3f2a9c1e` com `project` informado à parte, ou o id completo. Cole a referência no chat e o agente a resolve sem precisar do projeto. Nas tools de proposta, `ref` é `mapping://projeto/p/3f2a9c1e`, `p/3f2a9c1e` (com `project`) ou o id da proposta; o código é único entre as propostas do projeto. Nas de conversa, `ref` é `mapping://projeto/c/5d0e8a41`, `c/5d0e8a41` (com `project`) ou o id da conversa. O `resolve` entende todas as formas e devolve `kind` `marking`, `arrow`, `container`, `annotation`, `layer`, `thread`, `field`, `entry` ou `row` (campo, par e linha trazem `annotation`, `key` e `value`). `get_annotation` e as demais tools de item aceitam campo, par ou linha como a anotação que os contém; numa tool de marcação ou de container uma parte é `wrong-kind`, uma camada ou conversa numa tool de item também é `wrong-kind`, um sufixo que a gramática não conhece continua `invalid-ref` e um campo, par ou linha que não existe na anotação é `not-found`. As referências antigas (`m`, `i`, `a`, `p`) valem como sempre. **Ctrl+Alt+C** copia o recorte da marcação como PNG.

As regras de uso das conversas estão no "Conversas" do `AGENT-GUIDE.md`.

### Código de instanciação das especializações (etapas 3b, 9 e Código de instanciação)

As especializações podem declarar **plataformas** (alvos em que o agente escreve a solução: Android, iOS, o BFF) e dizer, em `code`, com que código se cria uma instância de cada tipo de anotação em cada uma: `symbol` é o que se chama, `path` é o arquivo que o define (para ler a assinatura), `params` e `values` dizem como passar os campos e `notes` orienta. O **repositório é da biblioteca**, logo da especialização (`platforms[].repo`: `url`, `urlTemplate?`, `ref?`); o projeto só sobrepõe o clone local (`platformRepos[<plataforma>].localPath`). O mapeamento não guarda nada sobre a solução (não há o campo `codeRef` desde a 0.4.0). Detalhes do formato em [`FORMAT.md`](FORMAT.md) e [`SPEC-FORMAT.md`](SPEC-FORMAT.md). O fluxo do agente está em [`AGENT-GUIDE.md`](AGENT-GUIDE.md): referência `mapping://` → `get_marking` e `get_marking_image` → `get_code_hints` → ler a `definition` de cada tipo → escrever as chamadas.

Na especialização 9, o `code` pode ter `variants` (a variante troca o `symbol`, como `Button` e `OutlinedButton` em Compose): `get_marking` e `get_annotation` entregam o código **já resolvido** para a variante de cada anotação, `get_code_hints` o traz na anotação da `tree` (o `types` é o cru da base), e `get_specialization` e `get_component` o cru.

Em `get_marking`, `get_annotation`, `find_by_code`, `get_component` (campo `code.<plataforma>`) e em `types` de `get_code_hints`, cada entrada de `code` tem a mesma forma, com a `definition` (o arquivo que define o `symbol`) resolvida ao lado:

```json
{
  "symbol": "com.app.ds.DSButton",
  "definition": {
    "path": "app/src/main/java/com/app/ds/DSButton.kt",
    "url": "https://github.com/org/app-android/blob/v3/app/src/main/java/com/app/ds/DSButton.kt",
    "ref": "v3",
    "localFile": "app/src/main/java/com/app/ds/DSButton.kt",
    "exists": true
  },
  "params": { "texto": "text", "estilo": "style" }
}
```

- `url` e `ref`: do `repo` da especialização. `url` é montada pelo `urlTemplate` (`null` sem ele); o caminho não tem linha. Sem `path`, `definition` é `null`.
- `localFile`: o `localPath` da plataforma (sobreposição do projeto, relativo à pasta do projeto) mais o `path`, **relativo ao diretório de trabalho do cliente** (o do processo do servidor; no Claude Code, o repositório). `exists` diz se o arquivo está lá. Sem `localPath`, os dois são `null` (a plataforma sem clone local não é problema: o agente abre a `url`). No `get_component` por `path` (pacote sem projeto), `localFile` e `exists` são sempre `null`.
- `find_by_code` responde "que tipos se instanciam com este arquivo ou símbolo, e onde estão marcados" (formato no [`AGENT-GUIDE.md`](AGENT-GUIDE.md)).
- **O servidor nunca lê nem grava arquivos de código**: só monta o caminho e confere a existência (`stat`), o que é coberto por teste. O agente lê o arquivo com as próprias ferramentas.
- **Limite de segurança**: o `localPath` pode subir pastas (`../../..`) e o `path` vem de um arquivo que outras pessoas podem editar. Por isso a conferência só olha **dentro do diretório de trabalho do cliente**, também depois de seguir links simbólicos. Se o caminho calculado sai dele, a `definition` traz `localFile: null`, `exists: null` e `localFileProblem: "outside-workdir"` (sem tocar no disco); um link simbólico que leva para fora vale `exists: false`. Para o `localFile` aparecer, abra o cliente na raiz do repositório clonado.
- `get_project` traz, em cada plataforma declarada pelas especializações aplicadas, `repos` (o `repo` de cada especialização que a declara, com `specId`) e `localPath` (ou `null`); `platformRepos` traz só o `localPath`. Não há mais avisos de repositório: a plataforma sem clone local não é problema.

### Setas e `near` (ME4)

- **`create_arrow`** (`from`, `to`, `style?`, `name?`, `as?`), **`update_arrow`** (`arrow`, `name?`, `style?`, `locked?`) e **`delete_arrow`** (`arrow`), operações de `plan_changes` e `propose_changes`. A seta liga duas marcações (nunca outra seta nem um container: `arrow-endpoint`; a mesma ponta duas vezes: `arrow-self`), com `style` `straight`, `curve` (padrão) ou `elbow`. **Nunca `points`**: a rota é da pessoa, e `points` em `create_arrow` ou `update_arrow` falha com `invalid-arguments`. A proposta leva só a criação e a remoção da seta (`create-arrow`, `delete-arrow`); `update_arrow` numa seta que já existe vale na prévia (`plan_changes`) e avisa com `ignored-argument` que não entra na proposta.
- **Referência da seta**: os ids das setas e os das marcações dividem o espaço, então a seta usa a letra `m` (`mapping://projeto/m/<código>`). `get_marking` e `resolve` com ela devolvem `kind: "arrow"`, `from`, `to` (no `get_marking`: referência, nome e caminho; no `resolve`, só a referência), `style`, `lock` e as anotações por camada; `create_annotation` aceita a referência da seta em `marking`.
- **`appliesTo` é imposto.** `create_annotation` com um tipo que não se aplica ao item (um tipo só de marcação numa seta, ou só de seta numa marcação) falha com `type-not-applicable` e uma `hint`; `update_marking` e `delete_marking` com o id de uma seta falham com `wrong-kind` e a `hint` aponta `update_arrow` ou `delete_arrow`. Uma anotação que deixou de se aplicar depois de uma atualização da especialização vira pendência (`type-not-applicable`), não erro; a prévia da atualização lista a mudança como `changed-applies-to` (aditiva).
- **`get_marking`** de uma marcação traz `arrows: { outgoing, incoming }` (quando há): `ref`, `id`, a outra ponta (`to` nas que saem, `from` nas que chegam), `name`, `style` e `locked`.
- **`get_marking_image`** recusa a seta com o erro `arrow` (e uma `hint`) e a marcação do canvas com `canvas-marking`.
- **`near`** em `create_marking` (referência, id ou apelido de um container ou de uma marcação): só para um tipo de anotação flutuante (sem `container`); a marcação nasce num lugar livre da margem do alvo (à direita, empilhada de cima para baixo com vão de 24 unidades do canvas, sem sobrepor containers nem outras flutuantes; se não couber, esquerda, embaixo, em cima). O `rect`, se vier, dá só o tamanho (x e y são ignorados). Em tipo ou marcação não flutuante, `near` é ignorado com aviso `ignored-argument`.
- `changes` de `plan_changes`/`propose_changes` ganha `arrows` (criadas, alteradas, excluídas) e `created` traz `kind: "arrow"`.

### Mudança da 0.25.0 (Comentários)

O que chega é a **conversa ancorada** (`mapping-thread` 1, `docs/COMMENT-FORMAT.md`): as pessoas comentam itens na app, em `comments/<id>.json`, e o agente lê, pergunta e responde pelo servidor. O `mapping.json` nunca é alterado por uma conversa.

- **Tools novas:** `list_threads`, `get_thread`, `open_thread`, `post_message` e `wait_for_comment` (tabela em "Tools"; regras de uso no "Conversas" do `AGENT-GUIDE.md`).
  - `list_threads` sem filtro devolve a **caixa de entrada**: as conversas abertas que aguardam o agente (a última mensagem é de pessoa). Uma conversa só entre pessoas também aparece assim; o guia manda responder só ao que lhe é pedido.

O servidor relê o arquivo antes de gravar, refaz a operação sobre a versão do disco se a app o mudou no meio e grava `revision + 1`; depois de 3 tentativas, o `revision-conflict` de sempre.

Numa tool de marcação ou de container, uma parte é `wrong-kind`; camada ou conversa numa tool de item, `wrong-kind`; sufixo desconhecido, `invalid-ref`; campo, par ou linha inexistente, `not-found`. As referências `m`, `i`, `a` e `p` não mudam.

- **Erros novos** (lista no `AGENT-GUIDE.md`): `thread-not-found`, `thread-resolved`, `stale-thread`, `invalid-anchor`, `anchor-not-found`, `empty-message`, `message-too-long` (10.000 caracteres) e `invalid-thread` (o arquivo da conversa está ilegível; não é sobrescrito). Avisos novos: `broken-cite` (citação que não resolve; a mensagem é gravada assim mesmo) e `thread-not-linked`.
- **Recurso novo:** `mapping-docs://COMMENT-FORMAT.md`, o formato da conversa.
- **Acordar o agente:** o servidor só age quando o agente já está de pé. Para abrir o agente quando alguém pergunta algo, o workspace traz o `watch-comments.mjs` (`examples/workspace/README.md`, "Conversas: acordar o agente"), fora do servidor, que o `setup.sh` instala e atualiza na raiz do workspace.

A 0.25.0 lê e responde as conversas gravadas pela app; um arquivo de conversa com formato que ela não entende vai para `broken` no `list_threads`.

### Mudança da 0.23.0 (Correção na mesma proposta)

Schema v14 e especialização (`formatVersion` 11) sem mudança; a proposta ganha o **formato 5** (`docs/PROPOSAL-FORMAT.md`, "Revisão pelo agente"), que **só a revisão grava** (a criação continua no formato 4).

- **Tool nova `revise_proposal(ref, project?, { operations?, drop?, dryRun? })`**: o agente corrige a proposta aberta na própria proposta, em vez de mandar outra com `supersedes`. Precisa de `drop` ou de `operations` com pelo menos um item (senão `invalid-arguments`); um resultado que não muda nada é `no-changes`.
  - `drop`: ids de mudança (`c3`, como o `get_proposal` mostra) a retirar. Segue as dependências: retirar a criação retira o que depende dela; retirar a remoção de uma cascata retira a de quem a causa. Id que não existe: `change-not-found`.
  - `operations`: o mesmo vocabulário e a mesma validação do `propose_changes`, aplicados sobre o **proposto inteiro** (o projeto atual mais todas as mudanças que ficaram, de qualquer decisão, inclusive as rejeitadas), depois do `drop`. Por isso se edita pelo id definitivo (referência `mapping://…`) um item que a própria proposta cria. Os apelidos `$nome` valem. Um lote com erro não grava nada e traz `errors` por operação.
  - `dryRun: true` calcula e devolve o resultado sem gravar (`revised: false`, `dryRun: true`).
- **Cada mudança sai da revisão de um tipo só:** _intocada_ (idêntica: id, `from`, `to`, decisão e notas), _trocada_ (mesmo id e `from`, `to` novo; a decisão sai, volta a sem decisão; as notas ficam; ganha a marca "Revisada"), _nova_ (id `c<n>` nunca usado, sem decisão, com a marca) ou _retirada_ (sai de `changes`; as notas dela sobem ao nível da proposta, com texto e data iguais). Só as decisões das trocadas e das retiradas mudam; as dependentes rejeitadas junto continuam rejeitadas (item Parcial na revisão).
- **O aceito fica congelado.** Mudança **aceita** e ainda não aplicada não é trocada nem retirada: se o lote tocaria uma, a chamada inteira é recusada, sem gravar, com `change-frozen` (os ids vêm no erro). A `hint` diz que o usuário já aceitou essas mudanças: peça a ele para limpar a decisão ou mande uma proposta nova com `supersedes`.
- **Quando pode:** proposta `open` com `applied` vazio. Com algo já aplicado: `proposal-applied` (use `propose_changes` com `supersedes`); em outro status: `not-open`; projeto somente leitura: `read-only`. Uma proposta que não se aplica mais ao projeto atual (`entity-missing`, `entity-exists`, `field-mismatch` ou invariante) é recusada com `proposal-not-applicable`, com os problemas e os ids das mudanças; a `hint` manda retirá-las no `drop` ou enviar uma proposta nova.
- **Pacote de biblioteca** (especialização em pasta) novo ou trocado numa revisão: `revise-unsupported` (vai numa proposta nova). Retirar a mudança de um pacote que já está na proposta pode, e os arquivos dele saem da pasta da proposta.
- **Imagens:** a troca de arquivo nova grava a imagem em `proposals/<id>/images/` sem sobrescrever nenhuma; a imagem de uma troca retirada sai da pasta (melhor esforço: a falha vira aviso no stderr e a revisão vale).
- **Resposta:** `revised` (`false` no `dryRun`, que também traz `dryRun: true`), `proposal` (`ref`, a mesma; `id`, `title`, `status`), `revision` (a do `proposal.json`, já com +1), `counts` (`changed`, `added`, `dropped`), as listas `changed`, `added` e `dropped` (cada item com `id` e um `summary` legível), `created` (as referências definitivas dos itens criados, como no `propose_changes`), `warnings` e `hint`.
- **Leituras que mudam:**
  - `get_proposal`: cada mudança com a marca traz `revised: { at, kind: "changed" | "added", previous?: { to, state } }` (`previous` só na trocada; `state` é `"rejected"` ou `null` = sem decisão), e só enquanto a mudança está **sem decisão** (decidir tira a marca, como na app), e a raiz traz `revisions: { count, last: { at, changed, added, dropped } }` (só quando há revisões).
  - `get_proposal_review`: `revisable` (aberta e nada aplicado) e uma `hint` que aponta `revise_proposal` ou, sem poder, `propose_changes` com `supersedes`; `awaitingUser` (as trocadas e novas ainda sem decisão: `change`, `target`, `revised`), que **não** contam como rejeitadas; e as notas que subiram para a proposta saem nas notas gerais com `fromDroppedChange` (o resumo da mudança retirada de onde vieram).
  - `list_proposals`: `lastRevisedAt` por proposta (ausente se nunca foi revisada).
- **Erros novos:** `change-frozen`, `change-not-found`, `proposal-applied`, `proposal-not-applicable` e `revise-unsupported` (lista no `AGENT-GUIDE.md`).
- **Compatibilidade:** uma app antiga em cache recusa o arquivo de formato 5 e não o sobrescreve; um servidor MCP antigo lista a proposta em `broken`. O `mapping.json` nunca é alterado pela tool.

### Mudança da 0.22.0 (Desempate estável)

Sem mudança no formato do `mapping.json` (schema v14), da especialização (`formatVersion` 11) nem da proposta (formato 4), e sem tool nova. O que muda é o resultado de reordenar e o de aplicar uma proposta: o assentar da hierarquia passa a **preferir a relação atual** nos empates, e a ordem do array `markings` só decide empate novo.

- **Reordenar não troca mais pais.** `move_marking` (e a **Ordem** dos Detalhes da app) só muda a ordem entre irmãs: duas marcações de mesmo retângulo onde uma é pai da outra continuam assim, mesmo que a reordenação ponha a filha antes no array; e, entre candidatas de mesma área a pai, o pai atual fica. Isso vale também no assentar seguinte (um `move_marking` ou um gesto depois), que antes podia inverter pai e filho.
- **Retângulos iguais:** a ordem de fora para dentro, dentro do grupo, é a dos `parentId` atuais (o pai antes do filho); quem acabou de chegar ao retângulo, sem pai no grupo, entra pelo array (a de antes é a de fora), como sempre.
- **A proposta aplicada é igual ao proposto, também com `move_marking` no lote.** Aplicar todas as mudanças de um `propose_changes` dá os mesmos pais (marcações e containers) e a mesma ordem entre irmãs que o `membership` e a visão Proposto mostraram, com ou sem `move_marking` (fim da "Exceção conhecida (#549)" das versões anteriores). Dois ajustes de apoio: a âncora `insertBefore` é escolhida para os empates saírem como no proposto, e a revisão não mostra mais uma mudança de posição a mais quando duas marcações novas entram no mesmo lugar. Limite conhecido (#625): um empate entre marcações que já existiam, decidido no lote por um passo intermediário que a proposta não registra, segue a relação da base e pode dar outro pai (cerca de 1 lote em 1.000 num fuzz); confira com `get_marking` depois de aplicar.
- **O `parentId` lido continua sendo a fonte da verdade:** o agente confere a hierarquia com `get_marking` e não deduz o pai pela posição no array.

**Vistas.**

- `get_annotation` de uma filha traz `parentRole` (o `id`) e `roleName` (o nome do papel); sem papel, as duas chaves não vêm. Numa dona cujo tipo declara papéis, traz também `linkedByRole`: `{ label, roles: [{ id, name, linked }], unassigned }`, com os filhos de cada papel na ordem do tipo (`linked` são referências `mapping://`) e, em `unassigned`, os sem papel ou com um papel que a dona não oferece. `label` é o `childRolesLabel` do tipo. **`get_component` com documento em repositório externo** (`doc` do tipo é `{ repo, path }`: um `.md` de um repositório de `docRepos`, fora do pacote).

- Com `project` + `specId`, o clone do repositório configurado (`docRepos[<repo>].localPath` do projeto) e o arquivo lá, **`doc` é o texto** do `.md` e `docExternal` é `{ repo, path, url, localFile, exists: true }`. `url` vem do `urlTemplate` do repositório (`null` sem ele) e `localFile` é relativo ao diretório de trabalho do cliente, como no `definition.localFile` do código.
- Nos demais casos, **`doc` é `null`**, `docExternal` traz o `url` (ou `null`) e uma `hint` diz o que fazer: sem `localPath` (`exists: null`: configure com `set_doc_repo` ou abra o `url`); clone sem o arquivo (`exists: false`: confira a `ref` do clone); `localPath` que leva para fora do diretório de trabalho (`localFile: null`, `exists: null`, `localFileProblem: "outside-workdir"`); leitura por `path`, sem projeto (`localFile` e `exists` sempre `null`). Arquivo acima de 1 MiB não é lido (`doc: null` e a `hint` manda abrir o arquivo ou o link).

A leitura passa pelo mesmo conferidor do `codeFiles.ts`: o caminho calculado (e o real, depois dos links simbólicos) precisa estar **dentro do diretório de trabalho do cliente**, senão nada é lido nem tocado no disco. O código de instanciação continua nunca sendo lido (`stat` apenas), e nada é gravado.

**`validate_library` com `docClones`.** O documento externo está fora do pacote, então o servidor não o encontra sozinho. `docClones` é `{ "<repo>": "<pasta dentro das raízes>" }`, um clone por repositório de documentos:

- Com o clone de um repositório, cada documento dele é conferido, e o ausente é **aviso** (nunca erro, porque o clone pode estar noutra `ref`): `documento não encontrado em <repo>: <path>`, no caminho do tipo (`layers[i].annotationTypes[j].doc`).
- **Sem** o clone de um repositório, vem **um aviso por repositório**, no caminho `docRepos[n]`: `N documentos de <repo> não conferidos (sem clone)` (no singular, `1 documento de <repo> não conferido (sem clone)`).
- Um `doc` objeto cujo `repo` não está em `docRepos` é **erro do nível 1**, como na app. Uma pasta de clone fora das raízes é recusada (`outside-roots`).
- `plan_library_update` confere o documento externo pelo `localPath` que o **projeto** já guarda (`docRepos`), com os mesmos avisos; não tem `docClones`. `validate_specialization` e `validate_library` aceitam a `formatVersion` 11, com os erros da app e o caminho exato (uma chave da 11 numa versão anterior é `só é permitido com formatVersion 11`).

O campo `blank: true` saiu: o container só com fundo mostra `file: null` e `background` (um container com arquivo traz `background: null`). Em `get_proposal`, `entity: "image"` (e o `level: "image"` das notas) continuam, porque são nomes gravados no `proposal.json`.
- **Códigos de erro.** `blank-image` virou `container-without-file` (`get_container_file` ou `replace_container` num container sem arquivo) e `not-blank` virou `container-has-file` (`update_container` com `background`, `width` ou `height` num container com arquivo); as mensagens estão em português e dizem o que fazer.
- **Propostas.** `PROPOSAL_FORMAT_VERSION` fica **2**, sem campo renomeado no `proposal.json`; só o valor da marcação grava `containerId` no lugar de `imageId`. Uma proposta gravada antes (formato 1 ou 2, com `add_image` ou `add_blank_image` nas `operations`, e `imageId` nos valores da marcação) ainda é lida e aplicada ([`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md)).
- **`get_specialization`** devolve `containers` quando a especialização (`formatVersion` 6) os declara: a lista de `{ id, name, width, height, background? }` que o agente pode usar nos tamanhos de `add_container`. O núcleo não traz tamanhos de dispositivo; vêm da especialização (a Material 3 tem Celular 360×800, Celular grande 412×915, Tablet 800×1280 e Desktop 1440×900).
- **`create_project` e a biblioteca de notas.** Por padrão (`notes` omitido ou `true`) o projeto nasce com a biblioteca de notas aplicada, como na app: a camada **Notas** (tipos `nota`, com `titulo` e `texto`, e `tabela`, com `titulo` e `linhas` chave/valor, ambos `floating: true`) no `mapping.json` e a pasta `specs/notas/` gravada ao lado. `notes: false` cria o projeto sem ela. Quem lê uma nota usa `get_specialization` (o tipo traz `floating: true` na `formatVersion` 7) e `get_marking`.
- O schema atual do `mapping.json` é o v13 (sem herança de anotações): um projeto v12 (ou mais antigo) é migrado na leitura, em memória, e a app o grava migrado, com backup, na primeira gravação.

### Biblioteca de componentes (0.5.0)

A especialização `formatVersion` 4 é um **pacote** (uma pasta com a especialização, `components/`, `docs/`, `examples/` e `fonts/`; ver [`SPEC-FORMAT.md`](SPEC-FORMAT.md), "Biblioteca: o pacote"). O servidor **valida, lê e leva o pacote numa proposta**; quem aplica (copia a pasta para `specs/<pasta>/`) é a app, na revisão.

- `validate_library({ path, previous?, level? })`: `path` é a pasta do pacote ou o arquivo da especialização dentro dela (relativo a uma raiz ou absoluto dentro delas). Lê a pasta (textos só de `.json` e `.md`; fontes e outros arquivos contam como presentes, sem ler o conteúdo; links simbólicos não são seguidos; no máximo 2000 arquivos e 32 MB de texto, senão `package-too-large`) e chama `validateLibrary`, a mesma função da app e da skill. `previous` é o arquivo da versão anterior da especialização e liga o contrato de versão (quebra sem `migrations` é erro); `level` (1, 2 ou 3, padrão 3) limita até onde validar. A resposta traz `valid` (sem nenhum `error`), `path`, `spec` (resumo com contagens de componentes, documentos, exemplos, fontes, origens e migrações), `summary` (o nível que rodou e as contagens do pacote), `errors` e `warnings` (cada um `{ file, path, message, severity }`; no máximo 100 de cada, com `moreErrors`/`moreWarnings` quando há mais) e `hint`. **Erro impede usar, aviso deixa usar.** Uma pasta sem especialização devolve `valid: false` com o motivo. Não aplica nada a projeto algum.
- `validate_specialization` aceita a `formatVersion` 4 mas valida só o **arquivo**; o resumo ganha `components`, `docs`, `examples`, `fonts`, `origins` e `migrations`, e a `hint` manda usar `validate_library` para o pacote.
- `list_components` e `get_component` leem a biblioteca **aplicada** (`project` + `specId`: a cópia em `specs/<pasta>/`, a pasta do `file` da especialização) ou um pacote qualquer (`path`). `list_components` devolve, por tipo com componente, `type`, `name`, `layer`, `size` e `minSize` (px), `hasDoc` e `examples` (quantidade). `get_component` devolve, para um `type` (id ou nome): `doc` (o markdown), `fields`, `examples` (`values`, ou `system` + `file` com o `json` do exemplo externo quando tem até 16 KB), `code`, `sources` e `component` (o JSON do arquivo). Um tipo sem componente ou documento não é erro: vem `hasComponent: false` e uma `hint`. Tipo inexistente: `unknown-type`.
- `get_specialization` devolve a v4 inteira (nada é descartado) e, quando a cópia do projeto é uma pasta `specs/<id>/`, `package: { dir, files }`.
- `plan_library_update({ project, path })`: a prévia, **somente leitura**, de aplicar ou atualizar a biblioteca de `path` (a pasta do pacote novo ou o arquivo da especialização dentro dela; também um arquivo v1 a v3) no `project`. Devolve `specId`, `from` (versão aplicada, `null` se não está) e `to`, `decision` (`apply`, `update` ou `not-newer`), `validation` (`valid`, `errors`, `warnings`; na atualização a cópia aplicada é o `previous`) e, em `update`: `additive` (só acrescenta, sem quebra e sem `freedLayers`: camada que some, mesmo sem anotações, não é aditiva; a `hint` pede a confirmação da pessoa), `refused` (quebra sem migração) com `missingMigrations`, `changes` (`code`, `kind`, `path`, `message`), `steps` (a `step` com `op` e chaves, e `annotations`, `values`, `converted`, `deleted`, `refs`, `lossCount` e as `losses` do passo), `losses` (`reason`, `message`, a anotação e a marcação em texto e em referência, `field`, `rowId` e `value`), `pending` (a anotação, `code` e `field`), `brokenRefs`, `addedLayers`, `freedLayers` e uma `hint`. Listas passam de 100 itens cortadas, com o total em `changesTotal`, `lossesTotal`, `pendingTotal`, `stepsTotal` e `missingMigrationsTotal`.
- **`apply_specialization` e `update_specialization` aceitam a pasta do pacote v4** em `file` (ou o arquivo da especialização dentro dela; v1 a v3 seguem por arquivo). O servidor lê a pasta (binários inclusive, até 500 arquivos e 64 MB, o limite da app), valida com `validateLibrary` (na atualização, com a cópia aplicada como `previous`) e: erro de validação → `invalid-library` (com os primeiros erros); versão não maior → `spec-not-newer`; quebra sem migração → `spec-missing-migrations` com `missingMigrations`. Avisos seguem e voltam em `warnings` (`library-warning`). O projeto proposto vem do modelo (`packageSpecName` = o arquivo da especialização, a pasta `specs/<id>/`; a atualização executa as `migrations` nas anotações), e **os arquivos do pacote são gravados em `proposals/<id>/specs/<pasta>/…`** (o mesmo princípio de `proposals/<id>/images/`; `files.packages` na resposta lista as pastas e a contagem de arquivos). Ao aplicar, a app **copia** a pasta para `specs/<pasta>/` e valida o pacote; o servidor nunca grava `specs/` nem o `mapping.json`. A descrição da operação resume a migração (passos, valores alterados, anotações convertidas ou apagadas, valores perdidos, pendências) e a proposta traz as mudanças `values.*` de cada anotação migrada.
- **Mudança da 0.5.0**: tools novas (`plan_library_update`), pacote v4 aceito na proposta (aplicar e atualizar com a pasta), e as operações e campos das telas com componentes (próxima seção); nada do que existia mudou de formato. Use a 0.5.0 com a app da mesma época (schema v10): um projeto v9 é migrado na leitura, em memória.

### Containers com componentes (0.5.0)

O schema v10 introduziu o **container sem arquivo** (`file: null`, com `width`, `height` e `background`) e a biblioteca de componentes desenha instâncias nela. O servidor lê os componentes das especializações em pasta (`specs/<id>/`) uma vez, ao carregar o projeto, e os usa só para **medir e conferir**; ele **nunca arruma** os filhos de um componente com slot (quem usa Arrumar é a pessoa, na app) e nunca grava desenho: o `mapping.json` não guarda nada dele.

- **Operações novas** de `plan_changes`/`propose_changes` (campos em [`AGENT-GUIDE.md`](AGENT-GUIDE.md)): `add_container` (chamada `add_blank_image` na 0.5.0; veja "Mudança da 0.8.0"; `width`, `height`, `background`, `name?`, `source?`, `center?`) e `move_marking` (`marking`, `index`: posição entre as irmãs, 0 = por baixo).
- **Operações mudadas**: `update_container` (antes `update_image`) aceita `background`, `width` e `height` num container sem arquivo (num container com arquivo, `container-has-file`); `create_marking` aceita `annotation` (`type`, `name?`, `values?`; cria a marcação e a anotação tipada de uma vez) e `annotationAs`, e, quando o tipo tem componente, dispensa `rect` (tamanho inicial do componente, no centro do container; dentro do slot do componente com `inside`, a partir da 0.33.0); `create_marking` e `update_marking` com `rect` respeitam o `minSize` do componente (`rect-too-small`, com o mínimo na mensagem).
- **Leitura**: `get_project`, `get_container` e `get_marking_image` mostram o container sem arquivo com `file: null` e `background`; `get_container_file` num container sem arquivo falha com `container-without-file`. As marcações trazem `order` (posição entre as irmãs; em `get_marking`, `{ index, count }`) e, quando desenham um componente, `component` (`specId/typeId`) e `minSize`.
- **`get_marking_image` num container sem arquivo** desenha o recorte: o fundo e, em ordem de desenho, os componentes que cruzam a região, com o mesmo desenho do `render_container` (`drawing: "rendered"` na resposta; ver "Imagem do desenho").

### Propostas (etapa 4)

Toda alteração feita pelo agente chega como uma **proposta**, uma espécie de pull request dentro da ferramenta. O formato do arquivo e as regras da revisão estão em [`PROPOSAL-FORMAT.md`](PROPOSAL-FORMAT.md); o fluxo do agente, em [`AGENT-GUIDE.md`](AGENT-GUIDE.md).

```
meu-projeto/
├── mapping.json                 # só a app grava
├── images/
└── proposals/
    └── 8c1f2d9e-…/              # id da proposta (referência: mapping://<projeto>/p/8c1f2d9e)
        ├── proposal.json
        └── images/              # imagens novas ou trocadas, até serem aceitas
            └── checkout.webp
```

- **`propose_changes`** aplica as operações a uma cópia do projeto (o mesmo código do `plan_changes`, só com as operações puras do `src/model/`), compara o antes e o depois entidade por entidade, campo por campo (`buildProposal`) e grava a proposta: uma mudança por criação, por remoção e por campo alterado, com o valor antes (`from`) e depois (`to`) e os **ids definitivos** dos itens criados. Um lote inválido não grava nada; um lote que não altera nada é recusado (`no-changes`: a reexportação coincide com o projeto).
- **Imagens** novas ou trocadas esperam em `proposals/<id>/images/` (já otimizadas, como na app) e só vão para `images/` quando o usuário aceita e aplica. O nome do arquivo não colide com `images/` nem com o que outra proposta ainda pode aplicar: numa aberta, as imagens pendentes e aceitas; numa substituída, só as aceitas (as pendentes dela não podem mais ser aplicadas). O conteúdo `base64` das operações não é copiado para o `proposal.json` (que guarda as operações só para referência). Por `base64`, cada imagem tem até 16 MB e a mensagem inteira até ~24 MB (o que passa pelo stdin do protocolo); imagens maiores, até 64 MB, vão por `file`. Uma mensagem acima desse teto encerra o servidor com `mapping-mcp: mensagem maior que N bytes` no stderr.
- **O `mapping.json` nunca é alterado pelo agente** (nem a migração de um schema antigo, nem `specs/`): a revisão, a aplicação das aceitas e a gravação do projeto são da app, que usa as mesmas funções puras do modelo (`applyAccepted`). Há teste de integração por stdio que confere o hash do arquivo depois de cada tool.
- **Revisão do usuário**: decisões (aceita, rejeitada, sem decisão) em quatro níveis (proposta, container, item, mudança) e notas, gravadas pela app no próprio `proposal.json`. O arquivo tem `revision` própria, com a mesma conferência do `mapping.json`: quando o servidor atualiza uma proposta (substituída, retirada ou revisada), relê o arquivo imediatamente antes de gravar, tenta de novo se a app gravou no meio e grava `revision + 1`; se o arquivo não para de mudar, recusa com `revision-conflict`.
- **Corrigir na mesma proposta** (`revise_proposal`): enquanto a proposta está `open` e nada foi aplicado, o agente troca, retira e acrescenta mudanças na própria proposta (ver "Mudança da 0.23.0"). Quem grava o quê: o agente grava `changes`, as `decisions` das trocadas e retiradas (que voltam a sem decisão), as `notes` das retiradas (sobem à proposta), `revisions` e a `formatVersion` 5; a app grava as decisões e notas da pessoa. A mudança aceita não é tocada (`change-frozen`).
- **Substituir** (`supersedes`), para quando a correção não cabe na mesma proposta (já há algo aplicado, ou um pacote de biblioteca novo): a proposta anterior, se ainda **aberta**, passa a `superseded` e mantém as decisões e notas. Se a revisão dela ainda tinha mudanças **sem decisão ou aceitas sem aplicar**, a resposta traz o aviso `superseded-incomplete`, com as contagens e o que a proposta nova repete (`same`), altera (`different`) ou deixa de fora (`missing`). Uma anterior já `applied` continua `applied` (é histórico): a resposta traz `superseded: { status: "applied", note }` e a app mostra nela "Aplicada · substituída por" a nova, derivado do `supersedes` da nova. A contagem casa as mudanças pela origem (`source`), pela entidade e campo e, nas criações sem origem (anotações, marcações), pelo caminho legível (imagem › pai › nome), mesmo com ids novos.
- **Conflitos e trava**: o `get_proposal` recalcula cada mudança contra o projeto **atual**: se o valor atual não bate com o `from`, a mudança vem com `conflict` (e o valor atual); mudanças de geometria ou remoção num item trancado vêm com `locked`. Aceitar sobrescreve o valor atual; rejeitar o mantém.
- **Na app**, a proposta aparece na janela **Propostas** (Ctrl+Shift+7; no celular, menu Painéis) e abre no modo revisão: o canvas mostra o projeto como ficaria, o projeto fica somente leitura e as decisões e notas são gravadas na própria proposta. "Aplicar aceitas" é o único caminho para as mudanças entrarem no `mapping.json`. Para testar a revisão sem um agente, abra `examples/proposta-exemplo.zip` na app.

### Concorrência com a app

O `mapping.json` tem `revision`, mas o agente não o grava. A proposta guarda a `revision` sobre a qual foi calculada (`baseRevision`); o `propose_changes` confere que o `mapping.json` não mudou enquanto calculava e, se mudou, recusa com `revision-conflict` (envie de novo). O `revise_proposal` relê o `proposal.json` imediatamente antes de gravar e, se a app gravou no meio (uma decisão da pessoa), **recalcula tudo sobre a versão nova** (uma mudança trocada que a pessoa acabou de aceitar vira `change-frozen`); confere também que o `mapping.json` não mudou durante o cálculo (`revision-conflict`) e grava `revision + 1`, com 3 tentativas antes de recusar com `revision-conflict`. Se o projeto mudar **depois** da proposta, nada é perdido: as mudanças afetadas aparecem como **conflito** na revisão, com o valor atual, o antes e o depois, sem perder as decisões já tomadas. Nas **conversas** (`comments/<id>.json`) a regra é a mesma: o `post_message` e a mensagem do `propose_changes` com `thread` releem o arquivo imediatamente antes de gravar, refazem a operação sobre a versão do disco se a app o mudou no meio (a guarda `after` vale também sobre ela) e gravam `revision + 1`, com 3 tentativas antes do `revision-conflict`; um arquivo ilegível não é sobrescrito (`invalid-thread`). A app aberta na mesma pasta percebe a proposta nova (a pasta é conferida junto com o `mapping.json`); se houver alterações locais ainda não gravadas, pergunta o que fazer ("Projeto alterado fora da app") quando o arquivo do projeto mudar.

### O limite de 60 s e o `wait_for_comment` (spike da decisão 37)

O `wait_for_comment` é uma tool que **fica esperando**, e os clientes MCP cortam a chamada que demora. Antes de fixar o prazo, a etapa mediu o que acontece, em 2026-11-07, com um servidor MCP de teste por stdio (uma tool `wait(seconds)` que dorme e responde):

| Cliente                                                                | Espera pedida                                           | Resultado                                                                                  |
| ---------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| SDK (`@modelcontextprotocol/sdk` 1.32.1, `Client.callTool`)            | 30 s                                                    | Passa.                                                                                     |
| SDK                                                                    | 70 s                                                    | `MCP error -32001: Request timed out` aos 60,0 s (`DEFAULT_REQUEST_TIMEOUT_MSEC = 60000`). |
| SDK                                                                    | 70 s, com progresso, sem `resetTimeoutOnProgress`       | Timeout aos 60 s do mesmo jeito.                                                           |
| SDK                                                                    | 70 s, com `onprogress` e `resetTimeoutOnProgress: true` | Passa (70,0 s).                                                                            |
| Claude Code 2.1.319 (`claude -p … --mcp-config … --strict-mcp-config`) | 30 s, com e sem progresso                               | Passa.                                                                                     |
| Claude Code                                                            | 120 s e 600 s, com e sem progresso a cada 15 s          | `MCP server "spike" tool "wait" timed out after 60s`: **o progresso não estende o prazo**. |
| Claude Code com `MCP_TOOL_TIMEOUT=900000` (ms) no ambiente do `claude` | 120 s                                                   | Passa (a tool foi para segundo plano e devolveu `{"waited":120.0}`).                       |

**Conclusão (caminho (b) da decisão 37):** no padrão do Claude Code, uma tool só passa abaixo de 60 s. Por isso o `timeoutSeconds` do `wait_for_comment` tem **padrão 45 e máximo 50**, e o agente **repete a chamada** (o laço está no "Conversas" do `AGENT-GUIDE.md`). O servidor envia progresso a cada 15 s para os clientes que o usam (o do SDK com `resetTimeoutOnProgress` ganha o prazo estendido), mas não conta com isso. Quem aumenta o `MCP_TOOL_TIMEOUT` só ganha a facilidade de repetir menos vezes: o servidor **nunca passa de 50 s** numa chamada.

## Publicar uma versão (mantenedores)

A versão do servidor é **uma por épico**: `SERVER_VERSION` em `mcp/version.ts` (hoje `0.36.0`) é o único `x.y.z` do código, e os canais abaixo só acrescentam um sufixo ao build (`MCP_BUILD_SUFFIX`, que o `mcp/build.mjs` valida). O workflow `.github/workflows/mcp-prerelease.yml` cuida dos dois primeiros; o `mcp-release.yml`, do terceiro.

**Arquivos de cada release.** O snapshot, a rc e a estável publicam os mesmos arquivos, montados por `scripts/release/workspaceAssets.mjs` (um só script, uma passada por job que compila; ele sai com erro se o `examples/workspace/AGENTS.md` não tiver exatamente um bloco gerenciado, com os marcadores `mapping:begin` e `mapping:end` na ordem). Cada um tem um `.sha256` no formato do `sha256sum` (conferido também por `shasum -a 256 -c`):

| Arquivo              | Para que serve                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `mapping-mcp.js`     | O servidor MCP.                                                                                                        |
| `setup.sh`           | Cópia de `examples/workspace/setup.sh`: instala ou atualiza o workspace na versão da release.                          |
| `SKILL.md`           | A skill `spec-author` do mesmo commit da release (cópia de `.claude/skills/spec-author/SKILL.md`).                     |
| `AGENTS.mapping.md`  | O bloco gerenciado do `examples/workspace/AGENTS.md`, entre `mapping:begin` e `mapping:end` (marcadores inclusive).    |
| `watch-comments.mjs` | Cópia de `examples/workspace/watch-comments.mjs`, o watcher de conversas: o `setup.sh` o instala na raiz do workspace. |

Releases anteriores a esta não têm os quatro últimos (o `watch-comments.mjs` só vem a partir da primeira estável com o watcher; com uma tag mais antiga, o `setup.sh` avisa e segue). Os workspaces que ainda têm o `setup.sh` antigo se atualizam uma vez, com a linha da transição (depois da primeira estável com os arquivos novos; antes disso, troque `latest/download` por `download/<tag da rc>` e passe a tag ao `./setup.sh`), que também vai nas notas de cada release:

O `setup.sh` baixa esses arquivos pelo download direto da release e, se o GitHub responder 5xx ou 429 ou não responder, tenta de novo e usa a API de assets (`api.github.com/repos/…/releases/assets/<id>`, sem token), conferindo o `sha256` do mesmo jeito; o erro final traz o código HTTP (etapa #877).

```bash
curl -fsSL https://github.com/fabianofranca/mapping/releases/latest/download/setup.sh -o setup.sh && chmod +x setup.sh && ./setup.sh
```

- **Snapshot por PR (automático).** Todo PR com base num `epic/**` gera um build de teste na pre-release fixa `mcp-snapshot-pr<N>` (versão `0.36.0-snapshot.pr<N>+<sha>`), sobrescrita a cada push e **apagada (release e tag) quando o PR fecha**, mesclado ou não (o fechamento cancela um snapshot em andamento). O código do PR é compilado num job só com leitura (`snapshot-build`); um segundo job (`snapshot-publish`), sem checkout, é o único que escreve na Release. Instalação: `./setup.sh mcp-snapshot-pr<N>` (ver `examples/workspace/`) ou baixe os arquivos da Release.
- **Release candidate pelo rótulo `mcp-rc` (automático).** O merge, num `epic/**`, de um PR com o rótulo `mcp-rc` (o da última fase do épico; o agente dessa fase põe o rótulo ao abrir o PR) gera a pre-release `mcp-v0.36.0-rc.<n>` (`n` = maior rc existente da versão + 1) a partir do commit do merge, depois de lint, typecheck e testes. Sem o rótulo, o merge não gera rc. Se esquecerem, rode o workflow "MCP pre-release" à mão (`workflow_dispatch`) no branch do épico. Elas são **apagadas (release e tag) quando a estável é publicada**.
- **Estável (automática no merge do épico).** A estável `mcp-v0.36.0` sai sozinha quando o épico entra na `main` com uma `SERVER_VERSION` que ainda não tem tag; ninguém cria a tag. No push na `main`, o workflow `.github/workflows/mcp-release.yml` roda dois jobs:

  1. **`decide`** lê `SERVER_VERSION` no commit do merge e confere no remoto se `mcp-v<versão>` existe (`scripts/release/stableRelease.mjs`). Se existe (épico sem versão nova, merge do Dependabot), termina verde com o aviso "mcp-v<versão> já publicada; nada a fazer" e o `release` é pulado.
  2. **`release`** (só se a tag não existe) roda lint, typecheck e testes (sem os orçamentos de desempenho), gera `dist-mcp/mapping-mcp.js`, o testa fora do repositório (`--version` imprime só a versão, ex.: `0.36.0`) e cria a tag e a Release juntas (`gh release create --target <commit do merge>`; uma tag criada só pelo `GITHUB_TOKEN` não dispararia outro workflow), com os 10 arquivos e o checksum. O título é o nome da tag. Por fim, apaga as pre-releases `mcp-v<versão>-rc.<n>`. Dois pushes seguidos com a mesma versão nova não publicam duas vezes (`concurrency` por tag): o segundo só anexa os arquivos. A tag de rc (`mcp-v<versão>-rc.<n>`) empurrada à mão não dispara a estável (`!mcp-v*-*`).

  **Trava no PR do épico.** O passo "Versão do MCP" do job `epic` (`ci.yml`) falha o PR de `epic/*` para a `main` que muda o que vai na release (as entradas de `scripts/release/releaseInputs.mjs`: `mcp/`, `src/model/`, a documentação embutida, a biblioteca `libraries/notas/` e as fontes dos arquivos do workspace) e mantém uma versão que já tem estável: suba `SERVER_VERSION` em `mcp/version.ts` (e os docs que a citam). Versão nova passa, desde que seja maior que a última estável; sem entrada mudada, passa com o aviso de que o merge não publica. O `package-lock.json` fica fora (um merge do Dependabot nunca publica).

  **Conferir a Release depois do merge.** Quem mescla o épico (no fluxo automatizado, o orquestrador) acha a execução do "MCP release" do commit do merge e espera por ela. Com versão nova, confere que a Release `mcp-v<versão>` existe, não é pre-release, tem `mapping-mcp.js`, `setup.sh`, `SKILL.md`, `AGENTS.mapping.md` e `watch-comments.mjs`, cada um com o `.sha256`, e que as rc da versão sumiram; sem versão nova, que o `release` foi pulado.

  **Plano B (manual).** Se o workflow falhou ou a Release ficou sem os arquivos, corrija a causa e crie a tag à mão na `main` (`git tag mcp-v0.36.0 && git push origin mcp-v0.36.0`, ou Releases › Draft a new release com a tag nova), o que dispara o mesmo workflow (a Release criada antes pela tela recebe os arquivos). Para uma tag que já existe, rode Actions › **MCP release** › Run workflow, com a tag (ex.: `mcp-v0.36.0`): o workflow usa o código da tag e só anexa os arquivos, sem apagar nem recriar a Release.
